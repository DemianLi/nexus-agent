# 評估工具層的量測規矩

`apps/harness/src/eval/` 這一層（基準任務、評分器、`eval:compare`、`eval:survey`、`eval:sessions`）怎麼量、
量出來的數字能拿去做什麼、哪些量法**現在不建**以及哪天要建。詞彙見 [`CONTEXT.md`](../CONTEXT.md)；
怎麼跑、報表怎麼讀見 [`docs/operations.md`](../../../docs/operations.md) 的 eval 一節。

**這一份只記「現在不建」的決定。** 已經落地的（結果落檔並記版本、「這題成功」判準與平凡地板、
以題目為單位的區間）寫在 operations.md，不在這裡重複。

來源：地圖 [#994](https://github.com/DemianLi/nexus-agent/issues/994) 與它的對談票
[#997](https://github.com/DemianLi/nexus-agent/issues/997)。證據是兩份對照表：
[`.docs/nexus-measurement-baseline-2026-10-04.md`](../../../.docs/nexus-measurement-baseline-2026-10-04.md)
（nexus 現況）與
[`.docs/dsh-measurement-practice-2026-10-04.md`](../../../.docs/dsh-measurement-practice-2026-10-04.md)
（dsh 做法）。規則的原文在
[`.docs/chat-agent-research/blueprint.md`](../../../.docs/chat-agent-research/blueprint.md) 第 3 節。

**這些不是偏離 dsh。** dsh 的開源 repo 在產品路徑上沒有任何評估機制（「dsh 沒有」只對開源 repo
成立），所以這一層是「dsh 沒有，做在評估工具層」，不碰產品路徑。

## 一、準入規則：這三樣量的東西 nexus 裡都不存在

下面三條規則要量的對象，nexus 現在**一個都沒有**。所以現在不建任何東西；寫在這裡，是讓哪天對象
出現時，有人知道要先過關。決定出自 [#997](https://github.com/DemianLi/nexus-agent/issues/997)：
「規則 6、T7-02、T7-03 沒有對象，寫成準入規則」。

**表格最後一欄是藍圖的建議做法摘要，不是 #997 拍板的內容。** #997 只定了「對象出現才要先過關」，
關卡的細節屆時再決定；藍圖的等級 A 也只代表有兩個以上獨立來源，不是已被證明。
原文在 `blueprint.md`：規則 6 約第 141 行、T7-02 約第 840 行、T7-03 約第 850 行。

| 規則 | 量的東西 | 今天為什麼沒有對象 | 藍圖建議的關（屆時再定） |
| --- | --- | --- | --- |
| 藍圖規則 6：模擬使用者是共用量具 | 用 LLM 扮演使用者來推進多輪對話的評估 | 基準任務每題一句話、單輪；goal 驅動器的續行輪是 agent 自己的迴圈，不是模擬使用者 | 換多個模擬器各跑一次並逐一報；模擬器自己的錯誤與 agent 的失敗分開記；不把目標答案寫進模擬器的指令；名次效度要拿多個獨立系統對真人驗過 |
| T7-02：評審對人的一致率 | 宣稱 LLM 評審「接近人類」 | nexus 的產品與 eval 都沒有 LLM 評審 | 一致率要同時報多數類基準、機會校正後的值（κ 一類）、樣本量與區間、人類參照的定義與人彼此的一致率；只報原始一致率不算數 |
| T7-03：成對比較要交換位置 | 兩個候選並排、由評審挑一個 | nexus 沒有成對比較的評審 | 逐題用兩種順序各判一次，報前後不一致的比例；合併規則在看結果前定好；換評審模型或提示模板就重量一次 |

「哪天出現」指的是有人要把 LLM 評審或使用者模擬器接進評估流程的那一刻。**在那之前不要預先建**：
沒有對象的量具量不出任何東西，只會留下一個看起來有人把關的空殼。

## 二、這七題的分數當上限，不當實力

[`dataset.ts`](../src/eval/dataset.ts) 那七題（見 `CONTEXT.md` 的「基準任務」）同時被拿來**挑設定**與**報成績**，
中間沒有切開：

- **預設模型**是在這七題上決選出來的（2026-09-04，七題 × 3 次，見
  [`.docs/model-inventory.md`](../../../.docs/model-inventory.md)）；`live-model.test.ts` 還要求預設的 id
  必須出自量過的清單。
- **迴圈上限 40 與時鐘 300 秒**（`EVAL_RECURSION_LIMIT`、`EVAL_DEADLINE_MS`，在 `compare.ts`）是照這七題
  實測的分佈挑的，註解裡記著挑在哪兩個觀測之間。
- **後四題是看了 [#84](https://github.com/DemianLi/nexus-agent/issues/84) 的結果才加的**：前三題在那份資料上
  已經分不出高下，後四題是為了讓參數那一欄重新有解析度。

所以這七題上的分數有兩個讀法限制：

1. **當上限，不當實力。** 設定是對著這份題挑出來的，這份題上的成績偏高；它回答的是「在我們挑好的
   條件下最多能到多少」，不是「換一批題會是多少」。
2. **用它挑改動時，被收下的候選要在沒參與挑選的新題上驗過才算數。** 新題從真實會話日誌造：

   ```bash
   pnpm --filter @nexus/harness run eval:sessions draft
   ```

   `draft` 撈出負向輪交人補期望答案，補完才是題。**它是造題，不是重判評分器**（兩件事不要混在一起）。

這一條對 [#343](https://github.com/DemianLi/nexus-agent/issues/343)（把這份基準包成 Proteus 的唯一
挑選依據）最要緊：它開工前的檢查表已經記了這一項。

## 三、暫緩項與重開條件

下面三批決定的是「現在不建，寫成規矩與重開條件」。每一批都掛在一張已存在的卡上；重開時看那張卡，
不在這裡另開一份清單。

### 過程與最終答案之外另量漏報（藍圖規則 5、T7-08）

今天的評分器只讀工具呼叫序列與最終回覆，沒量過「判成功、但過程違反」的比例。

- **掛在**：[加上每晚跑真模型的冒煙回歸](https://github.com/DemianLi/nexus-agent/issues/436)。
- **重開條件**：那張卡自己的重開條件成立時（給自動測試專用的金鑰準備好；或又發生一次端點改動、
  模型下架而沒被即時發現）。**重開時併入**，不另外開卡。

### 產品路徑閘門的誤報與漏報（藍圖規則 2）

重複呼叫提醒器的門檻 `[3, 5, 8]`、`session-scan` 的打轉旗標、goal 的阻擋門檻、限流分類
（`isRetryableRateLimit`）：都沒有在含成功與失敗兩類樣本的集合上分方向量過。

- **決定出處**：[#997](https://github.com/DemianLi/nexus-agent/issues/997)；現況與沒量過的清單見
  baseline 表「規則 2」那一列。
- **重開條件**：有人要調整其中任何一個門檻時，**先量再調**。
- **動它們要先問 dsh。** 這幾個閘門的形狀是照 dsh 做的（提醒器門檻逐格照抄、限流分類照 dsh 認碼
  不解析訊息、goal 門檻照 dsh 的閘門本體），所以調整它們適用 AGENTS.md 的規則：先讀 dsh 的實際做法，
  偏離要在決議或 PR 內文標註。

### 人工重判（T7-01 後半、T8-03）

評分器兩個方向（把對的判錯、把錯的判對）的誤判率、依難度分層的誤判率，都沒有人工標註可對照。

- **掛在**：[用我們的 eval 當 evaluator](https://github.com/DemianLi/nexus-agent/issues/343)
  **開工前的檢查表**。沒量就在檢查表上標「沒量」，不一律擋。
- 這件事需要人手標，所以不是 agent 能自己補上的。

## 附：永遠逾時的模型怎麼估時間

這一節不是「現在不建」的決定，是估時的事實。[#1251](https://github.com/DemianLi/nexus-agent/issues/1251) 把 `live-model` 的
首事件逾時 `timeoutMs` 從 90 秒放寬到 180 秒（細節見 operations.md 的 `live-model` 一節），
對 `eval:compare`／`eval:survey` 碰到「端點開了線卻一個位元組都不吐」的模型有影響：

- **產品路徑**：一次呼叫最壞 180 秒 × 7 次加退避，約 22–23 分鐘（以前約 12 分鐘）。
- **eval 路徑被單次執行的時鐘 `EVAL_DEADLINE_MS`（300 秒，`compare.ts`）截斷**，所以每次執行最多 300 秒：首次嘗試等 180 秒逾時、退避 1–2 秒、
  第二次嘗試在 300 秒那條線被切掉。2026-10-09 實測：本機假端點永不回話、時鐘設 1.5 秒，這一次執行在 1.5 秒收尾、端點只收到 1 個請求，
  結果記成 `budget`（不是 `transport`，也不是逾時）。拆分之前同樣是 300 秒封頂（90 秒逾時 3 次，第 4 次被切），所以**單次執行的上限沒有變**，變的是封頂前的嘗試次數。
- **估時**：整份調查的最壞時間 ≈ 永遠逾時的候選數 × 題數 × 取樣次數 × 300 秒。CLI 沒有改時鐘的旗標；只有程式呼叫端把 `deadlineMs` 設成 `0`（不設時鐘）時，
  每次執行才會落到上面產品路徑的 22–23 分鐘。要跑 `eval:survey` 先用 `--models` 排掉已知永遠逾時的候選（名單見 `src/eval/survey.ts` 檔頭）。
