### Autopilot-full

**The PM owns the queue and the verdicts, never the PRs. One engineer carries each issue from build to merge, and nothing merges until a verifier that never wrote the code has passed the code that lands.**

1. **The operator's gates come first.** The queue is the open issues labeled `ready-for-agent`. Issues the operator names as theirs stop at merge-ready. A request to state the plan is not a go. Releasing to `main` is always the operator's.
2. **Start one engineer per issue.** Record the assignment on the issue, then start the engineer session in its own worktree off `origin/develop`. Its kickoff is `Read <path>/worker.md before anything else.`, the issue number, and this playbook's path. The engineer builds per **Feature** or **Bug fix**, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges per `playbooks/shipping.md` once step 4 clears it. At its code-ready head the engineer reports to the PM and ends its turn. The PM relays each verdict to it by message. Start no more engineers than the operator's current limit allows.
3. **Run engineers in parallel off `develop`, never stacked,** so each PR lands on its own. Two issues that would write the same file run one after the other.
4. **Verify once at code-ready.** When the engineer reports its code-ready head (after **no-comments**, and with the repo's checks for the touched paths run on that head), start one verifier with the issue and PR number only. It reruns the gates, proves the load-bearing behavior live, and audits the diff against the issue and the repo's standards. A conflict resolution or a code change after the verdict gets a fresh verifier at the new head. So does any commit that answers a `FAIL`, even a wording-only one. Other wording-only changes get none. Block a PR only for a problem the verifier can show: a failing run at the head, a doc line the PR made wrong, or a bug a user would hit. A problem `develop` already has does not block unless the PR copies it or newly reaches it. Everything else goes in a follow-up issue.
5. **Run the root layer.** Anything that loosens a gate, such as a disabled check or an allowlist entry, needs the verifier's proof and then the operator's approval, because the engineer is the one who wants green. Never give or bypass an approval the forge enforces. Track each issue's state on the issue itself, linking each verdict rather than copying it. An engineer is stuck when it errors, cannot start turns, or shows no push and no issue comment for longer than past runs of its kind took. Replace a stuck engineer with a fresh one, passing the issue, the branch, and the prior report. When the same verifier `FAIL` reason shows up on two different issues, open a **correct** issue for it. Archive each verifier once its verdict is on the PR. After an issue merges and its post-merge run is green (or its revert has merged), remove `ready-for-agent`, close the issue if the engineer's report says the issue is done (otherwise write what is left on it), archive the engineer, and remove its worktree per `playbooks/worktree-cleanup.md`.
6. **Stand down at once on the operator's stop.** A hold reaches every engineer as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** each issue's state and verdict, what merged, open operator gates, and parked follow-ups, with links to each issue and PR.
