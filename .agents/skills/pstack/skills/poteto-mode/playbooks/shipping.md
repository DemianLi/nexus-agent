### Shipping

**You own what lands. Merge only a PR whose verdict still covers its code, one PR at a time, then watch the post-merge run.** The engineer runs this playbook for its own PR.

1. **Only a verdict from an agent that did not write the code counts.** The PM starts the verifier with the issue and the PR number. It runs the change the way a user would, reruns every Evidence command, mutates each new or changed guard to prove it goes red, and posts `PASS`, `PASS+NOTES`, or `FAIL` on the PR. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. On `FAIL`, fix, write the new head SHA on the PR or issue, and end the turn without messaging the PM; the PM, woken by the stop, starts a fresh verifier. After the third `FAIL` on one issue, stop. Every `FAIL` counts, including one after a conflict resolution, so a broken resolution cannot bounce forever. The PM labels the issue `needs-info`, removes `ready-for-agent`, and escalates to the operator. The engineer keeps its worktree and is not archived until the operator answers.
2. **Re-check that the verdict still describes the code.** A verdict covers a patch. Compare `git patch-id` at the verdict SHA with the current head before trusting it. When `gh pr update-branch` brought in `develop` without conflicts and the patch-id is unchanged, the verdict stands. When you resolved a conflict, or the patches differ in code, write that on the PR or issue with the new head SHA, end the turn without messaging the PM, and wait for a fresh verifier. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files.
3. **Merge.** Wait until `gh pr view <pr> --json mergeStateStatus,statusCheckRollup` shows the newest `gate` run `COMPLETED:SUCCESS` (or `SKIPPED` with `plan` `COMPLETED:SUCCESS`, which is how a light-mode run with `rust` false passes) and the state `CLEAN`. Then `gh pr merge <pr> --squash --match-head-commit <full head SHA>`. Read the PR back with `gh pr view <pr> --json state,mergedAt,baseRefName`, because a merge command can report success without merging. Never arm auto-merge.
4. **Watch the post-merge run.** `.github/workflows/post-merge.yml` runs the full CI on your merge commit. If it goes red, rerun only the failed jobs once. Still red: if a revert passes `gate`, open a revert PR at once so `develop` is green again and merge it once `gate` is green (a pure `git revert` needs no verifier), then fix it yourself and open a new PR, which goes through a verifier as usual. If the revert only passes by raising a ratchet baseline (try it on the latest `develop`, keeping `develop`'s baseline or setting it to the actual value; `check_ratchets.py --base` blocks both), fix forward instead: open the fix PR at once, attach the blocked revert's output, and take it through a verifier and `gate` as usual; a pure-revert shortcut does not apply. The fix PR may only fix this run's red. Never raise a baseline or change a gate to let a revert pass. Open no other PR until your merge commit's run is green or reverted; when you fix forward, until the fix PR's post-merge run is green. The fix PR itself is the exception. If you cannot fix it, label the issue `needs-info`, hand it to the operator, and keep the engineer and worktree. Green after the rerun, and the same tree was green on the PR: treat it as a flake and record it on a backlog issue.
5. **Report on the issue.** One comment: what landed, the merge commit, the post-merge run, whether the issue is fully done or what is left, and every reversible default you chose with its reason, so the operator can overturn any of them by replying there.

**Reply:** the verdict and who produced it, what landed and how you confirmed it, the post-merge run, and the defaults you listed on the issue.
