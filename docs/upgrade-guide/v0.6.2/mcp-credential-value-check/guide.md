# MCP 引用的憑證先修頭尾、再照 env 與 header 的規則檢查

## 變更

只影響 MCP 那一列在 `connection.env` 或 `connection.headers` 寫了 `{ credential: <名字> }` 的主機；值從哪一層來（受管檔、啟動環境、`.env`）都一樣。

- **頭尾的空白與換行修掉。**
  - 舊行為：值原樣代入。受管檔用 `|` 區塊寫的值，子行程的環境變數或 header 會多一個尾端換行。
  - 新行為：先修掉頭尾的空白與換行，代入的是修過的值。
- **修完是空的，拒收。**
  - 舊行為：只有空白的值照樣代入。
  - 新行為：那一列連不上，警告寫 `<名字>（來自<哪一層>）是空白的`。
- **`connection.env` 的值裡有 NUL，拒收。** 中間的空白與非 ASCII 字元照收，跟以前一樣。
  - 舊行為：stdio 子行程起不來，Node 拋的 `ERR_INVALID_ARG_VALUE` 會把整個值寫進訊息。
  - 新行為：起子行程之前就拒收，警告寫 `<名字>（來自<哪一層>）含有 NUL 字元`，不含值的任何片段。
- **`connection.headers` 的值裡有 header 放不下的字元，拒收。**
  - 收的字元：tab、可列印 ASCII（含空白）、0x80–0xFF。換行、NUL 這類控制字元，以及中文這種 U+00FF 之後的字元，都拒收。
  - 舊行為：在 Node 送請求那一層才失敗，而且值裡有換行或 NUL 時，那則錯誤會把整個值寫進日誌。
  - 新行為：送請求之前就拒收，警告寫 `<名字>（來自<哪一層>）含有 HTTP header 放不下的字元`，不含值的任何片段。
- **修完不到 8 個字元（以 code point 算）的值，拒收。** `env` 與 `header` 都一樣。
  - 為什麼：宿主會把已解析的憑證值從送回模型的文字裡遮掉，成功的工具結果也遮；harness 自己的 MCP 路徑隨後跟上，用同一條規則。太短的值（例如 4 位數的 PIN）會偶然撞上正常內容，把答案改壞；短值又不能「不遮」，那等於洩漏。所以改在源頭擋。
  - 舊行為：任何長度的值都代入。
  - 新行為：那一列連不上，警告寫 `<名字>（來自<哪一層>）修掉頭尾空白之後不到 8 個字元`，不含值的任何片段。
- 拒收時跟找不到值一樣處理：預設是那一列沒有工具、伺服器日誌一則警告；寫了 `failOnStartupError: true` 的整列不掛。
- 受影響的：
  - 受管檔裡用 `|` 或 `>` 寫 MCP 憑證、而那台 server 剛好靠尾端換行運作的主機（很少見）；
  - 憑證值修完是空的主機，升上來之後那一列連不上；
  - 憑證值不到 8 個字元的主機（常見的是短密碼、PIN），升上來之後那一列連不上；
  - 值裡帶 NUL、或 header 的值帶控制字元或 U+00FF 之後字元的主機，本來就連不上，現在改成送出前拒收、訊息不帶值。
- 不受影響的：模型 key（照舊走 [#1541](https://github.com/DemianLi/nexus-agent/issues/1541) 的檢查）；MCP 那一列直接寫成字串、沒有引用憑證的值。

## 遷移

1. 找出引用憑證的 MCP 列：在 patch 檔與 `cordis.serve.yml` 裡搜 `credential:`，記下每一個憑證名。
2. 打開 `~/.nexus-agent/.credentials.yaml`（或你設定的 harness home 底下的那一份），逐一看這些名字的值：
   - 只有空白的，改成真正的值，或把那一列的引用拿掉；
   - 放進 `connection.headers` 的，確認值裡沒有換行與中文，例如不要用 `|` 跨行寫；
   - 值在啟動環境或 `.env` 的，同樣檢查；
   - 不到 8 個字元的，換成較長的憑證；那個值其實不是秘密（帳號、埠號）的，改寫成那一列的字面值，不再用 `{ credential: <名字> }` 引用。
3. 確認改好了：重啟 serve，開一條新對話，那一列的工具出現在工具清單裡，伺服器日誌沒有那一列連不上的警告。
