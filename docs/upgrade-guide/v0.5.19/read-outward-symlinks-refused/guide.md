# 經往外指的符號連結讀，改成拒絕

## 變更

v0.5.19 的檔案圍堵只管變更（寫、改、刪）。讀一律放行，所以工作區裡一條指向工作區外的**目錄**連結，
`read_file`、`ls` 經它讀得到那邊的檔案。只有最後一段是檔案連結時，讀才會失敗（`ELOOP`）。

新版（#1982）讀之前先把路徑 canonicalize，落在工作區根外就拒，碼是 `FS_SANDBOX_DENIED`。
模型看到的錯誤裡含 `[containment] 拒絕 read "…"：經符號連結解析之後落在根之外（mode: …）`。

- **新版會拒的讀法：**
  - `read_file`、`ls`；
  - `grep`、`glob` 的起點；
  - `submit_record` 讀既有表頭；
  - 技能目錄的掃描。
- **最後一段指向根外的檔案連結：** 錯誤從 `ELOOP` 變成這一句。
- **照舊能讀的：**
  - 指向工作區裡的連結；
  - `danger-full-access` 下的讀取。
- **技能會整份消失，不只是那一份。** 技能掃描只要有一份讀不到，那一次就算不完整；不完整時一份都不列。所以只要
  `skills/` 本身、底下任何一個技能目錄、或任何一份 `SKILL.md` 是指向工作區外的連結，升級後**所有**技能都不見了，
  包括工作區裡的（自訂的技能來源同理）：
  - 送給模型的技能清單是空的；
  - `/名字` 叫不出任何技能；
  - web 的技能清單（`skill.list`）是空的；
  - serve 記 warn，每一句都含 `掃描不完整`；哪幾句出現看走了哪條路，例如 web 打開技能清單時是
    `技能清單這一次是空的：掃描不完整（有技能讀不到）`。
- **`AGENTS.md` 是連結時讀不到，這件事不是新的。** v0.5.19 開檔就不跟最後一段的連結（`ELOOP`）。新版裡指向工作區外的
  換成上面那句 `[containment] 拒絕 read …`，指向工作區裡的仍是 `ELOOP`。兩版都不會把它放進模型的基線。
- **受影響的是：** 工作區（serve 的 `--workspace` 共用區，或 CLI 的 `--workspace`）裡，放了指向工作區外的連結的部署。
  要模型讀那邊內容的，那些內容讀不到；連結落在技能目錄的，全部技能都會消失。

## 遷移

1. 找出工作區裡指向工作區外的連結。在 `--workspace` 指的目錄跑：
   `find . -type l -exec sh -c 'case "$(readlink -f "$1")" in "$(pwd -P)"|"$(pwd -P)"/*) ;; *) echo "$1";; esac' _ {} \;`。
   沒有輸出就不受影響，後面幾步不必做。
2. 每一條連結決定怎麼處理：
   - **連結在技能目錄裡**（`./skills` 本身、`./skills/<名字>`，或 `./skills/…/SKILL.md`）：**一定要處理**，否則全部技能都會消失。
     把技能目錄複製進工作區，或把連結換成實際的目錄與檔案。
   - **`./AGENTS.md` 是連結**：v0.5.19 本來就讀不到它。要模型讀的話，換成實際的檔案。
   - **模型要讀那邊的內容**：把內容複製進工作區，或把連結換成實際的檔案或目錄。不要把工作區改指到更上層去包住那邊，
     那會連同不該給模型看的東西一起放進來。
   - **其餘模型不需要讀的**：不必處理；留著的話，模型讀到它會得到拒絕。
3. 確認：
   - 技能：開一條 thread 送一句話，再在 web 打 `/`，列得出技能；serve 的日誌裡找不到 `掃描不完整`。
   - 其餘連結：開一條新 thread，請模型讀其中一個留下的連結底下的檔。會話日誌（home 底下的 `sessions/`）裡那一筆 `tool/result`
     帶 `"code":"FS_SANDBOX_DENIED"`；換成工作區裡實際存在的檔，照常讀得到。
