# 會話根讀不了時，啟動就失敗

## 變更

v0.5.19 建會話後端時不碰檔案系統。會話根（`--session-log` 給的目錄，沒給就是 home 底下的 `sessions/`）不是目錄、
或這個行程沒權限讀它，`serve` 與 CLI 照樣起來；要等第一條會話第一次寫，才在伺服器日誌或終端機上出一行 warn，
那條會話的日誌就沒寫下來，畫面照跑。

新版（#1559）建後端時就讀一次那個目錄，照 dsh 的 `assertUsableRoot`：

- 目錄還不在：照常起來，第一次寫才建，跟以前一樣。
- 其餘讀不了的情況（`ENOTDIR`、`EACCES` 等）：`serve` 與 CLI 在啟動時就拋出那個錯，原樣帶著系統的訊息，例如
  `ENOTDIR: not a directory, scandir '…'`，不起來。

讀的是**這一次真的會寫的那一格**：`serve` 是 `<會話根>/<專案目錄名>`，CLI 是 `<會話根>/<這一次的 run 目錄>`。

受影響的：會話根所在的路徑被一個一般檔案佔住、或權限設成這個行程讀不了，而以前沒注意到（以前只看得到一行 warn）
的部署。落盤關掉（清單拿掉 `session-persistence` 那一列）的不受影響：那時不建後端。

## 遷移

1. 找出這一台的會話根：有給 `--session-log` 就是它，沒給就是 `<home>/sessions`（home 見 `docs/operations.md`）。
2. 那個路徑若是一般檔案，移走或改名；若是目錄，確認跑 `serve`／CLI 的使用者讀得了、也進得去
   （`ls -ld <會話根>` 與其下的專案目錄），需要的話把擁有者改成那個使用者。
3. 確認：重新啟動 `serve`（或跑一次 CLI），不再出現上面那種 `scandir` 的錯；開一條 thread 跑一輪之後，
   `<會話根>/<專案目錄名>` 底下有那條 thread 的檔。
