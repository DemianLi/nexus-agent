## 量什麼

### 兩臂

兩臂同時活著，逐輪交錯。第 k 輪兩臂誰先，依 (k + 回合序) 輪轉。

| 臂 | 起法 | MCP 連線池 |
|---|---|---|
| `single` | 一個 `node lib/serve.js` 放所有 thread | 整個行程一份 |
| `per-thread` | `--process-model per-thread`：監督行程起前台、宿主、預熱池，每條 thread 一個對話行程 | 每個 Node 行程一份 |

### 負載

- 每回合兩臂都重新起，home 也是新的。各開 N 條 thread，跑暖機 W=5 輪，再跑量測 T=40 輪。
- 每輪是一道**柵欄**：N 條同時送出，全部收到 root 的 lifecycle 收尾，才進下一輪。CPU 只在柵欄的兩端取樣。
- 每台 serve 掛 M=3 台 MCP server：
  - 兩台 stdio，都是純 `node` 跑型別剝除，不經 tsx；
  - 一台 HTTP，無狀態的舊協議，起在驅動裡，每臂一台。
- 三台都只有一支 `lookup`，`approval.exempt` 都列了它，所以一輪不會停下來等核准。
- 假模型一輪依序叫 `mcp__mcpa__lookup`、`mcp__mcpb__lookup`、`mcp__mcph__lookup`，再回一段約 3000 字的文字，串流 20 段。所以正常一輪是 4 個模型請求。每條 thread 的第 1 輪多一個不帶工具的標題請求，這一輪落在暖機裡。

### 矩陣

| N | single | per-thread |
|---|---|---|
| 4 | ✓ | ✓ |
| 8 | ✓ | ✓ |
| 16 | ✓ | ✓ |
| 64 | 只量 single 當參考（smoke 放得下才跑） | **不量** |

- 同一個 N 的兩臂在同一次執行裡交錯。每組至少 3 回合，每組各自拿一次計時鎖。
- **per-thread 沒有 N=64，原因是監督行程的容量上限。** 容量是產品照記憶體上限算的，超過它去量的不是真實的設定，所以不給 `--capacity` 硬撐。

## CPU 的總和

**每輪 CPU 總和** 定義為：柵欄之間，該臂整棵行程樹所有 thread 的 schedstat 增量加總，再除以這道柵欄完成的輪數 N。

**行程樹**由兩部分組成：

- 根 pid 的所有後代。single 的根是 serve；per-thread 的根是監督行程，它是 `execve` 換過去的，pid 不變。
- cmdline 帶 `--tag <臂>` 的行程。MCP stdio 子行程不論掛在誰底下都算在內，被 reparent 的也撈得到，包含前台自己那 M 台。

**分開列的角色**（照 cmdline 認，D166 Q5）：

- `serve`
- `supervisor`
- `front`
- `conversation`
- `host`
- `spawner`
- `mcp-stdio`
- `other`

前台與監督行程只列它們自己的 Node／Rust 行程。

**每條對話行程的每輪中位數**（D162）：

- 適用範圍：只在 per-thread。
- 每道柵欄取各個對話行程自己的 schedstat 增量。預熱池裡那一個這一輪沒有接 thread，所以取最大的 N 個。
- 跨柵欄取中位數。

**HTTP fixture 的 CPU 不算進來**：它代表部署方的外部服務，跑在驅動行程裡。

**對帳**：每道柵欄同時記 `/proc/<pid>/stat` 的 utime＋stime 增量。這個值含已經結束的 thread，解析度 10 ms。只拿來跟 schedstat 的總和對帳，不進統計量。

## 主要統計量

- **窗**：暖機之後的第 1–10、11–20、21–40 輪，等於 D162 從第 1 輪算起的第 6–15、16–25、26–45 輪。
- **每回合每窗**：該窗內每道柵欄的「每輪 CPU 總和」取中位數。
- **跨回合**：取中位數，附 bootstrap 90% 區間。區間的算法：對回合重抽 10000 次，種子 1947，取第 5% 與第 95% 位，同 #1947。
- **比值**：每回合每窗 per-thread ÷ single，跨回合取中位數與區間。
- **按角色拆**：同樣的窗與中位數，各角色分開算。
- **per-thread 的值是 #2576 的宣告值，標成「代用值」**：它是今天每個行程一份池的量，不是 #2576 最後的形狀。

## 池的指標

每回合每臂各記一份，從 spawn 前一刻起算，包含起動時的握手。

| 指標 | 怎麼量 |
|---|---|
| stdio 子行程數 | 每道柵欄兩端數活著的 `mcp-stdio` 行程 |
| stdio 起了幾次、完成幾次握手 | server 自己寫的日誌（`start`、`initialized`） |
| HTTP 的 initialize 次數 | fixture 記的 JSON-RPC 方法 |
| HTTP 連線數 | fixture 記的現在開著、峰值、累計接過 |
| 各角色的 RSS／PSS 與 thread 數 | 回合結束、關下行之前 |
| 起動 | ready 毫秒數、起動 CPU、起動完的各角色記憶體 |
| 首次呼叫延遲 | 第 1 道柵欄送出那一刻，到每台 server 第一次收到 `tools/call` 的毫秒數。另報第 1 輪每條 thread 的 wall 中位數 |

首次呼叫延遲與第 1 輪的 wall 都落在暖機裡，在 D162 的窗之外，另外報，不跟穩態每輪 CPU 混在一起。

## 有效性、排除與標記

以下任何一條不成立，**整回合標記、主統計量排除它**，另報含它的值：

1. 每一輪的 outcome 都是 `completed`。
2. 同一個 k 上兩臂的 `llmReq` 相同。正常是 4N，第 1 輪是 5N。
3. 量測輪的每道柵欄 `readErrors`＝0。`readErrors` 是認得出、但讀不到 schedstat 或記憶體的被量行程，加上連 `stat` 都讀不到的行程。
4. 量測輪的每道柵欄 `born`＝0、`died`＝0。死掉的行程會丟掉增量，所以 `idleEvictAfterMs` 設 0，不讓 thread 在回合中被逐出。
5. 量測輪的每道柵欄，兩端的 stdio 子行程數相同，而且跨柵欄不變。
6. 收掉 serve 之後沒有留下帶 `--tag` 的行程（`leftovers` 是空的）。

另外兩項只記錄、不排除：

- **容器內的 loadavg**：N 條並行本身就會把它推高，不當排除條件。
- **宿主負載**：每 10 秒取樣一次 uptime。計時鎖已經排除了走鎖的重負載。

## 怎麼跑

- 每組用計時鎖（`~/.nexus-agent-evidence/.bench-lock`）包著跑：先在鎖外等宿主安靜，拿到鎖才起容器。
- 容器一律 `--pull=never --network none`。
- 被量的 serve 以 uid 10001 跑；驅動同一個 uid，用 tsx 跑。
- 原始數據、指令與鎖的紀錄放在本機證據目錄，不進 repo。

## 限制

- **Rust 用的是 gnu 版，不是 musl**：監督行程、宿主、spawner 都是 `rust:1.98.1-slim-bookworm` 離線 `--locked` 編的 release 版。出貨若改用 musl，記憶體配置器與起動成本可能不同。
- **per-thread 的兩個入口是繞過去的（#2657）**：
  - 問題：develop 的 `build:lib` 不會編 `front-process.js`、`conversation-process.js`，照產物起 per-thread 時，前台找不到入口。
  - 為什麼不用 manifest 補入口：在 manifest 加入口，會讓 rolldown 把 serve 的本體搬進共用 chunk，`lib/serve.js` 只剩一行 re-export，`import.meta.main` 永遠是 false，single 會安靜地以 0 結束。
  - 繞法：只在量測容器裡，`build:lib` 之後另跑一次 tsdown，只編這兩支，`--no-config --no-clean -d lib --format esm --platform node --target es2024 --no-dts --no-fixed-extension --deps.never-bundle '/^[^./]/'`。
  - 證明原有產物沒被覆蓋：另編之前、之後各記一次 `lib/` 每個檔的 md5，原有的檔一個都不能變，否則進入點就停下來。`lib/serve.js` 兩次的 md5 寫在結果段。
  - 這樣編出來的前台和對話行程，各自內含一份 serve 等相對模組的拷貝，chunk 配置跟 #2657 修好之後出貨的不同。這只影響起動、載入與 **RSS**；D162 的窗從暖機 5 輪之後才起算，穩態每輪 CPU 不受影響。所以 per-thread 的起動數字與記憶體數字，要註明是在這個繞法之下量的。
  - **#2657 修好之後要重驗**：照修好的產物重跑 per-thread，至少 N=16 一組。
- **假模型**：模型端沒有延遲。量的是 harness 與池這一側的 CPU，不是端到端的回應時間。
- **stdio server 都講舊協議**：smoke 時看到，每次 stdio 連線都起兩個行程，第一個沒有完成握手就結束，第二個才完成 initialize。這跟 `pool.ts` 檔頭寫的「版本協商 `auto` 先試新協定、再試舊協定」一致，但這是推論，還沒逐行核實。池的指標照實記「起了幾次」與「握手幾次」。
- **量測環境**：同一台機器。

## 看過數字之後補的（2026-11-10）

以下是跑完之後才發現或才補的，不改上面的規則。

1. **規則第 2 條寫的「正常是 4N」不對**：每條 thread 從第 8 輪起，每輪都多一個不帶工具的模型請求，所以第 1 輪與第 8 輪之後是 5N，第 2–7 輪才是 4N。四組都一樣（假模型計數：n4 的 `notools` 936 次＝39 道柵欄 × 4 條 × 6 臂回合，n64s 7488＝39 × 64 × 3）。兩臂在每個 k 上都相同，第 2 條的判準（兩臂相同）照樣成立，沒有回合因此被標記。它落在兩臂的量測窗裡，兩臂都付了這份 CPU，比值不受它偏向哪一臂。來源見第 5 條。
2. **N=16 的記憶體數字疑似受記憶體回收影響**：single 的 `mcp-stdio` 兩個行程合計 RSS 從 N=8 的 161.8 MB 掉到 55.1 MB，per-thread 每個 stdio 行程也從約 79 MB 掉到約 36 MB。所以 N=16 的 RSS／PSS 偏低，不能跟 N=4、8 直接比較。CPU 數字照用。
3. **報告的兩處補實作**（n4、n8、n16 跑完之後）：規則裡的「另報含它的值」與「標成『代用值』」原本報告沒有印。補上的範圍：每窗的每輪 CPU 總和另印含被標記回合的一段（這次沒有回合被標記，所以沒印）；per-thread 的每輪 CPU 總和與每條對話行程每輪標「代用值」。比值、按角色、池與記憶體沒有另標，本文表格裡的 per-thread 欄一律視為代用值。主統計量的算法沒變。
4. **規則開頭的兩處說明**：
   - `344b3bb7` 在 squash 合進 develop 之後就查不到了，以這張 PR 為準。「照原樣搬入」的例外是拿掉了環境描述。
   - 「拿 #1947 的原始數據比對，輸出逐字相同」是在本機手跑 `mcp-pool-agg-1947-cli.ts` 比對的，結果寫在 PR 內文的 Evidence。repo 裡釘住的是合成數據的逐字相同（`mcp-pool-stats.test.ts`）。
5. **第 8 輪起多出來的請求是壓縮**（診斷 smoke：single、N=1、10 輪，跑完把 home 拷出來讀會話日誌）：
   - 第 8、9、10 輪各有一顆 `compaction/summary`。`messagesBefore` 依序是 60、68、76，`cutoffIndex` 依序是 8、16、24。第 1 輪那一個是標題請求（`session/title-llm-request`）。
   - 門檻是產品預設的 `messages: 60`（`packages/nexus-core/src/summarization.ts` 的 `DEFAULT_SUMMARIZATION`）。fixture 一輪是 8 則訊息：人話一則、三次工具呼叫各兩則、回覆一則。所以第 8 輪的第三則訊息時，訊息數到 60。
   - 之後**每一輪都再壓一次**，每次只切掉前面 8 則（一輪）。推測是保留量照 token 算，每輪約 3000 字的回覆讓保留下來的訊息數一直貼著 60；沒有逐行核實。
   - 量測的意思：從第 8 輪起，兩臂每條 thread 每輪都含一次摘要的模型往返與寫檔，三個窗都在這個狀態裡。這是 fixture 對話的形狀撞上產品預設門檻，不是量具的錯；「每輪都重壓」是不是產品該有的行為，交給另開的卡。
6. **per-thread 的池有 N＋2 份**（診斷 smoke：per-thread、N=1，從容器外讀行程表的 ppid）：
   - stdio 子行程的父行程：兩個對話行程（`c1.sock`、`c2.sock`）與前台，各兩台，合計 6＝2 ×（N＋2）。
   - 多出來那一份是**預熱池裡的對話行程**：監督行程預設留一個熱的（`--warm` 預設 1，`native/sandbox-spawner/src/supervisor/args.rs` 的 `DEFAULT_WARM`），它還沒接 thread 就已經把三台 MCP 連上了。回合結束時對話行程的個數是 N＋1，也對得上。
   - 所以 per-thread 的池＝N 個接了 thread 的對話行程＋1 個預熱池＋前台。HTTP initialize 的 N＋2 也是這三類各一次。
   - 哪個是預熱池是照 pid 先後推的（`c1` 先起、接了 thread，`c2` 後補）；三類各掛一份這件事是從行程表直接讀到的。

## 後測的規則（#3000 E4b，2026-11-19，量之前寫、先 commit，跑完不改）

前面各節是 E4b 之前的前測；以下是 per-thread 的 MCP 切到宿主之後的後測。**規則在量之前寫好、先 commit**；看過數字之後才補的，一律另起一段，標明時間與理由。

### 一、池的後測

沿用前測的負載、矩陣（N＝4、8、16，不量 64）、主要統計量、窗、有效性與排除規則（上面各節原樣適用），差別只在 per-thread 臂換成 E4b 之後的產物：

- 兩臂仍同一次執行交錯。**對照組是前測記下的 per-thread 臂與 single 臂**（同一台機器、同一份驅動與 fixture）。後測 single 臂不變，用它抵掉機器漂移。
- 後測 per-thread 臂的對話行程不再建自己的池；每一列 server 的子行程由宿主起。「stdio 子行程的父行程」那一欄因此預期是宿主，不再是對話行程與前台各一份。前台自己的那 M 台照舊（前台不經宿主）。

**過關條件（量之前定，三條全成立才算過）：**

1. **CPU**：每個 N、每個窗，後測的「per-thread ÷ single」比值（跨回合中位數）不高於前測同一格比值的 bootstrap 90% 區間上緣。**用比值，不用絕對值**：前後測不在同一次執行裡，single 臂是機器漂移的對照；絕對的每輪 CPU 總和照常報，只當參考。
2. **server 子行程**：每道柵欄兩端，每一列 stdio server 的活子行程數都是 1，而且父行程是宿主。預熱池與每條對話行程底下不再有 stdio server 子行程。
3. **握手**：每列 stdio 與 HTTP 的 initialize 次數不超過前測 per-thread 臂的次數（池從 N＋2 份降成 1 份，只會變少）。

**只記錄、不設門檻：** 起動 ready 毫秒、起動 CPU、各角色 RSS／PSS（含宿主）、首次呼叫延遲與第 1 輪 wall。這幾項受宿主多一道轉送影響，數字要報，但本卡不拿它們擋合併。

**未過關怎麼辦：** 任何一條不成立，不自己調規則或重跑到過為止，回報 PM。

### 二、W 的量測

W 是對話行程等宿主重連、重新 `open` 的上限（現值 5 秒，`DEFAULT_REBIND_WAIT_MS`）。正式值要量到宿主啟動時間與重新 `open` 的時間再定（#2570 留言 6942234754 的決定 (f)）。

**量兩段，都在對話行程那一側的時鐘量：**

- 段 A：宿主被殺（SIGKILL）的那一刻 → 對話行程重新連上、收到 `ready`。
- 段 B：段 A 結束 → 重新 `open` 的綁定可用（第一個 `open` 收到 `ready` 塊）。

**時鐘：** 段 A 的兩端在不同行程（驅動送 SIGKILL，對話行程收 `ready`），所以兩端都用全系統共用的單調時鐘 `process.hrtime.bigint()`（Linux 的 `CLOCK_MONOTONIC`，跨行程同一個起點）；**不用 `performance.now()`**，它的起點是各行程自己的。對話行程那一側的時間點由 `HostClient` 的 `onReady` 與綁定可用時記下，回報給驅動。

**監督行程的退避（讀 `supervisor/mod.rs` 的 `host_failed` 與 `args.rs` 確認的）：** 宿主 `ready` 之後被殺、重起時**有退避**，且 `--host-start-failures`「`ready` 一次就歸零」只管 `ready` 之前的失敗，不管這個退避。規則是：第一次重起等 `--host-backoff-ms`（預設 1 秒），之後每次加倍到 `--host-backoff-max-ms`（預設 30 秒），**宿主活過 `--host-stable-ms`（預設 60 秒）才結束，下一次才回到 1 秒**。所以連續殺 30 次，後面的樣本會被 2、4、8…秒的退避撐大，W 就被高估了。因此：

- **每次殺之前，要等宿主這一代已經活過 `--host-stable-ms`**（預設 60 秒，用預設值量，不為了量測改它），這樣每一筆樣本的退避都是最低一級（1 秒）。每筆樣本之間因此至少隔 60 秒，30 次每個架構約 35 分鐘。
- **每筆樣本記下當時的退避等待**（監督行程 stderr 的 `宿主 N ms 後重起`），報告裡兩段時間要連同它一起列，並另報「扣掉退避等待之後」的段 A。退避不是 `open` 的成本，但它是對話行程實際等到的時間的一部分，W 要蓋住它。
- 另外多量一組**連續殺**的樣本（不等穩定，連殺 4 次，每個架構做 3 輪），只記錄每一次的退避等待與段 A，不進 W 的公式：這是在寫明「W 蓋住幾次連續重起」。預期第 4 次的退避（8 秒）超過現值 W＝5 秒，這是預期內的事實，要在報告與 `docs/host-mcp.md` 寫明。

**怎麼量：**

- 起一台 per-thread serve，掛一列 stdio MCP server，一條 thread 已叫過一次工具（綁定在）。殺宿主，量兩段，等綁定恢復，再重複。
- **每個架構重起 N＝30 次**，x64 與 arm64 都量；每次殺之前先確認上一次的綁定已恢復。
- 報 p50、p95、最大值，兩段分開報、也報兩段相加。
- 同一台機器、計時鎖內、容器 `--pull=never --network none`，跟池的量測一樣。
- **W 的正式值與退避的關係：** 公式用的「兩段相加」是不含連續殺那組、每次退避都是最低一級的樣本。公式算出的 W 只保證蓋住**一次**重起；連續重起的覆蓋範圍用上面那組連續殺的數字另寫，不靠調高 W 去蓋（退避最高 30 秒，W 不跟著它走）。

**W 的正式值怎麼從數字推出來（量之前寫死）：**

> W ＝ ⌈ 兩段相加的最大值（兩個架構取較大者）× 1.5 ⌉ 取整到秒，**下限 5 秒**。

**要回報 PM、不自己調的情況：**

- 兩段相加的最大值超過 3 秒（W 會超過現值的一半以上被吃掉）；
- p95 超過 2 秒；
- 兩個架構的最大值差一倍以上；
- 30 次裡有任何一次沒恢復（綁定沒回來）。

算出來的 W 若與現值 5 秒不同，改 `DEFAULT_REBIND_WAIT_MS`、`docs/host-mcp.md`、`.docs/rust-host-survival-2568-2026-11-08.md` 要另開 commit，並寫明依據這一節。

### 三、段 A、B 的記時：偏離與替代（量測專用入口）

原文：段 A、B 的時間點「由 `HostClient` 的 `onReady` 與綁定可用時記下」，也就是在真的對話行程那一側記。驅動不是被監督的行程，拿不到監督行程發給對話行程的 host token（`conversation-control.ts` 的 `hostToken`），自己當客戶端會被宿主拒絕，所以**不能由驅動自己連宿主來量**。

- 包裝實際打到的模組路徑，與該模組所在產物檔的 sha256，都寫進結果。
- 與沒有包裝的產物，對 `lib/` 每個原有檔記 md5，一個都不能變（同前測 #2657 繞法的做法）。
- **自我檢查**：每次殺宿主，包裝記到的 `onReady` 與 `open` ready 各**恰好一筆**；記不到或多於一筆，這一輪作廢，不拿缺的樣本算，作廢次數另報。

### 五、補充（量之前，2026-11-20，寫量測驅動時定下的實作細節）

1. **記時用預載，不另寫入口檔**：第三節說的「包住真的 conversation-process 的量測專用入口」，實作成 `node --import apps/harness/src/measure/host-kill-preload.ts`（驅動把它放進被量 serve 的 `NODE_OPTIONS`，只有 `argv[1]` 是 `conversation-process.js` 時動作）。理由：`conversation-process.js` 靠 `import.meta.main` 才跑 `main()`，被另一個入口 `import` 時不會跑；預載能在不改入口、不改產物的情況下，在產品碼載入之前包住同一個 `@nexus/host-bridge` 模組實例的 `HostClient.prototype.onReady`（包住 listener）與 `call` 的 `open`（包住 `onChunk`，收到 `ready` 塊記一筆）。第三節的證明、自我檢查與「包不到就停下回報」全部照舊；預載起來時另記 `loaded`（被包的模組 URL、實際檔案路徑與 sha256）。

3. **百分位用 nearest-rank**：第 p 百分位是排序後第 ⌈p/100 × n⌉ 個，n＝30 時 p95 是第 29 個，寫在 `host-kill-stats.ts`。回報條件「p95 超過 2 秒」，段 A、段 B、兩段相加任何一個超過就觸發。「30 次裡有任何一次沒恢復」包括自我檢查不過而作廢的。綁定 90 秒內沒回來的那一次，驅動不往下殺，直接收尾回報。

6. **池的後測的 per-thread 臂不再有「前台」那 M 台**，所以回合結束的 `mcp-stdio` 個數預期是 2，前測是 2×（N＋2）；這是第一節說的預期，不是判準。
