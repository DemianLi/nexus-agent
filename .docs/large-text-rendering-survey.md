# 大檔文字在 web 上的渲染：量測紀錄

2026-09-23，[#543](https://github.com/DemianLi/nexus-agent/issues/543)。起因是 demian 回報「預覽一個長的
txt，側欄轉不停然後整個分頁沒反應（游標轉不停）」。這份紀錄的用途是**對照組**：下次再有人說「大檔會卡」，
先拿這裡的數字比，不用重跑真模型、重造一百多 MB 的檔。

## 結論先講

1. **位元組上限推導不出畫面時間。** 渲染成本有一部分按**字元出現次數**算（字型回退、shaping），不是按位元組。
   同樣 2 MiB 可以是 111ms，也可以是 12964ms。所以「一頁最多 2 MiB」擋得住記憶體，擋不住主執行緒。
2. **一次進畫面的量要按數量設限。** 三個吃大量文字的面裡，改動審查有（`MAX_RENDERED_LINES = 5000`）、
   工具卡有（wire 端 40000 bytes），交付檔預覽原本沒有 —— #543 補上 20 行一塊的 `content-visibility`。
3. **那次的症狀最可能出在 #452 開發中的中間狀態**：路由（#509）與預覽（#510）落地當下就有三個上限與翻頁，
   develop 上從來沒有「整份檔直接畫出來」的版本。

## 一、四格基線（2026-09-23，develop `516f0d9`）

真的 `serve --live`、真模型用 `present` 宣告、真的 HTTP。每一發 server 請求都併發打 `/threads`
（閒置基線 0–2ms）偵測 event loop 有沒有被擋住。

### 交付檔預覽 × server

| 檔 | 狀態 | 耗時 | 回應 |
| --- | --- | --- | --- |
| 50 MiB／1048576 行 | 413 | 1–5ms | 63 字元 |
| 50 MiB／50 行（每行 1 MiB） | 413 | 2–6ms | 62 字元 |
| 30 MiB／629145 行 | 200 | 37–70ms | 255 KB |
| 20 MiB／52298 行（每行 400 B） | 200 | 11ms | 2.01 MB（滿頁） |
| 2 MiB／41943 行 | 200 | 4ms | 255 KB |

併發的 `/threads` **一次都沒被擋住**。整檔讀（NUL 掃描、UTF-8 解碼、`split('\n')`）快到量不出阻塞。
50 MiB 在 `stat` 那道就回 413，不可能轉不停。

**一頁有兩道門**（`maxLines` 5000、`maxBytes` 2 MiB），誰先到算誰。每行 50 B 的檔一頁只有 255 KB ——
要量到滿頁 2 MiB，每行得約 400 B。

### 交付檔預覽 × 瀏覽器（當時的實作：整頁一個 `<pre>`）

| 動作 | 主執行緒最大間隔 |
| --- | --- |
| 畫一頁 2 MiB（ASCII） | 239ms（一次） |
| 捲動那一頁 | 52ms |
| 「讀下一段」翻完 11 頁 | 每頁 257–316ms |
| 下載 30 MiB | 51ms |

### 改動審查 × server

`changes/summary` 1ms、`changes/diff` 32–37ms。`oversized` 門檻 2 MiB
（`@nexus/plugin-workspace-changes` 的 `maxFileBytes`），比交付檔的 32 MiB 嚴 16 倍。

### 改動審查 × 瀏覽器（攔 `Response.prototype.json` 注入最壞情況）

| 注入的 diff | 最大間隔 | heap |
| --- | --- | --- |
| 41,861 行新增 | 384ms | 17MB |
| 2,000,000 行新增（7.6 MB JSON，server 在門檻下能交的極限） | 364ms | 31MB |
| 單一 2 MiB 的行 | 130ms | 15MB |

`MAX_RENDERED_LINES` 有效：畫面只畫 5000 行。**不能攔 `window.fetch`** —— store 在 `useMemo` 建立時就把
`globalThis.fetch` 綁走了。

## 二、內容的形狀

前兩格的檔全是 `x` 重複 —— 那是相似品。2 MiB 一頁、只換內容（裸 `<pre>`，Chromium／macOS）：

| 內容 | layout | 總計 |
| --- | --- | --- |
| ASCII | 92ms | 111ms |
| 中文 | 51ms | 335ms |
| 中英混排 | 93ms | 109ms |
| 組合字 | 181ms | 650ms |
| 阿拉伯文 | 412ms | 448ms |
| emoji 那一組 | **12446ms** | **12964ms** |

那 12 秒追下去是**一個字元**。固定 8000 行、每行只差結尾一個字元：

| 結尾 | layout | 每次出現 |
| --- | --- | --- |
| （無） | 45ms | 6µs |
| **裸 `🏳`（U+1F3F3，沒有 VS16）** | **15068ms** | **1884µs** |
| `🏳️`（＋VS16） | 69ms | 9µs |
| `🏳️‍🌈` | 75ms | 9µs |
| `🙂` | 62ms | 8µs |
| `☂`／`☂️` | 54／175ms | 7／22µs |
| `中`、`│`、`𠀋` | 51–61ms | 6–8µs |

孤兒代理 294ms、懸空 ZWJ 289ms、U+FFFD 32ms 都正常 —— 不是「壞掉的 Unicode」那一類。第一次見到那個字元
只要 41ms，之後照樣每次 1.7ms —— 不是一次性的冷成本。

**不要把它讀成「🏳 很慢」。** 那是這個瀏覽器、這版字型的結果；換平台，會慢的就是另一組字元。只挑了十個
候選字元，能站得住的只有「存在一個按出現次數算、200 倍的離群值」。

## 三、`content-visibility` 的顆粒

headless Chrome（`--headless=new`，`visible`，1024×681），1000 行、每行結尾一個裸 `🏳`，
每種設定三個乾淨頁面，量「打開預覽」那一次追加：

| 設定 | 三次 |
| --- | --- |
| 無 cv | 1781／1584／1664ms |
| cv，**一段一個邊界** | 1634ms —— 等於沒加 |
| cv，50 行一塊 | 178／199／201ms |
| cv，20 行一塊 | 152／167／163ms |
| cv，20 行一塊，ASCII | 27／27／27ms |

cv 只跳過**畫面外**的東西，而打開預覽那一段就在畫面裡。邊界要比視窗小才有用。10 行、5 行一塊壓不下去 ——
地板是「視窗加 cv 預留邊距」裡那幾十行的 layout，跟塊多大無關。

## 四、#543 的實作，真元件驗收

worktree 建的 web、worktree 起的 serve、真模型宣告兩個 20 MiB、每行 400 B 的檔（ASCII，與每行結尾一個裸
`🏳`）。headless Chrome 打開真的 app，心跳 25ms 一拍。三輪（跳著捲只取後兩輪，第一輪的步長跟總長成比例，見第六節）：

| | 打開 | 每次自動接下一段（5000 → 30000 行） | 固定步長跳著捲，全新區域 |
| --- | --- | --- | --- |
| 病理 | 199／213／196ms | 196 198 182 200 206／187 186 201 188 194／202 166 205 187 192ms | 211／216ms |
| ASCII | 28／31／32ms | 27–37ms | 39／39ms |

接到 30000 行、1500 塊時，`checkVisibility({ contentVisibilityAuto: true })` 說**實際被畫的只有 2 塊** ——
這是畫面上限真的在作用的直接證據，任何時間數字都證明不了這件事。

**每次追加的成本不隨已載入的段數增加**：五次追加從 5000 行一路到 30000 行，數字是平的。

**病理內容的 ≤ 200ms 驗收沒有達成。** 打開與追加共 18 個樣本，5 個超過：213、206、205、202、201，超出 1–13ms。那條線是用 1000 行的探針數字事先定的，真元件的第一段是 5000 行。剩下的成本是
「視窗加 cv 預留邊距」裡那幾十行的 layout —— 第三節量過，塊切到 10 行、5 行都壓不下去。

跳著捲另外量過「載了 6 段之後、從第 25001 行起跳」得到 28–38ms，**那個數字不能用**。

- 對位用的是 `offsetTop`，但在 cv 塊裡它是相對於塊本身算的，所以根本沒跳到第 25001 行（見第六節）。畫面最可能被帶回檔頭附近，落在「一段時」剛跳過、已經畫過的區域。
- 這裡原本的解釋是「五次追加都捲到過底，那一區早就畫過了」，但那頂多讓起跳的那一格畫過，後面九跳仍然是新的區域，解釋不了整組都便宜。

第五節改用 `getBoundingClientRect` 對位，重量了一次。

## 五、行號折行與長行（2026-09-23，v0.5.10 之後）

### 行號折行（已修）

v0.5.10 的預覽（#548）有一個版面 bug：**行號的位數跟最後一行一樣多時，行號會被折成兩行，那一行變成兩倍高。**

原因是行號欄寬寫成「位數 + 1ch」，但裡面還要扣掉 `pr-3` 的 12px 內距。在 `text-xs` 下，1ch 約 7px，比 12px 窄，所以最大位數的行號永遠放不下。換行開著的時候（預設），`overflow-wrap:anywhere` 也作用到 `::before`，行號就從中間被折斷。jsdom 不做排版，所以單元測試看不到。

修正前後的對照：同一個 serve、同一組真模型宣告的檔，只換 web 的 dist。量的是畫出來的塊裡短行的高度：

| 檔 | 修正前 | 修正後 |
| --- | --- | --- |
| 50 行 | 20px × 9、**40px × 41**（第 10–50 行） | 20px × 50 |
| 4901 行（逐一捲到第 1、99、100、999、1000、1990、4901 行） | 第 1–999 行 20px，**第 1000 行起全是 40px** | 全部 20px |

修正後在 Chrome 裡讀 `::before` 的實際寬度：兩位數的檔是 26.39px，等於 2 × 7.2px（1ch）+ 12px；四位數的檔是 40.80px，等於 4 × 7.2px + 12px。第 1、9、10、50、999、1000 行的內文起點 x 完全相同。所以行高變回 20px 是因為寬度算對了，不是因為 `nowrap` 把放不下的數字擠到溢出。

還有一個連帶的症狀：塊的高度用每行 20px 估，實際卻是 40px，對不上。修正前捲到第 1990 行，畫面頂端停在第 1941 行；修正後正好停在那一塊的開頭，第 1981 行。

**第四節的數字依排版推論不受影響，但沒有對照過。** 那兩個檔每行 400 B，換行後本來就佔好幾行，行號折成兩行不會讓整行更高。不過修正前的 dist 沒有拿同一組檔跑過，這次的檔也是照同樣形狀重新產生的，不是當時那一份。修正後重跑三輪（每輪重開 Chrome），數字跟第四節同一級。病理內容的「打開」這次是 215–232ms，比第四節的 196–213ms 高約 20ms，這個差距沒有拆開量：

| | 打開 | 每次自動接下一段（5000 → 30000 行） | 跳著捲，一段時 | 跳著捲，六段時（從第 25001 行起） |
| --- | --- | --- | --- | --- |
| 病理 | 217／215／232ms | 181–209ms | 202／205／207ms | 209／212／196ms |
| ASCII | 36／30／28ms | 27–38ms | 31／30／27ms | 49／44／35ms |

- 「六段時」那組這次有效：起跳時用 `elementFromPoint` 讀回來，畫面頂端確實是第 25001 行。數字跟「一段時」同一級，段數多了之後跳著捲並沒有變貴。
- 30000 行、1500 塊時，實際畫了的仍然只有 2 塊。
- 病理內容仍然有樣本超過 200ms：打開 3 個、接段 5 個、跳著捲 5 個。第四節的結論不變。

### 長行

單行很長時，cv 只能跳過畫面外的「塊」，切不進一行裡面，所以那一行得整行排版。測試條件是每個檔開一個乾淨頁面，數字是主執行緒最長卡住的時間：

| 檔 | 打開 | 往下捲 | 切成不換行／切回換行 |
| --- | --- | --- | --- |
| 單行 1.9 MiB，minified JSON | 118–135ms | 27ms | 92–115／135–146ms |
| 單行 1.9 MiB，有空白的文字 | 154ms | 27ms | 126／152ms |
| **單行 1.9 MiB，夾 4931 個裸 `🏳`** | **702／704／713ms** | 28–30ms | 111–139／**744–747ms** |
| 4901 行，第 2001 行長 1.5 MiB | 27–54ms | 28ms（有捲過長行） | 28／39ms |
| 單行 2.5 MiB | 「檔案太大，沒辦法在這裡預覽」＋下載鈕 | — | — |

- **長行造不出「整個分頁沒反應」**，最壞是 0.7 秒。所以長行也解釋不了當初的症狀。
- **捲軸會跳。** 長行所在的塊還沒畫時用 20 行估，約 400px；畫出來後約 47 萬 px。
- **切成不換行後捲軸長度不對。** 捲出畫面的長行塊還記著換行時的高度（`contain-intrinsic-size: auto`），`scrollHeight` 停在 570736。
- **單頁上限（2 MiB）是整頁拒絕。** 長行跟同一頁其他行加起來超過上限，整頁都拿不到。

這幾件的後續處理在 [#555](https://github.com/DemianLi/nexus-agent/issues/555)。

## 六、量具的陷阱（每一個都差點變成錯的結論）

- **藏起來的窗格量不了可見性。** Claude 瀏覽器窗格藏著時頁面是 `hidden`、`innerWidth/innerHeight` 為 0；
  給了尺寸之後仍是 `hidden`。cv 一塊都不畫、IntersectionObserver 不觸發 —— 第一支探針因此量到「1000 行
  病理內容、有 cv、在視窗裡 → 7ms」，那是「什麼都沒畫」的時間。要用 headless Chrome，並配一個分得出「畫了」
  與「跳過」的偵測器（`contentvisibilityautostatechange` 事件、塊的實際高度 vs `contain-intrinsic-size`、
  或 `checkVisibility`）。
- **對照組是好的不代表量具是好的。** 同一頁裡沒有 cv 的對照組照樣量到 1.5 秒（強制 layout 不看可見性）。
- **探針自己會造出病。** 第一支 emoji 探針用 `slice(0,120)` 切行，每行結尾多出一個裸 `🏳` —— 12 秒全來自它。
- **跳著捲的步長不能跟總長成比例。** 段數越多跳得越遠、越落在沒畫過的區域，量的是「跳多遠」不是「載了多少」。
- **排序會改變結果。** 同一個設定排第一個跑是 4526ms、排後面是 214ms；在乾淨頁面上重現不出前者。
  認證數字要每個設定開乾淨頁面。
- **`x` 重複的檔是相似品。** 前兩輪四格全綠，換成真實會出現的內容才撞到。
- **cv 塊裡的 `offsetTop` 是相對於塊本身算的。** cv 塊會成為裡面元素的 offsetParent，所以
  `el.offsetTop - scroller.offsetTop` 只是一個很小的數，「跳到第 1990 行」其實停在第 12 行，量到的是別的區域。
  對位要用 `getBoundingClientRect`，捲完再用 `elementFromPoint` 讀回畫面頂端是哪一行，拿來對照。
- **不截圖就看不到版面 bug。** 行號折行在 #548 驗收時就在，但那次只量時間，沒有截圖；jsdom 也不做排版。
