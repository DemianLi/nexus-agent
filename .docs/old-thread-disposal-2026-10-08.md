# 仍在用舊版插件的 thread：能列、能結束、能續接嗎

回答 [#1138](https://github.com/DemianLi/nexus-agent/issues/1138)：「只給新對話更新」留下的殘留風險是——發現舊版插件有漏洞時，進行中的 thread 仍在用它。客戶會問「怎麼確定舊版不再被用」。

**量測日期**：2026-10-08。nexus `develop`（PR #1154 之後）。探針是 `apps/harness/src/measure/old-thread-disposal.test.ts`，跑一次約 3 秒：

```bash
pnpm --filter @nexus/harness exec vitest run src/measure/old-thread-disposal.test.ts
```

## 結論

三條通過標準，今天各是這個狀態：

| 通過標準 | 結果 | 實情 |
| --- | --- | --- |
| 能列出受影響的 thread | **部分** | 落盤的 header 記了建立當下的插件清單，離線讀得到；線上的列表沒有這一格，要自己把兩邊對起來。而且 header 在續接後會**過期**（缺口 2）。 |
| 能讓它們乾淨結束，日誌不壞 | **有，但沒有「退役」這件事** | 取消與關機兩種結束，日誌都讀得完；但沒有「這條 thread 不再收新輸入」的狀態，取消之後它照收照用舊版（缺口 3）。結束的單位是**整台 server**。 |
| resume 後走新版，歷史完整 | **有** | 走新版、歷史逐則都在；被關機切斷的那一輪，人話也留著。 |

## 怎麼量

「新舊並存」今天只有一種形狀：**兩台以上的 serve**——插件清單在起動時解一次（`loadDefaultPlugins`），一台 server 只有一版。探針起 `runServe` 三次（`v1`、`v2`、再一台 `v2`），共用同一個會話根，各自 `--patch` 一份指向不同版本目錄的清單。

兩版插件是不 import 任何東西的 `.mjs`，每次模型請求往共用的見證檔 append `{version, shape}`——哪一版被呼叫、模型收到什麼，都看見證檔，不看日誌也不看畫面。「卡住」的那一輪模擬一次進行中的網路呼叫：中止訊號舉起來就中斷（取消的載體見 `turn-cancel.ts`）。

## 量到的

### 問題 1：列出

- **落盤那條路能列**：`StoredSessionHeader.plugins` 記建立當下疊完的清單，`file:` 條目帶絕對路徑，版本目錄因此分得開。`store.list()` 濾 `plugins` 裡有 `/v1/plugin.mjs` 的，得 `[old-busy, old-idle]`，不含 v2 起的 `new`。
- **線上那條路列不出**：`GET /threads` 每一列是 `threadId`、`updatedAt`、`running`、`blank`、`title`，沒有任何插件欄位。`running` 是這台 server 自己的，列的卻是整個會話根——v1 那台的列表裡也有 v2 那台起的 `new`。要答「哪些**活著**的 thread 在用 v1」，得把「header 清單」與「`running`」自己對起來。
- 記憶體裡也沒有：`ThreadState` 沒有插件資訊，`NexusPlugin` 沒有版本欄位。

### 問題 2：結束

| 做法 | 日誌尾巴 | 讀得完？ |
| --- | --- | --- |
| `run.cancel`（中斷進行中的模型呼叫） | `…model/start, model/end, turn/end`——那一輪正常收尾，沒有模型回覆 | 是 |
| 不取消，直接關 server | 停在 `model/start`，沒有 `turn/end` | 是（讀到實體上有效的前綴） |

- 取消之後，關機**不再動**日誌（前後逐事件相同）。
- **取消不是退役**：同一條 thread 取消之後再 `run.start`，照收、照跑、見證檔顯示全是 v1。`ThreadPump` 只有 `cancel()`（這一輪）與 `close()`（整台關機時才叫），`wire-handler.ts` 的 `threads`／`ready` 兩張表也註明「沒有逐條刪除」。
- 所以今天「讓舊 thread 結束」的粒度是**整台 server 關掉**。在「一台一版」的現況下這與「退役這一版」等價，但會連同那一版上所有 thread 一起（含進行中的）。

### 問題 3：續接

換一台 v2 的 server 接同一個會話根，`old-idle` 與被關機切斷的 `old-busy` 各說一句：

- 見證檔裡 resume 之後的每一次模型請求都是 **v2**，一次也沒回到 v1。
- `old-idle`：模型第一次請求帶著完整六則歷史＋新的一句。
- `old-busy`：完整那一輪在，**被切斷那一輪的人話也在**，所以模型看到兩句連續的人話（`human:卡住了`、`human:接著說`）。
- 日誌接著寫：舊事件原封不動，中間隔一顆 `session/end-seed`。
- **header 不更新**（續接規則沿用已存的 header，見 `StoredSessionHeader.build` 的說明）：這兩條現在跑在 v2，`store.list()` 仍把它們列成 v1 的使用者。

## 缺口

1. **沒有「活著的 thread → 插件版本」這張表**。能問的只有落盤的 header，且只問得到 specifier。
2. **header 的清單只記建立當下，續接不回填**。後果是反方向的誤報：已經換到 v2 的 thread 仍被列為 v1 使用者；「確認舊版不再被用」的答案偏保守，但沒有辦法把它們從名單上消掉。另外 header 記的是 `name`（模組 specifier），**就地覆蓋同一個路徑**的更新分不出新舊——版本目錄的做法才分得出（#1139）。
3. **沒有逐條退役**：沒有「不再接受新輸入、等這一輪結束後收掉」的狀態，也沒有 per-thread 的 close 路。

## 沒量的、沒解釋的

- 這是**一台 server 內的行為**；「新對話拿新版」需要每條 thread 重讀清單，今天做不到（#1139 的前提 3，草稿 §五第 3 項），所以沒有「同一台 server 上新舊並存」可量。
- 事件詞彙在新舊版不同時續接的行為沒驗（新版多發一種事件、舊日誌裡沒有）。
- 探索時用過一個**不聽中止訊號**的模型呼叫：取消之後那一輪沒有收尾（日誌停在 `model/start`），同一個測試行程裡接著起的第三台 server 在載入插件時停住。前半是合作式取消的已知性質（`turn-cancel.ts` 檔頭）；後半沒查到原因，也只在 vitest 的行程裡看過，**沒有拿它下結論**。真的模型呼叫由 fetch 層吃中止訊號，不是這個形狀。

## 要補的話，最小的順序

這張卡只驗證；做不做、怎麼做是 demian 的決定。若要做：

1. 續接時把「這一次實際載入的清單」另記一格（不改原 header 的 `plugins`，同 `build` 的規則；或事件日誌記一顆）——解缺口 2，不碰結構。
2. 線上列表加「這條 thread 載入的插件」——要先有 1，否則給的是過期的答案。
3. 逐條退役——要先決定語意（拒收新輸入？等這一輪？），是新功能，不是修補。
