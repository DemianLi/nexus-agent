# 摘要拆成凍結的索引條目與一份可變現況：設計（#2776）

狀態：**草案，等核可**。核可前不實作。

- 卡：[#2776](https://github.com/DemianLi/nexus-agent/issues/2776)，主卡 #2336。
- 前置：#2774（保真度評估與基準，已合併）、#2775（生摘要重播上一次主請求，已合併，`6b37e438`）。
- 行號對的是 develop `6b37e438`；dsh 對的是本機 clone 的 SHA `8bd0733`。

## 1. 現況與問題

有效訊息串是「一則摘要加尾巴」：`[summaryMessage, ...messages.slice(cutoffIndex)]`（`packages/nexus-core/src/summary-cutoffs.ts:133-141`）。第二次摘要時，引擎從有效串的開頭切，舊摘要那一則跟新訊息一起交給模型重寫；合併規則只有摘要指令裡「PRIOR checkpoint」那一條。

後果有三個：

1. **早期事實每一代被改寫一次。** 基準量到的 `double`（連續摘要兩次）三輪裡有兩輪第二次摘要被輸出上限截斷拒收（`.docs/summary-fidelity-baseline-2026-11-15.md`）；#2775 的重播模式三輪都完成，但得分 0.93（0.89–1.00），掉的是經過兩次摘要的 `todo` 與第二段的 `runbook`。
2. **被推翻的決定靠模型自己記得刪。** 沒有任何結構標出「這條取代了那條」。
3. **每次摘要之後請求前綴從第一則就變了。** 摘要那一則整份重寫，下一次主請求的前綴快取從系統訊息之後全部失效。

## 2. dsh 怎麼做、為什麼

**現行實作**跟 nexus 一樣整份重摘：可摘範圍永遠從第一個非 system 節點開始（`packages/compaction/compaction-basic/src/region.ts:130-149`），合併靠提示詞。它解決的是「上下文要縮」，代價就是上面三條。

**尚未實作的提案** `.agents/notes/proposed/feature/2026-07-06-recallable-compaction.md`（狀態 proposed）講同一個方向，重點：

- 一份摘要同時扮兩個角色：**索引**要凍結、照時間排、便宜；**工作記憶**要看全局、能重排、可變。合在一起兩邊都做不好。
- 被摘掉的歷史照確定的規則切塊，每塊各一次模型呼叫，產出 100–200 token 的 **index stub**：兩三行發生了什麼、一行字面錨點、一行**程式組的**指標。寫入後不再改、不再進任何一次摘要的輸入。
- 一份可變的 **state checkpoint**，放在所有 stub 之後、尾巴之前，每次用「上一份加這次被摘掉的」重寫。
- 請求前綴變成 `[system][stubs…][state][tail]`，快取失效點落在 state。
- 舊會話的頭一則摘要收編成 state。
- 膨脹守衛：摘完沒有變小就整次不提交。
- 它自己拒絕的做法：一次呼叫產出全部（沒有結構化輸出的強制，要把自由文字切開，脆弱）；模型自己寫指標（指標要精確）。
- 它自己列的風險：stub 目錄佔注意力；每次摘要的輸入大約是基準的兩倍；兩個後端的維護成本。

因為沒有實作、沒有實際使用驗證過，這張不能用「照 dsh」帶過。

條目的固定形狀、大小上限與取代鏈，卡上指到 `kiaqyn/hierarchical-attention-memory`（SHA `31a8a8c`，`scripts/hfa_manager.py:1443-1450`、`:2540`）。**這個 repo 不在本機 `references/`，寫這份文件時沒有重新核對那幾行**；下面只用卡上寫明的兩點：記錄有長度上限、被取代的記錄只列名不展開。

## 3. 設計

### 3.1 頭一則的形狀：一則訊息，程式組出來

有效串維持 `[頭一則, ...尾巴]`，**頭一則仍然只有一則訊息**，內容由程式照固定格式組：

```
<前言：一句，與現在的包法同一句>
<index>
[#1 訊息 0–41 · c17] 標題一行
- 發生了什麼（至多三行）
錨點: ENOSPC; retention_days=14; /srv/backup/run.sh
[#2 訊息 42–97 · c63] 標題一行
- …
取代: #1 的「週三同步」改成週四
錨點: …
</index>
<state>
（現況，模型寫的 Markdown，有上限）
</state>
```

- **索引條目在前、現況在後。** 條目一旦寫進日誌就不變，新條目只會接在後面，所以頭一則的位元組前綴跨多次摘要相同，快取失效點落在 `<state>`。供應商的前綴快取比的是 token 前綴，不要求訊息邊界對齊。
- **方括號那一行整行由程式組**：序號、被摘掉的訊息範圍（state 訊息串的座標，`[上一次 cutoffIndex, 這一次 cutoffIndex)`）、那筆 `compaction/summary` 的 `seq`。模型不寫、也改不到。
- **條目的其餘三格由模型寫、程式驗**（3.3）。

### 3.2 每次摘要兩次模型呼叫，各寫一樣東西

被摘掉的那一段 `S` = 有效串 `[1, 切點)`，**不含頭一則**。

1. **條目呼叫**：指令是「替緊接在上面的這一段寫一筆索引條目」，輸出只有標題、至多三行、錨點，以及選填的「取代」一行。
2. **現況呼叫**：指令是「用上面的現況加這一段重寫現況；被推翻的決定移除」。輸出是新的現況全文。

兩次都沿用 #2775 的重播形狀：`[system…, 頭一則, ...S, user: 指令]`，都是上一次主請求的前綴，第二次連第一次的前綴一起命中。退回模板的條件不變（`replayedSummaryCall` 的那幾條）；模板形狀下同樣是兩次呼叫，上一份現況與 `S` 攤成字串放在指令前面。

**提交是原子的**：兩次都通過檢查才寫一筆 `compaction/summary`、才換切點。任一次失敗就整次不摘，走 #1374 既有的退路（照原請求送出）。

**取代**：條目的「取代」一行由條目呼叫寫（它看得到頭一則裡的舊條目與現況）。程式只驗它引用的序號存在。舊條目不改寫。

### 3.3 大小上限與超過時的行為

| 東西 | 上限（設定鍵，數字在實作時用評估定） | 超過時 |
|---|---|---|
| 條目標題 | 一行，字元上限 | 重生一次；仍超過就退成只有指標的條目 |
| 「發生了什麼」 | 至多三行，每行字元上限 | 同上 |
| 錨點 | 一行，字元上限 | 同上 |
| 取代 | 至多一行；引用的序號要存在 | 引用不存在就丟掉這一行，其餘照留 |
| 現況 | token 上限，量級同現在的摘要 | 重生一次；仍超過就整次不摘（不截斷） |

- **不截斷內文**：截斷的錨點是錯的錨點。
- **只有指標的條目**是合法條目：`[#3 訊息 98–140 · c88]` 一行，沒有內文。它保住「這一段存在、在哪」。
- **膨脹守衛**：新頭一則加尾巴的估計 token 不小於摘之前就整次不摘。這是新增的檢查（在 `summarizer-engine.ts` 裡沒有找到同性質的既有檢查），量具用引擎現有的 token 估算。

### 3.4 日誌

`compaction/summary` 加兩格，都是選填：

- `entry`：`{ index, title, lines, anchors, supersedes?, range: [from, to) }`，`title`／`lines`／`anchors` 在只有指標的條目上缺席。
- `state`：現況全文。

`summary`（整則頭一則訊息）照舊記。所以：

- **舊讀者照舊能讀**：它只看 `summary`、`cutoffIndex`、`messagesBefore`，三格的語意都沒變。
- **日誌推導不動座標**：`conversation-replay.ts:412-427` 照舊用 `summary` 與 `cutoffIndex`，`compaction-misaligned` 的檢查照舊成立。#2775 的重播靠「有效串與日誌推出來的串逐位對齊」，頭一則仍是一則，對齊不受影響。
- **舊日誌續接**：最後一筆 `compaction/summary` 沒有 `state` 就是舊格式，它的摘要全文收編成現況，條目從零開始（同 dsh 提案的收編）。之後第一次摘要產生第一筆條目。
- **條目從日誌重建**：行程重啟後，條目清單是所有帶 `entry` 的 `compaction/summary` 照 `seq` 排；現況是最後一筆的 `state`。不另存檔。

加選填欄位不升日誌格式版本，同 `durationMs` 那次的做法；附 `docs/persistence-changes/` 文件與 schema。

### 3.5 上下文分項

#2774 的上下文分項把頭一則算成「舊摘要」一格。改成兩格：索引（`<index>` 到 `</index>`）與現況（其餘，含前言）。兩格相加等於原本那一格，總和規則不變。切分用程式組頭一則時的偏移，不解析文字。

### 3.6 不動的東西

- 摘要前言裡「原文在哪」那句話：讀回原文的卡負責。
- 讀回原文的工具：另一張卡。這張只把範圍指標寫進條目。
- 觸發門檻、留多少尾巴、工具參數截斷：不動。

## 4. 別的做法，同一組標準比較

| | A：一則頭訊息，程式組（本設計） | B：每筆條目各一則訊息，現況一則（dsh 提案的形狀） | C：維持整份重摘，只加強提示詞 |
|---|---|---|---|
| 正確性 | 條目位元組不變由程式保證；座標不變 | 同樣保證；但有效串多出 k 則，所有座標換算都要改 | 不保證，靠模型 |
| 失敗與恢復 | 兩次呼叫原子提交；失敗走既有退路 | dsh 提案要處理「提交到一半」，因為它是多個節點逐一替換 | 同現況 |
| 效能 | 每次摘要兩次呼叫，都吃 #2775 的前綴快取；摘完的主請求快取保住條目那一段 | 同 A | 一次呼叫；摘完快取全失效 |
| 維護成本 | 切點表、日誌推導、`compaction-misaligned`、#2775 的對齊都不動 | `summaryCutoffIndex` 的算式、切點表、日誌推導、shadow 比對、token 分項全部要改成「k+1 則頭」 | 最低 |
| 產品需求 | 稽核：條目與現況分開記在事件上，查得到哪一次寫了什麼、取代了什麼 | 同 A | 稽核只看得到整份摘要 |
| 現有基座 | 做得到，引擎是自己的（`summarizer-engine.ts`） | 做得到但動的面大；遷往 Cordis 時這些座標邏輯要再搬一次 | 做得到 |

**選 A。** 相對 B，快取與凍結的性質完全一樣（前綴快取不看訊息邊界），但不必動 state 座標與日誌推導，這兩塊是 #1301、#2355、#2775 一路釘過不變量的地方。相對 C，C 沒辦法滿足驗收的「已寫入的條目逐位元組不變」。

**與 dsh 提案不同的地方：**

1. 條目不是獨立節點，是頭一則訊息裡的段落（上表）。
2. dsh 提案把被摘掉的歷史切成多塊、並行摘；這裡一次摘要一筆條目。nexus 每次摘掉的量由門檻與尾巴決定，量級是一塊；並行與分塊留到觀察到單筆條目蓋太大範圍時再做。
3. dsh 提案把舊的 state 折進下一次的第一塊當一般歷史；這裡現況呼叫直接讀上一份現況，條目呼叫的輸入不含它要寫的東西以外的義務（它看得到頭一則，但指令只要它描述 `S`）。
4. 沒有 recall 工具（另一張卡）。

**一次呼叫產出兩樣**（省一半輸出成本）沒有選，理由同 dsh 提案：摘要路徑沒有結構化輸出的強制，把一份自由文字切開是最容易壞的地方，而這裡壞了就是條目寫錯、永久留著。

## 5. 風險與未決

1. **條目目錄只增不減。** 每筆約 100–200 token，一場摘 30 次就是 3,000–6,000 token 的固定前綴。dsh 提案把「最舊的條目由程式捲成一筆」列為後續；這張也先不做，但條目數與索引 token 進上下文分項，看得到。**要不要在這張就定一個條目數上限，請決定。**
2. **成本**：每次摘要兩次呼叫。#2775 量到重播的輸入大半命中快取，多出來的主要是條目那次的輸出（上限小）。
3. **`zh` 的基準**：重播模式 0.87（0.60–1.00），模板基準 0.93，n=3 分不出來。驗收寫「其餘不低於基準」，**建議**實作前先用現行 develop 跑 `--samples 5 --summary-call replay` 當這張的基準（140 次請求，要另外核可），不然比的是不同請求形狀。
4. **`double` 的題庫只有兩段**，條目最多兩筆，量不到「目錄佔注意力」。要不要加一個摘四次以上的變體，請決定。
5. **模型不照格式寫條目**的比例沒量過；退成只有指標的條目是安全網，但比例高的話索引就沒用了。實作時把「重生次數」與「退成指標的次數」記進事件。
6. **HAM 的行號沒有在本機核對**（第 2 節）。要核對就得抓那一支檔（固定 SHA、只讀），要另外核可。
