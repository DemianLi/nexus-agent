# 07｜Agent Evaluation / Eval（評估方法）

## 這一章回答什麼

本章處理「怎麼評」agent，涵蓋三塊：可執行的評估環境與基準（網頁、工具 API、作業系統、軟體工程與終端機任務）；多輪對話與互動式評估；LLM-as-a-judge、agent-as-a-judge 與評估本身的可靠性，包括偏差、資料污染、可重現性與人評協定。其中資料污染與人評協定只透過基準論文自己的設計主張與人類基準出現，計入的 24 篇沒有一篇以污染量測或人評方法本身為題（見〈已知缺口與未讀〉）。分數怎麼定義與聚合歸 T8，軌跡的步驟級評分歸 T4，本章遇到時只點出交界。本節點精讀 24 篇、計入 24 篇，另有 5 篇候補未讀（篇數由 reading-status.json 計算）。計入篇數依子領域分佈如下：agent 基準與評估環境設計 10 篇（配額 10）、多輪對話與互動式評估 6 篇（配額 6）、LLM/agent-as-judge 與評估可靠性 8 篇（配額 8）。全章的主軸是：三個子領域越往後期，力氣越從「設計評分方式」移到「證明評分器可信」，但各篇驗證評估器時用的口徑、樣本量與方向都不一致（本章歸納）[arXiv:2207.01206][arXiv:2601.11868][arXiv:1603.08023][arXiv:2410.10813][arXiv:2303.16634][arXiv:2502.06193]。

**範圍與時間窗。** 計入的 24 篇，arXiv 年月最早是 How NOT（2016-03），最晚是 Terminal-Bench（2026-01），由文獻表的 arXiv 年月欄計算。本章引用別節點論文當反例時，最晚用到 2602.16666（2026-02，T8 計入）[arXiv:2602.16666]，但它不在本章的計數裡。5 篇候補沒有讀，各自對應的缺口如下（說明只依標題，不代表它們的內容或結果）：
- AppWorld: A Controllable World of Apps and People for Benchmarking Interactive Coding Agents（arXiv 2407.18901，未讀）：依標題，是由多個應用與人組成、可控的互動式寫程式 agent 基準。
- LiveBench: A Challenging, Contamination-Limited LLM Benchmark（arXiv 2406.19314，未讀）：依標題，以限制資料污染為設計目標的 LLM 基準。
- Proving Test Set Contamination in Black Box Language Models（arXiv 2310.17623，未讀）：依標題，研究怎麼在黑盒模型上證明測試集污染。
- Evaluating Human-Language Model Interaction（arXiv 2212.09746，未讀）：依標題，研究怎麼評估人與語言模型的互動。
- Can LLM be a Personalized Judge?（arXiv 2406.11657，未讀）：依標題，研究 LLM 能不能當個人化的評審。

所以本章的結論不涵蓋 2026-01 之後的工作，也不涵蓋上面這幾塊與〈已知缺口與未讀〉列出的區域；寫「沒有」「只有」的句子，範圍都是本調研讀過的論文。

## 問題的演進

歸屬的寫法分三層。只附 [arXiv:ID] 的句子，是論文自己的主張或表格數字。寫「精讀時發現」「精讀時指出」「精讀時推算」「精讀時依公開資料查到」的，是精讀筆記 limitations_observed 裡精讀 agent 自己的分析，不是論文的結論，也沒有經過同儕審查。寫「本章重算」「本章核對全文」「本章歸納」的，是組章時用論文報告的數字自行算出、到快取全文逐表核對，或把幾篇串起來的結果，算式寫在句子裡。另外，精讀時的主張後面若接「程式驗證證實」，表示另寫了程式從快取全文解析表格、重算精讀時的主張，做法與保留條件見〈程式驗證〉一節。

三個子領域的時間大致重疊：對話評估指標的反省最早（2016），可執行的 agent 基準集中在 2022 到 2026，LLM 評審的後設評估集中在 2023 到 2025（年份取自 arXiv 編號前四碼）[arXiv:1603.08023][arXiv:2207.01206][arXiv:2601.11868][arXiv:2303.16634][arXiv:2502.06193]。下面先依子領域各自串成一條線，最後一小節把跨子領域的傳承接起來。

### agent 基準與評估環境設計（2022–2026）

十篇依 arXiv 編號排成：WebShop（2022-07）、Mind2Web（2023-06）、WebArena 與 ToolLLM（同在 2023-07）、AgentBench（2023-08）、SWE-bench（2023-10）、GAIA（2023-11）、OSWorld（2024-04）、SWE-Bench Pro（2025-09）、Terminal-Bench（2026-01）[arXiv:2207.01206][arXiv:2306.06070][arXiv:2307.13854][arXiv:2307.16789][arXiv:2308.03688][arXiv:2310.06770][arXiv:2311.12983][arXiv:2404.07972][arXiv:2509.16941][arXiv:2601.11868]。十篇都在問 agent 在接近真實的環境裡能不能把一件事做完，差別落在三條軸上（本章歸納）：

- **環境要真到什麼程度、又要多可重現。** 光譜從簡化的模擬網站、離線快照、Docker 自架副本、虛擬機，一路到直接打 live API 或開放網路 [arXiv:2207.01206][arXiv:2306.06070][arXiv:2307.13854][arXiv:2404.07972][arXiv:2307.16789][arXiv:2311.12983]。這條軸只涵蓋桌面、網頁文字介面與命令列；本章十篇沒有行動裝置環境，也沒有非看圖不可的網頁任務（本章歸納）。別節點的論文碰到過這兩類環境：2404.06474 在 Android-in-the-Wild 與 iOS 上評估 agent，AgentRewardBench 的軌跡有一部分來自 VisualWebArena [arXiv:2404.06474][arXiv:2504.08942]。專門的基準見〈已知缺口與未讀〉。
- **成敗由誰判定。** 隱藏規格的 reward 函數、人類示範的參考軌跡、最終環境狀態或隱藏測試、唯一短答案的比對，或交給 LLM 評審 [arXiv:2207.01206][arXiv:2306.06070][arXiv:2404.07972][arXiv:2310.06770][arXiv:2311.12983][arXiv:2307.16789]。
- **要不要把「正確放棄」算成成功。** WebArena、OSWorld、ToolLLM 都會算，Mind2Web 與 SWE-bench 沒有這類題目 [arXiv:2307.13854][arXiv:2404.07972][arXiv:2307.16789][arXiv:2306.06070][arXiv:2310.06770]。

這不是一條單線演進。WebArena 與 ToolLLM 同月上傳，對「真實性與可重現性」給出相反的答案；SWE-bench 的對手是 HumanEval 這類程式碼基準，不是網頁基準 [arXiv:2307.13854][arXiv:2307.16789][arXiv:2310.06770]。

**2022 年 7 月：WebShop 在真實語言、大規模的購物環境裡做到程式化自動評分。**

- **要解的問題。** 當時的語言互動環境，不是語言不真實（遊戲、3D 導航、MiniWoB 的低階點擊），就是要靠人評或人類回饋才算得出分數（例如 WebGPT），難以擴大規模 [arXiv:2207.01206]。
- **做法。** 從 amazon.com 抓 1,181,436 件商品，在 AMT 上收 12,087 條購物指令；每條指令由一件隱藏的目標商品反推，取它的屬性子集、選項子集與價格上限寫成自然語言 [arXiv:2207.01206]。購買後依 Eq.1 算 [0,1] 的部分給分 reward，同時報 Task Score（100 × 平均 reward）與 Success Rate（r = 1 的比例）；另附一般與 expert 兩層人類基準、可存取隱藏 reward 的 choice oracle，以及 Amazon／eBay 各 100 條指令的 sim-to-real 檢查 [arXiv:2207.01206]。
- **結果。** Score／SR 依序為 Rule 45.6／9.6%、IL 59.9／29.1%、IL+RL 62.4／28.7%、人類 expert 82.1／59.6%；choice oracle 在四種搜尋詞下的 SR 是 84.2–87.8%，作者據此判定「選擇」才是主要瓶頸 [arXiv:2207.01206]。自動 reward 與人工重評比較，一般工作者軌跡是 74.9 對 76.3（Pearson 0.856），expert 軌跡是 81.5 對 89.9（Pearson 0.773）[arXiv:2207.01206]。
- **留下的問題。** 作者自述只做 i.i.d. 切分，reward 採精確比對會低估同義詞 [arXiv:2207.01206]。精讀時發現，附錄印出的 r_type 公式與釋出程式碼的邏輯相反；人工稽核的 200 條樣本全是人類軌跡，協定只抓得到漏給分、不抓過度給分 [arXiv:2207.01206]。

**2023 年 6 月：Mind2Web 把真實網站存成離線快照。**

- **要解的問題。** MiniWoB++、WebShop 用的是模擬或簡化過的網站；RUSS、PixelHelp、MoTIF 只涵蓋少數網站，而且多半給逐步的低階指令，量的是「把指令翻成動作」而不是規劃 [arXiv:2306.06070]。
- **做法。** 在 137 個真實網站、31 個次領域上，由 MTurk 標註者示範 2,350 題高階任務；每一步存下 MHTML、DOM snapshot、HAR 與 Playwright trace，全部可離線重播 [arXiv:2306.06070]。判分逐步比對「元素＋操作」，每一步都餵正確的歷史動作，整題每一步都對才算成功；另切出 Cross-Task、Cross-Website、Cross-Domain 三層泛化測試集 [arXiv:2306.06070]。
- **結果。** 最佳的 Step SR 是 52.0%，整題 SR 最高只有 7.1% [arXiv:2306.06070]。
- **留下的問題。** 論文自承，收集時沒被快取的動作會讓任務立刻失敗，同一任務的多條可行路徑會造成偽陰性，而且還沒做過線上評估 [arXiv:2306.06070]。精讀時發現兩個方向相反的偏差：teacher forcing 讓 agent 自己的錯誤永遠不會延續，單一參考路徑則誤罰替代解，所以 SR 既不是上界也不是下界；動作空間也沒有「回傳答案」，資訊類任務到達結果頁就算完成 [arXiv:2306.06070]。

**2023 年 7 月：WebArena 與 ToolLLM 同月走上相反的路。**

- **WebArena 自架網站，只看結果。** 它把前人的毛病分成三種：MiniWoB++、WebShop 過度簡化，WoB、Mind2Web 只能走資料蒐集時存下的狀態，AndroidEnv 依賴線上服務而無法重現；也批評前人多半比對動作序列的表面文字，不承認有多條合法路徑 [arXiv:2307.13854]。做法是用 Docker 自架 Magento 電商、Postmill 論壇、GitLab、商店後台四類網站，加上地圖、計算機、筆記本與離線維基；241 個模板展開成 812 題 [arXiv:2307.13854]。判分只看功能正確性：資訊查找題用 exact_match、must_include 與由 gpt-4-0613 判斷的 fuzzy_match 比對答案，導覽與操作題用 locator 從資料庫、API 或頁面取值；另設參考答案為 N/A 的不可達題 [arXiv:2307.13854]。最佳的 GPT-4（CoT、不給 UA hint）是 14.41%，人類是 78.24% [arXiv:2307.13854]。精讀時發現三個缺口：官方 config 裡 812 題的 require_reset 全是 false，每題只開新的瀏覽器 context、不重設網站資料庫；fuzzy_match 的評審和最強受測 agent 都是 gpt-4-0613；判分只看目標狀態，不罰過程中改壞的東西 [arXiv:2307.13854]。
- **ToolLLM 直接打 live API，判分交給 LLM 評審。** 它指出既有工具資料集的 API 不是真的或數量太少、只有單工具情境、有些甚至不實際執行，並說明標不出固定 ground truth 的理由：真實 API 的回應會變，同一指令又有無限多條正確路徑 [arXiv:2307.16789]。做法是從 RapidAPI 實測過濾出 3,451 個 tool、16,464 支 API 當 live 環境，由 ChatGPT 依文件寫指令；ToolEval 由 ChatGPT 評審依「指令可解或不可解」與「以答案或以放棄收尾」判 Pass、Fail 或 Unsure，並對 ChatGPT-ReACT 做成對 win rate，每次判定至少預測 4 次取多數決 [arXiv:2307.16789]。評審與人評的一致率，pass 是 87.1%，win 是 80.3% [arXiv:2307.16789]。論文自己說比較模型時必須用同一版本的 API；精讀時依公開資料查到，ToolBench 伺服器在 2024/07/28 到 2024/09/03 之間停擺，同團隊後來另做了以 API 回應模擬為基礎的 StableToolBench [arXiv:2307.16789]。

兩篇並排看：WebArena 為了可重現而自架環境、讀最終狀態；ToolLLM 為了規模與真實性打 live API，並以「回應會變、路徑無限多」為由改交評審判定（本章歸納）[arXiv:2307.13854][arXiv:2307.16789]。

**2023 年 8 月：AgentBench 把多種可執行環境統一成同一套對話協定與總分。**

- **要解的問題。** LLM agent 應用大量出現，卻沒有跨情境的系統化基準；既有資料集各附一套評估程式，只能一次評一個 agent 對一個 task [arXiv:2308.03688]。
- **做法。** 8 個環境（OS、DB、KG、DCG、LTP、HH、WS、WB）全部包成同一種兩角色對話，環境扮演 user、受測 LLM 扮演 agent；只用 CoT 加 greedy 解碼，刻意不做重試、反思或搜尋 [arXiv:2308.03688]。總分 OA 是各環境分數除以 Weight-1 後取平均，Weight-1 是當時 27 個受測模型在該環境的平均分；每條軌跡依結束原因歸入 Complete、CLE、IF、IA、TLE 五類 [arXiv:2308.03688]。
- **與前人的承接。** WS 環境就是把 WebShop 直接包進來；精讀時指出，WB 用的是 Mind2Web 的頁面快照、逐步對照 reference 動作 [arXiv:2308.03688]。
- **結果。** gpt-4 的 OA 4.01，在 8 個環境中拿下 6 個第一；API 模型平均 OA 2.32，開源模型平均 0.51 [arXiv:2308.03688]。最主要的失敗是回合耗盡（TLE），在 LTP 佔 82.5%、KG 佔 67.9%；超過 90% 的 TLE 軌跡，在最後 10 輪內有兩則回應的 Rouge-L ≥ 0.8 [arXiv:2308.03688]。
- **留下的問題。** 作者自述 LTP 由 gpt-3.5-turbo 自動主持與判分，比人評寬鬆，對開源模型更明顯 [arXiv:2308.03688]。精讀時指出 OA 的權重槓桿不對稱、每個模型每個環境只跑一次、各環境處理格式錯誤的政策不一，也沒有做資料污染檢查 [arXiv:2308.03688]。

**2023 年 10 月：SWE-bench 把開源協作留下的痕跡當成免費標註。**

- **要解的問題。** HumanEval 這類基準多是幾行就能寫完的自足函式題，很快飽和，量不到跨檔案定位與多處協調修改；靜態基準又會被污染，需要一條能持續更新、人工成本低的收集流程 [arXiv:2310.06770]。
- **做法。** 從 12 個熱門 Python repo 的 93,139 個 PR 出發，留下「已合併、連結了 issue、改到測試檔」的 PR，再經執行式驗證剩 2,294 題；判分只看行為，PR 附帶、模型看不到的 FAIL_TO_PASS 與 PASS_TO_PASS 兩份清單都要全部 pass [arXiv:2310.06770]。
- **結果。** BM25 檢索下，摘要寫的最佳是 Claude 2 的 1.96%；v3 的 Table 5 裡 Claude 3 Opus 是 3.79% [arXiv:2310.06770]。它的基線是一次檢索加一次生成，完全不與環境互動，所以精讀時的判斷是：它對 agent 評估的貢獻在環境與判定協定，不在量到了 agent 的能力 [arXiv:2310.06770]。
- **留下的問題。** 論文自述只有 Python、只靠執行測試不足以保證品質、每個 release version 的執行環境都要人工建 [arXiv:2310.06770]。精讀時發現，PASS_TO_PASS 只涵蓋 test_patch 涉及的測試檔，repo 其他地方被改壞看不到；測試品質的過濾也很弱，抓不到過嚴的測試 [arXiv:2310.06770]。精讀時依官方 repo 查到，它在 2024-06-27 改成全 Docker 容器化的 harness，2024-08-13 再釋出人工篩過的 500 題 Verified 子集（見 [SWE-bench README](https://github.com/SWE-bench/SWE-bench)）[arXiv:2310.06770]。

**2023 年 11 月：GAIA 把環境換成開放網路，把評分縮成比對唯一答案。** [arXiv:2311.12983]

- **要解的問題。** MMLU、GSM8k 這類「對人很難」的題目已接近飽和也可能被污染；開放式生成要靠人評或模型評，兩者各有擴展性與偏差問題 [arXiv:2311.12983]。GAIA 也點名 AgentBench 這類封閉環境，認為它們預設有特定 API 與一條正確路徑，可能只量到模型學會特定 API [arXiv:2311.12983]。
- **做法。** 466 題概念上對人簡單、卻要一連串搜尋、瀏覽、讀檔、計算才能解的題目；答案唯一且簡短，以依型別正規化的 quasi exact match 自動評分 [arXiv:2311.12983]。每題交給兩位新標註者獨立作答；§3.4 正文寫出題者與兩位驗證者答案一致才算有效、不一致就修題或刪題，但 Table 3 腳註的「有效題」較寬：兩位驗證者都與出題者相同，或只有一位相同、另一位的錯誤屬於作答失誤；依出題者用到的步數與工具數分成 Level 1/2/3；166 題 dev 公開附答案，300 題 test 保留答案 [arXiv:2311.12983]。
- **結果。** 人類約 92%，GPT-4 加插件約 15%；所有受測系統在 Level 3 都是 0 分；新題第一次驗證就有效的只有 68%，Level 3 只有 47% [arXiv:2311.12983]。
- **留下的問題。** 作者自述不評推理軌跡、GPT4 + plugins 的分數靠人工逐題選插件而不可重現、基準會隨網頁變動與預訓練污染而衰退 [arXiv:2311.12983]。精讀時指出，human score 與「有效題」的定義共用同一批驗證者，形成循環（見〈評估方式與關鍵數字〉的人類基準一節）[arXiv:2311.12983]。

**2024 年 4 月：OSWorld 把環境擴大到整台電腦。**

- **要解的問題。** 它同時批評兩類前人：Mind2Web、AitW、OmniAct 這類靜態示範資料集只比對下一步動作，會誤罰其他正確解；MiniWoB++、WebArena、InterCode 這類可執行環境只限單一領域，動作空間也簡化過 [arXiv:2404.07972]。
- **做法。** 用虛擬機跑真實的 Ubuntu、靠快照重置；每題一份設定檔，寫明初始化步驟、要從環境取回哪些資料（getter）與用哪個評估函式判定（evaluator）[arXiv:2404.07972]。369 題共用 134 個評估函式、302 種初始狀態；其中 30 題是做不到的 infeasible 題，agent 輸出 FAIL 就得分；reward 可以是 0 到 1 之間的小數 [arXiv:2404.07972]。它也以自己的協定重測 100 題 WebArena 的人類表現，另有 84 題改編自 NL2Bash、Mind2Web、GAIA 等公開基準 [arXiv:2404.07972]。
- **結果。** 人類 72.36%，最佳的 GPT-4（只讀 a11y tree）12.24% [arXiv:2404.07972]。
- **留下的問題。** 論文自述評估腳本仍有假陽性與假陰性、評估函式不看不必要的破壞性動作、infeasible 題有運氣成分 [arXiv:2404.07972]。精讀時發現，agent 第一步就回 FAIL 就能拿到 30/369 = 8.13%，程式驗證證實；這是下限，若有 feasible 題在初始狀態就被評估腳本判成功，一律回 FAIL 會拿得更多（見〈程式驗證〉）[arXiv:2404.07972]。精讀時依官方 repo 查到，它在 2025-07-28 推出 OSWorld-Verified，修正社群回報的問題，並要求改和新版結果比較（見 [OSWorld README](https://github.com/xlang-ai/OSWorld)）[arXiv:2404.07972]。

**2025 年 9 月：SWE-Bench Pro 用資料來源與存取政策防污染，用人寫的規格收窄解空間。**

- **要解的問題。** SWE-bench 系列取自寬鬆授權的熱門 repo，可能已進入預訓練語料；SWE-Bench Verified 的 500 題中有 161 題只要改 1–2 行，分數已超過 70%；單元測試只接受特定介面，verifier 容易把合理的解判錯 [arXiv:2509.16941]。
- **做法。** 共 1,865 題、41 個 repo，分三層存取：public 731 題來自 copyleft 授權的公開 repo，commercial 276 題來自購買的新創私有 repo、只公開成績，held-out 858 題完全不公開 [arXiv:2509.16941]。每題至少 10 行變更，gold patch 平均 107.4 行、橫跨 4.1 個檔案；每題由人工寫出 problem statement、requirements 與選配的 interface；工程師手寫 Dockerfile，gold 測試重跑多次排除 flaky 測試，再人工剔除無關或過寬的測試；評估固定用 SWE-Agent、上限 50 輪、報 Pass@1 [arXiv:2509.16941]。
- **結果。** public set 最佳是 Claude Sonnet 4.5 的 43.6%，commercial set 最佳是 Claude Opus 4.1 的 17.8%；拿掉 requirements 與 interface 之後，GPT-5 (high) 從 25.9% 掉到 8.40%，Claude Opus 4.1 從 22.7% 掉到 8.20% [arXiv:2509.16941]。
- **留下的問題。** 作者自述依賴測試套件，預設設定量的是資訊充分時的實作能力、不是釐清歧義的能力 [arXiv:2509.16941]。精讀時指出，主要對比跨了不同預算設定，「抗污染」只有論證沒有量測，requirements 與 interface 也有洩題疑慮 [arXiv:2509.16941]。

**2026 年 1 月（arXiv v1）：Terminal-Bench 把力氣從「怎麼評分」移到「怎麼證明評分器是對的」。**

- **要解的問題。** 現有 agent 基準不是不夠真實，就是難度拉不開前沿模型；終端機已是 Claude Code、Codex CLI、Gemini CLI 等商用 agent 的主要工作介面；困難任務的規格是否完整、測試是否只在正確時成立、有沒有捷徑，都極難驗證 [arXiv:2601.11868]。
- **做法。** 每題由指令、Docker 環境、只檢查最終容器狀態的測試、人寫的 oracle 解與時間限制組成；93 位貢獻者提交 229 題，選出 89 題，平均每題約 3 小時審查人力 [arXiv:2601.11868]。品管依序是：oracle 解必須跑過而什麼都不做的代理人必須失敗、確定性 CI 檢查、11 項 LLM 規格檢查、由 LLM 除錯工具判斷失敗來自規格不足還是能力不足、對抗式作弊代理人、兩位稽核者決定是否納入 [arXiv:2601.11868]。另提供只有一個終端機工具的中立 scaffold Terminus 2；6 個 agent、每個組合至少跑 5 次，共 32,155 次試跑，附 95% 信賴區間 [arXiv:2601.11868]。
- **與前人的承接。** 它的 adapter 把 SWE-Bench Verified 等 26 個既有基準轉成自己的任務格式；相關研究段提到 WebArena 與 OSWorld，但全文沒有提到 WebShop、AgentBench、GAIA（本章核對全文）[arXiv:2601.11868]。精讀時依公開資料查到，Google 官方部落格在 2025-11-18 已引用 Terminal-Bench 2.0 的分數，所以 2.0 在它自己的 arXiv v1 之前就已公開（見 [Gemini 3 公告](https://blog.google/products/gemini/gemini-3/)）[arXiv:2601.11868]。
- **結果。** 最高分是 Codex CLI 加 GPT-5.2 的 62.9%±3.0，其次是 Terminus 2 加 Claude Opus 4.5 的 57.8%±2.5；作者難度標籤與模型經驗難度的相關 r = 0.436 [arXiv:2601.11868]。軌跡失敗分析的兩位標註者在 20 次試跑上 Cohen's κ 0.93，GPT-5 判官對 120 條人工標註軌跡的一致率 90%；以 Agentic Benchmark Checklist 自評平均 0.896 [arXiv:2601.11868]。
- **留下的問題。** 作者自述允許上網、資料全公開只放 canary 字串、測試品質沒有客觀指標 [arXiv:2601.11868]。精讀時指出任務數在文中有 89 與 74 兩種說法、ABC 自評給分偏寬、入選流程可能有篩選效應 [arXiv:2601.11868]。

**這條線的兩個走向（本章歸納）。** 第一，評估器的投資方向在移動 [arXiv:2207.01206][arXiv:2311.12983][arXiv:2509.16941][arXiv:2601.11868]：

- WebShop 的主要工夫在設計 reward，事後只用 200 條人類軌跡做一次人工稽核 [arXiv:2207.01206]。
- GAIA 把保證唯一答案的人工驗證寫進建題流程 [arXiv:2311.12983]。
- SWE-Bench Pro 把人工審查測試寫進建題流程 [arXiv:2509.16941]。
- Terminal-Bench 把 oracle／no-op 健全性檢查、LLM 規格檢查、LLM 除錯工具與對抗式作弊代理人都寫進建題流程；判官對人工的一致率則屬於事後的失敗分析，不在建題流程裡 [arXiv:2601.11868]。

第二，防污染的做法沒有同步演進 [arXiv:2306.06070][arXiv:2307.13854][arXiv:2404.07972][arXiv:2308.03688][arXiv:2311.12983][arXiv:2509.16941][arXiv:2601.11868]：

- Mind2Web 把測試資料放在有密碼保護的短網址後；論文沒說用意，精讀時判斷這能降低被爬進預訓練語料的機會 [arXiv:2306.06070]。
- 精讀時發現，WebArena 與 OSWorld 的題目、答案與評估腳本全部公開，沒有私有測試集，也沒討論污染 [arXiv:2307.13854][arXiv:2404.07972]。
- AgentBench 沒有做污染檢查（精讀時指出）[arXiv:2308.03688]。
- GAIA 保留 test 答案 [arXiv:2311.12983]。
- SWE-Bench Pro 用授權、私有 repo 與保留集 [arXiv:2509.16941]。
- Terminal-Bench 只放 canary 字串、全部公開 [arXiv:2601.11868]。

### 多輪對話與互動式評估（2016–2024）

**這個子領域實際涵蓋什麼。** 名稱沿用選文時的分類，但六篇裡有系統地讓受測模型在閉環裡多輪互動、讓前一輪的結果改變下一輪輸入的只有 MINT；Chatbot Arena 是真人互動，但平均每筆只有 1.3 輪；LoCoMo 讀的是既有對話，MT-Bench-101 與 LongMemEval 是靜態重播，How NOT 是靜態評分（本章歸納）[arXiv:2309.10691][arXiv:2402.17753][arXiv:2402.14762][arXiv:2410.10813][arXiv:1603.08023][arXiv:2403.04132]。所以本小節講的是「多輪對話怎麼評」，其中「互動式」只有一篇撐。閉環的對話評估在別節點的論文裡比較多：τ-bench、τ²-bench 與 ToolSandbox 讓 agent 和模擬使用者來回對話，SOTOPIA 讓兩個角色互動 [arXiv:2406.12045][arXiv:2506.07982][arXiv:2408.04682][arXiv:2310.11667]；2601.17087 在 τ-bench 上讓真人使用者和固定的 GPT-4o agent 對話 [arXiv:2601.17087]。依標題研究怎麼評估人與語言模型互動的一篇在本節點的候補裡，沒有讀（見〈已知缺口與未讀〉）。

這六篇掛在同一個子領域，其實在回答三個不同的問題：評估器本身可不可信、多輪互動要怎麼量、跨 session 的長期記憶要怎麼量（本章歸納）[arXiv:1603.08023][arXiv:2309.10691][arXiv:2402.14762][arXiv:2402.17753][arXiv:2403.04132][arXiv:2410.10813]。依 arXiv 編號排：How NOT（2016-03）、MINT（2023-09）、MT-Bench-101 與 LoCoMo（2024-02）、Chatbot Arena 論文（2024-03，平台本身在 2023-04 就已上線）、LongMemEval（2024-10）[arXiv:1603.08023][arXiv:2309.10691][arXiv:2402.14762][arXiv:2402.17753][arXiv:2403.04132][arXiv:2410.10813]。

**2016 年 3 月：How NOT 先問指標可不可信。** [arXiv:1603.08023]

- **要解的問題。** 開放領域回應生成沒有 task completion 這類監督訊號，大家便把機器翻譯與摘要的 BLEU、METEOR、ROUGE 搬來，拿模型回應跟唯一一句參考回應比字面重疊 [arXiv:1603.08023]。
- **做法。** 把這些指標當成受測物：Twitter 與 Ubuntu 各取 20 個 context、每個配 5 種回應，共 100 筆，由 25 位志工評 1–5 分的 adequacy，剔除 κ<0.2 的 2 人後剩 23 人，再逐筆算 Pearson 與 Spearman 相關 [arXiv:1603.08023]。
- **結果。** Twitter 上最好的 BLEU-2 也只有 Spearman 0.3576；Ubuntu 上所有指標的 |Spearman| 與 |Pearson| 都不超過 0.17；人類分半相關是 0.9476 與 0.9550 [arXiv:1603.08023]。
- **留下的教訓。** 同一批嵌入指標在 Table 2 可以把 DE 與兩種 TF-IDF 分出統計顯著的高下，卻和人評幾乎不相關，所以「分得出模型」不能當作指標有效的證據 [arXiv:1603.08023]。它沒有提出替代指標，只預告了「從資料學、會看 context 的評估模型」這個方向 [arXiv:1603.08023]。這個方向後來在開放領域回應生成上的學習式指標與多輪人評協定，本章都沒有收，所以本小節從 2016 年直接跳到 2023 年的 MINT；這個七年的空白是本章選文造成的，不代表領域在這段時間沒有工作（見〈已知缺口與未讀〉）。精讀時指出，How NOT 評的是「給定 context 評下一句」的靜態設定，5 種回應裡只有 HRED 是模型生成的，外推到 LLM 輸出要打折扣 [arXiv:1603.08023]。別節點讀過的兩篇是這個方向的部分反例，但都針對任務導向對話，不是 How NOT 評的開放領域回應：2105.03748 用對話前文學出逐輪的使用者滿意度估計器，1605.07669 用 GP 分類器從整通對話的向量估計任務成功機率 [arXiv:2105.03748][arXiv:1605.07669]。

**2023 年 9 月：MINT 把「多輪」變成可控的自變數。** [arXiv:2309.10691]

- **要解的問題。** 當時的 LLM 評估幾乎都是單輪，但作者引用的 ShareGPT 統計顯示約 73% 的對話超過一輪；多輪評估又貴，ReAct、Reflexion 各自抽測試子集，彼此難比 [arXiv:2309.10691]。
- **做法。** 受測模型以 Python 程式碼當工具，在最多 5 輪內解題，並由 gpt-4-0613 模擬使用者寫自然語言回饋；指標有互動上限為 k 時的成功率 SR_k、SR_k 對 k 的迴歸斜率 Δ_tools、有無回饋的 SR_5 差 Δ_feedback [arXiv:2309.10691]。題目從 8 個既有資料集的 29,307 題，用 gpt-3.5-turbo-0613 篩掉兩輪內可解者再分層抽樣，壓到 586 題 [arXiv:2309.10691]。
- **與前一篇的關係。** 它繞開 How NOT 的指標效度問題，方法是只挑有標準答案可驗的任務（程式碼跑測試、數學比答案、ALFWorld 看環境狀態），代價是把評估限在「難解但易驗證」的任務上（本章歸納）[arXiv:1603.08023][arXiv:2309.10691]。
- **結果。** 單輪強不代表多輪強：claude-2 的 SR_1 是 26.4、claude-instant-1 只有 12.1，到 SR_5 變成 39.9 對 45.9 [arXiv:2309.10691]。
- **留下的問題。** 精讀時指出，提出解答時由 ground truth 判對錯，這個「使用者」其實是握有標準答案的神諭，對客服、寫作這類開放式任務不成立；而且只到 5 輪、4,096 token [arXiv:2309.10691]。

**2024 年 2 月：MT-Bench-101 回到開放式對話，用 LLM 評審細分多輪能力。** [arXiv:2402.14762]

- **要解的問題。** 它沿用 MT-Bench 以 GPT-4 當評審的做法，但認為 MT-Bench 每題只有兩輪、只分 8 類主題，看不出多輪情境裡是哪一種能力壞掉 [arXiv:2402.14762][arXiv:2306.05685]。
- **做法。** 把多輪能力拆成 3 大能力、7 項能力、13 個任務，用 GPT-4 生成、5 位標註者全票篩選出 1388 段對話共 4208 輪 [arXiv:2402.14762]。協定有三個設計：歷史一律用金上下文、只評最新一輪；GPT-4 依任務專屬的分段評分準則打 1–10 分；每段取各輪最低分 [arXiv:2402.14762]。
- **結果。** 100 段對話上 GPT-4 與專家的 agreement 是 87%，專家彼此是 80% [arXiv:2402.14762]。
- **與前兩篇的關係。** 相對 How NOT，它把參照比對換成「評審＋評分準則」並補上對人評的驗證；相對 MINT，它刻意不讓受測模型自己的錯誤滾下去，理由是公平與避免錯誤累積，但它自己的 Figure 6 也顯示金上下文會讓後續輪的分數虛高（本章歸納）[arXiv:1603.08023][arXiv:2309.10691][arXiv:2402.14762]。
- **留下的問題。** 精讀時指出，對 IC（反問澄清）與 PI（主動互動）這兩個最依賴互動的任務，受測模型問了跟金回覆不同的問題時，下一輪「使用者」仍照稿回答，所以它量的是「給定理想歷史時的單輪條件表現」[arXiv:2402.14762]。

**2024 年 2 月：LoCoMo 把「多輪」拉長到數十個 session。** [arXiv:2402.17753]

- **要解的問題。** 既有的長期對話資料集（MSC、Conversation Chronicles）最多約 5 個 session、1K token 左右，測不出 long-context LLM 或 RAG 在跨數月對話裡記不記得 [arXiv:2402.17753]。
- **做法。** 用「人格＋帶日期與因果邊的事件圖」驅動兩個具記憶模組的 gpt-3.5-turbo agent 逐 session 對話，再人工修正，得到 50 段、平均 19.3 個 session、9,209 token 的對話 [arXiv:2402.17753]。7,512 題 QA 的答案盡量直接取自對話原文，每題標註含答案的證據 turn ID，因此能把「檢索是否取回證據」（recall@k）和「答案對不對」（token F1）拆開量；生成時的事件圖則直接當成事件摘要的標準答案 [arXiv:2402.17753]。
- **結果。** 人類總體 F1 87.9，截斷上下文的最佳模型 gpt-4-turbo 只有 32.1；以 observation 為檢索單位的 RAG 在 top-5 時得 41.4，是全文最高 [arXiv:2402.17753]。
- **留下的問題。** QA 用正規化後的 token F1，正是 How NOT 批評的字面重疊一族（本章歸納）[arXiv:1603.08023][arXiv:2402.17753]。精讀時發現人類基準 87.9 完全沒有描述作答協定；受測模型只是閱讀兩個模擬人格之間的第三方對話，不是互動式評估；事件圖也只會單調累積，沒有「事實被更新」的題目 [arXiv:2402.17753]。

**2024 年 3 月：Chatbot Arena 把評判交還給真人偏好。** [arXiv:2403.04132]

- **要解的問題。** 靜態題庫封閉、會被訓練資料污染、很多任務根本沒有標準答案，而既有的人評又小規模或以 GPT-4 近似 [arXiv:2403.04132]。
- **做法。** 讓真實使用者對兩個匿名模型自由提問、盲選較好的一方，投票後才揭露身分；用反機率加權的 Bradley-Terry 估計、sandwich 穩健標準誤、同時信賴集合得到附不確定性的「近似排名」，用主動抽樣省票，並用逐票 p 值加 Fisher 合併檢定抓異常投票者 [arXiv:2403.04132]。規模是 243,329 場對話、90,051 位使用者、149 種語言 [arXiv:2403.04132]。
- **與前人的關係。** 同一個平台的早期投票，已經在 2023 年 6 月的 MT-Bench 論文裡被當成量 LLM 評審一致率的人類金標準（見下一小節）[arXiv:2306.05685][arXiv:2403.04132]。這篇同時繞開了參照比對指標（How NOT 批評的那一族）與 LLM 評審（MT-Bench-101 採用的那一種），代價是評估對象變成「單次回答的偏好」（本章歸納）[arXiv:1603.08023][arXiv:2402.14762][arXiv:2403.04132]。
- **結果。** 群眾與專家的同意率是 72.8%–83.1%，專家彼此是 79.4%–89.8% [arXiv:2403.04132]。
- **留下的問題。** 多輪訊號很薄：平均每筆 1.3 輪、一整段對話只有一張票；精讀時指出多輪樣本是依「難分勝負」被選出來的 [arXiv:2403.04132]。

**2024 年 10 月：LongMemEval 把記憶基準改成使用者與助理、長度可延伸。** [arXiv:2410.10813]

- **要解的問題。** 它批評包含 LoCoMo 在內的既有長期記憶基準：多半是人與人對話、歷史只有幾千 token 且長度固定、沒測助理自己說過的內容與使用者資訊的更新；它的 Table 1 把 LoCoMo 的知識更新（KU）一欄標為沒有涵蓋 [arXiv:2410.10813][arXiv:2402.17753]。
- **做法。** 人工撰寫 500 題與證據陳述，用 Llama 3 70B self-chat 把證據間接藏進任務導向 session，再插入大量無關 session，組成長度可調的歷史：S 約 115k token、M 為 500 個 session 約 1.5M token [arXiv:2410.10813]。評分分兩層：題型專屬提示詞的 gpt-4o-2024-08-06 judge，評 GPT-4o 與 Llama 3.1 8B 的回答時與專家平均一致率 0.98 與 0.97；再用人工標註的證據位置算 Recall@k 與 NDCG@k，把失敗拆成「沒找到」與「找到但讀錯」[arXiv:2410.10813]。
- **與前人的關係。** 相對 LoCoMo，它把 token F1 換成有後設評估的 judge，也就是 How NOT 要求的「先驗證評估器」那一步（本章歸納）[arXiv:1603.08023][arXiv:2402.17753][arXiv:2410.10813]。
- **結果。** GPT-4o 讀完整個 S 的正確率 0.606，只讀證據 session 的 oracle 是 0.870；有記憶功能的 ChatGPT（GPT-4o）在只有 3 到 6 個 session 的短歷史上只有 0.5773，同模型直接讀完整歷史是 0.9184 [arXiv:2410.10813]。
- **留下的問題。** 精讀時指出，它名為 interactive，實際上是離線重播：歷史中的助理回覆全是事先生成，受測系統自己的回覆從不影響後續使用者輪次 [arXiv:2410.10813]。

**六篇合起來看，有三條線（本章歸納）。**

- **評估器。** 從參照比對指標，走向「有後設評估的 LLM 評審」與「附統計保證的真人偏好」[arXiv:1603.08023][arXiv:2402.14762][arXiv:2410.10813][arXiv:2403.04132]。
- **互動的量法分成四種。** MINT 是閉環但使用者握有標準答案；MT-Bench-101 與 LongMemEval 是靜態重播；LoCoMo 是閱讀第三方對話；Arena 是真人互動但平均只有 1.3 輪 [arXiv:2309.10691][arXiv:2402.14762][arXiv:2410.10813][arXiv:2402.17753][arXiv:2403.04132]。
- **時間跨度。** 從 How NOT 的單一下一句、MINT 的最多 5 輪，拉長到 LoCoMo 平均 19.3 個 session、LongMemEval_M 的 500 個 session [arXiv:1603.08023][arXiv:2309.10691][arXiv:2402.17753][arXiv:2410.10813]。

### LLM/agent-as-judge 與評估可靠性（2023–2025）

八篇從 2023 年三月到 2025 年二月，主線是「評審本身也要被評估」[arXiv:2303.16634][arXiv:2305.14387][arXiv:2305.17926][arXiv:2306.05685][arXiv:2404.04475][arXiv:2410.10934][arXiv:2411.16594][arXiv:2502.06193]。2023 年三月先有人主張 LLM 可以取代參考式指標；兩到三個月內，三篇分別追問它有沒有系統性偏差、該用什麼口徑和人類比、在模擬器裡會不會改變下游結論 [arXiv:2303.16634][arXiv:2305.17926][arXiv:2306.05685][arXiv:2305.14387]。本章八篇裡，2024 年的兩篇走了兩條路：一條在事後用回歸移除已知偏差，一條把評審做成會自己找證據的 agent [arXiv:2404.04475][arXiv:2410.10934]。這是選文造成的印象，不是 2024 年只有這兩條路：同期至少還有「訓練專用的開源評審模型」與「替評審本身建基準」兩條線，本章都沒有收（見〈已知缺口與未讀〉）。別節點讀過的論文碰到過這兩條線：Shepherd 是訓練出來的評論模型，SE 研究把評估專用的微調模型當成一個對照組，R-Judge 與 AgentRewardBench 則是拿來評評審的基準，前者只看安全、後者看 web agent 軌跡 [arXiv:2308.04592][arXiv:2502.06193][arXiv:2401.10019][arXiv:2504.08942]。年底的綜述把領域分類，2025 年初的 SE 實證研究則顯示評審可不可信要看任務 [arXiv:2411.16594][arXiv:2502.06193]。

**2023 年三月：G-Eval 把評估從「算生成機率」改成「填表打分」。** [arXiv:2303.16634]

- **要解的問題。** BLEU、ROUGE 與人評相關低又要參考答案，而 GPTScore 這類以生成機率打分的無參考評估器，與人評的一致性仍不如 UniEval [arXiv:2303.16634]。這和 How NOT 對參照式指標的否定是同一條問題線，但 G-Eval 全文沒有引用 How NOT（本章核對全文）[arXiv:2303.16634][arXiv:1603.08023]。
- **做法。** 提示詞給任務說明與單一維度的評估準則，讓 LLM 自己把準則展開成評估步驟（auto-CoT），最後只填分數；分數以 Σ p(s_i)·s_i 對候選分數做機率加權，GPT-4 不提供 token 機率，改以 n=20、temperature=1 取樣估計 [arXiv:2303.16634]。
- **結果。** SummEval 平均 Spearman ρ 0.514，高於 UniEval 的 0.474 與 GPTScore 的 0.417 [arXiv:2303.16634]。
- **留下的問題。** 精讀時指出增益多半來自骨幹模型而不是框架：G-Eval-3.5 在 SummEval 只有 0.401、低於 UniEval；GPT-4 單獨拿掉 CoT 仍有 0.500，單獨拿掉機率加權仍有 0.502 [arXiv:2303.16634]。它也發現 G-Eval-4 一律給 GPT-3.5 摘要比人寫摘要高的分數，並警告拿它當 reward 會自我強化；但那份資料的人評者間一致性 Krippendorff's α 只有 0.07 [arXiv:2303.16634]。

**2023 年五月：AlpacaFarm 把評審當成模擬器，改用「系統排名」來驗證。** [arXiv:2305.14387]

- **要解的問題。** 人工成對標註昂貴，而只看逐例一致率不夠：模擬回饋的雜訊結構若與人類不同，方法層級的結論會反過來 [arXiv:2305.14387]。
- **做法。** 評估用的標註者是 13 個 API LLM 組成的池（5 個 GPT-4、4 個 ChatGPT、4 個 Davinci003），每次隨機挑一個、兩個輸出的順序也隨機；訓練用的標註者另加 25% 標籤翻轉；評估協定是 805 條指令對 Davinci003 的 win-rate [arXiv:2305.14387]。
- **結果。** 模擬管線與真人管線的方法排名 Spearman 0.98；評估標註者池與人類多數決的一致率 65%，held-out 人類 66%；每 1000 筆成本從 $300 降到 $12 [arXiv:2305.14387]。單一 GPT-4 標註者的 variance 只有 0.1（人類 0.35），拿它當回饋時完全看不到過度最佳化，會得出「可以最佳化更久」的錯誤結論，也就是評審的變異度本身會改變下游結論 [arXiv:2305.14387]。
- **留下的問題。** 人類與模擬標註者偏好較長回答的比例是 62% 與 64% [arXiv:2305.14387]。精讀時指出，同一套偏好同時被當成訓練訊號與評估尺規，所以長度偏好會同時進到訓練與評估兩端 [arXiv:2305.14387]。它的 805 題與「對參考模型的 win-rate」協定，後來成為 AlpacaEval 的資料集（見 [AlpacaEval README](https://github.com/tatsu-lab/alpaca_eval)）[arXiv:2305.14387]。

**2023 年五月：FairEval 把位置偏差量成 Conflict Rate，提出三層校準。** [arXiv:2305.17926]

- **要解的問題。** 用 GPT-4 比較兩個回答的 Vicuna 式流程已被大量採用，論文認為還沒人檢查過排列順序會不會左右勝負 [arXiv:2305.17926]。
- **做法。** 同一題以正反兩種順序各問一次，結論不一致的比例就是 Conflict Rate；校準分三層：先寫理由再打分並多次取樣（MEC）、把正反順序的分數平均（BPC）、以 2k 次判定的分歧熵挑題交人工（BPDE／HITLC）[arXiv:2305.17926]。
- **結果。** ChatGPT 當評審時，Vicuna-13B 對 ChatGPT 的衝突率 82.5%，Vicuna-13B 放在第二位置時「贏」了 80 題中的 66 題；GPT-4 對同一組配對的衝突率也有 46.3%，對品質差距大的 Alpaca-13B 只有 5.0% [arXiv:2305.17926]。以三位作者的多數決為標準答案，GPT-4 的準確率從 Vanilla 的 52.7% 升到 MEC+BPC 的 62.5%，人工平均 71.7% [arXiv:2305.17926]。
- **留下的問題。** 精讀時依 repo 公開的標籤統計，80 題中 ChatGPT 勝 41 題，全猜多數類就有 41 / 80 = 51.25%，GPT-4 Vanilla 幾乎沒超過這條線；有人工標籤的也只有一組配對、80 題，標註者都是作者本人 [arXiv:2305.17926]。

**2023 年六月：MT-Bench 與 Chatbot Arena 把「評審與人類比一致率」做成標準流程。** [arXiv:2306.05685]

- **要解的問題。** MMLU、HELM 分不出 RLHF 聊天模型與基座模型的差異；許多工作已直接拿 GPT-4 當裁判，論文認為還沒人系統驗證它和人類偏好多一致、會犯哪些系統性錯誤 [arXiv:2306.05685]。
- **做法。** MT-bench 是 80 題、每題兩輪，由 58 位專家投了約 3K 票；Chatbot Arena 是群眾匿名對戰，從 30K 票中抽單輪票分析 [arXiv:2306.05685]。一致率分兩種口徑：S1 含平手、把前後不一致算平手，隨機基準 33%；S2 只計非平手票，隨機基準 50% [arXiv:2306.05685]。裁判失誤被拆成位置、名稱、冗長、自我偏好、推理不足幾類，各配小型壓力測試與緩解法：交換位置取一致、reference-guided 評分、把多輪整段放進同一個提示 [arXiv:2306.05685]。
- **結果。** S2 下 GPT-4 對專家第一輪 85%，專家彼此 81%；交換位置的一致性 GPT-4 65.0%、GPT-3.5 46.2%、Claude-v1 23.8%；repetitive list 攻擊的失敗率 Claude-v1 與 GPT-3.5 都是 91.3%、GPT-4 8.7%；數學判分的失敗數從 default 14/20 降到 reference-guided 3/20 [arXiv:2306.05685]。
- **與 FairEval 的差別。** 兩篇都交換位置，但 MT-Bench 把前後不一致記為平手，FairEval 把兩種順序的分數平均 [arXiv:2306.05685][arXiv:2305.17926]。
- **留下的問題。** 精讀時指出「GPT-4 比人彼此更一致」只在 S2 成立，而 S2 剔除的正是交換位置後不一致的票：G4-Pair 對 Human 從 S1 的 1343 票降到 S2 的 859 票，(1343 − 859) / 1343 ≈ 36%；S1 第二輪是 GPT-4 對人 66%、人對人 67% [arXiv:2306.05685]。它的「多輪」也只是寫死的兩輪腳本，沒有工具呼叫與軌跡 [arXiv:2306.05685]。

**2024 年四月：LC AlpacaEval 用回歸在事後移除長度偏差。** [arXiv:2404.04475]

- **要解的問題。** AlpacaEval 成為公開排行榜後，光改 verbosity 提示詞，baseline 自己的 win rate 就能在 22.9%–64.3% 之間擺動；AlpacaEval 原本不控制長度，理由是當初發現人類也有類似的長度偏好 [arXiv:2404.04475]。AlpacaFarm 量到的 62% 與 64%，與這個理由一致 [arXiv:2305.14387]。
- **做法。** 把評審偏好擬合成 logistic GLM，特徵是模型項、標準化長度差經 tanh 的長度項、題目難度項；預測時把長度項歸零，得到「兩邊等長時」的反事實 win rate [arXiv:2404.04475]。每一項對兩個模型都反對稱，所以「baseline 對自己 50%」與「交換雙方對稱」自動成立 [arXiv:2404.04475]。
- **結果。** 以 Chatbot Arena 為驗證目標，Spearman 從 0.94 升到 0.98；verbosity 擾動下的 normalized std 從 25% 降到 10%；截斷攻擊下，原始 win rate 3.7，無正則化的 LC 被拉到 25.9，有正則化的 LC 為 12.2 [arXiv:2404.04475]。
- **留下的問題。** 相關係數提升的 bootstrap p 值是 0.07 與 0.06 [arXiv:2404.04475]。精讀時發現論文寫 L2 正則化，官方程式碼卻是 L1，再加上以 gamed baseline 資料當先驗 [arXiv:2404.04475]。

**2024 年十月：Agent-as-a-Judge 讓評審自己去找證據。** [arXiv:2410.10934]

- **要解的問題。** agent 評估只看最終結果，它點名 SWE-bench 只靠最終的 resolve rate、看不出系統內部發生什麼；逐步人審又貴又不一致；LLM-as-a-Judge 只看得到塞進提示詞的內容，面對整個工作區與長軌跡時抓不到關鍵證據 [arXiv:2410.10934]。
- **做法。** 評審對工作區建結構圖、依需求定位檔案、讀取 33 種格式的檔案，gray-box 時再從開發軌跡擷取錯誤訊息，最後才問 LLM 這條需求是否達成；同時釋出 DevAI，55 題 AI 開發任務、365 條帶相依的階層式需求 [arXiv:2410.10934]。標準答案是三位專家先各自評分、再辯論出的共識，16.5 + 19.5 + 22 + 28.5 = 86.5 小時 [arXiv:2410.10934]。
- **結果。** 與人類共識的一致率，Agent-as-a-Judge black-box 在 MetaGPT／GPT-Pilot／OpenHands 為 88.52／83.88／90.44%，LLM-as-a-Judge black-box 為 84.15／65.30／60.38%；成本 $30.58、118.43 分鐘 [arXiv:2410.10934]。模組消融顯示增益主要來自 graph、read、locate：只有 ask 時 65.03%，三者加齊後 90.44% [arXiv:2410.10934]。它也把人評本身的不可靠量了出來：兩兩不一致率約 10–30%，三人多數決相對共識仍有約 5% 誤差 [arXiv:2410.10934]。
- **留下的問題。** 精讀時指出評審不執行程式碼，只讀靜態檔案與軌跡；論文自己列出的八個模組（graph、locate、read、search、retrieve、ask、memory、planning）確實沒有一個負責執行程式（本章核對全文）[arXiv:2410.10934]。精讀時也指出，locate 帶來的大幅增益（82.24→90.44）建立在 DevAI 的需求都寫明檔案路徑上，搬到不指名產物位置的任務可能就消失 [arXiv:2410.10934]。精讀時還發現，模組是用最後回報結果的同一份人類共識逐一挑出來的，論文也沒有寫評審用哪個 LLM [arXiv:2410.10934]。

**2024 年十一月：綜述把評審設計拆成三個軸。** [arXiv:2411.16594]

- **做法。** 把評審形式化成「n 個候選進、分數／排序／選擇出」，再依評什麼（6 個屬性）、怎麼評（調校與 6 種提示策略）、怎麼評評審（4 類基準）整理文獻 [arXiv:2411.16594]。
- **留下的問題。** 它沒有實驗，也沒有彙整被引工作的一致率或偏差幅度 [arXiv:2411.16594]。精讀時指出，它 Table 4 的 20 個基準裡只有 R-Judge 以 agent 為對象，而且只看安全 [arXiv:2411.16594]。本章只收了這一篇綜述；另一篇同主題、被引次數更高的綜述在選文時落選，沒有讀，所以本章對「領域怎麼分類評審設計」的描述只代表這一篇的切法（見〈已知缺口與未讀〉）。精讀時找到一處可在文本內驗證的引用錯置：位置偏差的指標被掛在一篇 prompt injection 論文名下 [arXiv:2411.16594]。它在 §7.4 提議讓評審挑難樣本交人工；精讀時指出，由評審決定送審子集後，人評結果就無法再無偏地估計評審的整體一致率，而 FairEval 的 BPDE 正是這種設計 [arXiv:2411.16594][arXiv:2305.17926]。

**2025 年二月：SE 實證研究量出「評審可不可信要看任務」。** [arXiv:2502.06193]

- **要解的問題。** 既有後設評估基準以 NLP 為主，程式題少又簡單，論文認為還沒人知道評審在真實 SE 任務上和人類對得多準 [arXiv:2502.06193]。
- **做法。** 程式碼翻譯、生成、摘要各 50 題，每題 3 個開源 code LLM 的回應，共 450 筆，由兩位評審打分；再拿傳統指標、embedding 類、機率類、output-based（含 G-Eval、BatchEval）與評估專用微調模型，對人評算 ρ／R／τ，成對比較另外量位置對調後的 Agreement [arXiv:2502.06193]。
- **結果。** 翻譯上 BatchEval 的 R 81.32、GPT-4o Vanilla 79.11，兩位評審彼此 85.86；生成上 DeepSeek-V2.5 的 R 68.51 與 METEOR 的 65.55 打平；摘要上所有 LLM 評審都輸給 ROUGE-L 的 R 47.01，多個方法與人評負相關；成對比較的 GPT-4o Agreement 在三個任務只有 13.33／13.33／16.00 [arXiv:2502.06193]。它等於在 SE 任務上重測了 G-Eval：在 GPT-4o 上，G-Eval 相對 Vanilla 的最大 ΔR 只有生成任務的 +6.03 [arXiv:2502.06193][arXiv:2303.16634]。
- **留下的問題。** 精讀時指出，人評看得到參考答案、output-based 評審看不到，所以摘要上的落敗混了「有沒有參考答案」與「評審能力」兩個因素 [arXiv:2502.06193]。

**這條線整體留下的東西（本章歸納）。**

- **評審最可靠的地方，是最不需要它的地方。** MT-Bench 的 GPT-4 對人一致率隨模型對的勝率差距從約 70% 升到接近 100%；FairEval 的 GPT-4 衝突率在相近配對是 46.3%、在差距大的配對是 5.0% [arXiv:2306.05685][arXiv:2305.17926]。
- **「接近人類」各用各的口徑。** S2、多數決、兩人平均、辯論共識，彼此不可比 [arXiv:2306.05685][arXiv:2305.17926][arXiv:2502.06193][arXiv:2410.10934]。
- **緩解手段一次只修一種偏差。** 交換位置修位置偏差，LC 修長度，reference-guided 修推理錯誤；MT-Bench 把位置、冗長、自我偏好都量了，給出緩解的只有位置偏差與推理錯誤；八篇沒有一篇同時校正位置、長度與自我偏好 [arXiv:2306.05685][arXiv:2305.17926][arXiv:2404.04475]。
- **只有一篇處理 agent 的產物。** 八篇裡只有 Agent-as-a-Judge 處理含工具與環境狀態的 agent 產物 [arXiv:2410.10934]。別節點有反例：2404.06474 讓 VLM 評審讀 web 與手機 agent 的軌跡判成敗，AgentRewardBench 拿 12 個 LLM 評審對專家標註的 web agent 軌跡 [arXiv:2404.06474][arXiv:2504.08942]。

### 跨子領域的傳承

三個子領域在引用上彼此接得起來，在問題上更是互相追問（本章歸納）。

**基準裡嵌著評審，而評審正是第三個子領域在追問的對象。** 各基準用 LLM 做判定的位置與驗證強度差很多：

| 基準 | LLM 在哪裡判定 | 驗證證據 | 出處 |
| --- | --- | --- | --- |
| WebArena | fuzzy_match 的答案等價判斷（gpt-4-0613） | 抽查 40 題中 39 題一致；日期與時長各用 900 題變體測試 | [arXiv:2307.13854] |
| ToolLLM | ToolEval 判 pass 與 win，直接進主指標 | 每種方法 300 條指令，pass 87.1%、win 80.3%，沒有 kappa | [arXiv:2307.16789] |
| AgentBench | LTP 的主持、拆解關鍵點與命中比對（gpt-3.5-turbo） | 作者只說比人評寬鬆；精讀時指出附錄沒有一致率或人評樣本數 | [arXiv:2308.03688] |
| SWE-Bench Pro | 未解決軌跡的失敗分類（GPT-5），不進主指標 | 精讀時發現它借用 SWE-agent 論文在另一套分類上的 87% | [arXiv:2509.16941] |
| Terminal-Bench | 軌跡與指令層錯誤分析（GPT-5），不進主指標 | 軌跡判官對 120 條人工標註 90%；指令失敗判定 66 對 92.4% | [arXiv:2601.11868] |
| MINT | gpt-4-0613 模擬使用者寫回饋，不判成敗 | helpfulness 上 91.2% 不輸人寫（113 條軌跡的人評） | [arXiv:2309.10691] |
| MT-Bench-101 | GPT-4 依任務準則打 1–10 分，直接進主指標 | 100 段對話，對專家 87%、專家彼此 80% | [arXiv:2402.14762] |
| LongMemEval | gpt-4o-2024-08-06 judge 判 QA 對錯，直接進主指標 | 與專家平均一致率 0.98／0.97，每格 30 題 | [arXiv:2410.10813] |

這些驗證用的口徑、樣本量與方向，正是 MT-Bench、FairEval、SE 研究指出會左右結論的變數（本章歸納）[arXiv:2306.05685][arXiv:2305.17926][arXiv:2502.06193]。

**Arena 這條線跨了兩個子領域。** 2023 年 6 月的 MT-Bench 論文拿 Arena 的早期投票當量 LLM 評審的人類金標準；2024 年 3 月的平台論文補上統計排名與異常偵測；LC AlpacaEval 又以 Arena 當去偏差是否成功的驗證目標；MT-Bench-101 則從 MT-Bench 延伸到細分的多輪能力 [arXiv:2306.05685][arXiv:2403.04132][arXiv:2404.04475][arXiv:2402.14762]。精讀時指出，LC 的驗證目標 Arena 當時沒有做風格控制，拿「與 Arena 更相關」證明「去偏差成功」有循環論證的風險 [arXiv:2404.04475]。

**Agent-as-a-Judge 是兩端的接點。** 它以 SWE-bench 只看最終 resolve rate 為出發點，引用 MT-Bench 的 LLM-as-a-Judge 為命名來源，是第三個子領域裡唯一回頭處理可執行基準產物的一篇 [arXiv:2410.10934][arXiv:2310.06770][arXiv:2306.05685]。

**How NOT 的教訓在後來反覆出現。** 「分得出模型」不等於指標有效；LoCoMo 仍以 token F1 評 QA，而 SE 研究的摘要任務上，ROUGE-L 反倒勝過所有 LLM 評審，說明參照式指標與 LLM 評審誰比較可靠，至今要看任務（本章歸納）[arXiv:1603.08023][arXiv:2402.17753][arXiv:2502.06193]。

**「一次給定、不能追問」是本章十篇可執行基準的共同預設。** SWE-bench、WebArena、OSWorld、Mind2Web、ToolLLM 都在開頭一次給定指令；Terminal-Bench 因為環境不支援提問，刪掉了 MAST 的「未要求澄清」失敗模式；SWE-Bench Pro 明說預設設定不量釐清歧義的能力 [arXiv:2310.06770][arXiv:2307.13854][arXiv:2404.07972][arXiv:2306.06070][arXiv:2307.16789][arXiv:2601.11868][arXiv:2509.16941]。這個預設不是可執行基準的通例，而是本章選文的結果：別節點讀過的 τ-bench、τ²-bench 與 ToolSandbox 都是可執行基準，agent 在執行途中可以向模擬使用者追問；ToolSandbox 還專門設計了資訊不足的情境，τ-bench 以對話結束時的資料庫終態當標準答案 [arXiv:2406.12045][arXiv:2506.07982][arXiv:2408.04682]。第二個子領域裡，能讓受測者在互動中補資訊的只有 MINT 的閉環與 MT-Bench-101 的 IC、PI 任務，而後者的使用者輪次是照稿重播（本章歸納）[arXiv:2309.10691][arXiv:2402.14762]。

## 評估方式與關鍵數字

### 各子領域用什麼量

- **agent 基準。** 成功率一族：Mind2Web 的 Element Accuracy、Operation F1、Step SR 與整題 SR；WebArena 的 SR、SR_AC、SR_UA；OSWorld 的 Success Rate（其實是平均 reward）；SWE-bench 的 % Resolved、% Apply 與 F2P×P2P 六種結果；SWE-Bench Pro 的 Pass@1；Terminal-Bench 附 95% 信賴區間的 resolution rate [arXiv:2306.06070][arXiv:2307.13854][arXiv:2404.07972][arXiv:2310.06770][arXiv:2509.16941][arXiv:2601.11868]。部分給分與加權總分一族：WebShop 的 Task Score、AgentBench 的 OA；LLM 評審一族：ToolLLM 的 pass rate 與 win rate；唯一答案一族：GAIA 的 quasi exact match [arXiv:2207.01206][arXiv:2308.03688][arXiv:2307.16789][arXiv:2311.12983]。
- **多輪與互動。** 參照比對指標（BLEU、METEOR、ROUGE、嵌入指標、LoCoMo 的 token F1）、以可驗證結果為準的 SR_k、LLM 評審分數（MT-Bench-101 的 1–10 分、LongMemEval 的 yes／no）、真人成對偏好（Arena 的 BT 係數與勝率）[arXiv:1603.08023][arXiv:2402.17753][arXiv:2309.10691][arXiv:2402.14762][arXiv:2410.10813][arXiv:2403.04132]。
- **評審的後設評估。** 一致率、準確率、Cohen's κ、Conflict Rate、Alignment Rate、Judge Shift、ρ／r／τ、win rate 與 LC win rate [arXiv:2306.05685][arXiv:2305.17926][arXiv:2410.10934][arXiv:2303.16634][arXiv:2502.06193][arXiv:2404.04475]。

下面的陷阱依主題橫向合併，同一主題下分篇列出。分數怎麼定義與聚合屬 T8，步驟級評分屬 T4，這裡只收它們在評估設計上造成的後果。

### 陷阱一：評估器本身會改變分數，而且只被稽核了一個方向

- **SWE-bench 的 harness 會自動修補 patch。** 套用失敗時，它會刪掉多餘的 context 行、重算 hunk header 再試一次 [arXiv:2310.06770]。精讀時發現，GPT-4 在 BM25 27k 下套用成功的 patch 中有 59/85 = 69.41% 是修補後才套上，ChatGPT-3.5 在 BM25 13k 下也有 60.1%，所以 % Apply 混進了評估器自己的貢獻 [arXiv:2310.06770]。
- **AgentBench 各環境處理格式錯誤的政策不一。** DB 只要格式不符就立即判失敗，Invalid Format 平均高達 53.3%；HH 在輸出不合法時會用 BLEU 把輸出改成最相近的合法動作 [arXiv:2308.03688]。精讀時指出，這使 HH 的 Invalid Format 恰好是 0.0、錯誤全被推到 Invalid Action（64.1%），IF／IA 比例因此不能跨環境比較 [arXiv:2308.03688]。
- **Mind2Web 由啟發式決定哪些元素可接受。** 精讀時發現，論文只抽查了 100 個啟發式改動過的案例，沒報錯誤率，也不處理同頁上位置不同、效果相同的兩個元素 [arXiv:2306.06070]。
- **WebShop 的稽核只看得到一個方向。** 論文把自動 reward 偏低歸因於精確比對 [arXiv:2207.01206]。精讀時發現，釋出程式碼從初版起就對屬性與選項用 fuzzy token_set_ratio > 85，可能造成過度給分，而人工重評協定只抓得到漏給分；自動與人工的差距在一般工作者組是 76.3 − 74.9 = 1.4 分、在 expert 組是 89.9 − 81.5 = 8.4 分，不是固定平移 [arXiv:2207.01206]。
- **SWE-Bench Pro 剔除「過寬」的測試，會降低 verifier 的靈敏度。** 精讀時指出剔除比例沒有報告 [arXiv:2509.16941]。
- **本章十篇裡，只有 Terminal-Bench 有系統地往偽陽性方向找漏洞（本章歸納）。** 它的作弊代理人找到 monkey-patch 測試環境、猜答案、列舉所有可能答案等捷徑，但 ABC 自評也承認沒有量化瑕疵對分數的影響 [arXiv:2601.11868]。別節點有做得更系統的：ABC 拿一份檢核表審了 10 個常用基準，再用什麼都不做或灌資料的 agent 實測，τ-bench 的 do-nothing agent 在 airline 拿到 38%，WebArena 的判定造成 1.4–5.2% 的高估；它也往反方向量到偽陰性，OSWorld 的 chrome 區塊 46 題中有 13 題因網站改版失效，UI-TARS 被低估 28% [arXiv:2507.02825]。AgentRewardBench 則把各基準的官方規則式判定也當成一個評審，和專家標註比 precision 與 recall [arXiv:2504.08942]。
- **GAIA 說答案無法輕易暴力猜中。** 精讀時以魔術方塊題為反例：被拿掉的是 edge 塊，答案只有 12 種，隨機猜中率 1÷12 ≈ 8.3% [arXiv:2311.12983]。
- **OSWorld 承認評估腳本有假陽性與假陰性，卻沒估比例。** 精讀時發現，人類 27.64% 的失敗沒有拆成人為失誤、評估腳本假陰性與指令歧義三類，這個失敗率本可當作「評估器誤判正確解」的上界 [arXiv:2404.07972]。

### 陷阱二：同樣叫「成功率」，量的不是同一個東西

- **部分給分與二元成敗混用。** OSWorld 的 Success Rate 是平均 reward，可以有部分分數；精讀時發現論文沒說哪些評估函式會給部分分數，Impress 有 47 題、二元成敗時最小非零值是 1/47 = 2.13%，Table 14 的 Mixtral 卻是 0.39% [arXiv:2404.07972]。WebArena 全部二元，fuzzy_match 判成 partially correct 也記 0 分 [arXiv:2307.13854]。ToolLLM 的 win rate 把平手對半分進 win 與 lose [arXiv:2307.16789]。
- **部分給分與二元 SR 會分岔。** WebShop 從 IL 到 IL+RL，Score 由 59.9 升到 62.4，SR 卻由 29.1% 降到 28.7% [arXiv:2207.01206]。全文 Table 9 中 IL 三個 seed 的 SR 標準差是 2.42，精讀時據此指出 0.4 個百分點的差距撐不起「RL 稍微傷害 SR」的說法 [arXiv:2207.01206]。
- **Mind2Web 的 SR 很嚴，卻不檢查答案。** 精讀時發現，論文沒說 Step SR 裡「操作正確」要值完全相同還是 F1 達某個門檻；資訊類任務到達結果頁就算完成，所以 SR 更接近導航準確率 [arXiv:2306.06070]。
- **AgentBench 的 OA 把性質不同的分數平均在一起，而且權重有槓桿。** WS 沿用 WebShop 的部分給分 reward，OS 與 HH 是二元 SR；精讀時指出，WB 用 Mind2Web 的快照逐步對照 reference 動作，選錯不會改變下一步的觀測，量的是單步選擇題準確度，卻和閉環環境一起算進 OA [arXiv:2308.03688]。精讀時也指出，LTP 每 1 分值 1÷3.5÷8 ≈ 0.036 OA，WS 每 1 分只值 1÷30.7÷8 ≈ 0.004 OA，相差 30.7÷3.5 ≈ 8.8 倍 [arXiv:2308.03688]。本章依全文 Table 3 重算：vicuna-13b 的 LTP 貢獻 8.0÷3.5÷8 ≈ 0.29，佔它 OA 的 0.29÷0.93 ≈ 31%；codellama-34b 的 LTP 貢獻只有 0.7÷3.5÷8 ≈ 0.025；兩者 OA 只差 0.96 對 0.93，換算成 LTP 分數，(0.96−0.93)×8×3.5 ≈ 0.84 分就足以讓名次對調 [arXiv:2308.03688]。作者據此說 vicuna-13b 與大三倍的 codellama-34b 相當，而這個結論所依賴的 OA，vicuna-13b 那一邊約三成來自作者自己承認判分偏寬、對開源模型尤甚的 LTP（本章歸納）[arXiv:2308.03688]。程式驗證證實這組數字：用 Weight⁻¹ 重算 OA，29 列全部對得上表上的值，所以權重的讀法沒錯；把 LTP 拿掉、只用其餘 7 項平均時，兩者不再相當，codellama-34b 反而拉開差距（數字見〈程式驗證〉）[arXiv:2308.03688]。拿掉 LTP 只是敏感度檢查，不代表 LTP 該被排除。
- **「正確放棄」會墊出地板，而且各類別的地板高低不一。** 放棄題占多少、怎麼聚合，屬於 T8 的分數定義；這裡只記它造成的評估後果。
  - OSWorld：精讀時發現，agent 第一步就回 FAIL 就能拿到 30/369 = 8.13%；Table 5 的 26 組模型×設定中只有 5 組高過這個值，純截圖設定最高 5.80%，全部低於它 [arXiv:2404.07972]。程式驗證證實這三個數字，也確認 Table 5 的整體分數大致是 369 題的等權平均（26 列中 22 列能由各類分數與題數重算回來），拿它和 30/369 比是同一個量；8.13% 是下限，理由同上（見〈程式驗證〉）[arXiv:2404.07972]。
  - 本章依 Table 10 的各應用 infeasible 題數重算類別地板：Professional 類（VS Code＋GIMP）是 (5+10)/(23+26) = 30.61%，Table 5 的 Professional 欄最高只有 GPT-4 a11y 的 26.53%，驗證程式逐列比對後也確認 26 列沒有一列高過這個地板；GIMP 單一應用是 10/26 = 38.46%，Table 14 的 GIMP 欄最高是 23.08%，26 組全都不如一律回 FAIL；Office 類的地板只有 (1+0+1)/(47+47+23) = 1.71% [arXiv:2404.07972]。地板差這麼多，類別之間的分數混進了「放棄剛好對」的成分，不能直接比較（本章歸納）[arXiv:2404.07972]。
  - WebArena：論文沒寫不可達題有幾題，精讀時由 Table 2 的百分比反推約 36 題 [arXiv:2307.13854]。程式驗證證實：在 1 到 200 題之間，要讓 Table 2 七列的 SR_UA 都寫成「整數 ÷ 不可達題數」、SR_AC 都寫成「整數 ÷ 可達題數」，容差放到 0.01 個百分點時只有 36 題相容；嚴格四捨五入下連 36 題都被 text-bison-001 的 4.00 擋住，因為 4.00% × 776 ≈ 31.04 不是整數，最接近的整數題數換算回去都不會四捨五入成 4.00（見〈程式驗證〉）[arXiv:2307.13854]。若以 36 題計，一律回 N/A 可拿 36/812 = 4.43%，已接近 text-bison-001 的 5.05%；GPT-4 給 UA hint 時的 11.70% 約對應 11.70% × 812 ≈ 95.0 題成功，其中不可達題約 77.78% × 36 ≈ 28.0 題，占 28/95 ≈ 29.5%（本章推算）[arXiv:2307.13854]。論文自己的錯誤分析也看到副作用：UA hint 讓 GPT-4 把 54.9% 的可達任務判為不可能 [arXiv:2307.13854]。
  - ToolLLM：可解的指令若「已大量嘗試所有 API 仍拿不到有用資訊」後放棄判 Pass，不可解的指令只要放棄一律 Pass；精讀時的判斷是這量的是「有沒有合理收尾」，不是「有沒有完成使用者要的事」[arXiv:2307.16789]。

### 陷阱三：只讀最終狀態的檢查器，管不到副作用與過程限制

- **WebArena。** 精讀時發現，r_prog 的例子多半只檢查最後的 URL 或特定內容，agent 順手改壞其他資料也照樣得分；must_include 只要求參考字串出現，列出一堆候選的冗長答案也能拿分 [arXiv:2307.13854]。
- **OSWorld。** 論文自承評估函式不看不必要的破壞性動作 [arXiv:2404.07972]。精讀時從附錄 D.3 找到兩個反例：指令要求用 GIMP 剪影片，agent 改用 ffmpeg；使用者明說不想失去其他開著的工作，agent 卻下了 killall soffice.bin，軌跡仍標成 Done [arXiv:2404.07972]。
- **SWE-bench 是反方向的例子：P2P 這一軸確實擋下了回歸。** 本章依 Table 23 重算 oracle 設定：Claude 2 有 26 個 patch 讓 F2P 全 pass 卻弄壞了 P2P，占 F2P 全 pass 者的 26/(110+26) = 19.1%；GPT-4 是 3/(10+3) = 23.1% [arXiv:2310.06770]。但精讀時也發現，P2P 只涵蓋 test_patch 涉及的測試檔，repo 其他地方的破壞一樣偵測不到 [arXiv:2310.06770]。
- **Terminal-Bench。** 測試只檢查最終容器狀態，過程中做了什麼不在判定範圍內 [arXiv:2601.11868]。

### 陷阱四：一致率沒有做機會校正，口徑也各不相同

- **ToolLLM。** 論文只報原始一致率，沒有 kappa，也沒有 Pass／Fail 的類別分佈；精讀時以受測方法的 pass rate 約 65% 粗估，兩邊亂標也有 65%×65% + (1 − 65%)×(1 − 65%) ≈ 55% 的一致率，推得 kappa 約 (87.1 − 55)/(100 − 55) ≈ 0.71 [arXiv:2307.16789]。win rate 的人評只涵蓋 ChatGPT+ReACT 對 ChatGPT+DFSDT 一組，卻撐起所有模型之間的對比（精讀時發現）[arXiv:2307.16789]。
- **Chatbot Arena。** 精讀時指出，用來驗證投票品質的兩組配對都是實力懸殊的（GPT-4-Turbo 勝率 76.3%–89.4%）[arXiv:2403.04132]。精讀時依 Table 3、Table 4 把勝率視為二元選擇粗估：群眾對專家 1（對 Llama-2-13b）的機會同意率是 0.812 × 0.894 + (1 − 0.812) × (1 − 0.894) ≈ 0.746，觀察值 72.8% 反而更低，κ 約 −0.07；其餘群眾對專家的 κ 約 0.18–0.42，專家彼此約 0.16–0.51 [arXiv:2403.04132]。程式驗證在這個假設下重現了這些數字，也做了兩項敏感度檢查（見〈程式驗證〉）[arXiv:2403.04132]：
  - 投票介面另有平手與「兩者皆差」的選項，所以票不一定是二元。把「不勝」的票裡有一部分是平手也算進機會同意率，κ 全部小幅上升；平手佔一半時，群眾對專家 1 那一格仍小於 0。「機會校正後遠低於 72.8%–83.1% 的字面印象」這個方向不受影響 [arXiv:2403.04132]。
  - 論文說兩組配對各隨機抽 160 場。Table 4 的 8 個勝率都能寫成「整數 ÷ 160」，Table 3 的 12 個同意率卻只有一半能，Llama 那組 6 格裡有 5 格不能。同意率很可能是在排除某些票後的子集上算的，和勝率不是同一個分母，所以個別 κ 值只是粗估，最低的那一格尤其不能當成精確值 [arXiv:2403.04132]。
- **How NOT。** 精讀時指出，人類分半相關約 0.95 是兩組各約 11–12 人的平均分互相比，單一評分者的 κ 中位數只有約 0.55，論文沒報單一評分者對其餘人平均的相關，指標與「一位人類評審」的差距因此容易被高估 [arXiv:1603.08023]。
- **MT-Bench 的 S1／S2。** 見「問題的演進」的 MT-Bench 段：G4-Pair 對 Human 的票數從 S1 到 S2 少了約 36%，GPT-4 要在 S2 這個子集上才顯得比人彼此更一致 [arXiv:2306.05685]。
- **FairEval。** 論文報 κ（GPT-4 從 0.24 升到 0.37），但沒有報多數類基線；精讀時依 repo 標籤算出全猜 ChatGPT 勝就有 51.25%，最佳全自動方法 62.5% 只多對約 9 題 [arXiv:2305.17926]。
- **Agent-as-a-Judge。** 作者承認需求判定是類別不平衡的任務，另外畫了 PR 曲線；精讀時指出內文沒有給 AUC 之類的數字 [arXiv:2410.10934]。精讀時以人評的 Requirements Met (I) 算出「全部判未達成」的基線：MetaGPT 為 100 − 22.13 = 77.87%，GPT-Pilot 55.20%，OpenHands 57.11%；LLM-as-a-Judge black-box 在 MetaGPT 的 84.15% 只比基線多 84.15 − 77.87 = 6.28 點 [arXiv:2410.10934]。它的 Judge Shift 還會讓正反誤判互相抵消：精讀時指出，Agent-as-a-Judge black-box 在 OpenHands 的偏移只有 0.27、一致率 90.44%，代表約 (1 − 0.9044) × 365 ≈ 34.9 條需求判錯；本章核對全文 Table 3，LLM-as-a-Judge gray-box 在 OpenHands 判出 43.16%、偏移同樣是 0.27，一致率卻只有 70.76%，約 (1 − 0.7076) × 365 ≈ 106.7 條判錯 [arXiv:2410.10934]。
- **MT-Bench-101 與 LongMemEval。** MT-Bench-101 的 agreement 沿用 MT-Bench 為成對比較設計的定義，精讀時指出在 1–10 分量表上「一致」指什麼沒有交代 [arXiv:2402.14762]。LongMemEval 的 judge 後設評估每格只有 30 題，精讀時指出它沒有涵蓋主實驗大量使用、最多 800 token 的 CoN 逐步推理輸出 [arXiv:2410.10813]。
- **基準裡的判官。** Terminal-Bench 的 Cohen's κ 0.93 是兩位人工標註者在 20 次試跑上彼此的一致性；GPT-5 判官對人工標註只報了 120 條軌跡上 90% 的原始一致率，沒有做機會校正 [arXiv:2601.11868]。SWE-Bench Pro 沒有自己量一致率，精讀時發現它借用 SWE-agent 論文在另一套分類上的 87% [arXiv:2509.16941]。

### 陷阱五：人類基準隨施測協定改變

- **同一批網頁任務，兩個人類天花板。** WebArena 自報的人類成功率 78.24% 由 5 位資工研究生做 170 題；OSWorld 以自己的協定（沒看過題目的資工系大學生）重測 100 題 WebArena，得到 88%，兩者差 88 − 78.24 = 9.76 個百分點 [arXiv:2307.13854][arXiv:2404.07972]。題目樣本、受試者與施測條件都不同，這個差距顯示「人類表現」至少一部分取決於施測協定（本章歸納）[arXiv:2307.13854][arXiv:2404.07972]。精讀時也發現，WebArena 的人類是從「170 個模板」各抽一題，但模板總數是 241；人類做 170 題、agent 做 812 題，78.24% 對 14.41% 不是同一題集上的比較 [arXiv:2307.13854]。
- **人類與 agent 的條件不對等。** OSWorld 的人類沒有步數限制，完成時間中位數 111.94 秒 [arXiv:2404.07972]。WebShop 的人類在 HTML 模式作答，模型只看 simple 模式的文字（精讀時指出）[arXiv:2207.01206]。Agent-as-a-Judge 的人類評審是 white-box，看得到受測框架原始碼 [arXiv:2410.10934]。精讀時指出，black-box 評審因此拿到的資訊比標準答案的產生者少 [arXiv:2410.10934]。
- **人類基準用評估器篩出來，或與題目定義互相循環。** WebShop 的 expert 是依同一套 reward 的資格測驗（平均 reward > 0.75）篩出來的，精讀時指出這等於用評估器挑出擅長該評估器的人 [arXiv:2207.01206]。GAIA 的 human score 只在有效題上計算；精讀時依 Table 3 重建 (55×2+13)÷(68×2) ≈ 90.4%，接近報告的 92%，並指出依 Table 3 腳註的定義，有效題至少有一位驗證者答對，所以這個分數在建構上就有 50% 的下限 [arXiv:2311.12983]。程式驗證證實並收緊了這一點：假設每位驗證者每題只答一次，human score 等於 1/2 + a ÷ (2v)，a 是兩人都答對的比例、v 是有效題比例，50% 的下限直接由式子成立；表上的 55% 與 68% 都是整數，推到進位範圍的最寬處也只有 1/2 + (55 + 0.5) ÷ (2 × (68 − 0.5)) ≈ 91.1%，而報告的 92% 最低也有 92 − 0.5 = 91.5%，兩者不重疊；要得到 92%，a 得是 (92% − 50%) × 2 × 68% ≈ 57.1%（見〈程式驗證〉）[arXiv:2311.12983]。腳註寫的是「all tentative」，若允許多次嘗試，這個重建就不適用，論文沒有說明。
- **參照點各篇不一樣。** MT-Bench 拿人對人的 81% 當比較對象；精讀時指出以附錄 D.3 自己定義的上限 human-majority 為參照，S2 第一輪是 90%，GPT-4 的 85% 差 90 − 85 = 5 個百分點 [arXiv:2306.05685]。FairEval 的人工平均 71.7% 是每位標註者對「包含自己那一票」的多數決算的，精讀時指出這本來就偏高 [arXiv:2305.17926]。SE 研究讓評審對兩位評審的平均分算相關，人類參照卻是兩位評審彼此的相關；精讀時指出，即使照論文算法，生成任務 DeepSeek-V2.5 的 R 68.51 也比人際 79.70 低 79.70 − 68.51 = 11.19 點 [arXiv:2502.06193]。AlpacaFarm 的 65% 對 66%，精讀時的讀法是它證明「評審可達到人類彼此的一致水準」，而人類彼此本來就只有 66% [arXiv:2305.14387]。
- **有些基準沒有人類基準，或沒寫協定。** Mind2Web 沒有人類基準，也沒有標註者之間的一致性（精讀時發現）[arXiv:2306.06070]。AgentBench 與 SWE-Bench Pro 的全文都沒有報人類解題基準（本章以全文搜尋確認）[arXiv:2308.03688][arXiv:2509.16941]。Terminal-Bench 只有作者自估的專家與初階工程師完成時間，精讀時指出它在 ABC 自評裡卻在「回報人類基線」一項給了 1 分 [arXiv:2601.11868]。LoCoMo 的人類基準 87.9 完全沒有描述作答協定（精讀時發現）[arXiv:2402.17753]。
- **人評方法本身的敏感度，本章沒有一篇處理。** 上面幾條談的都是「人類當受試者」的基準；人類當評審時，用 Likert 量表還是成對比較、逐輪評還是整段評，會不會改變結論，本章 24 篇沒有一篇拿來當題目（本章歸納）。別節點讀過的 2010.06595 從統計檢定力的角度碰到這一塊，它對 EMNLP 2019 人評的兩個統計用的是不同母體：41 篇論文的 117 筆 Likert 比較裡，69% 用 100 題以下；97 個有模型比較的人評實驗（51 + 38 + 8 = 97，依序是 Likert、直接比較與其他）裡，只有 24% 以某種形式報了顯著性檢定（附錄 H.1，本章核對全文）；模擬顯示最常見的 3 位評分者 × 100 題設計，在高變異參數下效果要達到 0.2（[0,1] 尺度）才有足夠的檢定力 [arXiv:2010.06595]。它處理的是樣本量，不是 Likert 與成對之間的比較；直接比較人評方法敏感度的論文沒有讀（見〈已知缺口與未讀〉）。

### 陷阱六：評審、資料生成器、模擬使用者與受測者同源

- **可執行基準。** ToolLLM 的 ChatGPT 一身四職：寫指令、當 teacher 標路徑、當評審，也是 win rate 的參照，而 ToolLLaMA 又是模仿 ChatGPT 的路徑訓練出來的（精讀時發現）[arXiv:2307.16789]。WebArena 的評審與最強受測者都是 gpt-4-0613（精讀時發現）[arXiv:2307.13854]。AgentBench 的 LTP 裡，gpt-3.5-turbo 是主持人、關鍵點拆解者、命中比對的裁判，同時也是受測模型 [arXiv:2308.03688]。SWE-Bench Pro 與 Terminal-Bench 都讓 GPT-5 評包含 GPT-5 系列在內的軌跡（精讀時指出）[arXiv:2509.16941][arXiv:2601.11868]。
- **多輪評估。** MT-Bench-101 的 GPT-4 同時是資料生成器、評審與受測模型，而且排第一；它用 Qwen-72B-Chat 重評前 5 名、排名一致，作為自偏誤不大的佐證 [arXiv:2402.14762]。精讀時指出 Qwen-72B 也在評同家族的 Qwen-14B，而且分數區間從 GPT-4 評審下的 8.86 − 7.38 = 1.48 壓縮到 8.75 − 8.32 = 0.43，鑑別度明顯變低 [arXiv:2402.14762]。LongMemEval 的 judge 與主要閱讀模型都是 GPT-4o，LoCoMo 以 gpt-3.5-turbo 生成對話又以其家族閱讀，Arena Bench 的評審與參考答案都出自 GPT-4-Turbo 而它也在被比較之列，三者都沒有檢驗同家族偏好（精讀時指出）[arXiv:2410.10813][arXiv:2402.17753][arXiv:2403.04132]。MINT 篩掉的是 gpt-3.5-turbo-0613 兩輪內解得開的題，gpt-3.5 的 SR_1 只有 2.7；精讀時指出這構成對 gpt-3.5 的對抗式選題偏差，而它又是回饋提供者實驗唯一的受測模型 [arXiv:2309.10691]。
- **評審的後設評估。** AlpacaFarm 的評估池裡有 GPT-4 與 ChatGPT 標註者，GPT-4 的模擬 win-rate 比真人高 9.2 個百分點（79.0 對 69.8）、ChatGPT 高 8.5（61.4 對 52.9），精讀時指出評估協定對同家族系統沒有任何校正 [arXiv:2305.14387]。MT-Bench §5 的 Vicuna-7B (selected) 只用 4.8M tokens 的 GPT-4 對話微調，MT-bench 分數就從 LLaMA-7B 的 2.74 升到 5.95，MMLU 卻只有 37.3（LLaMA-7B 35.2），精讀時把這讀成 GPT-4 裁判會獎勵模仿 GPT-4 風格的模型 [arXiv:2306.05685]。SE 研究裡 DeepSeek-Coder-V2-Lite 同時是受評模型與評審 [arXiv:2502.06193]。

### 陷阱七：預算、scaffold、提示格式與步數上限綁住分數

- **同一模型、不同預算。** SWE-Bench Pro 的 Claude Sonnet 4 在 Table 1 是 42.7%，在 50 輪加 $2 上限的 Table 5 只有 17.6%，相差 42.7 − 17.6 = 25.1 個百分點（本章核對全文）[arXiv:2509.16941]。精讀時指出「public 最高 43.6%、commercial 不到 20%」的對比很可能跨了兩種設定，同一設定下 Opus 4.1 是 22.7% 對 17.8%；也依公開資料查到 Scale 自營的排行榜多數條目是 250 輪、不設成本上限 [arXiv:2509.16941]。
- **同一模型、不同 scaffold。** Terminal-Bench 中同一個 Gemini 2.5 Pro 在四種 scaffold 之間從 15.7% 到 32.6% [arXiv:2601.11868]。GAIA 的 Level 1 上，人工選插件的 GPT4 + plugins 是 30.3%，自動選工具的 AutoGPT 是 14.4% [arXiv:2311.12983]。
- **步數上限。** OSWorld 的實驗上限是 15 步、30 分鐘，WebArena 最多 30 次狀態轉移 [arXiv:2404.07972][arXiv:2307.13854]。精讀時依公開資料查到，Anthropic 的 Claude 3.5 Sonnet 公告裡 OSWorld 純截圖成績是 14.9%，給更多步數時升到 22.0%；Claude Sonnet 4.5 公告則改在 OSWorld-Verified 上以 100 步上限、4 次執行取平均回報，都不能和論文的 Table 5 直接比較 [arXiv:2404.07972]。
- **提示格式。** OSWorld 先照 VisualWebArena 用 (觀測, 動作) 的 few-shot 格式，純截圖只有 2.79%，後來改成放最近 3 輪的 chat 格式 [arXiv:2404.07972]。WebArena 只差 UA hint 一句話，GPT-4 的 SR 就在 11.70% 與 14.41% 之間擺動；精讀時也指出它的基線 prompt 只給上一個動作，論文歸因給模型的失敗有一部分可能來自拿不到歷史 [arXiv:2307.13854]。AlpacaEval 上同一個 baseline 只改 verbosity 提示詞，win rate 就在 22.9%–64.3% 之間擺動，LC 後縮到 41.9%–51.6% [arXiv:2404.04475]。
- **別節點把預算與 scaffold 當成主題來量。** 本章十篇都把預算與 scaffold 當成實驗設定寫出來，沒有一篇以「成本對準確率」的前緣來排名（本章歸納）。T8 讀過的兩篇把它當成主題：AI Agents That Matter 主張 agent 評估要把美元成本與準確率一起畫成 Pareto 前緣，它在 HumanEval 上重跑，LATS(GPT-4) 是 88.0%、$134.50，簡單的 Warming(GPT-4) 是 93.2%、$2.45 [arXiv:2407.01502]。HAL 用同一套 harness 跑了 21,730 次 rollout，量到換 scaffold 會讓成本差一個數量級而準確率幾乎不變：Online Mind2Web 上 SeeAct＋GPT-5 Medium 花 $171、42.3%，Browser-Use＋Claude Sonnet 4 花 $1,577、40.0%，成本差 1,577 ÷ 171 ≈ 9.2 倍；36 個模型、agent、基準的組合裡，有 21 個在加大推理強度後持平或下降 [arXiv:2510.11977]。精讀時指出，這 21 個把平手也算了進去，摘要卻寫成推理強度「降低」準確率 [arXiv:2510.11977]。
- **格式遵循被算進能力分數。** MINT 的 CodeLLaMA-34B-Instruct 在程式碼任務 100% 輸出 [PYTHON] 標籤，精讀時指出這些輸出被嚴格的標籤解析器判成格式錯誤 [arXiv:2309.10691]。SWE-Bench Pro 的開源模型靠語法解析做 tool-use，精讀時依 Table 4 重算 Qwen3 32B 的失敗中有 267÷643 ≈ 41.5% 屬於 Tool-Use [arXiv:2509.16941]。GAIA 的正規化規則只存在於另外釋出的 scorer，論文也沒量格式失敗率，所以 AutoGPT 這類輸出冗長的系統分不出是答錯還是答案抽取失敗（精讀時指出）[arXiv:2311.12983]。

### 陷阱八：小分母、單次執行，區間沒報或報得太窄

- **可執行基準。**
  - OSWorld 主表用 temperature 1.0、每題跑一次；整體 1 題約等於 100/369 = 0.27 個百分點，OS 類只有 24 題，1 題就是 100/24 = 4.17 個百分點；精讀時指出「SoM 讓 GPT-4V 下降」的依據是 11.77% 對 12.17%，差 0.40 個百分點，大約 1.5 題 [arXiv:2404.07972]。
  - WebArena 主實驗也是溫度 1.0、每組跑一次；溫度 0 與 1.0 的比較（GPT-3.5 6.28% 對 6.16%）只是單點 [arXiv:2307.13854]。
  - SWE-bench 全是 greedy 解碼、單一樣本，GPT-4 因預算只跑 574 題的子集 [arXiv:2310.06770]。Mind2Web 的 GPT-4 每個測試集只跑 50 題，SR 2.0% 就是各剛好 1 題 [arXiv:2306.06070]。AgentBench 每個模型每個環境只用 greedy 跑一次，DCG 的 Test 只有 20 局，HH 只有 50 題（精讀時指出每 1 題就是 2 個百分點）[arXiv:2308.03688]。SWE-Bench Pro 每個模型只跑一次 Pass@1，沒有信賴區間 [arXiv:2509.16941]。GAIA 只對有 API 的模型跑 3 次，GPT4 在 Level 1 的標準差就有 ±2.5 [arXiv:2311.12983]。
  - Terminal-Bench 報了 95% 信賴區間，但沒寫算法 [arXiv:2601.11868]。本章依全文 Table 2 檢查：假設 ± 值是把每次試跑當成獨立樣本的 95% 二項區間（Wald 近似），57.8%±2.5 這一列就需要 1.96×1.96×0.578×(1−0.578)÷(0.025×0.025) ≈ 1499 次試跑（1.96 是 95% 雙尾的常態分位數，不是論文數字）；Table 2 共 55 列，程式驗證逐列算出所需試跑數，加總是 55,438 次，超過全文報告的 32,155 次；平均分配時每列只有 32,155÷55 ≈ 585 次 [arXiv:2601.11868]。所以這組 ± 值不可能全表都是逐次獨立的 Wald 95% 區間，而這種算法忽略任務群聚、本來就偏窄（本章重算）[arXiv:2601.11868]。精讀時指出相鄰排名（57.8% 對 56.9%、42.8% 對 42.5%）因此更分不出高下 [arXiv:2601.11868]。範圍要收窄成「不可能全表都是」，有兩個理由（見〈程式驗證〉）[arXiv:2601.11868]：
    - 論文說每個組合至少跑 5 次，Table 2 的說明文字說 token 數是跑全部 74 題。以此當下限，每列至少 5 × 74 = 370 次，55 列合計 55 × 5 × 74 = 20,350 次，還剩 32,155 − 55 × 5 × 74 = 11,805 次可以分給要更窄區間的列；程式驗證依所需次數由少到多分配這筆預算，最多 28 列能同時是獨立的 Wald 95% 區間，改用正文的 89 題計是 24 列 [arXiv:2601.11868]。
    - 另一個解讀同樣和報告相容：± 其實是 1 個標準誤，卻標成了 95% 區間。這時 57.8%±2.5 那一列只需要 0.578×(1−0.578)÷(0.025×0.025) ≈ 390 次，全表合計 14,431 次，套上每列 5 × 74 = 370 次的下限後是 20,422 次，都在 32,155 以內 [arXiv:2601.11868]。兩個解讀只靠表格分不開。
  - 別節點的 HAL 也是單次執行為主：精讀時指出，它的附錄一處說多數評估只跑一次，另一處說排行榜取每個組合最好的那一次、以 min–max 當誤差棒，兩者並存時，跑過多次的組合因為取最大值而佔便宜 [arXiv:2510.11977]。
- **多輪評估。** MINT 每個設定只跑一次，精讀時發現多給預算反而變差的情形：Vicuna-7B 從 15.4（k=4）掉到 12.6（k=5），CodeLLaMA-7B base 從 7.2 掉到 4.3；附錄 C 程式碼子集的 +0.74 正好是 100 / 136 ≈ 0.74，也就是一題 [arXiv:2309.10691]。MT-Bench-101 的評審 temperature 是 0.6，卻沒有重跑（精讀時指出）[arXiv:2402.14762]。LoCoMo 每個設定只跑一次推論，精讀時指出多模態任務的增益只有 57.8 − 56.1 = 1.7 個 MM-Relevance 點 [arXiv:2402.17753]。How NOT 每個領域只有 100 筆、共 9 × 2 × 2 = 36 個檢定，精讀時指出 Bonferroni 校正後門檻約 0.0014，Twitter 上三個嵌入指標的 p 值（0.024–0.067）校正後都不顯著 [arXiv:1603.08023]。Arena 對排名報了附多重比較校正的信賴區間，但它自己的 Table 2 每個主題群只有 30 則提示詞，精讀時估算勝率 60% 時的 95% 信賴區間半寬約 ±17.5 個百分點 [arXiv:2403.04132]。
- **評審的後設評估。** FairEval 在 n=80 時一題就是 1.25 個百分點，精讀時算出準確率約 0.6 時的 95% 信賴區間約 ±10.7 點 [arXiv:2305.17926]。MT-Bench 的冗長攻擊只有 23 個回答，數學判分只有 20 次判斷 [arXiv:2306.05685]。SE 研究每任務 150 筆來自 50 題，精讀時估計 R≈0.8 的 95% 信賴區間約 ±0.06，BatchEval 81.32、GPT-4o 79.11、G-Eval 77.14 的差距都在誤差內 [arXiv:2502.06193]。AlpacaFarm 的 Table 2 每格 win-rate 附約 ±1.7 個百分點，論文沒說明它是標準誤還是信賴區間 [arXiv:2305.14387]。它的平方 1.7 × 1.7 ≈ 2.9，接近 805 題、勝率約五成時的二項變異數 100 × 100 × 0.5 × 0.5 ÷ 805 ≈ 3.1（單位是百分點的平方），所以它較像標準誤，常用的信賴區間半寬約是它的兩倍（本章推算）[arXiv:2305.14387]。精讀時指出相鄰方法的差距小，評估集對相近方法的鑑別力有限 [arXiv:2305.14387]。本章核對全文 Table 2：模擬欄從 PPO 到 Binary Reward Conditioning（含兩個 SFT 基線）共 9 列、8 個相鄰差距，其中 4 個不到 2 個百分點：46.8 − 46.8 = 0、46.8 − 45.0 = 1.8、36.7 − 36.6 = 0.1、36.6 − 35.6 = 1.0 [arXiv:2305.14387]。

- **重跑與原報告對不上。** 這一類 T8 讀過的論文量得比較直接。AI Agents That Matter 重跑 HumanEval 上的幾個 agent：LDB 論文把 GPT-4 zero-shot 基線報成 75.0%，重跑是 89.6%；它也發現 WebArena 上 STeP 的紀錄裡，Reddit 速率限制影響了 129 題中的 30 題，而因速率限制停下的任務仍記成 reward 1.0 [arXiv:2407.01502]。
- **記憶基準。** LoCoMo 公開的 locomo10.json 只有 50 段中的 10 段，精讀時指出論文 Table 2–4 的數字無法在公開資料上重現；廠商官方頁面又各取子集、各用指標，例如 Mem0 研究頁用 1,540 題、排除 adversarial（https://mem0.ai/research），精讀時指出這些數字彼此不可比 [arXiv:2402.17753]。LoCoMo 全文 Table 5 給了全集 50 段的五類題數：single-hop 2,705、multi-hop 1,104、temporal 1,547、open-domain 285、adversarial 1,871，合計 7,512 題；排除 adversarial 後剩 7,512 − 1,871 = 5,641 題，其中 single-hop 佔 2,705 ÷ (7,512 − 1,871) ≈ 48.0%，open-domain 只佔 285 ÷ (7,512 − 1,871) ≈ 5.1% [arXiv:2402.17753]。Hindsight 全文沒寫各欄題數，Table 2 的 LoCoMo 題數只寫「Varies」（本章核對全文）[arXiv:2512.12818]。T2 精讀它時依它的 Table 4 反推，以 Single-Hop／Multi-Hop／Open Domain／Temporal 各 282／96／841／321 題加權，可以把除了 Zep 以外各列的整體分數重現到誤差 0.01 以內，四欄合計 282 + 96 + 841 + 321 = 1,540 題，也就是廠商常用的 1,540 題裡，標為 Open Domain 的那一欄約 841 題 [arXiv:2512.12818]。若這個反推成立，而且公開版的題目是全集的子集、類別又沒被改標，任何一欄都不能多於全集同類的題數；反推出的 841 大於全集的 285，所以那一欄的欄名和內容很可能對不上（本章歸納）[arXiv:2402.17753][arXiv:2512.12818]。但 locomo10 只有 10 段，全集的類別比例不能直接套用到它身上，這一點只縮小了範圍，不是結論。精讀時依官方 repo 查到，LongMemEval 在 2025/09 做過資料清理，論文數字屬於清理前的版本 [arXiv:2410.10813]。
- **Arena。** 論文 §7 用的 213,576 票重播資料沒有公開，已公開的 33K 與 100K 資料集都不是分析期間的同一批，精讀時指出 §6–§7 的數字無法原樣重算 [arXiv:2403.04132]。
- **評審版本。** MT-Bench 作者自己說 single grading 的絕對分數在換裁判時較不穩定；精讀時查到 NVIDIA 的 model card 報的是以 GPT-4-Turbo 當裁判的 MT-Bench 8.98（https://huggingface.co/nvidia/Llama-3.1-Nemotron-70B-Instruct-HF），和論文用的 gpt-4-0314 已經不是同一把尺 [arXiv:2306.05685]。精讀時指出，G-Eval 的 GPT-3.5 骨幹 text-davinci-003 已下架，GPT-4 快照版本也沒指明 [arXiv:2303.16634]。LC 分數依賴凍結的題目難度與 gamed 資料版本；精讀時發現官方 README 寫與 Arena 的相關是 0.93，論文寫 0.94 [arXiv:2404.04475]。

### 陷阱十：資料污染的處理多半停在設計主張

這一節的範圍是本章讀過的基準論文怎麼處理自己的污染風險。本章計入的論文沒有一篇以污染偵測或量測為主題，所以下面收的全是基準自己的防污染主張；專門量測污染的方法論文在本節點的候補或候選池外，沒有讀（見〈已知缺口與未讀〉）。

- **SWE-bench 的時間切分分析檢定力不足。** 作者依 Table 7 認為解題率與 issue 年份沒有一致的相關，所以模型不是靠記憶作答 [arXiv:2310.06770]。Table 21 顯示 GPT-4 所用子集中 2023 年的題目只有 61 題，GPT-4 在這一列是 0.00；本章以它 oracle 整體的 1.74% 計算，期望成功數是 61 × 1.74% ≈ 1.06 題，在「年份沒有影響」的前提下一題都沒解出的機率約為 0.34，所以這個 0.00 不足以說明任何方向 [arXiv:2310.06770]。精讀時也發現，「可持續更新」只是設計主張，論文沒實際示範過一輪更新 [arXiv:2310.06770]。
- **GAIA 的出題守則要求答案不以明文存在於網路上。** 但人工搜尋引擎基線在 Level 1 有 7.4%，精讀時指出約 146×0.074 ≈ 11 題可以直接從第一頁搜尋結果推得答案；GAIA 以「可以檢查推理軌跡」作為防污染的理由之一，實際評分卻只比對最終答案 [arXiv:2311.12983]。
- **SWE-Bench Pro 的防污染論點是 copyleft 授權構成法律障礙。** 精讀時指出 GPL repo 的完整 commit 歷史（包括 gold patch）本來就公開在 GitHub 上；它沒有做任何污染檢測，held-out 集的成績也還沒報告 [arXiv:2509.16941]。
- **Terminal-Bench 直接承認只有 canary 字串、資料全公開，而且 agent 可以上網。** 對於 agent 會不會上網找到 oracle 解，作者只說在數萬條軌跡中沒觀察到 [arXiv:2601.11868]。
- **其他。** AgentBench 的 HH 示範直接取自公開的 ReAct repo（精讀時指出）[arXiv:2308.03688]。OSWorld 有 84 題改編自公開基準，題目、答案與評估腳本也全部公開（精讀時發現）[arXiv:2404.07972]。Chatbot Arena 把「靜態題庫會被污染」列為改用即時真人提問的理由之一 [arXiv:2403.04132]。
- **別節點碰到的相鄰問題。** 這幾篇量到的都不是「受測模型的預訓練資料見過多少題」，而是評估流程本身的洩漏：
  - HAL 從軌跡分析發現，TAU-bench 官方 repo 裡 few-shot scaffold 的示範檔直接含有測試集範例，整組結果因此作廢；只看最終正確率的評估不會發現這件事 [arXiv:2510.11977]。
  - 2403.16416 稽核對話推薦的 LLM 模擬使用者評估，發現目標標題會經由對話歷史與模擬器回覆洩漏；排除受洩漏影響的成功對話後，ReDial 上 KBRD 的 Recall@50 掉了 21.6%，模型排名也跟著改變 [arXiv:2403.16416]。
  - HumanEval 以手寫題目避開 GitHub 上已有的解答；精讀時指出它的污染防護只靠「手寫」這個流程，沒有報告任何與訓練集的 n-gram 或近似重複比對 [arXiv:2107.03374]。
- **holdout 不足是相鄰的另一個問題。** AI Agents That Matter 審了 17 個 agent 基準，7 個沒有 holdout、也沒有建立的計畫；有 holdout 的 10 個裡，只有 5 個的層級和它宣稱的通用程度相符 [arXiv:2407.01502]。這量的是「會不會對基準過擬合」，和污染相鄰，但不是同一件事。

### 陷阱十一：參照式指標、聚合方式、平手規則與 oracle 會決定你量到什麼

- **參照式指標。** How NOT 發現 BLEU-3／BLEU-4 在逐句層級幾乎全是 0，大於 10^-9 的只有 4 筆，相關主要來自 smoothing 常數；BLEU 與 METEOR 會懲罰與參考答案長度差距大的回應（BLEU-1 在兩組為 0.1724 對 0.1009，p<0.01），人評則沒有這個傾向（2.66 對 2.57，p=0.73）[arXiv:1603.08023]。LoCoMo 以 observation 為檢索單位時，top-5 的證據召回比原始對話輪低（49.6 對 58.8），F1 卻高很多（41.4 對 31.7）；精讀時的解讀是 observation 本身由 gpt-3.5-turbo 寫成斷言句，措辭可能剛好對上 token F1，但論文沒有做對照實驗 [arXiv:2402.17753]。
- **聚合方式。** MT-Bench-101 自己的消融顯示，把每段取最低分改成取平均，與人評的 agreement 從 87% 掉到 75%；精讀時指出 SC 與 SA 每段只評 1 輪，最低分就等於單輪分數 [arXiv:2402.14762]。MINT 的總分是跨任務 micro-average，ALFWorld 佔 134 / 586 ≈ 22.9%；精讀時指出 Δ_feedback 的差異集中在決策任務（例如 CodeLLaMA-7B base 決策 +41.0、程式碼 +0.0）[arXiv:2309.10691]。LongMemEval 的「時間感知查詢擴充使 round 設定召回平均提升 11.3%」，精讀時依 Table 4 換算是 (7.1 − 0.8 + 7.6 + 31.3) / 4 ≈ 11.3，主要由單一格撐起 [arXiv:2410.10813]。Mind2Web 的步級指標對任務取 macro average，長短任務等權（精讀時發現）；步級與整題指標可以差一個數量級，Flan-T5XL 在 Cross-Task 上 Step SR 52.0、整題 SR 5.2 [arXiv:2306.06070]。
- **平手怎麼算。** G-Eval 的 −Probs 變體 Kendall τ 反而較高（0.446 對 0.418），作者解釋為大量平手灌高了 τ，精讀時指出論文沒說用的是 τ-a 還是 τ-b [arXiv:2303.16634]。SE 研究的成對標準答案把分數差小於 0.5 判為平手，G-Eval 的平手門檻 0.7 也一樣，都是調到約三分之一為平手，精讀時指出這等於看過標籤分布才定門檻 [arXiv:2502.06193]。FairEval 的 MEC+BPC 只有在兩個平均分數完全相等時才判平手，人工標籤卻有 14/80 是平手，精讀時指出這些題目很可能被強制判出勝負 [arXiv:2305.17926]。
- **oracle 不一定是上界。** LongMemEval 用「相對 oracle 下降 30% 到 60%」論證長脈絡閱讀的難度 [arXiv:2410.10813]。精讀時發現附錄 Table 8 裡 Phi-3.5-mini 在 S 上走記憶檢索（0.550）高於 oracle（0.488），Qwen2.5-7B 在 M 上走檢索（0.390）也高於 oracle 直接作答（0.282），原因可能是檢索欄預設套用 CoN 與 JSON 格式而 oracle 欄沒有 [arXiv:2410.10813]。

### 陷阱十二：難度分級與相關係數會被題目範圍左右

- **難度分級量到的不一定是難度。** GAIA 的 Level 以步數與工具數定義，人類在三級的正確率是 93.9／91.8／87.3%，耗時卻從 6.8 分鐘增加到 17.7 分鐘，精讀時據此指出分級量到的多半是繁瑣程度；所有系統在 Level 3 都是 0 分，「難度與模型表現相關」只靠 Level 1 對 Level 2 兩點成立 [arXiv:2311.12983]。Terminal-Bench 作者標為 Medium 的任務有 54.5% 對模型是經驗上的 Hard；精讀時指出 Figure 7 的百分比只對得上 28÷30 ≈ 93.3% 與 30÷55 ≈ 54.5%，也就是 30＋55＝85 題，附錄的 4 題 Easy 在難度分析中被無聲排除 [arXiv:2601.11868]。
- **能力跨度會墊高相關。** AlpacaFarm 的 0.98 橫跨 LLaMA 7B（模擬 11.3%、真人 6.5%）到 GPT-4（79.0%、69.8%），拿掉非本文訓練的灰點後只剩 0.94 [arXiv:2305.14387]。精讀時推論這個 0.94 只建立在 6 個點上：6 個點、一次相鄰互換時 1 − 6 × 2 / (6 × 35) ≈ 0.943，再多一次就掉到 1 − 6 × 4 / (6 × 35) ≈ 0.886 [arXiv:2305.14387]。本章核對全文 Table 2：兩欄都有值的只有 10 列，其中沒有星號的正好 6 列，而且只有 SFT 10k 與 SFT 52k 相鄰互換，與這個推論一致 [arXiv:2305.14387]。
- **全距受限會壓低相關。** 精讀時從 SE 研究的重現套件算出摘要任務的人評標準差只有 0.72，翻譯與生成是 1.08 與 1.14；論文只把摘要的失敗歸因於冗長偏誤 [arXiv:2502.06193]。MT-Bench 自己的散佈圖顯示實力相近的模型對一致率約 70%，GPT-4 的位置一致性在 GPT-3.5 對 Claude-v1 時 67.5%、對 LLaMA-13B 時 98.8% [arXiv:2306.05685]。
- **跨模型相關推不到模型內。** Terminal-Bench 報 episode 數與成功率的相關 r = −0.028，精讀時指出這只是約十幾個模型點的跨模型相關，在同一模型、同一任務上，長軌跡可能正好代表卡住或逾時 [arXiv:2601.11868]。LC AlpacaEval 用 38 個模型、MT-bench 用 34 個模型各自算與 Arena 的相關，精讀時指出兩者不是同一組模型上的配對比較 [arXiv:2404.04475]。

## 爭議、矛盾與反證

〈評估方式與關鍵數字〉的陷阱多半是單篇自己的缺口；這一節收的是論文之間互相拉扯、或論文內部前後不一的地方。

### 一、結果導向與參考軌跡互相指出的缺陷，兩邊都成立

- **批評 Mind2Web 的一方。** WebArena 把 Mind2Web 歸為只能走資料蒐集時存下狀態的靜態環境；OSWorld 把它歸為只比對下一步、會誤罰其他正確解的示範資料集 [arXiv:2307.13854][arXiv:2404.07972]。Mind2Web 自己也承認，多條可行路徑會造成偽陰性 [arXiv:2306.06070]。
- **結果導向有反方向的漏洞。** OSWorld 附錄裡改用 ffmpeg、下 killall 的軌跡都沒被判錯，WebArena 的 r_prog 也不罰副作用（精讀時發現，見陷阱三）[arXiv:2404.07972][arXiv:2307.13854]。
- **本章十篇沒有一篇兩頭都顧。** 本章讀過的十篇可執行基準，沒有一篇同時量「替代路徑可以接受」與「過程限制有被遵守」（本章歸納）[arXiv:2306.06070][arXiv:2307.13854][arXiv:2404.07972][arXiv:2310.06770][arXiv:2601.11868]。別節點有反例：ToolSandbox 把必須發生的關鍵事件寫成 milestone，彼此的時間相依構成 DAG，評分時在所有符合拓樸順序的對應中取最佳匹配，所以任何路徑都能評；另把絕不能發生的事件寫成 minefield，任一命中就整條軌跡歸零 [arXiv:2408.04682]。2602.16666 則讓 LLM 評審讀完整軌跡判政策違規 [arXiv:2602.16666]。這兩篇沒有解掉的部分：ToolSandbox 自述 milestone 與 minefield 都要人寫、難以擴大規模；精讀時也發現它 28 個資訊不足情境裡有 26 個沒有 milestone，什麼都不做的 agent 在這些情境拿到滿分 [arXiv:2408.04682]。2602.16666 的評審沒有經過人工驗證 [arXiv:2602.16666]。

### 二、同樣叫「多輪」，量的是五種不同的東西

- **金上下文重播。** MT-Bench-101 主張金上下文讓比較公平、避免錯誤滾雪球，並以取最低分抵銷虛高 [arXiv:2402.14762]。但它自己的對照顯示金上下文會讓後續輪虛高，改用模型自己的上下文時分數隨輪數下降；這個對照只用 ChatGLM3-6B 在 SI 與 IC 兩個任務上做，也只以曲線呈現、沒有數值 [arXiv:2402.14762]。
- **閉環互動。** MINT 走相反的路，讓受測模型自己的錯誤留在軌跡裡，由環境與模擬使用者回饋 [arXiv:2309.10691]。
- **事先生成的歷史。** LongMemEval 稱自己為 interactive，精讀時指出歷史中的助理回覆全由 Llama 3 70B 事先生成，受測系統只負責吸收 [arXiv:2410.10813]。LoCoMo 的受測模型只閱讀第三方的對話 [arXiv:2402.17753]。
- **真人互動。** Arena 是真人互動，但平均 1.3 輪、一段對話一張票，精讀時指出它沒有逐輪歸因 [arXiv:2403.04132]。
- **本章十篇可執行基準多半一次給定。** SWE-bench、WebArena、OSWorld、Mind2Web、ToolLLM 都在開頭一次給定指令，過程中沒有使用者可以追問；Terminal-Bench 因為環境不支援提問，刪掉了 MAST 的「未要求澄清」失敗模式，SWE-Bench Pro 也明說預設設定不量釐清歧義的能力（見「跨子領域的傳承」）[arXiv:2310.06770][arXiv:2307.13854][arXiv:2404.07972][arXiv:2306.06070][arXiv:2307.16789][arXiv:2601.11868][arXiv:2509.16941]。這是本章選文的結果；τ-bench、τ²-bench 與 ToolSandbox 都讓 agent 在執行途中向模擬使用者追問 [arXiv:2406.12045][arXiv:2506.07982][arXiv:2408.04682]。
- 這五種形狀的分數不能互換，本章這幾篇也沒有一篇拿兩種形狀在同一批題目上對照過（本章歸納）[arXiv:2309.10691][arXiv:2402.14762][arXiv:2402.17753][arXiv:2403.04132][arXiv:2410.10813]。別節點的 τ²-bench 做過一次：No-User 模式把和使用者的對話換成一張寫好問題與成功條件的 ticket，在同一批任務上和預設的對話模式比 [arXiv:2506.07982]。

### 三、LLM 能不能代替人當使用者與評審

- **正面的數字。** MINT 的 GPT-4 回饋在 helpfulness 上 91.2% 不輸人寫，接續解題的 SR 人寫 32.7% 對 GPT-4 33.6% [arXiv:2309.10691]。MT-Bench-101 的 GPT-4 對人評 agreement 87%，高於人評之間的 80% [arXiv:2402.14762]。LongMemEval 的 judge 與專家平均一致率 0.98／0.97 [arXiv:2410.10813]。
- **反證與保留。** 精讀時指出，MINT 的「92% 難以區分」是把「一樣像人」與「GPT-4 比較像人」加總（69.9% + 22.1% = 92.0%），後者其實是分得出來的；113 條軌跡上 32.7% 對 33.6% 約差 1 題；附錄範例中不看 ground truth 的 GPT-4 對錯誤的中間結果回了 This is GOOD，把模型推向錯答，而 Δ_feedback 只報淨值 [arXiv:2309.10691]。MINT 的回饋者實驗也顯示給回饋的能力並不穩定：固定 gpt-3.5 受測，gpt-3.5-turbo-16k 當回饋者是 −10.4，Llama-2-70b-chat 是 −14.0 [arXiv:2309.10691]。
- **真人那一邊的立場。** Arena 選擇真人投票，理由之一正是既有評估以 GPT-4 近似人類偏好；它量到群眾對 GPT-4 評審的同意率是 75.6% [arXiv:2403.04132]。
- **樣本都很小。** 這些「LLM 接近人」的結論分別建立在 MINT 113 條、MT-Bench-101 100 段、LongMemEval 每格 30 題上（本章歸納）[arXiv:2309.10691][arXiv:2402.14762][arXiv:2410.10813]。
- **「評審已達人類水準」的反證。** MT-Bench 在 S2 下是 85% 對人彼此 81%，但對 human-majority 上限 90% 仍差 5 點（精讀時的讀法）[arXiv:2306.05685]。FairEval 最好的全自動方法 62.5%，仍低於人工平均 71.7% [arXiv:2305.17926]。Agent-as-a-Judge 宣稱比單一人評更接近共識；精讀時指出 OpenHands 上 90.44% 對最佳個人 89.89% 只差約 2 條需求，black-box 評審在 MetaGPT（88.52 < 89.34）與 GPT-Pilot（83.88 < 84.88）上都低於人評的個人平均 [arXiv:2410.10934]。SE 研究裡翻譯接近人際一致，生成只和傳統指標打平，摘要全面輸給傳統指標 [arXiv:2502.06193]。「接近人類」同時取決於任務、模型對的差距與人類參照的口徑（本章歸納）[arXiv:2306.05685][arXiv:2305.17926][arXiv:2410.10934][arXiv:2502.06193]。

### 四、位置偏差的方向，在兩篇之間相反

- MT-Bench 的 Table 2 中，GPT-3.5 在 default 提示下偏好第一個位置 50.0%、偏好第二個 1.2% [arXiv:2306.05685]。FairEval 以 gpt-3.5-turbo-0301 當評審，Vicuna-13B 放第一位置時勝率 2.5%、放第二位置時 82.5%，方向是偏好第二個 [arXiv:2305.17926]。
- GPT-4 在兩篇都偏好第一個，但兩篇報的不是同一個量：MT-Bench 報判決比例，交換位置後偏向第一位 30.0%、偏向第二位 5.0%（其餘 65.0% 前後一致）[arXiv:2306.05685]；FairEval 報勝率，Vicuna-13B 放第一位時勝 ChatGPT 51.3%、放第二位時 23.8% [arXiv:2305.17926]。上一條 GPT-3.5 的兩組數字也是同樣的差別：MT-Bench 是判決比例，FairEval 是 Vicuna-13B 的勝率（本章歸納）[arXiv:2306.05685][arXiv:2305.17926]。
- 兩篇的模板不同：MT-Bench 直接輸出 [[A]]／[[B]]／[[C]] 判決，FairEval 先給兩個 1–10 分再比大小 [arXiv:2306.05685][arXiv:2305.17926]。FairEval 自己也發現，光是換成不打分、直接選優的模板，ChatGPT Vanilla 的準確率就從 44.4% 變成 50.2% [arXiv:2305.17926]。
- 所以偏差方向不是模型的固定屬性，要對每個模板重量；交換位置取平均不管方向都適用，但兩篇都假設偏差大致對稱（本章歸納）[arXiv:2306.05685][arXiv:2305.17926]。

### 五、成對比較還是逐一打分，建議相反

- MT-Bench 指出 single grading 分不出細微差異、絕對分數換裁判時不穩；pairwise 的缺點是配對數隨模型數平方成長 [arXiv:2306.05685]。
- SE 研究則建議現階段優先用逐一打分，因為成對比較準確率低，GPT-4o 對調位置後的 Agreement 只有 13.33 [arXiv:2502.06193]。
- 這個矛盾目前無法裁決。精讀時指出，SE 研究沒有套用 MT-Bench 與 FairEval 都用的「兩種順序各判一次再合併」，也沒有把逐一打分的分數用同樣的 0.5 門檻轉成成對標籤、在同一尺度上比較 [arXiv:2502.06193]。
- 兩篇談的都是 LLM 評審。人類當評審時，成對比較與 Likert 打分哪個較敏感，是同一個問題的人評版本；直接比較人評方法敏感度的論文本調研沒有讀，所以這一節也無法拿人評那邊的證據來參照（見〈已知缺口與未讀〉）。

### 六、長度偏好是偏差，還是人類偏好

- AlpacaFarm 把「模擬標註者也偏好長回答」當成保真的證據：人類 62%、模擬 64% [arXiv:2305.14387]。LC AlpacaEval 則把長度造成的偏好整個歸零 [arXiv:2404.04475]。精讀時指出，這等於假設沒有「內容品質同時讓輸出變長、又讓評審偏好」的混淆，較完整的回答自然較長，這部分合理的長度效應也會被扣掉 [arXiv:2404.04475]。
- MT-Bench 的 GPT-4 幾乎不吃 repetitive list 攻擊（失敗率 8.7%），但在 GPT-4 turbo 評審下，同一個 baseline 的 win rate 隨 verbosity 提示在 22.9%–64.3% 之間擺動 [arXiv:2306.05685][arXiv:2404.04475]。兩者不矛盾：MT-Bench 的攻擊只重複、不增加資訊，AlpacaEval 的 verbose 提示則讓內容本身變詳細；「GPT-4 不怕冗長攻擊」推不到「GPT-4 對長度不敏感」（本章歸納）[arXiv:2306.05685][arXiv:2404.04475]。
- SE 研究有一個反例個案：GPT-4o 把一段違反「精簡摘要功能」要求、逐步列出內部流程的摘要評為 5/5 [arXiv:2502.06193]。
- 精讀時還指出，LC 的驗證目標 Chatbot Arena 當時沒有做風格控制，拿「與 Arena 更相關」證明「去偏差成功」有循環論證的風險 [arXiv:2404.04475]。

### 七、自我偏好：有、沒有、還是測不出來

- G-Eval 把「GPT-4 給 GPT-3.5 摘要較高分」當作 LLM 偏好 LLM 文本的初步證據；精讀時指出這是跨模型比較、不是嚴格的自我偏好，也沒有對照組 [arXiv:2303.16634]。
- MT-Bench 說自我偏好無法定論；觀察上 GPT-4 自評的勝率比人類給的高約 10%，Claude-v1 高約 25% [arXiv:2306.05685]。AlpacaFarm 的 GPT-4 與 ChatGPT 在模擬評估下分別比真人高 9.2 與 8.5 個百分點（見陷阱六）[arXiv:2305.14387]。
- LC AlpacaEval 的初步實驗結論較明確：自偏存在，但通常小於模型之間的差距，3 個評審給 5 個模型的排名相同 [arXiv:2404.04475]。這和上面 MT-Bench 與 AlpacaFarm 觀察到的偏高方向一致，差在它明確判定幅度不大（本章歸納）[arXiv:2404.04475][arXiv:2306.05685][arXiv:2305.14387]。精讀時指出，mistral-large 評審把所有模型都往 50 壓，它給自己 45.5 分分不清是自偏還是整體寬鬆 [arXiv:2404.04475]。
- SE 研究裡 DeepSeek-Coder-V2-Lite 同時是受評模型與評審；Agent-as-a-Judge 連評審用哪個 LLM 都沒交代 [arXiv:2502.06193][arXiv:2410.10934]。
- 就自我偏好這一項，八篇評審研究沒有一篇做了固定回答品質的受控實驗；上面各篇都是觀察式比較，綜述沒有實驗，Agent-as-a-Judge 沒交代評審用哪個 LLM，FairEval 沒測自我偏好（本章歸納）[arXiv:2303.16634][arXiv:2305.14387][arXiv:2305.17926][arXiv:2306.05685][arXiv:2404.04475][arXiv:2410.10934][arXiv:2411.16594][arXiv:2502.06193]。MT-Bench 說明了原因：沒辦法在不改變品質的前提下，把一個回答改寫成另一個模型的風格 [arXiv:2306.05685]。這是 MT-Bench 在 2023 年的說法。專門研究自我偏好與「偏好洩漏」的後續論文本調研沒有讀，其中至少有一篇依標題研究的是評審能不能認出自己的生成；所以本章無法判斷 MT-Bench 這個理由今天是否仍成立，只能說本章八篇沒有這種實驗（見〈已知缺口與未讀〉）。

### 八、換模型與換 scaffold，哪個重要

- Terminal-Bench 主張模型的影響大於 scaffold，證據是兩組對比：Codex CLI 從 GPT-5-Nano 換成 GPT-5.2 提升 62.9−11.5 = 51.4 個百分點，Gemini 2.5 Pro 從 OpenHands 換成 Terminus 2 提升 32.6−15.7 = 16.9 個百分點 [arXiv:2601.11868]。
- 精讀時指出這個比較不對等：一邊是同家族最大與最小模型的差距，另一邊只挑一組 scaffold；廠商自家 CLI 也不一定最好，Claude Opus 4.5 在 Claude Code 是 52.1%，低於 Terminus 2 的 57.8%；廠商 CLI 只配自家模型，不是完整的因子設計，交互作用估不出來 [arXiv:2601.11868]。
- GAIA 在 Level 2，人工選插件的 GPT4 + plugins 是 9.7%，自動選工具的 AutoGPT 只有 0.4%；作者自己也推測 AutoGPT 的低分來自它呼叫 GPT4 API 的方式 [arXiv:2311.12983]。精讀時指出，AgentBench 的 claude-2 在 WB 得 0.0，舊版 claude v1.3 卻有 25.0，較像解析或 prompt 相容問題 [arXiv:2308.03688]。SWE-Bench Pro 只用 SWE-Agent 一種 scaffold，捨棄 Agentless 時沒有報數字（精讀時指出）[arXiv:2509.16941]。
- 所以這些基準的結論都附帶一個條件：量到的是「模型在這個 scaffold 與這份 prompt 下」的表現（本章歸納）[arXiv:2308.03688][arXiv:2311.12983][arXiv:2509.16941][arXiv:2601.11868]。

### 九、規格該給多完整，做法彼此相反

- SWE-Bench Pro 拿掉 requirements 與 interface 之後，GPT-5 (high) 剩 8.40÷25.9 ≈ 0.32，作者歸因於單元測試 verifier 的偽陰性 [arXiv:2509.16941]。精讀時發現，附錄 B 的範例點名了檔案路徑、函式名稱與要呼叫的方法，這和「不洩漏解法」的聲稱互相矛盾；作者也沒有人工檢查只給 problem statement 那組的失敗 patch 裡有多少其實是對的，所以「資訊變少」與「verifier 太窄」沒有被拆開 [arXiv:2509.16941]。
- Terminal-Bench 要求指令與測試雙向對齊，並用 LLM 除錯工具把「規格不足」的失敗挑出來 [arXiv:2601.11868]。GAIA 為了保證答案唯一，題目常塞滿細節，作者自己也承認這讓題目顯得不自然 [arXiv:2311.12983]。
- WebShop 走相反的路：指令只描述隱藏屬性的子集，reward 卻以隱藏屬性為準；精讀時指出這樣「agent 能力」與「指令歧義」會混在一起 [arXiv:2207.01206]。
- 這四篇都沒有量「agent 面對不完整規格時會不會問」（本章歸納）[arXiv:2207.01206][arXiv:2311.12983][arXiv:2509.16941][arXiv:2601.11868]。別節點的 ToolSandbox 專門設計了資訊不足的情境，τ-bench 與 τ²-bench 也讓 agent 可以向模擬使用者追問 [arXiv:2408.04682][arXiv:2406.12045][arXiv:2506.07982]。但精讀時依官方 repo 現行版本查到，ToolSandbox 的 28 個資訊不足基底情境裡有 26 個沒有任何 milestone；評分程式在沒有 milestone 時把 milestone 分數記為 1，所以這 26 個情境只看有沒有踩到 minefield，什麼都不做也拿滿分，分數不要求 agent 開口問 [arXiv:2408.04682]。repo 現行版本不一定等於論文當時的版本，精讀時拿這個機制解釋論文裡這一類的分數，也只說到兩者吻合 [arXiv:2408.04682]。

### 十、SIFT／RLHF 對多輪能力的影響：兩篇方向相近，證據都站不穩

- MINT 的結論是多數模型的 SIFT 與 RLHF 讓多輪表現變差，例如 LLaMA-2-70B 的 RLHF 版比 base 少 8.5 點 [arXiv:2309.10691]。MT-Bench-101 的結論是 RLHF／DPO 對多輪能力幾乎沒幫助：InternLM2-Chat-7B 6.69→6.85、20B 6.95→7.05，Mistral-7B 的 DPO 版 6.95→6.89 [arXiv:2402.14762]。
- MINT 方面，精讀時依 Tab. 3 各子任務以題數加權拆解：LLaMA-2-70B 的決策任務從 59.0 掉到 21.6，貢獻 (21.6 − 59.0) × 134 / 586 ≈ −8.55 點，推理反而是 RLHF 較好（18.7→20.2）；13B 更極端，決策 50.0→3.7、推理 3.5→19.6 [arXiv:2309.10691]。精讀時據此判斷 MINT 量到的比較像「chat 模型在這套程式碼化的 ALFWorld 動作格式上崩掉」，而且 70B RLHF 沒有列在格式失敗表裡，格式因素無從排除 [arXiv:2309.10691]。
- MT-Bench-101 方面，精讀時指出只有 3 組配對、差距 0.06–0.16，評審 temperature 0.6 卻沒有重跑，Mistral 的 DPO 版又是第三方的 Snorkel-Mistral-PairRM-DPO，不是受控消融 [arXiv:2402.14762]。
- 兩篇的模型家族（LLaMA-2／CodeLLaMA 對 InternLM2／Mistral）與協定（閉環工具互動對金上下文重播）都不同，不能拿來下「對齊訓練傷害或無助於多輪能力」的一般結論（本章歸納）[arXiv:2309.10691][arXiv:2402.14762]。

### 十一、記憶要存成什麼形狀、長上下文幫不幫忙

- **結論方向不同。** LoCoMo 發現以 observation（由對話抽出的斷言句）為檢索單位的 RAG 最好，top-5 得 41.4，高於原始對話輪的 31.7 [arXiv:2402.17753]。LongMemEval 則發現把 session 壓縮成摘要或使用者事實當 value，整體會因資訊流失而變差，只有跨 session 推理題受惠；但把抽出的事實前置到原 value 上當 key，Recall@k 平均 +9.4%、QA +5.4% [arXiv:2410.10813]。
- **兩篇至少同時差了三件事（本章歸納）。** 抽取器不同：精讀時指出 LoCoMo 的 observation 是資料生成管線的副產品，由生成 agent 在對話當下寫成、附證據 turn ID，是受測系統部署時拿不到的特權資訊；LongMemEval 的事實一律由 Llama 3.1 8B 抽、只看使用者端話語，「事實壓縮有害」可能部分反映抽取器品質 [arXiv:2402.17753][arXiv:2410.10813]。指標不同：token F1 對 LLM 評審 [arXiv:2402.17753][arXiv:2410.10813]。歷史形狀不同：人與人的閒聊對使用者與助理的任務導向 session [arXiv:2402.17753][arXiv:2410.10813]。
- **兩篇都同意的只有一件事：session 摘要會流失資訊。** LoCoMo 以摘要 top-10 檢索時召回 90.7、F1 只有 31.5，LongMemEval 的摘要 value 也變差 [arXiv:2402.17753][arXiv:2410.10813]。
- **長上下文。** LoCoMo 的 gpt-3.5-turbo-16k 從 4K 到 16K 總體 F1 由 24.1 升到 37.8，adversarial 卻由 13.1 掉到 2.1 [arXiv:2402.17753]。精讀時指出這個比較同時換了模型版本與窗口大小（同樣給 4K，gpt-3.5-turbo-16k 得 24.1、gpt-3.5-turbo 得 22.4），long-context 也只測了一個模型 [arXiv:2402.17753]。LongMemEval 顯示長脈絡 LLM 讀完整個 S 比 oracle 低 30% 到 60%，例如 Llama 3.1 70B 從 0.744 掉到 0.334 [arXiv:2410.10813]。兩篇都說「塞進全部歷史不夠」，但前者的反證只來自單一模型，後者的比較基準 oracle 又混入閱讀格式（見陷阱十一；本章歸納）[arXiv:2402.17753][arXiv:2410.10813]。

### 十二、推理放在分數前面還是後面，兩種設計都缺證據

- FairEval 主張先寫理由再打分，理由是自迴歸模型先吐結論時，後面的解釋撐不住結論；精讀時指出 GPT-4 的 EC 只比 Vanilla 多 3.8 點（約 3 題），而且作者自己引用的 Turpin et al. 正說明解釋可能不忠實 [arXiv:2305.17926]。
- G-Eval 附錄的完整提示詞把評估步驟直接嵌在提示中，最後要求只輸出分數；步驟由哪個模型生成、是否逐樣本重生，論文沒有說明 [arXiv:2303.16634]。SE 研究照原作法重做 G-Eval 時要求先輸出分數，並自承這削弱了 CoT 的作用 [arXiv:2502.06193]。
- 兩條路的增益都很小：G-Eval-4 拿掉 CoT 後 ρ 0.500 對 0.514；SE 研究在 GPT-4o 上加推論策略的最大 ΔR 是 +2.21、+6.03、+3.04 [arXiv:2303.16634][arXiv:2502.06193]。換骨幹模型的差距則大得多，例如 G-Eval-3.5 與 G-Eval-4 在 SummEval 是 0.401 對 0.514 [arXiv:2303.16634]。「G-Eval 的增益主要來自骨幹」是精讀時的推論，論文沒有同時拿掉 CoT 與機率加權的變體可以直接驗證 [arXiv:2303.16634]。

### 十三、大型評審彼此一致，不等於正確

- SE 研究的摘要任務上，使用大模型的 output-based 方法彼此的 ρ 最高到 79.43，卻都與人評脫節 [arXiv:2502.06193]。
- Agent-as-a-Judge 的 memory 模組會讓前面的誤判一路連鎖，前一條被判達成也會讓後面相依的需求傾向被判達成 [arXiv:2410.10934]。它在 GPT-Pilot 上兩種設定都判得比人評寬：black-box 判出 Requirements Met (I) 53.00%、gray-box 46.44%，人評 44.80%；解題率兩種設定都判 5.45%，人評 1.81% [arXiv:2410.10934]。論文沒有替這個偏寬找原因；精讀時把它歸因於評審不執行程式、只靠讀檔，分不出 GPT-Pilot 大量使用的假資料路徑 [arXiv:2410.10934]。它的標準答案本身也取決於辯論過程：精讀時指出三位人評第一輪的判定規則互相衝突，有人無視相依、有人實際執行程式、有人只用眼睛看 [arXiv:2410.10934]。
- 前者表示幾個大型評審投票抵銷不了它們共同的偏差，後者表示讓評審參考自己先前的判定會放大錯誤（本章歸納）[arXiv:2502.06193][arXiv:2410.10934]。

### 十四、頭條數字背後的設定

- **GAIA。** 摘要的 15% 來自作者逐題手選插件的設定，等於有人替 agent 做了工具選擇 [arXiv:2311.12983]。精讀時依 Table 4 的題數加權重算：可重現的 AutoGPT 只有 (146×14.4+245×0.4+75×0)÷466 ≈ 4.7%，手選插件那一列是 (146×30.3+245×9.7+75×0)÷466 ≈ 14.6% [arXiv:2311.12983]。「92% 對 15%」比的也不是同一組題目：人類只算有效題，模型在全部 466 題上計分（見陷阱五）[arXiv:2311.12983]。
- **SWE-Bench Pro。** Conclusion 用「約 23%」對比 Verified 的 >70%；精讀時指出 23% 取自有 $2 上限的 Table 5，而且本文沒有在同一個 scaffold 下跑 Verified，是跨 harness、跨預算的比較 [arXiv:2509.16941]。
- **Terminal-Bench。** 精讀時指出，任務在入選前會先用前沿模型實跑，論文沒說解出率是否影響入選；若有影響，「低於 65%」的標題數字有一部分是篩選造成的 [arXiv:2601.11868]。精讀時另查到廠商自報的分數與論文不一致：Google 官方部落格報 Gemini 3 Pro 在 Terminal-Bench 2.0 為 54.2%（https://blog.google/products/gemini/gemini-3/），本文 Terminus 2 加 Gemini 3 Pro 是 56.9% [arXiv:2601.11868]。

### 十五、建立在一兩題差距上的結論

- **OSWorld 的跨作業系統轉移。** 43 題上 Ubuntu 4.88%、Windows 2.55%，相關係數 0.7，作者據此主張結論可以轉移 [arXiv:2404.07972]。精讀時指出，這大約只對應 43 × 4.88% ≈ 2.1 題與 43 × 2.55% ≈ 1.1 題成功，而且移植時逐題做過調整，兩邊並不是同一批題目 [arXiv:2404.07972]。
- **OSWorld 的視窗擾動實驗。** 這 28 題是挑 agent 表現較好的（成功率 50.79%），即使不擾動，重跑也會因均值回歸而下降，論文沒報這個對照（精讀時發現）[arXiv:2404.07972]。
- **Mind2Web 的「難點不在領域」。** 作者由 Cross-Website 38.9 與 Cross-Domain 39.6 相近，推論難點在網站設計而不在領域知識 [arXiv:2306.06070]。精讀時指出 Cross-Domain 只保留 Information 與 Service 兩個領域，領域轉移與這兩個領域本身的難易分不開；兩個測試集是 912 題對 177 題，差距也沒有信賴區間 [arXiv:2306.06070]。
- **ToolLLM 的檢索器與 OOD 結論。** 精讀時發現「檢索器勝過 oracle」平均只差 67.3 − 66.7 = 0.6 個百分點，六組裡有三組反而下降；引言說 OOD 上與 Gorilla「相當」，但同樣用 oracle 時，AST 三個領域都輸 Gorilla-RS（88.80 對 89.27、85.88 對 93.01、88.62 對 94.16）[arXiv:2307.16789]。
- **FairEval 的順序設計。** 「一半交換順序（MEC k=3 + BPC）勝過全同順序（MEC k=6）」在 GPT-4 上是 62.5% 對 60.9%，只差約 1.3 題（精讀時指出）[arXiv:2305.17926]。精讀時也算出 BPDE 實際多修的有限：GPT-4 從 0.625 × 80 = 50 題升到 0.738 × 80 ≈ 59 題，16 題中修正 9 題，隨機挑的期望是 16 × 30 / 80 = 6 題 [arXiv:2305.17926]。

### 十六、主張寫得比證據強

- **Chatbot Arena。** 精讀時發現異常偵測的 p 值對二元票是單側的，新票為 0 時 p 恆為 1、不累積證據，而配對順序由模型編號決定，一個永遠投給編號較小那一方的惡意使用者永遠不會被抓到 [arXiv:2403.04132]。精讀時也指出，主動抽樣只在「以重播資料擬合的 BT 係數再模擬抽票」下評估，等於假設 BT 設定正確 [arXiv:2403.04132]。精讀時還查到一個例子：Meta 官方部落格報的 LMArena ELO 1417 屬於實驗性聊天版本而非正式釋出版本（https://ai.meta.com/blog/llama-4-multimodal-intelligence/），顯示開放平台上的分數可能由供應商未正式釋出的版本拿到，這是論文的統計保證覆蓋不到的風險 [arXiv:2403.04132]。這一點在本章只有這一個部落格例子撐著；專門分析 Arena 上供應商行為的論文本調研沒有讀，所以這種情形有多普遍，本章無法判斷（見〈已知缺口與未讀〉）。

先講結論：T7 的採納幾乎全是「被當作對外評估指標」，也就是廠商在發表文、model card 或研究頁上拿這些基準報分數；沒有一篇的評估方法被證實嵌進某個產品的內部評估流程，也沒有一篇的 agent 或模擬器本體被部署進產品（本章歸納）[arXiv:2310.06770][arXiv:2404.07972][arXiv:2306.05685][arXiv:2403.04132][arXiv:2402.17753][arXiv:2410.10813]。以下只收附 URL 的證據；除了「論文自述部署」那一類，其餘各條都是精讀者依官方頁面、model card 或 repo 查到的，不是論文本文的內容。查證範圍有限：精讀者的網路搜尋額度在這批筆記中途用盡，多數頁面是以已知網址直接打開確認的，所以「未見證據」是有限檢索下的結論，不是「確定沒有」[arXiv:2305.17926][arXiv:2307.13854][arXiv:2308.03688][arXiv:2410.10934]。引用數與學術影響力一律不算採納。

### 論文自述部署

## 與其他節點的關係

T7 的兩條入邊是 E5（T5 的修正紀錄回流評估）與 E6（T6 的互動紀錄回流評估）。兩條邊的標註都是精讀者自己標的，有鬆散標註；以下依各筆記的 how 逐篇判斷，把「真的讓紀錄流進評估」與「只是沾到邊」分開。分數怎麼定義與聚合是 T8 的範圍，步驟級評分是 T4 的範圍，這裡不展開。

### E5 修正紀錄（T5→T7）

**標註概況。** 23 篇筆記標了這條邊，沒有一篇是 T7 的 24 篇之一（本章核對）[arXiv:2206.05802][arXiv:2310.01798][arXiv:2510.11977]。也就是說，在本調研讀過的論文裡，這條資料流完全由修正方法的論文自己在評估自己的修正；本章計入的 24 篇基準與評審研究沒有一篇把修正紀錄當輸入（本章歸納）。

**真的讓修正紀錄流進評估的，依深度分四層。**

- **轉移記帳：最完整的一層。** 這幾篇把每題修正前後的對錯配對成轉移類別，單獨追蹤「對改錯」，而不是只報修正後的總準確率。
  - 2310.01798 把轉移分成不變、對→錯、錯→對、錯→錯四類，以呼叫次數記帳成本，再與 self-consistency 做等成本比較 [arXiv:2310.01798]。
  - 2311.08516 依原始答案對錯分組記錄 Δaccuracy✓ 與 Δaccuracy✗，並以隨機位置當對照，據此推算不同基線準確率下的淨效益（50%→68.6%、99%→92.8%）[arXiv:2311.08516]。
  - 2404.17140 以每次修正嘗試的紀錄算出驗證器的觸發頻率與觸發後的貢獻，並畫出驗證器加 refiner 的混淆矩陣 [arXiv:2404.17140]。2405.14092 統計 3 輪後對改錯與錯改對的比例，並逐輪列出 EM、F1、token 與耗時 [arXiv:2405.14092]。2407.18219 逐輪統計 correct→correct、incorrect→correct、correct→incorrect 的比例，用來判斷改進是真修正還是隨機換答案 [arXiv:2407.18219]。
  - 2409.12917 用 Δ^{i→c}、Δ^{c→i} 與兩輪回應的 edit distance ratio 偵測「幾乎不改」的行為崩塌；同一組轉移資料也被轉成訓練訊號 [arXiv:2409.12917]。
- **量觸發器或 critic 本身準不準。** Reflexion 把內部測試判定與隱藏測試結果交叉成 TP／FN／FP／TN（Table 2），量修正觸發器的可靠度 [arXiv:2303.11366]。Shepherd 把每則 critique 交給 GPT-4 與人工評審，並量出 GPT-4 獨立打分普遍偏高（Alpaca 4.69 對人工 2.91）[arXiv:2308.04592]。2206.05802 把 critique 當判別器，以 best-of-N 的品質差量 critic 對評估訊號的貢獻 [arXiv:2206.05802]。WebCanvas 把 reward 模組發出的完成判斷對照人類標註的 key node 打分 [arXiv:2406.12373]。
- **逐輪版本打分。** Constitutional AI 保留初始回應與 4 輪 revision，用三種 PM 逐輪打分，量出修正的邊際效益與代價；Appendix A 也發現 critique 常不準確 [arXiv:2212.08073]。Self-Refine 保留每輪版本與回饋，做逐輪分數曲線與 70 例成功／失敗歸因（回饋錯位 33%、錯的修法 61%、改寫失誤 6%）[arXiv:2303.17651]。RARR 的輸出本身就是原文、修正後文本與證據報告三件組，評估同時看歸因與改動幅度 [arXiv:2210.08726]。CoVe 只在狹義上成立：§4.3 拿驗證答案的正確率（約 70%）對比草稿中同一批實體（約 17%），但逐事實的一致性標籤沒被記錄 [arXiv:2309.11495]。
- **一次性的人工分析。** Self-Debug 依錯誤類型、題目難度與除錯輪數拆解增益 [arXiv:2304.05128]。CRITIC 人工標註修正前後的紀錄，發現錯誤樣本中 49% 其實是標籤模糊、錯誤或過時造成的 false negative，據此指出 EM／F1 有偏 [arXiv:2305.11738]。多代理辯論保留每輪每個 agent 的回答，用來選輪數與提示詞 [arXiv:2305.14325]。SWE-agent 把被 lint 拒絕的編輯與後續恢復紀錄當評估資料，失敗分類裡 Failed Edit Recovery 佔 23.4% [arXiv:2405.15793]。這一層都是作者離線、事後做一次，沒有回流成持續的管線 [arXiv:2304.05128][arXiv:2305.11738][arXiv:2305.14325][arXiv:2405.15793]。

**只提議，或標得鬆的。** 2308.03188 的 §7.2 主張評估自我修正要記錄任務複雜度、初始錯誤程度與修正後的提升，但沒有實作 [arXiv:2308.03188]。2406.01297 的查核清單規定評估端要算什麼（與初始回應比較、揭露是否用 oracle、直接評估回饋的錯誤偵測準確率、與同成本基準比較），卻沒有定義紀錄格式 [arXiv:2406.01297]。2211.00053 的修正紀錄流向的是「評分後再訓練」，不是評估報表 [arXiv:2211.00053]。2407.00215 的 critique 確實進了評估流程，但服務的是 RLHF 標註，不是 agent 的離線評估 [arXiv:2407.00215]。

**最接近「系統」的一篇。** HAL 用 Docent 事後從軌跡回收修正片段，例如 agent 修正失敗工具呼叫的段落，再與任務成功做條件機率比較（RR 1.47–2.97），讓修正行為成為評估的一個維度 [arXiv:2510.11977]。它是事後從 transcript 標出來的，不是執行期產生的修正紀錄 [arXiv:2510.11977]。

**缺的那一半（本章歸納）。**

- **沒有共用的紀錄格式。** 轉移記帳那一層各記各的欄位；2406.01297 規定了要算的量，這些論文裡卻沒有一篇規定紀錄要長什麼樣 [arXiv:2310.01798][arXiv:2311.08516][arXiv:2406.01297]。
- **被拒絕的編輯與中間的閘門判定沒被記下來。** RARR 的精讀者明確指出這一點，所以閘門本身的準確度無從量起 [arXiv:2210.08726]。
- **觸發器準確度多半沒量。** 標了這條邊的 23 篇裡，把觸發器或 critic 的判定拿去和外部答案對照的，只有 Reflexion、2404.17140、WebCanvas、Shepherd、2206.05802 與 CRITIC 這六篇（本章歸納）[arXiv:2303.11366][arXiv:2404.17140][arXiv:2406.12373][arXiv:2308.04592][arXiv:2206.05802][arXiv:2305.11738]。2206.05802 除了 §5 以 best-of-N 的品質差間接量 critic，附錄 D 也拿成對的誠實與刻意誤導答案當真值，量 critique 的 helpfulness 分數挑中誠實答案的準確率，結果只以圖呈現（本章核對全文）[arXiv:2206.05802]。CoVe 比的是驗證問題答對的比例與草稿的正確率，逐事實的一致性判定沒有被記錄或評估，所以這裡不列 [arXiv:2309.11495]。CRITIC 在附錄 D.1 量了 QA 工具驗證器偵測錯誤的 AUROC，拿驗證器的判定對照 F1>0.6 的正確性，AmbigNQ、TriviaQA、HotpotQA 各是 0.810、0.818、0.831 [arXiv:2305.11738]。精讀時指出，這個量了 AUROC 的驗證器從沒接成觸發閘門：QA 與數學在非 oracle 設定下一律進入修正，實作是答案或執行結果連兩輪不變才停 [arXiv:2305.11738]。降毒任務確實依偵測結果決定停不停，但用的是 Perspective API 的整體毒性分數（低於 10% 就停），和那個 QA 驗證器是兩個不同的訊號 [arXiv:2305.11738]。
  - 沒標這條邊的 2404.06474 也量了：它的評估器和 WebArena 手寫 oracle 的一致率在 74.4% 到 82.1% 之間，並被拿來當 Reflexion 的獎勵訊號 [arXiv:2404.06474]。精讀時指出，被評的 GPT-4 軌跡若成功率落在 14.4% 到 15.6% 之間，永遠答「失敗」就有 100% − 15.6% = 84.4% 到 100% − 14.4% = 85.6% 的準確率，高於這四個評估器；論文只報準確率，文字裡算不出偽陰性率 [arXiv:2404.06474]。
- **全部是離線的。** 標了這條邊的 23 篇沒有一篇把修正紀錄持續送進獨立的評估系統；有幾篇還讓同一份紀錄同時回流訓練，評估與訓練共用同一個來源 [arXiv:2409.12917][arXiv:2211.00053][arXiv:2212.08073]。
- **T7 這一端最接近的只是鄰居。** MINT 的 Δ_feedback 比較有無回饋兩組軌跡的成功率，但只報淨值，不拆錯→對與對→錯；精讀時也看到 GPT-4 回饋把模型推向錯答的例子 [arXiv:2309.10691]。MT-Bench-101 的 SC 任務裡「被指出的錯誤」是 GPT-4 預先寫進金上下文的，不是受測模型自己的錯 [arXiv:2402.14762]。SWE-bench 的 P2P 算得出「改壞了什麼」，但它評的是最終 patch，不是修正過程（本章歸納）[arXiv:2310.06770]。

### E6 互動紀錄（T6→T7）

**標註概況。** 56 篇筆記標了這條邊，其中 10 篇是 T7：G-Eval、AlpacaFarm、MT-Bench、AgentBench、MINT、MT-Bench-101、LoCoMo、Chatbot Arena、LongMemEval 與評審綜述 [arXiv:2303.16634][arXiv:2305.14387][arXiv:2306.05685][arXiv:2308.03688][arXiv:2309.10691][arXiv:2402.14762][arXiv:2402.17753][arXiv:2403.04132][arXiv:2410.10813][arXiv:2411.16594]。另有兩篇是 📖（精讀後判為低價值、不計入），下面只當背景：2309.13233 把模擬對話與真人互動紀錄用同一套 MultiWOZ 指標對照，2510.07777 逐輪量模擬器相對參考模擬器的偏離 [arXiv:2309.13233][arXiv:2510.07777]。

**依紀錄從哪裡來，分四類。**

- **真實使用者的紀錄。**
  - Chatbot Arena 整個平台就是把真實使用者與兩個模型的互動加投票回流成評估訊號：進入彙總前先用逐票 p 值與 Fisher 合併檢定篩掉異常使用者，再以反機率加權的 BT 估計排名；還把提示詞分群、挑出高難度題，轉成靜態的 Arena Bench 給 LLM 評審離線重跑 [arXiv:2403.04132]。MT-Bench 把約 30K 段 Arena 對話與票拿來做三件事：抽 3K 張單輪票當人類偏好金標準、產生排行榜、微調 Vicuna-13B 成分類 judge [arXiv:2306.05685]。
  - 部署紀錄直接變成評估資料的還有 BlenderBot 3（使用者的讚與倒讚，再抽樣請 crowdworker 重標得到一致率）與 2208.03270（部署時的逐輪回饋協定就是 Table 3 的評估指標）[arXiv:2208.03188][arXiv:2208.03270]。1911.02557 用 3 個月的真實互動紀錄算 friction rate，以 Z-test（p=0.01）決定改寫要不要上線，上線後再以 A/B defect rate 評估 [arXiv:1911.02557]。
  - AlpacaFarm 用 Alpaca Demo 的真實互動人工篩出 200 條指令，驗證公開評估集的代表性（r²=0.97）；但這批資料因使用條款不能公開 [arXiv:2305.14387]。
  - 真實紀錄當正解有雜訊：1805.04655 發現原題只有 20% 被兩位專家都選為最佳、88% 至少一位認為可以接受，因此改以專家標註為主要評估 [arXiv:1805.04655]。Constitutional AI 的 18,409 組真人比較也顯示，評估指示一改，結論的排序就跟著變 [arXiv:2212.08073]。
  - 有些部署紀錄主要流向訓練：1901.05415 從部署紀錄抽出訓練資料定期重訓，重訓後的品質卻是在靜態測試集上評的 [arXiv:1901.05415]。1605.07669 的 GP 成功估計器同時是評估結果與 RL 獎勵 [arXiv:1605.07669]。
- **模擬器閉環。**
  - 工具與 agent 評估：τ-bench 在模擬器輸出 ###STOP### 或達到 30 個動作上限後，拿最終資料庫狀態與 agent 的訊息算獎勵，再彙總成 pass^k；完整軌跡另外交給人工做失敗分類 [arXiv:2406.12045]。τ²-bench 以 assertion 檢查終態，並請兩位標註者逐回合稽核模擬器錯誤 [arXiv:2506.07982]。ToolSandbox 把使用者模擬器、agent 與環境的完整訊息加上每輪世界狀態快照留下來，事後交給 milestone／minefield 比對 [arXiv:2408.04682]。TheAgentCompany 模擬的是同事而不是下指令的使用者，Collaboration 類 checkpoint 檢查 agent 有沒有找對人、問對問題 [arXiv:2412.14161]。
  - 社交與對話：SOTOPIA 把整段互動送給 GPT-4 評審與 MTurk 標註者，逐角色打七個維度 [arXiv:2310.11667]。2505.06120 把每輪回應分成七類策略，並從 20 萬段互動紀錄分析首答時點與冗長度 [arXiv:2505.06120]。
  - 澄清與主動性：2410.13788 用同一套模擬互動同時算訓練用的偏好配對與評估指標，但訓練端與評估端用了不同的模擬器 [arXiv:2410.13788]。CollabLLM 的模擬互動算出的 MR 同時變成 DPO 配對與評估指標 [arXiv:2502.00640]。
  - T7 自己的兩篇：MINT 以互動軌跡為單位算 SR_k 與 Δ_feedback，並掃描全部軌跡統計格式失敗，也公開了所有受測模型的軌跡 [arXiv:2309.10691]。AgentBench 保存所有環境的完整互動紀錄並依結束原因分類，但只有 LTP 的對手是 LLM 模擬的對話角色，其餘環境的 user 是確定性的程式環境 [arXiv:2308.03688]。
  - 早期的任務導向對話模擬器（1612.05688、GenTUS、2204.00763、2306.00774）也都把模擬互動的成敗直接算成評估分數 [arXiv:1612.05688][arXiv:2208.10817][arXiv:2204.00763][arXiv:2306.00774]。
- **靜態重播或離線語料：沒有閉環。**
  - MT-Bench-101 吃的是事先寫好的金上下文逐字稿，使用者輪不會依模型回覆改變 [arXiv:2402.14762]。它的 Figure 6 正面回答了「送進評估的歷史該由誰產生」：用理想歷史會因模仿而虛高，用模型自己的歷史會累積錯誤 [arXiv:2402.14762]。
  - LoCoMo 由兩個模擬 agent 產生多 session 紀錄，經人工修正後當評估材料：QA 答案取自對話並標註證據 turn ID，生成時的事件圖成為事件摘要的標準答案，生成時寫下的 observation 則是提供給 RAG 基線的檢索庫 [arXiv:2402.17753]。LongMemEval 由 Llama 3 70B 扮演使用者的 self-chat 產生任務導向 session，與真實風格的紀錄組成帶時間戳記的歷史逐 session 餵給受測系統 [arXiv:2410.10813]。
  - G-Eval 只實作了消費端的格式：Topical-Chat 實驗把對話歷史、知識事實與候選回應填進表單式提示詞，逐維度打分；它沒有模擬器也沒有互動迴路 [arXiv:2303.16634]。
  - MultiWOZ 把完全成功的 1k 則人對人對話當固定 test set，2105.03748 以既有語料逐輪推估滿意度但沒有彙整成系統層級分數，2009.11352 只規劃了要蒐集什麼 [arXiv:1810.00278][arXiv:2105.03748][arXiv:2009.11352]。
- **稽核這條資料流本身。**
  - 2601.17087 把模擬與真人兩種互動紀錄送進同一套 τ-Bench 判分（受測 agent 固定為 GPT-4o），指出只用模擬紀錄會過度強調 agent 的執行錯誤、掩蓋真人帶來的失敗 [arXiv:2601.17087]。精讀時指出，GenTUS 以模擬器互動算出的排名與真人互動相反 [arXiv:2208.10817]。2310.11589 的 Appendix D 把模擬與真人的互動紀錄改算成同一套指標逐方法做相關，用來判斷模擬能否代替真人 [arXiv:2310.11589]。2403.16416 從紀錄中標出標題洩漏、排除後重算 Recall@k，稽核評估是否被灌水 [arXiv:2403.16416]。
  - 2507.02825 用 do-nothing agent 與 spamming agent 實際跑過 τ-bench 的資料流，量出它可以被鑽漏洞（airline 38%／40%）：拒絕類任務只看狀態沒變，完全不看對話裡有沒有查規則、給理由 [arXiv:2507.02825]。
  - 2602.16666 把完整互動軌跡交給 gpt-4o judge 判政策遵守與嚴重度，強調只看終態看不到未驗證身分、未經確認就修改這類中間違規 [arXiv:2602.16666]。HAL 用 Docent 分析 TAU-bench 的互動並做了人工 precision 驗證（0.94，n=36），但 TAU-bench 因 few-shot scaffold 洩漏被排除在主要分析之外 [arXiv:2510.11977]。
  - 評審綜述只整理了兩種做法（以 Arena 為參照檢驗 judge 排行榜、LLM-as-examiner 自己與被評模型多輪互動），沒有實作 [arXiv:2411.16594]。

**共同的缺口（本章歸納）。**

- **消費端多半只讀終態。** τ-bench 系列的判分只看最終資料庫狀態與子字串，2507.02825 與 2601.17087 都量到這會漏掉對話中的失誤 [arXiv:2406.12045][arXiv:2507.02825][arXiv:2601.17087]。讀完整軌跡的分成兩種（本章歸納）：
  - 判分時就讀整段互動的，有 2602.16666 的 gpt-4o judge、SOTOPIA 的 GPT-4 評審、TheAgentCompany 的 Collaboration checkpoint，以及 ToolSandbox 拿整段訊息與每輪世界狀態做的 milestone／minefield 比對 [arXiv:2602.16666][arXiv:2310.11667][arXiv:2412.14161][arXiv:2408.04682]。
  - 只在人工或事後分析時讀的，有 τ-bench 的人工失敗分類、τ²-bench 的逐回合模擬器稽核與 HAL 的 Docent 分析；這些讀法不回到分數裡 [arXiv:2406.12045][arXiv:2506.07982][arXiv:2510.11977]。
- **模擬器相對真人的效度很少被驗。** 本調研讀過的論文裡，拿多個受測系統以模擬使用者與真人各排一次的，有 NUS、GenTUS、MetaSim 與 iEvaLM [arXiv:1805.06966][arXiv:2208.10817][arXiv:2204.00763][arXiv:2305.13112]。結果並不一致：iEvaLM 的四個系統在模擬與人扮使用者下排名一致；GenTUS 則是精讀時指出，它的模擬器互動排名與 human trial 相反，論文沒有討論 [arXiv:2305.13112][arXiv:2208.10817]。
  - 另外幾篇比的不是多個系統的排名。2310.11589 比的是幾種偏好引出方法，模擬與真人的相對表現在內容推薦與 email 兩個領域大致一致、在道德推理不一致 [arXiv:2310.11589]。2601.17087 固定 GPT-4o 一個 agent，比的是模擬與真人帶出的成功率與失敗分佈 [arXiv:2601.17087]。📖 的 2309.13233 只當背景：它比了兩個系統 [arXiv:2309.13233]。
  - T7 裡的 MINT 也只驗了 113 條軌跡 [arXiv:2309.10691]。
- **同一個判斷來源同時當獎勵與評估。** 1612.05688 的模擬器產生行為與判定成敗用同一套規則，1605.07669 的估計器同時是評估與獎勵 [arXiv:1612.05688][arXiv:1605.07669]。2410.12361 以人工標註訓練的 reward model 當模擬使用者判斷接受與否，精讀時依 repo 查到同一個判斷也被拿來篩訓練資料 [arXiv:2410.12361]。STaR-GATE 的形狀不同，模擬使用者只負責回答問題、不做判斷：篩訓練資料用的是 Q_BASE 對 GPT-4 所寫 gold 回應的 log-prob，測試時也報同一個 log-prob，另以 GPT-4 評審算 win rate；精讀時指出 gold 與評審都出自 GPT-4，是同源偏誤 [arXiv:2403.19154]。刻意把兩端的模擬器分開的只有 2410.13788 [arXiv:2410.13788]。
- **真實紀錄當正解也有雜訊，而且多半不能公開。** 1805.04655 量到原題只有 20% 被兩位專家都選為最佳 [arXiv:1805.04655]；Arena 的分析用票與 AlpacaFarm 的 Demo 指令都沒有公開（見陷阱九）[arXiv:2403.04132][arXiv:2305.14387]。

## 未解問題

1. **判定器的雙向誤差怎麼量、用什麼單位回報。** 本章十篇可執行基準的檢查器多半只被往一個方向稽核：WebShop 的人工重評只抓得到漏給分，OSWorld 承認評估腳本有假陽性與假陰性卻沒估比例，往偽陽性方向系統性找漏洞的只有 Terminal-Bench，而它也沒有量化瑕疵對分數的影響（本章歸納）[arXiv:2207.01206][arXiv:2404.07972][arXiv:2601.11868]。別節點有兩個方向都量的例子：ABC 同時量到高估（WebArena 1.4–5.2%）與低估（OSWorld 的 UI-TARS 被低估 28%），AgentRewardBench 把官方規則式判定也當成一個評審，和專家標註比出 precision 83.8、recall 55.9 [arXiv:2507.02825][arXiv:2504.08942]。但兩篇都是一次性的稽核：精讀時指出 ABC 把 trivial agent 能拿到的分數與真實 agent 的偏差量都叫「高估」，AgentRewardBench 只涵蓋網頁基準 [arXiv:2507.02825][arXiv:2504.08942]。評審這一側的回報單位各不相同，一致率又多半沒有機會校正；Agent-as-a-Judge 的 Judge Shift 還會讓正反誤判互相抵消 [arXiv:2307.16789][arXiv:2403.04132][arXiv:2410.10934]。卡在兩件事：雙向稽核要人工重判「判成功」與「判失敗」兩批，單向稽核只重判其中一批，這筆成本差多少，讀過的論文沒有人量過（本章推論）；而且每題的判定單位（整題、每條需求、每張票）不同，沒有共同的誤差回報格式可以跨基準比較（本章歸納）[arXiv:2207.01206][arXiv:2410.10934][arXiv:2403.04132]。
2. **兩個實力相近的系統，現有評估分不開。** MT-Bench 自己的散佈圖顯示實力相近的模型對一致率約 70%，而最需要評審的正是比較兩個相近的前沿模型或同一 agent 的兩個版本 [arXiv:2306.05685]。精讀時估算的區間也都很寬：Arena 每個主題群約 ±17.5 個百分點、FairEval 約 ±10.7 點、SE 研究的 R 約 ±0.06，Terminal-Bench 相鄰名次也分不出高下 [arXiv:2403.04132][arXiv:2305.17926][arXiv:2502.06193][arXiv:2601.11868]。卡在交換位置、多次取樣這類去偏差手法處理的是偏差，不是變異；本章十篇可執行基準又多半只跑一次，連變異有多大都不知道（本章歸納）[arXiv:2306.05685][arXiv:2404.07972][arXiv:2509.16941]。別節點把成本與重複執行放進比較：AI Agents That Matter 主張把成本與準確率一起畫成前緣，HAL 用同一套 harness 跑了 21,730 次 rollout；但精讀時指出 HAL 的排行榜取每個組合最好的一次、以 min–max 當誤差棒，所以變異的問題並沒有因此解掉（見陷阱七、八）[arXiv:2407.01502][arXiv:2510.11977]。
3. **本章讀過的論文裡，還沒有一個判定器能在規模上既接受替代解、又檢查過程限制與副作用。** 參照軌跡會誤罰其他正確路徑，結果導向又放過 killall、改用 ffmpeg 這類違反指令的做法；SWE-bench 的 P2P 能抓回歸，但只涵蓋 test_patch 涉及的測試檔 [arXiv:2306.06070][arXiv:2404.07972][arXiv:2310.06770]。卡在判定器的規格語言：現有的 getter＋evaluator、單元測試或 r_prog 都只描述「最後要成立什麼」，沒有一種能同時寫出「任何路徑都可以」與「過程中不准做什麼」[arXiv:2404.07972][arXiv:2307.13854][arXiv:2601.11868]。τ-bench 一類的互動評估也有同樣的問題，只看終態的判分會被 do-nothing agent 鑽過去 [arXiv:2507.02825]。別節點有兩種部分做法：ToolSandbox 用 milestone 的 DAG 容許多條路徑、用 minefield 標出不准發生的事件，2602.16666 讓 LLM 評審讀完整軌跡判政策違規（見爭議一）[arXiv:2408.04682][arXiv:2602.16666]。還沒解掉的是規模與效度：milestone 與 minefield 要逐情境人寫，精讀時也發現它 28 個資訊不足情境裡有 26 個沒有 milestone；2602.16666 的評審沒有經過人工驗證 [arXiv:2408.04682][arXiv:2602.16666]。
4. **真實感與可重現互相拉扯，跨版本的分數沒有換算方法。** 用真實網站與即時資料的 OSWorld 題目會隨時間變，WebArena 的評估過程不重設資料庫，SWE-bench 也有看似會對外連線的測試 [arXiv:2404.07972][arXiv:2307.13854][arXiv:2310.06770]。精讀時查到的修正方式是發新版（WebArena v0.2.0、SWE-bench Verified、OSWorld-Verified），但每發一版，舊分數就和新分數不可比；評審版本也一樣，精讀時指出 text-davinci-003 已下架、MT-Bench 分數換了裁判就換了尺 [arXiv:2307.13854][arXiv:2310.06770][arXiv:2404.07972][arXiv:2303.16634][arXiv:2306.05685]。卡在本章讀過的論文沒有一篇提出跨版本的錨定或換算方法；精讀時也查到排行榜會換掉預算與輪數設定（SWE-Bench Pro 的論文 50 輪對排行榜 250 輪）[arXiv:2509.16941]。同一版本也不一定重跑得出原數字：AI Agents That Matter 重跑 HumanEval 的 GPT-4 zero-shot 基線得到 89.6%，原論文報 75.0%（見陷阱九）[arXiv:2407.01502]。
5. **閉環多輪評估與澄清能力的 gold：開放式任務沒有，有終態的任務只看終態。** 金上下文重播可重現、可比較，但 MT-Bench-101 自己的對照顯示它會讓後續輪虛高；閉環互動保留了錯誤的累積，但每個受測者看到的歷史都不同 [arXiv:2402.14762][arXiv:2309.10691]。本章十篇可執行基準幾乎不讓 agent 追問，Terminal-Bench 直接刪掉了「未要求澄清」這個失敗模式 [arXiv:2601.11868][arXiv:2509.16941]。閉環與固定 gold 並不互斥：本章的 MINT 只挑有標準答案可驗的任務，別節點的 τ-bench、τ²-bench 與 ToolSandbox 也讓 agent 在閉環裡追問，並以最終資料庫狀態或 milestone 當 gold [arXiv:2309.10691][arXiv:2406.12045][arXiv:2506.07982][arXiv:2408.04682]。所以沒解掉的是兩種情形：一是沒有明確終態的開放式任務，閉環之下沒有固定的標準答案可以比對，只能靠模擬使用者；二是有終態的任務只看終態，2507.02825 量到這會放過對話中途的失誤；精讀時依 ToolSandbox 的官方 repo 現行版本查到，28 個資訊不足基底情境裡有 26 個沒有 milestone，這 26 個的分數不要求 agent 開口問（見爭議九）[arXiv:2507.02825][arXiv:2408.04682]。兩種情形的閉環都靠模擬使用者撐著，而模擬使用者相對真人的效度很少被驗，MINT 只驗了 113 條軌跡，2601.17087 則量到模擬紀錄會扭曲失敗的分佈 [arXiv:2309.10691][arXiv:2601.17087]。
6. **本章讀過的基準處理資料污染，多半停在主張，沒有自己量過。** SWE-bench 的時間切分分析檢定力不足，GAIA 的人工搜尋基線在 Level 1 就有 7.4%，SWE-Bench Pro 以授權當防線但 GPL repo 的歷史本來就公開，Terminal-Bench 只有 canary 字串 [arXiv:2310.06770][arXiv:2311.12983][arXiv:2509.16941][arXiv:2601.11868]。卡在本章讀過的論文沒有一篇真的量過受測模型見過多少題；held-out 集要嘛還沒報成績，要嘛因法律理由不能釋出，外界無從檢驗（本章歸納）[arXiv:2509.16941][arXiv:2311.12983]。別節點碰到的是評估流程本身的洩漏，例如 HAL 發現 TAU-bench 的 few-shot 示範含有測試集範例、2403.16416 發現模擬使用者會洩漏目標標題（見陷阱十）[arXiv:2510.11977][arXiv:2403.16416]。專門量測污染的方法論文本調研沒讀，所以「文獻裡有沒有量測協定」本章無法回答，只能說讀過的基準論文沒有用上（見〈已知缺口與未讀〉）。
7. **模型、scaffold 與同源偏誤還沒被拆開。** Terminal-Bench 的「模型比 scaffold 重要」建立在不對等的兩組對比上，GAIA 與 SWE-Bench Pro 的頭條數字都綁著特定工具選擇或預算 [arXiv:2601.11868][arXiv:2311.12983][arXiv:2509.16941]。評審與受測者同源的情形又幾乎每篇都有，例如 GPT-5 判官評 GPT-5 系列、gpt-3.5-turbo 同時當 LTP 的主持人與受測者 [arXiv:2509.16941][arXiv:2601.11868][arXiv:2308.03688]。卡在廠商 CLI 只配自家模型，做不出完整的因子設計；自我偏好方面，MT-Bench 在 2023 年說做不了受控實驗，因為沒辦法在不改變品質的前提下把一個回答改寫成另一個模型的風格；本章讀過的論文也沒有人做過 [arXiv:2601.11868][arXiv:2306.05685]。專門研究自我偏好與偏好洩漏的後續論文本調研沒讀，所以這個理由今天是否仍成立，本章無法判斷（見爭議七與〈已知缺口與未讀〉）。
8. **把評審搬到 agent 軌跡上，以及去偏差該控制哪些特徵。** Agent-as-a-Judge 是八篇評審研究裡唯一評 agent 的，但它只在 55 題的 DevAI 上驗證；精讀時指出評審不執行程式，而它在 GPT-Pilot 上兩種設定都判得比人評寬（black-box 53.00%、gray-box 46.44%，人評 44.80%），不過這只是單一受測 agent 上的觀察；標準答案本身也取決於人評的辯論過程 [arXiv:2410.10934]。去偏差這一側，LC AlpacaEval 只控制長度，精讀時指出較完整的回答自然較長、合理的長度效應也會被扣掉，而它的驗證目標 Arena 當時又沒有做風格控制 [arXiv:2404.04475]。卡在兩處：一是人工標註的 agent 軌跡資料有，但規模與領域都窄。本章讀過的只有 Agent-as-a-Judge 的 55 題 DevAI 與 Terminal-Bench 的 120 條人工標註軌跡 [arXiv:2410.10934][arXiv:2601.11868]；別節點的 AgentRewardBench 有 1,302 條由專家標註的網頁 agent 軌跡（351 個任務），TRAIL 標了 148 條軌跡、Who&When 標了 184 條多 agent 失敗軌跡 [arXiv:2504.08942][arXiv:2505.08638][arXiv:2505.00212]。它們只涵蓋網頁、GAIA 與 SWE-bench 式任務、多 agent 對話這幾類，而 AgentRewardBench 量到沒有一個 LLM 評審的整體 precision 超過 70%（最高是 GPT-4o (A) 的 69.8）；官方規則式判定的 precision 是 83.8，但 recall 只有 55.9 [arXiv:2504.08942]。二是該控制哪些特徵，目前是由「哪些量得到」決定，而不是由「哪些是偏差、哪些是品質」決定（本章歸納）[arXiv:2410.10934][arXiv:2404.04475][arXiv:2411.16594]。

## 已知缺口與未讀
