### 主幹五條箭頭 M1–M5（T1→T2→T3→T4→T7→T8）：推論的介面契約

**這一段整體是推論，每一條契約的等級都是 C。** 圖上實線的主幹不在調研一開始定義的六條邊裡（`data/topics.json` 只有 E1–E6），沒有論文把這五條箭頭整條當成「邊」來研究，所以「該傳／不能傳」不是從文獻逐字彙整的，是從相鄰的決策卡與 E3–E6 的欄位推出來的。每一項都標出處卡；出處卡本身的等級照該卡的標題，不因為被引用而升級。

**M2、M3 另外逐欄標了證據標記**（地圖 #962 補強的結果；M1、M4、M5 沒有補證據，也沒有欄位標記）。標記只說「這個欄位本身有沒有人量過」，不改變契約的等級，也不替欄位背書。每個欄位都另寫了覆蓋範圍與查過什麼、沒找到什麼。四種標記：

- 【直接】：有論文量到「這個欄位在交接點上有或沒有，結果因此不同」，而且沒有毛病 F1–F4（定義見第 1 節〈五種毛病〉）。
- 【直接（帶毛病：F?）】：同上，但至少有一個 F1–F4；一定寫出是哪一個、影響哪個方向。
- 【單側】：只有交接點的一端有證據，也就是只有生產端、只有消費端，或量的是同一件事、但下游不是這條箭頭；每一列寫明覆蓋哪一端。
- 【推論】：沒有論文量過。只有某個系統這樣設計、沒有對照的，也算推論，另寫成「設計先例」供建造者參考，不當證據。

補強用的 16 篇論文不在八章與 README 的已讀清單內（其中 2005.07362 在第 8 章只列為未讀），列在附錄 D，沒有精讀筆記；收錄上限是：標了 RECENT-INELIGIBLE（2025 年以後、不是頂會、沒有採納證據、影響力引用數太低）或卡在水論文判準邊上的論文，最多支撐【單側】，不能單獨當【直接】或【直接（帶毛病）】的依據。

**五條契約都做過一輪對抗稽核**（地圖 #962 的稽核票）：三位稽核員各從不同角度攻擊，一位看得到證據、對全文重驗每個標記（虛標），另兩位只拿拿掉證據的契約，一位去語料裡找反例（反證），一位站在建造者角度找對不上與含糊（建造者）。原始記錄與每一筆發現的處置（採納、部分採納、不採納與理由）在 `data/blueprint/audit-spine.json`。稽核之後本節的改動：三列【單側】退成【推論】；幾處寫錯的事實與出處已更正，更正的地方在該句裡直接註明；和 E3–E6 對不上的欄位已補進 M3、M4、M5；M4 的驗收改成逐條進線分開判；含糊的詞在下面〈幾個詞的用法〉定義。沒有任何一條契約整條移到待決：唯一被反證的是 M2 缺口 1 的支撐句，不是欄位。

五條契約共用同一個理由，這個理由本身也是推論：**箭頭上的東西要寫成可單獨檢查的交接物，這樣上下游才量得開，不會把上游的錯和下游的錯混成一個成敗**。T1-10 對 M1 就是這樣說的（「目標推斷得對不對」要能單獨量），T7-10 對 M4 用「只拿紀錄、不重跑」來驗收，T3-05 要求一次只換觀測，其餘固定，都是同一個形狀。單獨量交接物，是為了定位錯在哪一段，不是為了挑元件；要換上游元件時仍以閉環的整體分數為準，並與單獨分數並列：DST 的元件分數較高、組成系統後成功率卻較低的反例有 22.4% 對 27.8%，作者說這可能部分來自狀態標註的雜訊，所以它只說明元件分數預測不了整體，不是說元件分數沒用 [arXiv:2005.07362]。以下把這個形狀逐條套到五條箭頭上。

每條契約有四欄：**該傳**（箭頭上要有的欄位）、**不能傳**、**收到之後的驗收**、**缺口與待決**。驗收欄借用的是各卡已有的量法，不是新發明的量測；金標替換這類做法只能當診斷上限，不能當系統分數報（T2-05）。

**幾個詞在整份契約裡的用法（推論，暫定；格式本身是 T4-08 的待決，這裡只固定意思）**：「輪」是從一則使用者或模擬器的發話算起，到 agent 下一次等著使用者為止，回合序號從 0 起算（Who&When 的提示詞從 0 起算，同一篇的演算法卻寫成 l1..ln，起算基準本來就沒人統一 [arXiv:2505.00212]）；「步」是一次模型呼叫，步驟索引在整集內連號，同一次呼叫產生的平行工具呼叫共用一個步驟索引、另以呼叫序號區分，多 agent 時另帶 agent 或 span id；集 id、回合序號、步驟索引、修正嘗試編號與來源的鍵名沿用第 5 節〈各邊沒有共同的連結鍵〉的五個欄位（`episode_id`、`turn_idx`、`step_idx`、`attempt_id`、`source`）。凡是錯誤率都要寫明正類是什麼、方向是哪一個，不用縮寫，沿用同一節 E3 的統一寫法：「把對的判錯的比率」與「把錯的放行的比率」。

##### M1　T1 → T2：把推斷出的目標交給狀態追蹤

- **該傳**：
  1. 顯式交接物：逐條列出使用者給的約束，外加一到兩句的明確目標；約束清單本身也交給下游保留核對，不只交一句壓縮過的自然語言（T1-10）。
  2. 閘門判定：放行、拒識、先問、輸出 null 之中的哪一種（T1-01、T1-02）；多個意圖時（T1-01 的閘門也決定該輸出幾個意圖）每個意圖各交一份交接物。T2 的處理（推論，暫定）：放行就寫入；先問與拒識不寫入，記成「這一輪沒有新的狀態可寫」；輸出 null 記成「T1 沒判出來」，並保留上一輪的狀態。閘門在同一份測試集上量過的兩類各自正確率是離線統計，不隨每一輪重傳，另存一份附測試集版本與量測日期的靜態紀錄，每一輪只用它的編號參照。
  3. 輸入的來源標記：真人，或哪一個模擬器與哪一份提示詞（E1 消費端；T1-08）。T2 的狀態分數要能只看真人子集、或換模擬器重評，就需要這個標記一路帶到 T2。
  4. 每一條約束出自第幾輪（T2-05 要求把分數按輪次序號拆開；輪的定義見上面〈幾個詞的用法〉）。
- **不能傳**：答案字串、目標標題、與評分標籤同源的描述文字（T1-08、E1 的「不能傳」）；只有壓縮過的單句目標而沒有約束清單（T1-10）；系統自己提議、使用者沒有明確拒絕的值，不經標記就當成使用者的約束寫進去（T2-12 是待決，這裡不替它下結論；推論：建議先標記為隱含接受，不混成明說）。
- **收到之後的驗收**：T1 這一端用 T1-10 的做法單獨量目標推斷對不對；T2 這一端照 T2-05 的做法，歷史一律由受測系統自己產生，不用參考回覆重播，再另跑一次把 T1 的輸出換成金標，兩次的落差是 T1 的錯誤傳到 T2 的上限，不是它的實際量：金標交接物本身比較完整、格式比較乾淨，這份增益也混在落差裡（MT-Eval 把換成金標歷史的進步歸給兩個原因，擋掉前面輪次的錯誤傳遞，以及金標回覆本身成了示範，作者沒有拆開量 [arXiv:2401.16745]）；要拆開，另加一組同格式但故意留錯的交接物。T2-05 卡上的同一句已一併改成上限的說法。
- **缺口與待決**：約束清單要不要直接等於 T2 的 schema 欄位，文獻沒有人量過；T2-03 只回答欄位要不要附描述。使用者中途改口時，交接物要用撤回或覆寫（T2-02 的撤回入口），舊值硬刪、標記失效或保留到讀取時裁決見 T2-08（待決）。多問一輪值多少、什麼時候停止發問見 T1-12（待決）。

##### M2　T2 → T3：把目前的狀態與該保留的指令交給觀測層

- **這是證據最薄的兩條之一（另一條是 M3），但不是零。** 沒有任何一張卡以「T2 交什麼給 T3」或「T3 從 T2 接什麼」為題，下面的欄位是把 T2 與 T3 各自有定論的卡拼在一起，這個拼法沒有人整條驗過。個別欄位在 T2 一側或別的論文裡有人量過，標記寫在每個欄位下面：16 列裡【直接】0 列、【直接（帶毛病）】4 列、【單側】6 列、【推論】6 列。沒有任何欄位有乾淨的【直接】；最接近的是「交記憶摘要對不交」（帶毛病 F2），只涵蓋摘要形式，不涵蓋逐欄的值、寫入輪次或來源。
- **該傳**：
  1. 目前狀態：每個欄位的值、這個值是哪一輪寫入或更新的、來源（使用者明說、系統提議而使用者沒拒絕的「隱含接受」、外部修正；外部修正要帶修正嘗試編號，才對得上第 5 節 E2 的修正紀錄）、以及值目前是有效還是已失效（T2-02、T2-05；T2-12、T2-08 待決）。已失效的值交不交給 T3 取決於 T2-08；未決之前一律不交，免得 T3 把失效值當有效值放進上下文（推論）。
     - 證據【直接（帶毛病：F2）】（整體：把 T2 自己追蹤出的狀態以記憶摘要的形式交給回覆模型，對不交）：同一個 ChatGPT、同一份資料的第 5 段，不給記憶的 F1 分數是 18.94，給自己產生的記憶摘要是 20.48，20.48 − 18.94 = 1.54 [arXiv:2308.15022]（Table 5）。覆蓋範圍很窄：交的是自由文字的記憶摘要，不是逐欄的值，沒有寫入輪次也沒有來源，所以下面 a、b、c 三項不因它升級。毛病 F2：評估是在第 5 段上，給當前段的對話脈絡（資料集裡人寫的前幾句）預測下一句，再與參考回覆比，歷史不是系統自己產生的；兩臂共用同一份脈絡，配對差不會被直接抬高，但不能說明歷史由系統自己產生、錯誤會累積時差距還在不在。另外單次執行、溫度 0、回覆長度沒有控制、差距只有 1.54，是雜訊旗標（F5）。
     - 證據【單側】（a 每個欄位的值；覆蓋：交接形狀，兩臂都交了值，沒有「不交」那一臂）：SimpleTOD 把金標或模型生成的 belief 交給動作與回覆生成，Inform 在四個設定下一律是金標那一臂較高，例如 2.0 資料搭 oracle 資料庫是 78.1 對 84，84 − 78.1 = 5.9，不用資料庫時是 84.4 對 88.9，88.9 − 84.4 = 4.5 [arXiv:2005.00796]；毛病 F2（兩臂從第 2 輪起的歷史都用參考回覆）、單次執行。LiC 的條列彙整（Recap）讓 GPT-4o-mini 從 50.4 升到 66.5、GPT-4o 從 59.1 升到 76.6 [arXiv:2505.06120]；毛病 F4（只在模擬使用者這一個設定上量），每個設定跑 10 次。Recap 重貼的是模擬使用者先前說過的話（附錄 M 寫明累積的是使用者模擬器說出來的話，不是原始 shard），不是系統追蹤出的狀態。這一格原本把 F2 掛在這筆上，理由是「交進去的是金標 shard」，全文推翻了這個說法，F2 的理由因此撤回；作者自己說 Recap 是不切實際的設定，因為它把重述放在最後一輪，而真實對話事先不知道哪一輪是最後。查過、沒找到：沒有任何一篇在同一個回覆模型上比「交自己追蹤出的逐欄狀態」與「不交」。
     - 證據【推論】（b 這個值是哪一輪寫入或更新的）：沒有論文量過「值附寫入輪次」。設計先例（不當證據）：Mem0 把時間戳連同記憶交給作答模型，要它矛盾時取最新 [arXiv:2504.19413]；Hindsight 每筆記憶帶發生區間，沒有消融 [arXiv:2512.12818]；Zep 交給回覆模型的每一條事實附有效期間，整套系統沒有拿掉時間欄位的消融 [arXiv:2501.13956]。T2-05 要的是把分數按輪次序號拆開，不是每個值附輪次。
     - 查過（1b）：在 T2 名單全文讀過的論文、筆記與 ch02 上掃 timestamp、時間戳、turn index、mention time、last updated、寫入輪次；命中的是 Mem0、Hindsight、MemoryBank、Generative Agents 的記憶時間戳設計，以及 FnCTOD 一句省略 turn index 的說明，沒有任何一篇逐格記錄或傳遞寫入輪次。
     - 證據【單側】（c 來源；覆蓋：生產端）：MultiWOZ 2.2 列出值的四種來源（使用者說的、系統提議的、從別的欄位沿用的、本體論給的），作者只說這個資訊可能對追蹤有益，沒有量 [arXiv:2007.12720]；TripPy 把「剛被系統告知」「已填過」兩個二元特徵餵回追蹤器，JGA 從 52.58 升到 54.08，差 1.50 [arXiv:2005.02877]，但那是追蹤器自己的輸入，不是交給下游。消費端沒有任何一篇把來源標記交給回覆模型；外部修正這個來源只有 T2-02 主張，ch02 L785、L795 說沒有一篇量過修正寫進去之後的效果。
  2. 需要被保留的早先指令：多輪之後仍要被遵守的規定，連同排定重插它的輪次（T2 決定；T2-10 量它有沒有漂移，T2-11 用重插來補救並要同時量能力成本）。「上一次實際被放進上下文的輪次」只有 T3 組上下文時才知道，主幹沒有 T3 回到 T2 的箭頭，所以由 M3 該傳 3 的標記記錄，不要 T2 交（這一格先前寫成由 T2 交，稽核指出它要的值在下游才產生）。
     - 證據【直接（帶毛病：F1、F4）】（a 早先指令在不在上下文；覆蓋：重插系統提示的對照，只有圖）：Instruction (In)Stability 在每次使用者發話前以機率 p 重插系統提示，掃 p，畫出穩定度與 MMLU 下降此消彼長的曲線 [arXiv:2402.10962]；毛病 F1（沒有平凡基準）、F4（對話的另一半由同款模型扮演的單一模擬使用者產生；判分本身是每個系統提示各自的 Python 函式，確定性地給 0 到 1 的分數，不是評審），只有 Figure 5、6，讀不到數字；作者也說重插吃掉相當大一塊上下文。影響方向：F1 使「穩定度上升」不能讀成比其他平凡做法好；F4 使「重插使穩定度上升、使 MMLU 下降」這個方向只在這一個模擬設定上成立，換成真人或別的模擬器時方向還在不在沒驗過（這一格先前把 F4 寫成評審、說絕對數字不可信，稽核對全文後更正）。消費端另有三筆單側：MT-Eval 的初始指令遵守隨距離衰退，規則判分、沒有介入 [arXiv:2401.16745]；Multi-IF 量先前遵守的指令在後續輪次被遺忘的比例 [arXiv:2410.15553]；MultiChallenge 有「指令保留」一類 [arXiv:2501.17399]；三篇都沒有「指令在不在上下文」或重插的對照。
     - 證據【推論】（b 上一次被放進上下文的輪次）：沒有論文記錄或傳遞「上次插在第幾輪」，SPR 只調插入的機率 [arXiv:2402.10962]；MT-Eval 量的是文件與問題之間插入干擾輪次的距離，不是指令上次放進上下文的輪次，而且評審是 GPT-4（毛病 F4），Vicuna 從 6.62 降到 5.47 [arXiv:2401.16745]。這一格曾被讀候補那一輪建議升為單側，主線維持推論。
     - 查過（2b）：掃 last insert、re-insert、repetition、重插、間隔、頻率；相關的只有 SPR，其餘是 MemGPT 把記憶搬回佇列與證明裡的無關用語，沒有任何紀錄或傳遞「上一次插入輪次」的設計或實驗。
  3. 使用外部記憶時，取回的內容以什麼單位交（T2-09 的起手是原文的 round）。
     - 證據【直接（帶毛病：F4；F3 未核）】（覆蓋：取回單位的比較；方向不一致）：LongMemEval 在預算受控下比較，GPT-4o 當讀者時 round 明顯優於 session，Llama 3.1 8B 當讀者時差不多，評審是單一 GPT-4o（毛病 F4；T2-09 卡另把 F3 列為未核，因為 GPT-4o 同時是受測的讀者與評審，可能自評偏誤），只有 Figure 5 [arXiv:2410.10813]；LoCoMo 的判分確定，GPT-3.5-turbo-16k 的總分裡 observation 在每個 k 都高於 dialog（k=5 是 41.4 對 31.7，k=50 是 37.8 對 34.8），會翻轉的是 summary 對 dialog（k=5 是 32.5 對 31.7，k=10 是 31.5 對 34.6），但 summary 的 k 是場次摘要數、dialog 的 k 是輪數，同一個 k 的預算並不相同 [arXiv:2402.17753]；RMM 在 LongMemEval 隨機抽的 100 題上，session 層級的檢索勝過 turn 層級，方向相反，但只有圖、全文沒寫兩臂的取回預算是否對齊，不是乾淨的反證 [arXiv:2503.08026]。所以這一格只支撐「單位會改變結果」，不支撐「該選 round」；T2-09 的起手預設是設計預設，而且只在讀者模型是 GPT-4o 這一級時有量測支持。影響方向：F4 讓絕對值不可信；F3 未核落在 round 較好的那一臂（GPT-4o 當讀者），所以「GPT-4o 當讀者時 round 較好」這個方向本身也未確認，Llama 3.1 8B 當讀者的那一臂（差不多）不受 F3 影響。另有兩筆不受控的整套機制比較（單側）：記憶摘要 20.48、全文歷史 19.41、取回 3 句 20.23 [arXiv:2308.15022]；1.6k token 的圖譜事實取代 115k token 的全文歷史，毛病 F3、F4 [arXiv:2501.13956]。

     - 證據【推論】（a 狀態版本）：沒有論文替狀態編修訂號，也沒有讓下游確認「我拿到的是第幾版狀態」。
     - 查過（4a、4b）：掃 tracker version、state version、model version、checkpoint、deprecat、版本；命中的是模型版本表、訓練檢查點、已下架的模型與資料集版本（MultiWOZ 2.x），沒有「狀態修訂號」或「交接時附追蹤器版本」的設計。
     - 證據【推論】（b 追蹤器版本；最近的鄰居是 T2-06）：T2-06 要求報分時附評估程式與相依套件版本，證據是同名分數因為沒寫明的設定差一大截，例如 SOM-DST 在三篇不同論文裡被記成 53.01、52.57、51.2（T2-06 的證據，見 ch02）；但那管的是報分，不是交接物上的版本欄位，延伸到交接物是推論。
- **不能傳**：
  1. 金標狀態代替系統自己追蹤出的狀態（T2-05 的金標替換只能當診斷上限）。
     - 證據【直接（帶毛病：F2）】（覆蓋：SimpleTOD 的交接形狀）：金標對生成 belief，Inform 四個設定一律金標較高（算式見該傳 1 的 a）；用 oracle 資料庫時 Success 也是金標較高，63.4 對 72.8，72.8 − 63.4 = 9.4，另一個資料版本是 65.4 對 73.5，73.5 − 65.4 = 8.1 [arXiv:2005.00796]；毛病 F2、單次執行。反向的附註：不用資料庫時 Success 方向相反，70.1 對 67.1，70.1 − 67.1 = 3.0，另一個資料版本 70.5 − 68.6 = 1.9，金標反而較低；兩組表是否同一個 checkpoint 全文沒寫，判斷不了。生產端（T2→T2）：SOM-DST 只報金標上一輪狀態那一臂是 81.00，系統實際用預測的是 53.01，81.00 − 53.01 = 27.99 點 [arXiv:1911.03906]。另一筆平手：記憶摘要那組給金標記憶是 20.46，與自己產生的 20.48 分不出高下 [arXiv:2308.15022]，這削弱 T2-05「金標是診斷上限」的附帶理由，不動這條禁令（禁的是拿金標當系統自己追蹤出的狀態來報分）。影響方向：金標那一臂本來就拿到答案的一部分，「金標較高」幾乎是構造出來的（F2 抬高金標臂）；這個對照量到的是金標會把分數抬高多少，不是證明它在別處也較高。單側旁證：MT-Eval 把自產的回覆歷史換成金標，Recollection 分數大升，Vicuna-13B 從 4.64 到 7.32，對象是回覆歷史而不是 T2 狀態 [arXiv:2401.16745]。
  2. 記憶系統的版本沒有在 T2-07 的考場上通過驗收時，它取回的內容要標成未驗證，T3 不得把它們當成使用者明說的事實呈現給模型（T2-07 驗的是記憶系統的版本，不是逐筆寫入，所以標記打在系統版本上；推論，稽核指出原句沒有欄位可以標）。
     - 證據【單側】（覆蓋：生產端的考場與結構分析）：T2-07 指出 Mem0 沒量 UPDATE、DELETE 的正確率，LoCoMo 沒有更新題（ch02 L468）；記憶寫入的人工抽查有錯誤率：捏造 2.7%、錯誤關係 3.2%、漏細節 3.9% [arXiv:2308.15022]，但沒有比「標成已驗證」與「標成未驗證」交下去的差別。Generative Agents 拿掉反思後可信度 TrueSkill μ 從 29.89 降到 26.88，29.89 − 26.88 = 3.01 [arXiv:2304.03442]；它比的是「整個拿掉」對「交出去」，量的是可信度不是事實錯誤擴散，不推翻這條，只說明未驗證的寫入整個不交，在可信度上會變差。
- **收到之後的驗收**：
  1. 評估 T3 的改動時，照 T3-05 的做法在同一批任務上一次只換觀測，動作空間、模型、步數預算與 T2 追蹤器都固定；差距要同時高過什麼都不做的地板與重跑雜訊。另加一條只驗交接本身的檢查（推論，本文新增）：每一步記錄 T3 實際放進上下文的狀態欄位與指令，與 M2 交出的同一輪的那一版比對，被丟掉的欄位都要能在 M3 該傳 3 的標記裡找到原因，找不到就判這條交接不及格。
     - 證據【單側】（覆蓋：生產端；T3 一側是 T3-05）：T2 這一側的證據說明不固定 T2 會混進多大的變動：同一個消費端只換交過去的狀態，SOM-DST 差 81.00 − 53.01 = 27.99 [arXiv:1911.03906]，SimpleTOD 的 Inform 差 84 − 78.1 = 5.9 [arXiv:2005.00796]。T3 一側只有「一次只換觀測」這一半有卡支持（T3-05）；「把 T2 追蹤器固定」這一半，T3 的論文裡沒有任何一篇有 T2 元件。
  2. 換 T2 時反過來，T3 固定；指標用逐輪的狀態準確率與整題成功率並列（T2-05），差距要同時高過什麼都不做的地板與重跑雜訊。
     - 證據【單側】（覆蓋：生產端的金標替換，加一筆換 DST、其餘元件固定的系統層級比較；那一筆的下游是規則式 policy，不是 T3 的觀測層，所以不升級；README 的數字只當旁證）：T2-05 的金標替換形狀就是「換掉 T2 的輸出、消費端不動」，但只能當診斷上限；生產端確實量過這個形狀：SimpleTOD 只換交過去的 belief、回覆生成器不動，Inform 差 5.9 與 4.5（算式見該傳 1 的 a），SOM-DST 差 81.00 − 53.01 = 27.99（這一筆的消費者是追蹤器自己）。ConvLab-2 的論文只有元件可替換與同一模擬器比較多個系統的功能，沒有任何換 DST 的數字 [arXiv:2002.04793]；換 DST、其餘元件固定的比較在另一篇：TRADE 的 DST 準確率高於 SUMBT，組成系統後成功率卻是 22.4% 對 27.8%，COMER 對 TRADE 也是同樣的反轉，作者說這可能部分來自狀態標註的雜訊 [arXiv:2005.07362]。工具包 README 的數字是旁證，提醒了同一件事：SUMBT 的 JGA 是 0.30、低於 TRADE 的 0.40，任務成功率卻是 29.4、高於 20.1（數字在 ch02 L460，定性說明在 L858–862），所以這一項的差距要量在 T3 之後的任務結果上，不能只看 JGA。
- **缺口與待決**：
  1. 每輪是從完整歷史重算整份狀態，還是只算本輪變化（T2-04，待決）。原本的說法是它決定了這條箭頭交整份還是差異；證據不支持這個依存關係（支撐句先前寫成「讀過的 DST 論文內部都算差異」，稽核以全文推翻，已更正）。
     - 證據【推論】：讀過的 DST 論文分兩派。累積派內部只算變化，但交出去的都是程式合成後的完整狀態：IC-DST 預測本輪變化，再把上一輪狀態複製過來、依變化執行新增、刪除、改值 [arXiv:2203.08568]；SOM-DST 每個欄位選一個操作，由操作決定新的值 [arXiv:1911.03906]；SGD 的原型累加差分（ch02 L112）。重算派（SimpleTOD、TOD-BERT、T5DST、TransferQA、DaP、D3ST）每一輪從完整歷史重寫整份狀態，不讀上一輪的狀態，交出去的當然也是完整狀態（ch02 L167、L286）[arXiv:2005.00796][arXiv:2109.07506]。MinTL 的回覆解碼器吃的是對話脈絡、上一輪完整狀態與資料庫查詢結果，不吃差分 [arXiv:2009.12005]（設計先例）。沒有任何一篇把差異直接交給回覆模型，所以 T2-04 決定的是追蹤器內部怎麼算，不決定這條箭頭交什麼；直接交差異有沒有效，沒人量過。
     - 查過（G1）：掃 state change、delta、diff、incremental、差分、累加、增量、本輪變化；命中的都是追蹤器內部的差分累加（IC-DST、SGD 原型、FnCTOD），或參考文獻標題與記憶論文的「逐步寫入」，逐筆看過，沒有一筆是把差異交給下游。
  2. 舊的觀測在上下文裡留多久、更早的要截斷、摺成一行還是做摘要（T3-02，待決），決定了 T3 會不會把 T2 剛交過來的東西擠出去。
     - 證據【單側】（覆蓋：消費端 T3；量的是舊內容被摺掉的效果，物件不是 T2 的交接物）：SWE-agent 留最後 5 則觀測、更早的摺成一行，是 18.0%，保留完整歷史是 15.0% [arXiv:2405.15793]；該系統的 system template 從不摺疊，也就是「要保留的指令」本來就被排除在摺疊之外。沒有任何一組量到「T2 交的東西被擠掉、結果因此變差」。
  3. 狀態裡哪些欄位算是「觀測」、哪些算是「記憶」，沒有卡定義過。
     - 證據【推論】：T2 與 T3 的卡都沒有定義這條界線。MemGPT 把主上下文與外部上下文分開，外部的要用函式搬回才看得到 [arXiv:2310.08560]，這個劃分沒有被量過。
     - 查過（G3）：掃 main context、external context、archival、觀測；只有 MemGPT 有主上下文與外部上下文的劃分，「觀測」在記憶論文裡是「observation 記憶」的用法、在 T2 的卡裡 0 筆，沒有一篇量過哪些欄位該進上下文、哪些留在外部。
- **可能漏掉的欄位（推論，只列不補進契約）**：以下由 T2、T3、補讀各表的證據顯示契約沒寫，每一條的出處是那篇論文；除了 AgentMonitor 拿掉任務描述那一筆（單次、差距在雜訊內，方向還相反）之外，沒有一條有「有或沒有」的對照：
  - 值的來源不只兩種：除了使用者明說與外部修正，MultiWOZ 2.2 另列系統提議、從別的欄位沿用、本體論給的 [arXiv:2007.12720]；系統提議的值要不要算，是 T2-12（待決）。
  - 有效性或有效期間：T2 若採「標記失效」而不硬刪（T2-02、T2-08），T3 要知道哪些值已失效；Mem0g 由 LLM 判定舊關係過時時標為 invalid 而不刪 [arXiv:2504.19413]。時間有兩條軸：系統時間（何時寫入、何時失效）與事件時間（事實何時成立），Zep 交給回覆模型的只有事件時間 [arXiv:2501.13956]；契約的 1b 只涵蓋系統時間。
  - frame 層的欄位：SGD 的狀態是逐服務的 frame，除了欄位指派還有 active intent 與 requested slots [arXiv:1909.05855]。
  - 交接物的呈現格式與排序：LongMemEval 比較 JSON 與自然語言、有沒有 Chain-of-Note，以 GPT-4o 為讀者時最差組合比最好的低最多 10 個百分點，只有 Figure 6 [arXiv:2410.10813]。
  - 取回的量或預算：LoCoMo 的 observation 從 k=5 的 41.4 降到 k=50 的 37.8 [arXiv:2402.17753]。
  - 截斷標記：SimpleTOD 超過 1,024 token 就無聲截斷 [arXiv:2005.00796]，交接物沒有「這份狀態或歷史有沒有被截斷」的標記。
  - 檢索的鍵與值要分開：LongMemEval 把它們拆成兩個控制點 [arXiv:2410.10813]，契約的「單位」沒說是鍵的單位還是值的單位。
  - 依狀態查到的資料庫結果：MinTL 交給回覆生成器的是資料庫查詢結果而不是本輪狀態 [arXiv:2009.12005]；SimpleTOD 的資料庫設定會改變 Success 的方向 [arXiv:2005.00796]。
  - 監控器拿到的任務或目標描述（T3 的監控器是消費者）：Ctrl-Z 與 AgentMonitor 的監控器都讀任務描述，AgentMonitor 拿掉它時 F1 反而從 89.4 升到 90.0，差距在雜訊內 [arXiv:2311.10538]。
  - 結構上的觀察（不是欄位）：T3 吃的「歷史」是 agent 自己的動作與觀測，沒有一條主幹箭頭交這個；它實際上是從軌跡回流到觀測層的。

##### M3　T3 → T4：把模型實際看到的東西寫進軌跡

- **證據概況**：這一條的每個欄位都沒有任何一篇論文做過「紀錄裡有這個欄位或沒有，T4 的結果因此不同」的乾淨對照；20 列裡【直接（帶毛病）】1 列（該傳 1 的 b）、【單側】12 列、【推論】7 列，沒有【直接】；稽核後退了三列（該傳 1 的 a、該傳 5 的 a、缺口 1）。契約的措辭有幾處已依證據改過，改了哪裡寫在各欄位下面。
- **該傳**：
  1. 每一步的觀測，同時留兩份：工具或環境的原始回傳（a），以及經過介面改寫、模型這一步實際收到的完整輸入（b，含改寫後的觀測、M2 交來的狀態與指令、各舊觀測是原樣、摺疊、摘要還是截斷，以及改寫層的版本；T3-01 的改寫層是產生這兩個版本的地方）。理由原本寫「工具自己的錯誤被摺成『沒有結果』，只留改寫版本就查不出來」，這個說法太重，已撤；換成量到的那一句：沒有每次呼叫的實際決策脈絡，就分不出「上游資訊缺了或被改寫」與「這個元件自己推理錯」。
     - 證據【推論】（a 原始回傳）：沒有論文量過紀錄裡留不留原始回傳。設計先例（不當證據）：SWE-agent 的介面改寫讓模型看到的版本與原始回傳不同：空輸出改成一句明示訊息、第 5 則以前的觀測摺成 Old output omitted 那一行 [arXiv:2405.15793]（同一篇另有一條「格式錯誤時系統回的錯誤訊息只留第一則」，那是系統自己回的訊息，不是工具的原始回傳，這一格先前把它當成原始回傳與改寫版的差異，已撤）。章內被引來當反例的 pylint-5859，模型看到的觀測同時有原始的 grep 錯誤與改寫層附加的「No matches found」，agent 也讀出了原因，所以這一例證明的是改寫層會附加誤導的摘要，不是「只留改寫版就查不出來」。消費端：AgentDebug 的偵測器讀的是「本步輸入」，不重跑 agent [arXiv:2509.25370]。查過、沒找到：補查兩輪六條查詢，沒有任何一篇在紀錄層比較「只有改寫版」與「原始加改寫」並量下游偵測或歸因的差；Who&When Pro 把原始工具回傳另存快取、與 LLM 摘要分開，是設計先例，沒有對照 [arXiv:2607.09996]。TelemetrySuffBench 給了反向的提醒：拿掉工具輸入、輸出與結果這一組因子時，五個模型中有四個持平或更好，承重的是決策內容與來源連結（見下面的漏欄），不是原始回傳；它是自建的合成語料、標了 RECENT-INELIGIBLE，不當證據 [arXiv:2608.07899]。
     - 證據【直接（帶毛病：F1；F2 疑慮）】（b 模型實際看到的版本；覆蓋要寫窄）：TraceElephant 用同一個 GPT-4o 歸因器、同一份人工標籤，在 220 條失敗軌跡上拿掉每一步的 input 欄位（模型這一步實際收到的完整輸入），All-at-Once 的步驟層從 0.28 掉到 0.18、agent 層從 0.62 掉到 0.54；Static Agentic 的步驟層從 0.30 掉到 0.19、agent 層從 0.66 掉到 0.56 [arXiv:2604.22708]（Table 3）；作者明說差距的關鍵不是中間推理有沒有出現，而是每次呼叫的實際決策脈絡有沒有被記錄。覆蓋：input 欄位包含角色提示詞、可見歷史、agent 之間的訊息與系統組出來的上下文，所以它支持「紀錄要留模型這一步實際看到的完整輸入」，撐的是 b 裡「完整輸入」那一部分；b 裡的改寫層版本與組裝清單是為了讓驗收 1 做得出來才加的推論，沒有任何量測；它也沒有單獨量「原始回傳對改寫後版本」（那是 a，現在是推論）。另有一個混淆：論文把 step_id 與 agent 身分也歸在 input 欄位，拿掉 input 時有沒有一併拿掉它們全文沒寫（A.6.2），若有，這筆落差也混了 5a、5b 的效果。毛病 F1：沒有位置基準，影響的是絕對準確率不能讀成有鑑別力，配對的差不受影響；F2 疑慮：這張表在 with ground truth 設定下，兩臂都有，配對差不會被直接抬高；沒報變異，只有一個歸因骨幹。反向的限縮：評估端多讀一種觀測不一定較好，AgentRewardBench 的 GPT-4o mini 評審在最終步兩份都給時成功 precision 是 62.1、只給截圖時是 64.5，但 recall 方向相反（81.7 對 78.3），兩份都不給最差（F1 66.7）；單一評審、單次執行，precision 差 2.4 點 [arXiv:2504.08942]；所以「紀錄裡兩份都要有」和「評估端兩份都要讀」是兩件事，前者有消費端需求撐著，後者只能說多讀不保證較好。
  2. 監控器（與評估端）實際讀到的欄位：有沒有推理、工具參數、工具輸出（T3-09；E3 T3 生產端），紀錄裡要標明它讀的是哪些。這一項原本寫「模型實際讀到」，但它引的 T3-09 與 E3 說的都是監控器；被監控的 agent 不會去讀自己的推理，已改成監控器。這一項只要求標明讀了什麼，不是要求都給：監控器讀的可以是原文，也可以是篩過或抽取後的版本，讀完整推理加行動不是預設（T3-09 卡的反證欄沒有收 2601.21112，它量到八組監控器與環境的組合中有七組是篩過資訊的監控器勝出）。另記兩個條件：被監控的模型知不知道自己被監控、監控的是不是推理模型，這兩者都改變了 CoT 監控器的表現 [arXiv:2601.21112]。
     - 證據【單側】（a 推理；覆蓋：生產端，量的是監控器的輸入，不是紀錄有沒有標明）：Baker 等人用同一個監控器、同一份提示，看完整軌跡的 CoT Monitor 合併召回率 95%，只看工具呼叫與輸出的 Action Monitor 60% [arXiv:2503.11926]；SHADE-Arena 的 GPT-4o 看得到 scratchpad 時 AUC 是 0.999，看不到時是 0.51 [arXiv:2506.15740]。同方向的反例：多看不一定較好，八組監控器與環境的組合中有七組，篩過資訊的監控器勝過讀完整推理加行動；只讀行動在其中五組最差、從不是最好 [arXiv:2601.21112]（標了 RECENT-INELIGIBLE，只當單側）。T4 評估端：評審讀哪些觀測欄位會改變輸出，GPT-4o mini 簡化評審的副作用 recall 從 31.9 擺到 76.4，但 precision 全部貼著基率 72/1106 ≈ 6.51%，只是操作點移動 [arXiv:2504.08942]。查過、沒找到：拿掉推理對評審判定的影響，T4 的 26 篇全文沒有任何量測。

     - 證據【單側】（a 標記；覆蓋：消費端，量的是偵測器抓不到這一類，沒有「有標記對沒標記」）：TRAIL 的 Context Handling 這一類，幾乎所有模型的偵測 F1 都是 0.00，只有 claude-3.7-sonnet 是 0.18 [arXiv:2505.08638]；MAST 說缺資訊這種表面行為可能來自隱瞞、忽略輸入或上下文管理，很難診斷，context loss 佔 2.80% [arXiv:2503.13657]；生產端 SWE-agent 在模型看到的版本裡留佔位行，也量過摺疊的效果（18.0% 對 15.0%）[arXiv:2405.15793]。查過、沒找到：補查兩輪六條查詢，命中的都是生產端的遮罩或摘要做法，沒有一篇讓 T4 拿帶標記與不帶標記的軌跡對照。

  4. 監控器的輸出：可疑分數；門檻與它怎麼校準（在哪一份誠實分布上、對應多少誤報率或稽核預算）；在同分布上量過的 recall 與誤報率（誤報率寫成「把正常步驟判成可疑的比率」）；量測時的陽性比例（T3-07、T3-11；E3 T3 生產端）。每一筆分數要註明是哪一種：每一步執行前給的、在已存軌跡上逐步回放給的、還是整條軌跡跑完才給一個。「逐步」這個詞要放寬：多數現有監控器是最後一種，所以這一項容納「單步或整條軌跡一個分數」，外加「判到第幾步為止、怎麼彙整」；但整條軌跡一個分數只能用在離線評估，不能當 E3 的觸發訊號，也不能填進 E3 T3 生產端的「每一步執行前的監控結果」，會產生外部效果的動作也擋不住（T3-11 要求執行前逐步給分）。監控器超過門檻之後的處置（送人工稽核、改用可信模型的行動、重抽並執行最不可疑的樣本；T3-11）也要記：agent 原本提出的動作、最後執行的動作、被丟棄的候選與各自的分數；否則軌跡裡的動作可能已不是 agent 原本的提議，T4 與 T7 會評到被換掉的動作而無從察覺。
     - 證據【單側】（a 可疑分數；覆蓋：生產端；T4 沒有論文消費它）：Ctrl-Z 每一步執行前打 0 到 9 分 [arXiv:2504.10374]；AgentMonitor 逐步打 0 到 100 分 [arXiv:2311.10538]；SHADE 預設整段軌跡一個分數，逐輪監控要靠彙整函式（取最後 20% 輪次的最大分數），只略有改善、標成高可疑的軌跡多很多 [arXiv:2506.15740]。查過、沒找到：T4 的 26 篇全文裡「suspicious」0 篇；補查兩輪六條查詢，命中的都是監控器自己的設計與彙整，屬 T3 內部，沒有讀。

     - 證據【單側】（c 陽性比例；覆蓋：消費端，量的是 T4 自己的偵測器要報基率）：AgentRewardBench 的副作用基率 72/1106 ≈ 6.51%，GPT-4o mini 的 precision 是 7.2、最好的是 14.1 [arXiv:2504.08942]；T3-07 另列了 R-Judge、Llama Guard、AgentMonitor 在不同基率下被基率蓋住的數字。沒有論文量「T3 監控器的陽性比例有沒有一起傳過來」造成的差別。

     - 證據【單側】（覆蓋：消費端；量的是評估端另外拿不拿 GT，不是 T3 寫不寫進軌跡）：Who&When 的同一個 GPT-4o 歸因器，step-by-step 的 step-level 是 25.51 對 15.31（有 GT 較高），all-at-once 是 12.50 對 13.53（有 GT 反而較低）[arXiv:2505.00212]；AgenTracer 的 Claude-Sonnet-4 在 math 的 agent-level 是 46.03 對 50.79，step-level 是 38.10 對 46.03，都是有 GT 較低，作者自己說有 GT 不一定較好 [arXiv:2509.03312]。反例的差距只有幾條軌跡，兩篇都沒報變異，兩篇在卡上都帶毛病 F1、F2。TraceElephant 每個設定都是有 GT 較高，方向與上面兩篇不同 [arXiv:2604.22708]。Who&When Pro：評審另外拿到任務正解時，感知類錯誤的歸因變好、推理類持平或變差，只有 Figure 7，沒有平凡基準（毛病 F1），標了 RECENT-INELIGIBLE，只當單側 [arXiv:2607.09996]。所以能說的只有：有沒有 GT 的結果不能混在一起報；方向本身證據不足。
  3. 被監控模型自己對可疑片段的辯護，不能當佐證一起傳（E3 T3 生產端的原話）；協定本來就會產生辯護時，留在軌跡裡並標明那是辯護，讓評估端稽核，只是不能進判定（推論；這一條先前寫成一律不能傳，比 E3 寬）。
     - 證據【單側】（覆蓋：消費端，只有定性描述，沒有數字）：AI Control 讓不可信模型替可信模型挑出的最可疑片段辯護，再交給監控器；攻擊策略會堅稱那段是對的，結果沒有幫助，附錄寫這個變體明顯不如原本的 trusted monitoring [arXiv:2312.06942]。條件是經過提示最佳化、專門替後門編理由的對抗設定、單輪程式題；非對抗情境下辯護有沒有資訊量沒人量。AgentRewardBench 質性觀察到評審會附和 agent 的錯誤推理 [arXiv:2504.08942]。沒有任何一篇做過拿掉自述的消融。
  4. 把監控分數接成訓練 reward（T3-10）。
     - 證據【單側】（覆蓋：訓練端，下游不是這條箭頭；而且只涵蓋讀 CoT 的監控器）：Baker 等人把「通過測試且不觸發只看 CoT 的監控器」當 reward，加壓的 agent 仍以可觀的比例作弊，監控器召回率掉到接近 0，約從訓練進度 25% 起，被選中的作弊解快速增加 [arXiv:2503.11926]（§3）。兩點限縮：只看行動的監控分數接進 reward 會怎樣沒人量；低度最佳化時這樣做是嚴格改善，壞處出在最佳化過頭，而實務上通常沒有地面真值判斷何時越線。所以這條禁令是作者的預防性建議，不是「一接就壞」；T4-06 的立場也是可以併、但要另留不參與訓練的判定，併過的偵測器要重量召回率才能再當觸發器。
  5. 單步離線分數當觀測改動的驗收依據（T3-06，只當開發中的診斷）。
     - 證據【單側】（覆蓋：量同一件事，但改變的是模型不是觀測）：SeeAct 在 90 題上（線上評估時因網站改版而失效的題目，從同一個切分重抽，所以線上與離線不完全是同一批），離線 Offline0 是 3.3，線上是 37.8；FLAN-T5-XL 對 GPT-4 的 Offline0 是 4.4 對 1.1，線上是 8.9 對 13.3，排名反轉 [arXiv:2401.01614]。這些都是模型之間的比較，沒有任何「同模型、只換觀測」的配對，所以理由要寫成「離線分數的大小與排名都不穩」，不能寫成「觀測改動的排名會被離線分數搞錯」，後者沒量到。T4 一側沒有任何論文評估觀測改動。
- **收到之後的驗收**：
  1. T4 這一端要能只靠軌跡回答「模型在這一步看到的是什麼」。做法：不重跑 agent，只拿紀錄把每一步的輸入還原出來。「對得上」的判準（推論，本文仿寫）：一、改寫層是確定性的時候，用記錄的改寫層版本對原始回傳重跑一次改寫，結果要與紀錄的改寫後觀測逐字相同；改寫層含隨機或 LLM 摘要而不能重放時，改比雜湊並標明「不可重放」。二、用組裝清單（M2 交來的狀態與指令、各舊觀測的處理方式）重建這一步的完整輸入，雜湊要與紀錄的完整輸入一致。兩項都過才算交接成功。這一句驗的是觀測；原本寫的「借 T7-10 第二項重建世界狀態」是兩件事，世界狀態快照在 M4 第 1 項，不在 M3 的欄位裡，驗收要分開驗。
     - 證據【單側】（覆蓋：消費端，只有做法；形狀最接近的是 TraceElephant 的 Static 對 Dynamic）：AgentDebug 的偵測器逐步讀本步輸入、不重跑 [arXiv:2509.25370]；SWE 軌跡研究只用原評估留下的日誌，把三個框架的日誌統一成（thought, action, result）；之後把動作分進 8 個類別時，有 8.3% 分不進任何一類、被排除在後續分析外 [arXiv:2506.18824]（這是分類法涵蓋不到，不是格式轉換損失，先前寫成「轉換時丟掉」，已更正）。TraceElephant 比較只靠紀錄（Static）與紀錄加可重放環境（Dynamic）：with GT 下步驟層 30.3 對 33.3、agent 層 65.9 對 66.7，without GT 下 26.1 對 27.6、59.1 對 60.6 [arXiv:2604.22708]；量的是歸因，不是「模型這一步看到什麼」的重建。內部落差（推論）：GiGPO 附錄只證明單步觀測不能當世界狀態的鍵（兩步的環境回傳一字不差，持有物卻不同）[arXiv:2505.10978]；整串觀測夠不夠重建狀態，沒人量過。查過、沒找到：補查兩輪六條查詢，agrepl、Chronicle、NovaFabric 這類重放系統都是沒有對照臂的自評，只有摘要，只算設計先例。
- **缺口與待決**：
  1. 軌跡用哪一種格式記錄、失敗用哪一套分類法標，文獻沒有答案（T4-08，待決）；所以這條契約只規定欄位，不規定格式。
     - 證據【推論】（支持「待決」這句否定宣稱）：ch04 L239 寫沒有一篇比較過軌跡格式之間的轉換損失，L494 寫五套分類法沒在同一批軌跡上互標。旁證（不是格式轉換損失）：SWE 軌跡研究把動作分進自己的 8 類分類法時，有 8.3% 分不進任何一類 [arXiv:2506.18824]，說明分類法涵蓋不到的動作確實存在。設計先例（不當證據）：TRAIL 主張 span 結構，但沒有做比較實驗 [arXiv:2505.08638]；InterCode 每一輪都記動作、觀測與狀態變更，沒有比較格式 [arXiv:2306.14898]；AgentGym 跨 14 個環境統一成 ReAct 格式，沒有比較格式或轉換損失 [arXiv:2406.04151]。
  2. 推理拿得到但被拿來當訓練目標時，監控器讀推理的訊號就不乾淨（T3-09、T3-10），這時第 2 項要標明推理已不可信。這個標記只能單向用：標了代表不可信，沒標不代表可信。
     - 證據【單側】（覆蓋：T3-10 與 Baker §3 涵蓋「併進獎勵」那一半；另擴充一點）：即使 reward 完全不看 CoT，Chen 等人量到 6 個環境中有 5 個的 CoT 說出 hack 的比例不到 2%，所以「沒被拿來訓練」不能推出「推理可信」[arXiv:2505.05410]。推理不可信還有第二個來源：事後補寫。AgentTuning 用 GPT-4 補上 thought [arXiv:2310.12823]，ETO 的 ScienceWorld 黃金軌跡沒有 CoT、由 GPT-4 產生對應的 rationale [arXiv:2403.02502]，IPR 也因原軌跡沒有 thought 而由 GPT-4 產生 [arXiv:2406.11176]；這類推理不是模型在決策當下寫的。
- **可能漏掉的欄位（推論，只列不補進契約）**：以下由 T3、T4、補讀各表的證據顯示契約沒寫；各條的出處是那篇論文。除了兩筆之外沒有「有或沒有」的對照：Fidelity 的逐工具呼叫紀錄（第一條，帶毛病 F2、只當單側），以及 TraceElephant 拿掉系統層中繼資料（倒數第三條）：
  - 動作端：模型的原始輸出，與介面實際執行的動作。AgentTuning 在格式錯誤時用 BLEU 對映到最接近的合法動作，存進訓練資料的是哪一個論文沒寫 [arXiv:2310.12823]；AutoCodeRover 有無法解析的動作與 Response Parse Error 事件 [arXiv:2506.18824]。第 1 項只管觀測端。逐工具呼叫的紀錄另有一筆量測：只看最終值的評分在植入的 50 個靜默失敗上抓到 0 個，讀逐工具呼叫紀錄的規則抓到 50 個，在 207 個正常格上 0 誤報 [arXiv:2608.28439]；但召回率是構造出來的（毛病 F2），而且是 25 個 claim 的自建基準，卡在水論文判準邊上，只當單側。
  - 推理的來源：是模型在決策當下寫的，還是事後由別的模型補寫的（見缺口 2）。
  - 評估端讀了哪幾步的觀測：Pan 只讀最後一格，OS-Genesis 只讀最後三個狀態，AgentRewardBench 只讀最後一步 [arXiv:2404.06474][arXiv:2504.08942]；第 2 項目前只列欄位種類，沒有涵蓋讀了哪些步。
  - 世界狀態快照，或 agent 的內部狀態（例如持有物）：驗收借來的 T7-10 第二項要它，M3 的欄位裡沒有 [arXiv:2505.10978]。
  - 步驟索引的起算基準與標籤版本：Who&When 的提示詞從 0 起算，演算法卻寫成 l1..ln；有標籤指到 log 結尾之後（ch04 L379）；T4-03 另要求記標籤版本 [arXiv:2505.00212]。
  - agent 端的視窗設定（每步帶幾步歷史）：GiGPO 帶 2 步，AgentDebug 帶 {history_length} 步；少了它就無法判斷「同一個觀測」對模型是不是同一個輸入 [arXiv:2505.10978][arXiv:2509.25370]。
  - 監控器的身分、模型版本與提示詞：同一份提示，GPT-4o 的合併召回率 95%，GPT-4o-mini 是 12% [arXiv:2503.11926]；以及判斷時機與彙整規則（每步執行前、整條跑完、在已存軌跡上回放）、監控器的處置與被丟棄的重抽樣本分數（Ctrl-Z，毛病 F2）[arXiv:2504.10374]。M4 第 2 項只有 T4 端判定器，M3 沒有監控器這一份。
  - 觀測來源是真實工具或模擬器（與哪一版模擬器）：ToolEmu 全程用 GPT-4 模擬工具回傳，真實沙盒重現時有一例觀測不同 [arXiv:2309.15817]。
  - 工具實際造成的改變（外部狀態），不只回傳值：SHADE 的 spam filter 一組，回傳的只是 agent 自己寫的描述（精讀時查程式碼，未對全文）[arXiv:2506.15740]。

  - 被觀測 agent 自己的系統層中繼資料與可重放環境的參照：TraceElephant 拿掉 metadata，Static Agentic 的步驟層從 0.30 降到 0.23、agent 層從 0.66 降到 0.57 [arXiv:2604.22708]；with GT 下 Dynamic 比 Static 多 33.3 − 30.3 = 3.0 個百分點的步驟準確率。M3 驗收要求「不重跑」，契約沒說要不要記可重放環境的參照。
  - 決策內容與出處連結（這一步做了什麼決定、依據的出處是哪一份），以及「證據不足以唯一定位時」的標記：TelemetrySuffBench 的兩項因子消融與 RQ3 都指向這兩處，但它標了 RECENT-INELIGIBLE、只在合成語料上跑（毛病 F4），只列出，不當證據 [arXiv:2608.07899]。拿掉決策與來源對應，五個模型的起源步驟準確率掉到 9.0%–66.0%，損失 19.4–79.9 個百分點；拿掉父子與相依邊在不同模型上是 56.2%–100.0%；工具輸入、輸出與結果那一組拿掉後反而有四個模型持平或更好，所以這支撐的是「記決策與來源連結」，不是「留原始回傳與改寫版兩份」。這一格沒有升進該傳 5，因為全部證據只有這一篇單一合成基準；若這個機制被別人在真實軌跡上重現，該傳 5 要加相依邊與取回內容的來源。

##### M4　T4 → T7：軌跡是評估端的主輸入（與 E5、E6 並列）

- **這是五條裡唯一有一張卡直接以它為題的一條**：T7-10（C，本身是推論）；T7-08（A）、T7-09（B）與 E5、E6 的消費端也都在規定評估端要讀到什麼。M5 引用的 A 級卡反而比 M4 多，所以不能說 M4 的依據最多。T7 有三條進線：M4、E5（修正紀錄）、E6（互動紀錄），M4 只負責 T4 自己產生的部分，另外兩條的欄位不在這裡重列。
- **該傳（T4 自己產生的部分）**：
  1. agent 這一側的完整軌跡：每一輪 agent 的訊息、工具呼叫與參數、模型這一步實際收到的完整輸入與原始回傳（M3 的兩個版本）、拿得到時的推理，附回合序號與步驟索引；每一步的輸入與輸出 token 數與模型呼叫數（M5 的成本欄位靠它，E6 缺口 4）；加上每輪的環境狀態（T7-10 第二項；T7-08；E6 消費端）。環境狀態有四種寫法，要標明是哪一種：可序列化的環境存快照（可用差異加每輪一份完整快照）；環境是決定性的而且可重設時，存初始狀態、動作紀錄與環境版本，由它們重建（τ-bench 的資料庫轉移是決定性的 Python 函式 [arXiv:2406.12045]）；沒有外部環境的純對話任務標「無環境」；線上環境拍不了快照也重建不了（OSWorld 的 chrome 區塊 46 題有 13 題因網站改版失效 [arXiv:2507.02825]），標「不可重建」，改存執行當下的關鍵節點檢查結果與每次外部呼叫的請求與回應，並附 T8-10 的環境指紋。只有終態、沒有過程的紀錄不及格（E6 的「不能傳」）。

  5. 這一份紀錄有沒有也被轉成訓練訊號（E5 消費端；T4-06）。
  6. 與 E5、E6 接起來的鍵：`episode_id`、`turn_idx`、`step_idx`、`attempt_id`、`source`（第 5 節〈各邊沒有共同的連結鍵〉的五個欄位；多 agent 時另帶 agent 或 span id）。E6 生產端也要帶集 id 與回合序號。E6 的同一則 agent 訊息對應 M4 同一集同一回合裡 agent 對使用者可見的那一步；「對上」的判準是鍵相同而且訊息文字逐字相同（或雜湊相同），找不到鍵或內容不同的那一筆列為不及格並列出來（推論）。
- **不由 M4 傳、各歸 E5 與 E6**：每一次修正嘗試的原始紀錄（E5 消費端）；使用者或模擬器的發話原文、模擬使用者的身分、版本、提示與拿到的目標原文，真人與模擬分開標記（E6 消費端與本節 E6 缺口 3）。這兩條邊各自的「不能傳」（驗證器自己的「修好了」、模擬器自己判的成敗不能當評估標籤）照舊，這裡不重複。環境或工具的回傳與世界狀態快照則只由 T4 經 M4 傳，E6 不重複記錄，只用鍵參照 M4 的那一筆；所以第 5 節 E6 缺口 1、2 裡「環境回傳與快照」的那一半改指向這裡，E6 只補使用者或模擬器的發話原文、目標原文、模擬器設定、結束原因與稽核標記。
- **不能傳**：被跳過或解析失敗的軌跡被當成「正常」放行（E4 的「不能傳」）；進過訓練的樣本混進評估而不標記（E5；T4-06）；只在失敗軌跡上評過的偵測器的位置被當成已驗證（E3 T4 生產端；T4-02）；用地面真值或 oracle 推出的判定不加標記就當成部署時拿得到的訊號，以及把過程缺陷標籤（例如 MAST 這一類）當成失敗原因（E3 T4 生產端的不能傳，這裡補列）。
- **收到之後的驗收**：T7-10 的五項驗收沿用，但每一項要寫明靠哪條進線的哪些欄位做到，哪一項失敗就只判那一條進線不及格，不用三條進線的聯集共用一個及格判準（否則 T4 全做對、E6 本來就不及格，這條箭頭照樣不及格，上下游就量不開）。只拿紀錄、不重跑 agent，評估端要能：一、重算報告裡的每個分數（M4 該傳 1 加 E6 的終態）；二、重建每一輪的環境狀態（M4 該傳 1；快照可序列化或可決定性重建的集才要求，標了「不可重建」的線上環境集數列為不適用並計數，不算不及格）；三、指出每個判定出自哪個評審與版本（M4 該傳 2；M5 該傳 3）；四、重跑洩漏稽核（T7-09）與平凡基準（T7-01）；只拿紀錄能做的是提示、示範、模擬器發話與對話歷史的字串掃描，訓練資料污染的偵測要資料集可交換、又要取得受測模型對整份資料的機率，不在「只靠紀錄」的範圍 [arXiv:2310.17623]；五、讀到設定欄位（M4 該傳 3）。M4 自己的及格條件只看 M4 該傳 1–6 負責的那幾項；E5、E6 各自判。
- **缺口與待決**：軌跡格式與失敗分類法（T4-08，待決）。多輪評估要用金上下文重播還是閉環、開放式任務沒有終態時 gold 從哪裡來（T7-11，待決），決定紀錄裡要不要同時存兩種歷史。E3、E5、E6 之間沒有共同的連結鍵（見上面「其他邊的同類缺口」），第 6 項就是這個鍵最該落地的地方：有了它，評估端才接得起同一集的偵測、修正與互動。

##### M5　T7 → T8：把判定結果與它的可信度交給計分

- **該傳**：
  1. 逐題、逐次重跑的原始結果，不要先彙整成單一成功率：每題要有重跑次數 n 與成功次數 c，才算得出 pass^k 與 pass@k（T8-05），也才算得出重跑標準差與以題目為單位的區間（T7-06、T8-06）。每次 run 還要帶它的最終輸出或終態與評分程式版本（評分程式的輸入是系統輸出或終態，不是 n 與 c；T8-04 引的統一重算靠的是取得各系統的輸出 [arXiv:2106.05555]），以及每次 run 用的使用者模擬器（模型、版本、溫度、提示版本）與有沒有 critical 模擬器錯誤的旗標（T6-04 要逐模擬器報分，T6-07 要把含 critical 錯誤的對話分開報）。
  2. 分類別的結果與題數：每一類的題數、各類的平凡 agent 地板（什麼都不做、把資料全吐出來、隨機挑合法動作）（T7-01、T8-01；類別、難度與群集來自 M4 該傳 3）；T8 要算「按題數加權」「按類別等權」「拿掉不做事也能拿分的類別」三種總分（T8-08）。
  3. 判定器的兩種錯誤率，分開報、依難度或類別分層：把失敗判成成功的比率（成功判定的偽陽性率）與把成功判成失敗的比率（偽陰性率）（T7-01、T8-03；這裡的正類是「成功」，與 M3、M4 偵測器的正類「異常」方向相反，所以要寫明）；T7-12（待決）問的是這兩個率怎麼傳進任務層級的誤差棒，所以這裡只規定要傳，不規定怎麼用。每一筆逐次結果都帶判定它的 T7 判定器（評審、檢查腳本、隱藏測試）的身分、版本與提示，以及它與每個受測模型是否同家族（T7-05）。
  4. 終態以外的檢查結果：回歸檢查與過程、禁止事件檢查的通過與否（T7-08）；三種成功定義（只看終態、終態加回歸、終態加回歸加過程）一律並列交出，各自的 c 都傳，不是只傳合併後的成功。要不要把成功改成「同時通過」、拿哪一個當主成功率，在看結果之前先登記門檻，沒登記就三個並列、不選主成功率（原本寫「比例不可忽略時」，沒有門檻也沒有人判；T7-08 自己說沒有一篇量過改用後的效度）。每多串一道用「且」連起來的檢查，就多一個偽陰性來源；偽陰性的增加大於偽陽性的減少時不改成「同時通過」，三項分開報（T8-02 的守門條件；AgentRewardBench 的規則式判定 recall 只有 55.9 [arXiv:2504.08942]）。
  5. 受洩漏影響的成功要標出來，排除後重算分數與排名，兩個版本並列（T7-09）。
  6. 每次 run 的失敗原因與環境指紋：agent 出錯、限流、逾時、環境壞掉、判準出錯，以及時間、地區、瀏覽器、外部 API 版本；並寫明這些 run 是重跑、排除還是照算（T8-10）。
  7. 每次 run 的成本：包含失敗的 run、judge 或驗證器的呼叫、使用者模擬器，以及輸入與輸出 token；單價另存（T8-09）。各項成本的來源：agent 與判定器的 token 與呼叫數在 M4 該傳 1、2，T5 的在 E5，使用者模擬器的在 E6（E6 目前沒列，見 E6 缺口 4）。
  8. 評分程式版本、任務集版本、步數上限、使用者模擬器與其溫度、單次 run 的判定組合規則（終態、回歸、過程怎麼合成成敗，多個評審怎麼合併）與刻度來源（T8-04；與 T7-10 第五項的設定欄位合併成一組）。跨題、跨類別的聚合方式是 T8 這一站做的事，由 T8 附在它自己的輸出上，不要 T7 先交。
- **不能傳**：只有一個合併後的數字（T8-04、T8-08）；只跑一次、又沒附以題目為單位的區間或配對檢定的分數當成排名依據（T7-06；只跑一次附題目層標準誤也是有效推論 [arXiv:2411.00640]，重跑次數仍要記，pass^k 需要它）；沒有標明同源的評審判定（T7-05）；沒有重算的別人自報的同名指標（T8-04）；部分分數單獨當完成率（T8-07，要與二元成功率並列）；在多次 run 中取最好的一次（T8-05）。
- **收到之後的驗收**：T8 只拿 M5 的內容，不回頭去讀軌跡，要能做到：一、只從 M5 的逐題逐次成敗與評分程式，重算報告裡每一個彙總分數（T8-04）；每次成敗本身的重判屬於 T7，由 M4 驗收一負責，T8 重判不了（原本寫成「重算每一個分數」，容易被讀成 T8 能重新評分）；二、算出三種總分並看名次有沒有變（T8-08）；三、算出每一類的地板並與受測 agent 並列（T8-01）；四、算出誤差棒與 pass^k（T8-05、T8-06）。做不到哪一項，就回頭補 T7 該交的欄位。
- **缺口與待決**：M5 要的欄位有好幾樣上游目前沒有人產生（見 M4 該傳 3 的擴充與 E6 缺口 4、5），這是接線時要補的缺口。T7-06 與 T8-06 都寫了區間與誤差棒，兩節的邊界沒有人劃過；這裡暫定「T7 交逐題逐次的原始結果，區間在算彙總的 T8 算」，這是推論。成功率、成本、使用者滿意度、失敗嚴重度要不要合成一個分數、嚴重失敗要否決還是扣分（T8-11，待決）；pass^k 的信賴區間與重跑變異怎麼拆成 agent 取樣、使用者模擬器、API 非確定性與環境漂移（T8-12，待決）。T8 是主幹的終點，沒有任何一條箭頭把分數送回去，見第 2 節的範圍說明。

**五條契約合起來的四個觀察（推論）**：

- **欄位會沿著主幹累積，不會在某一站消失**。M3 的第 1、3 項是 M4 第一項的前提；M4 第 3 項是 M5 第 8 項的前提（M5 第 3 項的前提是 T7 自己的判定器紀錄與 T7-01 的雙向人工重判，不在 M4）。上游少記一個欄位，下游多半補不回來；例外是決定性環境，可以由初始狀態、動作紀錄與環境版本重建。累積的是儲存，不是每個 LLM 消費端的輸入：監控器、偵測器、評審實際讀的內容要另外挑選並記錄挑選方式，軌跡變長時 LLM 判定器的準確率可能下降（Who&When Pro 量到軌跡從 3K token 以下到 12K 以上，步驟歸因準確率從 94% 掉到 50% [arXiv:2607.09996]，標了 RECENT-INELIGIBLE，只是相關，只當旁證），要依長度分桶報。所以實作時應該從 M4 倒推需要的欄位，再往上游補。
- **各條契約的驗收借來的量法厚薄不一**：M4 借 T7-10（C，推論）的五項可執行檢查；M5 的四項驗收分別借 T8-04（A）、T8-08（B）、T8-01（B）、T8-05（B）與 T8-06（A）的現成量法，但 M5 的欄位介面本身沒有卡；M1 與 M2 借 T2-05、T3-05 的金標替換與一次只換一件事；M3 的驗收是本文照 M4 的形狀仿寫的，沒有現成的量法，補強後最接近的一筆量測（TraceElephant 的 Static 對 Dynamic）量的是歸因，不是驗收句要驗的那件事。
- **M2 的缺口最大**，值得優先自己量：T3-02 的答案會改變舊觀測留不留、會不會擠掉 T2 交來的東西。T2-04 的影響要收窄：讀過的 DST 論文分累積派（內部算差異）與重算派（每輪從完整歷史重寫整份狀態），兩派交出去的都是完整狀態，所以它不決定這條箭頭交整份還是差異（見 M2 缺口 1）。
- **「紀錄該留哪些欄位」在 M2、M3 上幾乎沒有實驗支持**：M3 只有一處（該傳 1 的 b，拿掉模型每一步實際收到的輸入，歸因準確率掉下來，而且帶毛病 F1），M2 只有一處量到「交 T2 自己追蹤出的東西對不交」（記憶摘要對不給記憶，20.48 − 18.94 = 1.54 [arXiv:2308.15022]，帶毛病 F2，只涵蓋摘要形式）。其餘欄位是從系統設計與相鄰的量測推出來的，不是這些欄位本身被量過。把這份契約當成待驗的設計清單，不要當成已被證實的最小欄位集。
