# Rust 插件樹內核（#2569 P2）

程式在 `native/sandbox-spawner/src/kernel/`，測試在 `native/sandbox-spawner/tests/kernel.rs`。範圍照 #1827 D251、D252。

## 現況

- **內核還沒有消費者。** 宿主（`nexus-host`）不建 `Kernel`，產品路徑上沒有任何呼叫點。接上去跟第一個消費者一起送：P3 的橋或 P4 的版本登記，哪一個先開工就由哪一張接。
- 只靠標準函式庫，不加 crate（`Cargo.toml` 與 `Cargo.lock` 沒動）。
- cordis-rs 以 `cd540033` 為準（D251 Q2），不查上游。本機沒有它的 clone，引用一律經 `.docs/nexus-cordis-full-rust-2026-11-02.md`。

## 架構

**單執行緒，沒有 async runtime。** 宿主的迴圈呼叫 `Kernel::run(now)`。`run` 依序做四件事：

1. 推進狀態；
2. 輪詢回 `Pending` 的 apply 與 dispose；
3. 觸發到期的計時器；
4. 再推進一次。

`next_deadline()` 告訴迴圈下一次最晚什麼時候要回來。這跟監督行程的 `poll` 迴圈是同一種寫法。

**外部操作只記下要做什麼，狀態轉換只發生在 `run` 裡（`settle`／`step` 與輪詢）。** 這裡的外部操作包括 `mount`、`dispose`、`update`，以及 `Cx` 上的 `plugin`、`load` 等等。所以插件的 callback 裡不管做什麼，都不會在半途重入狀態機。例外是 `emit`：它同步呼叫 listener，但 listener 一樣只能登記，不會重入狀態機。

`Kernel` 上的公開方法是給宿主（框架層）用的。插件只拿得到 `Cx`：它綁在自己的 fiber 上，能讀的服務只有自己提供的與自己宣告過的。

| 模組 | 內容 |
| --- | --- |
| `mod.rs` | 型別：`FiberId`、`State`、錯誤、`Plugin`、`Spec`、`Row`、`KernelEvent`、`Health`；`Kernel` 的公開 API；`Cx`；內建的 `Group` 插件 |
| `fiber.rs` | 狀態機：epoch、`settle`／`step`、載入、回滾、卸載順序、輪詢、計時器觸發 |
| `service.rs` | 服務表（名稱加 `TypeId`）、semver 版本與範圍 |
| `event.rs` | 型別化事件、listener 快照派發、保留名稱 |
| `deadline.rs` | `Applied`／`Step`、`Effect`、`Limits`、計時器 |
| `config.rs` | 嚴格設定：拒 `__jsExpr`、拒未知鍵、`null` 不覆寫 |

## 語意清單逐條

| 語意 | 做法 | 測試 |
| --- | --- | --- |
| 型別化的服務 | 服務以名稱加 `TypeId` 登記；名稱對、型別錯，回 `TypeMismatch` | `a_service_is_matched_by_type_as_well_as_name` |
| 同名只能有一個提供者 | 第二個 `provide` 回 `AlreadyProvided`；插件把這個錯回出去，那個 fiber 才進 FAILED | `a_second_provider_of_the_same_name_fails` |
| 讀沒宣告的服務會錯（偏離 #11） | `Cx::service` 只讀自己提供的，或 `Spec.inject` 有宣告的；沒宣告回 `Undeclared`，有宣告但這次 apply 的 epoch 裡沒有它回 `Inactive` | `reading_a_service_that_was_not_injected_is_an_error` |
| 依賴者可以改它注入的服務 | `Cx::service_mut`，規則同上 | `a_dependent_can_change_a_service_it_injected` |
| fiber 六種狀態，每次轉換都發事件 | PENDING、LOADING、ACTIVE、FAILED、UNLOADING、DISPOSED；每次轉換發一筆 `KernelEvent::Status` | `a_plugin_goes_through_every_state_and_each_transition_is_an_event` |
| C1 (b)：PENDING、FAILED 卸載也經 UNLOADING | 卸載一律走 `start_unload` | `a_fiber_that_never_activated_still_goes_through_unloading`、`a_failed_fiber_still_goes_through_unloading` |
| 依賴沒到就等 | epoch 是 `[revision, 每個依賴的實例 uid…]`；缺依賴時沒有 target，留在 PENDING，`report` 顯示 `Waiting { missing }` | `a_dependent_waits_in_pending_until_the_service_is_provided` |
| 提供者換手，依賴者跟著重載 | 提供者重新 apply，實例 uid 就換；依賴者的 target 跟著變，先卸再載 | `a_new_provider_epoch_reloads_the_dependent` |
| 依賴者先收完，提供者才收 | 提供者卸載時先進 `WaitDependents`，等所有依賴者卸完才收自己的 effect；依賴者收尾時仍讀得到舊服務 | `a_dependent_is_unloaded_before_its_provider_and_can_still_read_it`、`disposing_the_root_takes_the_whole_tree_down` |
| 同一個 fiber 的 effect 反序收 | 照登記的反序逐個呼叫 dispose；回 `Pending` 的不擋下一個，之後在輪詢裡交錯推進 | `effects_of_one_fiber_are_disposed_in_reverse_order` |
| 子插件跟著父插件收 | 子 fiber 是父 fiber 的一個 effect | `children_are_collected_with_their_parent` |
| 第一次 apply 失敗就整個回滾 | 失敗前登記的 effect、服務、listener、計時器全收掉；結束在 FAILED，發 `ApplyFailed` | `a_failed_first_apply_rolls_back_everything_it_registered` |
| FAILED 只有 `update` 救得回來 | `update` 合併設定後重 build，revision +1 | `update_brings_a_failed_fiber_back_and_null_keeps_the_old_value` |
| 被拒的 `update` 什麼都不動 | 先合併、先檢查、先 build，都過了才換 | `a_rejected_update_changes_nothing` |
| apply 有時限並可取消（偏離 #12） | apply 回 `Pending` 就由輪詢推進；逾時呼叫 `cancel`、當成失敗回滾 | `a_pending_apply_is_polled_until_done`、`an_apply_past_its_deadline_is_cancelled_and_fails` |
| 卸載途中 apply 還沒完就取消 | apply 在 Pending 時被 dispose，下一次 `run` 推進到它時 `cancel` | `disposing_during_a_pending_apply_cancels_it` |
| dispose 有時限 | effect 的 dispose 回 `Pending` 就由輪詢推進；逾時呼叫 `cancel`、發 `DisposeFailed`，fiber 照樣收掉 | `a_dispose_past_its_deadline_is_cancelled_and_the_fiber_still_goes_away` |
| 卸載中的 fiber 不能再登記 | 回 `InactiveEffect`；收掉的 `FiberId` 回 `UnknownFiber` | `registering_on_a_fiber_that_is_unloading_is_refused` |
| `FiberId` 不重用 | 槽位重用時 generation +1；generation 用完的槽位不再重用 | `a_stale_fiber_id_never_points_at_a_new_fiber` |
| listener 各自接錯（偏離 #13） | 每個 listener 回 `Result`，錯誤變成 `ListenerFailed`，其他照跑，`emit` 的一方收不到 | `a_listener_error_does_not_stop_the_others_or_reach_the_emitter` |
| 派發取快照；重入跳過 | 派發前複製 listener 清單；listener 正在跑時又被觸發，那一次不呼叫，記一筆 | `dispatch_uses_a_snapshot_and_a_reentrant_listener_is_skipped` |
| listener 跟著 fiber 收 | listener 是 fiber 的 entry | `listeners_go_away_with_their_fiber` |
| `internal/*` 只給內核用 | 插件登記或送 `internal/` 開頭的事件，回 `Reserved` | `internal_events_are_reserved_for_the_kernel` |
| 慢 callback 會被記下 | apply、poll、dispose、listener、計時器的一次同步呼叫超過 `Limits.slow_callback` 發 `SlowCallback` | `a_slow_listener_is_reported` |
| 計時器綁在生命週期上 | 計時器是 fiber 的 entry，dispose 時一起取消；callback 回錯發 `TimerFailed` | `timers_fire_on_time_and_are_cancelled_with_their_fiber` |
| 設定嚴格解析 | 拒 `__jsExpr`（錯誤帶鍵的路徑）、`Fields::finish` 拒未知鍵、型別錯回錯；那一列不掛，其他照掛 | `a_row_with_a_bad_config_is_skipped_and_the_others_are_mounted`、`config_helpers` |
| `null` 不覆寫 | `config::merge`：`null` 保留原值，陣列整個換 | `config_helpers`、`update_brings_a_failed_fiber_back_and_null_keeps_the_old_value` |
| semver 契約 | 支援 `*`、精確、`^`、`~`、`>=`；不合當成缺依賴，發一次 `ContractMismatch`；範圍寫錯，那一列被拒 | `a_semver_range_gates_the_dependency_and_a_mismatch_is_reported_once`、`a_range_against_a_provider_without_a_version_does_not_match`、`semver_parsing_and_ranges` |
| group 與停用的 group | group 是內建插件，apply 時載入自己的列；停用的 group 整棵子樹都不掛，子樹裡的必掛列報成 Off | `a_disabled_group_mounts_nothing_below_it`、`the_same_group_mounts_its_rows_in_order_once_enabled` |
| 自我停用另外報 | apply 回 `Applied::Disabled(理由)`：回滾、進 FAILED，`Health::SelfDisabled`，不併進 Off | `self_disabled_is_reported_apart_from_failed_and_off` |
| 必掛列檢查 | `check_required` 列出必掛但不是 ACTIVE、被拒、被關掉的列；被拒的列跟著父 fiber 卸載或重新 apply 作廢，不重記 | `check_required_lists_every_required_row_that_is_not_active`、`a_rejected_row_is_reported_once_after_its_parent_is_applied_again` |
| 每一輪有步數上限 | 一輪 settle 超過 `Limits.max_steps` 就停，發 `Overrun`，下一輪接著做；一次 `run` 有兩輪 settle | `a_plugin_that_never_settles_is_cut_off_per_run` |
| 延後的三項會大聲失敗 | 見〈延後的三項〉 | `the_three_deferred_entries_fail_loudly` |

## 對照 dsh

dsh 一律以 `8bd0733` 為準，行號是在 `references/deepseek-harness` 讀的，那份 clone 的 HEAD 就是 `8bd0733`。

### dsh 怎麼做、為什麼

dsh 的插件核心是 vendor 的 TS Cordis，非同步、靠 Promise。下面四點跟內核有關：

- **卸載等所有依賴者卸完，沒有時限。** `vendor/cordis/src/fiber.ts:713-718`：只要自己提供的服務還有依賴者，就一直等；註解寫的理由是依賴者收尾時還可能讀這些服務。等完之後所有 disposable **並行**跑（`:720` 的 `Promise.all`），拋錯只寫 log（`:727-729`）。
  - 解決的問題：提供者不會比依賴者先死。
  - 代價：一個卡住的依賴者讓提供者永遠關不掉。
- **一般的 `emit` 不接 listener 的錯。** `vendor/cordis/src/events.ts:203-206`：一個拋錯，後面的不跑，錯也冒到呼叫者。只有卸載通知那一條路逐個 try/catch（`fiber.ts:119-137`）。
- **沒宣告就讀服務會拋錯。** `vendor/cordis/src/reflect.ts:152`：`cannot get property … without inject`。
- **apply／dispose 沒有時限。** 卸載的 while 迴圈只等 `_release`（`fiber.ts:716-718`）。

### 另一種做法與比較

| 標準 | 自寫、單執行緒輪詢（本卡） | 照 dsh：async、無時限 |
| --- | --- | --- |
| 正確性 | 卸載順序同 dsh；每個 listener、dispose、計時器的錯都變成結構化事件 | listener 的錯冒到呼叫者 |
| 失敗與恢復 | 卡住的 apply、dispose 到時限就取消，樹會前進 | 卡住的依賴者擋住整條卸載 |
| 效能 | 沒有 runtime；每輪有步數上限 | Promise 排程 |
| 維護 | 插件作者要把長工作寫成 `Pending` 狀態機 | 寫 async 就好 |
| 產品需求（多人共用主機） | 一支插件出錯不會拖住宿主 | 一支卡住，整台關不掉 |
| 基座做不做得到 | 不加 crate，跟監督行程同一套迴圈 | Rust 要 async 就得加 tokio 之類的相依 |

### 選哪個、好在哪

- **卸載順序照 dsh**：依賴者先收完，收尾時還讀得到提供者的服務。
- **同一個 fiber 的 effect 照反序開始收。** 跟 dsh 的 `Promise.all` 一樣不互相等：回 `Pending` 的不擋下一個，之後在輪詢裡交錯推進；差別是開始的順序固定為反序，讓後登記的（通常依賴先登記的）先開始收。
- **加時限與取消（#12）、listener 各自接錯（#13）。** 多人共用一台主機，一支插件的錯不能擋住整棵樹，也不能傳到別人身上。
- **代價：「要不要 tokio」推到 #2570。** 插件要把長工作寫成 `Pending`，#2570 的 MCP client 也得用同一種寫法，到時可能會回頭要 tokio。

## 偏離 dsh

照搬 #1948 的編號，理由見 #2569〈偏離 dsh〉。

| # | 偏離 | 內核怎麼做 |
| --- | --- | --- |
| 8 | 主機級的樹用 Rust 自寫內核 | 本卡的整個 `kernel` 模組 |
| 8a | 擁有者顯式傳遞；服務值只存資料 | 每個 effect、服務、listener、計時器都掛在一個 `FiberId` 上（`Entry`）；服務是 `Box<dyn Any>`，不帶行為代理 |
| 11 | 讀沒宣告的服務會錯 | `Err(KernelError::Undeclared)` |
| 12 | apply／dispose 有時限並可取消 | `Limits.apply`、`Limits.dispose`，逾時呼叫 `Plugin::cancel`／`Effect::cancel` |
| 13 | 每個 listener 各自接錯 | `ListenerFailed`；計時器、dispose 也一樣 |

## Q6：一律回 `Result`，`panic = "abort"` 不動

- listener、apply、poll、dispose、計時器的 callback 都回 `Result<_, PluginError>`。錯誤只在內核裡變成事件，不往外傳。
- release 照舊 `panic = "abort"`：插件 panic 就是整支行程退出，內核不用 `catch_unwind`。
- 代價：插件作者必須把可預期的錯都寫成 `Err`。漏掉一個 `unwrap`，整支宿主行程就退出。宿主退出之後怎麼處理（重起、退避、上限）歸監督行程，見 #2569〈要做的事〉第 2 條；內核不自己再做一層攔 panic。

## 延後的三項（D251 Q5）

呼叫時回 `KernelError::NotImplemented { what, card }`，寫一行 log（`kernel: … 還沒實作（#卡號）`），再發 `KernelEvent::NotImplemented`。

| 項目 | 入口 | 卡 |
| --- | --- | --- |
| Loader 以 diff 做執行期編輯 | `Kernel::apply_diff` | #2596 |
| update 否決 | `Cx::on_update_veto` | #2597 |
| isolate | `Cx::isolate` | #2598 |

**列上沒有 `intercept`（#1827 C2、D256）。**
- `Row` 是 Rust 型別（`Row::Plugin { spec, config, disabled }`、`Row::Group { name, disabled, rows }`），沒有這個欄位，寫不出來。
- 把設定檔解析成 `Row` 的那一層還不存在，跟宿主接上內核的那一張一起做。那一層碰到 `intercept` 鍵要明確拒絕，錯誤指到 #2596。

## 已知限制

- **不認得的設定鍵靠插件自己拒絕。** 內核對 config 只擋 `__jsExpr`，其餘整份交給 `Spec.build`。`build` 用 `config::Fields` 並呼叫 `finish()`，打錯的鍵就會被拒；`build` 沒呼叫 `finish()`，打錯的鍵會被靜靜忽略。要不要在內核層級統一拒絕不認得的鍵，等有真的插件時再定。
- **apply 到了時限直接取消，不再最後輪詢一次。** 輪詢只在 `run` 被呼叫時發生；宿主的迴圈如果晚於 `next_deadline()` 才回來，工作可能其實已經可以完成，卻在那一次 `run` 被判逾時。
- **宿主掛在插件 fiber 底下的東西，會在那個 fiber 重新 apply 時一起收掉。** `Kernel::mount`／`load` 可以掛在任何還沒進 UNLOADING 的 fiber 底下；那個 fiber 因 epoch 改變或 `update` 重新 apply 時，先卸載全部 entry，宿主掛的子樹也在內，重新 apply 不會把它掛回來。宿主要掛子樹，應該掛在自己的 fiber 或 group 底下。
- **PENDING、FAILED 的 fiber 底下照樣可以登記。** 宿主經 `Kernel::mount`／`load` 掛在它們底下的東西會留到那個 fiber 卸載或重新 apply。

## 跟 #1385 Fog、組合層接縫的關係

- **「必掛列在樹上自我停用接不住」**：自我停用回報成 `Health::SelfDisabled`，不併進 Off；`check_required` 會列出它。宿主接上內核之後，啟動時 `check_required` 不過就以非 0 起不來。這是接上那一張的事。
- **plan-mode、sandbox-policy 缺的接縫**：屬於每條 thread 的組合層（#2572、#2573），不在宿主。內核這邊只保證兩件事：
  - 表達得出「以 thread 為範圍掛子樹」：`Kernel::load` 可以掛在任何 fiber 底下，`dispose` 那個 fiber 就整棵收；
  - 事件派發照登記順序呼叫 listener。listener 拿到的是 `&E`，改不了事件、也擋不了後面的 listener；要「攔截」得另外設計，不在本卡。
