# 同一個 plugin 的兩個版本並存：實測結果

回答 [#1139](https://github.com/DemianLi/nexus-agent/issues/1139)，也就是 [`admin-plugin-swap-decision-draft-2026-10-07.md`](https://github.com/DemianLi/nexus-agent/pull/1140)（草稿，PR #1140）§四「新舊並存」這個**未驗證假設**。

**量測日期**：2026-10-07。nexus `2a2e6885`（develop）；Node 25.9.0、macOS arm64（36 GB）、`tsx` 4.22；V8 預設堆上限 4288 MB。

## 結論

| 要驗的事 | 結果 |
| --- | --- |
| 1. 能不能並存、模組實例獨立 | **版本目錄：能。** 同一個行程載兩個版本，plugin 物件不同、模組層級狀態不共用。**查詢字串（`?v=`）：不能當並存用**——只有入口檔重新求值，它靜態 import 的輔助檔共用 |
| 2. 能不能各被不同 thread 使用 | **版本目錄：能。** thread A 載 v1、thread B 載 v2，並行呼叫，各拿自己版本的回應，計數互不墊高 |
| 3. 舊版會不會被再呼叫 | **不會**（版本目錄）。A 結束後它的計時器停了（有正對照：B 的計時器同時段在跳）。查詢字串那種因為輔助檔共用，舊版的計時器被新版接手繼續跳 |
| 4. 記憶體累積 | **線性、不回收**（`r²` ≥ 0.99，200 次沒有彎）。每「載入一個新版本」多留的量見下表，跟 plugin 原始碼大小和有沒有自己的相依成正比 |

**對設計假設的判斷：成立，而且產品現有的載入器不用改。** `resolveEntryModule` 對 `file:` 開頭的 `name` 本來就走絕對路徑的 `import()`，版本目錄各一份就是不同網址。要準備的是**每個版本一個目錄**這件事，載入器那一側已經夠用。

## 記憶體累積

量法：每一次「更新」＝ `resolveEntryModule` 載一個**新**版本 → `loadPlugins` → 呼叫一次工具 → `dispose`，丟掉所有引用；每 5 次強制兩輪 GC 之後取 `heapUsed`／`rss`。第 0 列是暖機一次之後的基線。最小平方擬合斜率。**對照組**：每次都載同一個網址（模組快取命中），斜率 0.006 MB／次、`r²` 0.59——也就是沒有累積，量具量得到差別。

### N = 50（每格各開一個乾淨行程；`tsx`）

| 載入方式 | 副檔名 | 原始碼 | 版本目錄自帶 `zod` | 堆／次 | RSS／次 |
| --- | --- | --- | --- | --- | --- |
| 版本目錄 | `.ts` | 5 KB | 否 | 0.09 MB | 0.05 MB |
| 版本目錄 | `.ts` | 5 KB | **是** | 1.92 MB | 1.93 MB |
| 版本目錄 | `.ts` | 300 KB | 否 | 2.88 MB | 4.01 MB |
| 版本目錄 | `.ts` | 300 KB | **是** | **4.71 MB** | **6.24 MB** |
| 版本目錄 | `.mjs` | 5 KB | 否 | 0.04 MB | 0.02 MB |
| 版本目錄 | `.mjs` | 5 KB | 是 | 1.87 MB | 1.79 MB |
| 版本目錄 | `.mjs` | 300 KB | 否 | 1.03 MB | 0.88 MB |
| 版本目錄 | `.mjs` | 300 KB | 是 | 2.87 MB | 2.86 MB |
| 查詢字串 | `.ts` | 5 / 300 KB | — | 0.02 MB | 0.01 MB |
| 查詢字串 | `.mjs` | 5 / 300 KB | — | 0.01 MB | 0.02 MB |

- 「原始碼 300 KB」取的是真實 plugin 的量級（`packages/nexus-plugin-*/src` 最大的 296 KB，含測試）；「自帶 `zod`」是把 `node_modules/zod`（6.4 MB 磁碟）完整放進每個版本目錄，模擬新版連同自己的相依一起安裝。**plugin 若與主程式共用同一份相依（同一個 `node_modules` 路徑），那一份不重複**，只有 plugin 自己的檔計入。
- **`.ts` 在 `tsx` 底下約是原始碼的 10 倍**（300 KB → 2.9 MB），`.mjs` 約 3.4 倍。`tsx` 會留轉譯後的碼與 sourcemap。產品今天就是 `tsx src/serve.ts`，沒有 `dist/`（`build` 是 `tsc --noEmit`），所以要用 `.ts` 那一列；若之後 plugin 以編譯後的 `.mjs` 發佈，成本會低一截。
- 查詢字串那一格看起來很便宜，是因為**它只重新求值入口檔**，壓艙檔與輔助檔都共用——那正是它不能當並存用的原因，不是它省。

### 重啟週期怎麼估

**單位是「某個 plugin 的某個新版本被載入一次」，不是「管理員按一次更新」。** 一次後台更新換 K 個 plugin 就是 K 份。同一個版本的第二個、第三個 thread 命中模組快取，**不累積**（對照組）。

粗估公式：`重啟前可用的更新次數 ≈ 預算 ÷ 每次增量`。

- 預算取「多花 1 GB RSS」：最壞那一格（`.ts`、300 KB、自帶 `zod`，約 6 MB／次）約 **170 次**；無自帶相依約 **250 次**。
- 預算取 V8 堆上限（本機 4288 MB）：最壞那一格約 **900 次**後 OOM。
- 每月更新幾次、每次換一兩個 plugin 的企業環境，一年也到不了這個量級；**實務上月度維護重啟就綽綽有餘**。要用的是下面「沒量到的」那幾條決定要不要更保守。

## 沒量到的、會讓上面的數字失準的

- **沒有量真實 plugin。** 夾具是照形狀生出來的（入口＋帶狀態的輔助檔＋壓艙檔＋選配的 `zod`），不是真的 `@nexus/plugin-goal`。真的 plugin 相依 `@nexus/core`、`@langchain/core`，若版本目錄各自帶一份，成本遠高於 `zod` 這一份（沒量）。
- **沒有量載入時間**，只量記憶體。
- **只量一個 plugin 的重複載入**，沒有量「同時掛著很多個 thread、每個都有完整的 agent」；agent 本身的記憶體不在這裡。
- **沒有量舊版 plugin 自己留下的東西**：夾具的 `apply` 有收計時器。若 plugin 開了 timer／socket／`process.on` 監聽而沒在 `dispose` 收掉，舊版會被它自己留下的引用拖著，也會繼續被呼叫——那是 plugin 的衛生問題，並存機制擋不住。**模組層級有 side effect 的 plugin 要歸到「需重啟」那一類**（#1136 的範圍）。
- **載入器的 `assertPrivateModule`**（祖先鏈只有自己寫得動）在 `/private/var/tmp` 的 `0700` 目錄下通過，沒有被版本目錄這種結構絆倒；沒有量「版本目錄放在有群組寫入權限的共用路徑」的情形，那會照規矩被拒。
- 在 **vitest** 裡量不到同樣的結果：它自己的模組執行器對查詢字串與 `import.meta.url` 的處理不同，`query` 那一列在 vitest 裡連「各自的網址」都對不上。所以測試是起 `tsx` 子行程跑的，不是在 vitest 內載入。

## 對 #1136、#1137、#1138 的連帶結論

- **載入方式定案：版本目錄。** 查詢字串出局。
- **#1136（共用狀態）**：版本目錄隔得開的是**模組層級**的狀態；plugin 若有行程級的資源（port、檔案鎖、`process.on`、持久化檔案），並存機制看不到。夾具驗到的只是前者。
- **#1137（相容性）**：載入器沒有檢查新版跟執行中的 `@nexus/core` 相不相容；模組並存不代表契約相容。
- **#1138（舊版 thread 的處置）**：舊版沒有任何機制讓它在 thread 還活著時退場——它活到那個 thread 的 `dispose`。

## 依 AGENTS.md 偏離規則的登記

dsh 做的是全域熱換，靠 `--expose-internals` 操作 Node 內部的模組快取，且它自己的 plugin-manager 承認「替換已有包要重啟進程」。我們退到「**新 thread 重新組裝，舊 thread 繼續用舊版**」，理由是 deepagents 建構後不可變（`.docs/development-plan.md` 已登記），表達不出全域熱換；而不碰 Node 內部是因為客戶的正式環境不能開 `--expose-internals`。退到的實作＝版本目錄加絕對路徑 `import()`，與這份實測一致。

## 重跑

```bash
cd apps/harness
# 並存／各被不同 thread 使用／舊版不再被呼叫（四種組合，各輸出一行 JSON）
npx tsx src/measure/plugin-coexist-cli.ts verify
# 一種組合的記憶體累積（輸出每個取樣點與最後一列擬合）
npx tsx src/measure/plugin-coexist-cli.ts memory --mode dir --ext ts --ballast-kb 300 --private-zod --updates 200 --sample-every 25
# 全部組合，各開一個乾淨行程（約 50 秒）
npx tsx src/measure/plugin-coexist-cli.ts matrix --updates 50
# 對照組：每次都載同一個網址，預期斜率≈0
npx tsx src/measure/plugin-coexist-cli.ts memory --mode dir --ext ts --ballast-kb 300 --control --updates 50
```

夾具放在 `/private/var/tmp/nexus-coexist-*`，跑完自己刪。
