## 一、需求（demian 2026-10-07 的原話整理）

1. **管理員分兩種**：買方管理員（買產品的企業那邊的帳號）與開發者管理員。**只有開發者管理員能插拔插件**；選擇這樣設計，是為了讓開發者不停機也能替企業更新插件。
2. **最小智能體所需的插件必須重啟才能改**，但仍要顯示在設定介面，並提示這需要重啟。
3. **管理員身分與稽核還沒有規劃**，demian 會在 **2026-10-12 之後**開始規劃與實作。
4. 第一個客戶是國家儀器中心；產品定位是企業級；部署是完全內網（見 `project-runs-fully-intranet` 的記憶）。

## 三、現況事實

### 3-1 nexus 側

- nexus **沒有 import Cordis 這個套件**，載入層是自寫的 `NexusPlugin`＋`PluginRegistry`（`packages/nexus-core/src/plugin.ts`、`load.ts`）。
- **沒有執行期熱插拔**，這是登記過的決定：`.docs/development-plan.md` 寫「射程限定為載入期回滾，不承諾執行期熱插拔——deepagents 建構後不可變」；與 Cordis 對照表裡「註冊是可逆副作用，reload 與 teardown 時撤銷」那一列標的是「部分」。
- 註冊會回傳撤銷函式，`loadPlugins()` 回傳 `dispose()`，載入失敗會原子回滾。
- **資料層已經有一半**：條目有 `id`／`disabled`／`config`；設定由 plugin 的 `Config`（zod strictObject）驗；出貨 `cordis.yml` 疊上 `$NEXUS_AGENT_HOME/cordis.patch.yml` 與 `--patch`；`--dump-config` 與 `--dump-config-schema` 可印出生效清單與欄位規格（後者可以直接拿來產後台表單）；單列設定壞掉只掉那一列，必掛的（如 `browser-session`）掉了才整個起不來（#751）。
- **serve 是「一個 thread 一個 agent」**，每個 thread 組裝時才 `loadPlugins`（`agent-factory.ts`）。但**清單是 server 啟動時解一次**（`serve.ts` 的 `loadDefaultPlugins`），而且有幾組設定被當成「server 的性質」啟動時只讀一次（瀏覽器會話、thread 標題、交付檔上限、落盤窗口，見 `startupSetting`）。
- 現有的認證是會話認證（#424），**沒有角色**。

### 3-2 dsh 側

- Cordis 對 dsh 的重要性來自幾個機制疊在一起：**可逆註冊**（每個貢獻走 `ctx.effect()`／`ctx.on()`，卸載時逆序撤銷）；**服務容器加 `inject`**（依賴沒到就 PENDING，提供者消失或回來時依賴者自動退回或重載）；**條目 `id` 加差異化配置**（只動變的那一列）；`isolate`／`intercept`／group；型別化事件與 waterfall。
- dsh 已經有後台頁：Web 側欄「插件」頁與 `plugin_manager` 工具。啟停條目只是改 profile 的 `cordis.patch.yml` 那一列的 `disabled`，由 HMR 偵測後只動變的條目。安裝新包走 pnpm，失敗會還原 `package.json` 與 lockfile，有版本相容性檢查與豁免機制。
- **dsh 自己承認的限制**（plugin-manager README「已知限制」）：
  - 替換已有包後需要重啟進程，才能載入新的 JavaScript 模組版本。
  - 沒開 HMR 時結果是 `restart-required`。
  - 改動影響該 profile 的**全部會話**。
  - 已安裝的 Host 程式碼在宿主進程內執行，不受工作區沙箱限制。
- dsh 的 HMR 能在開發時改程式碼生效，是靠 `--expose-internals` 去動 Node 內部的模組快取，不適合放在客戶的正式環境。
- **dsh 沒有管理員登入、角色或稽核**：授權靠沙箱模式（`danger-full-access` 或逐次審批），identity 只有「每個安裝一個匿名 id」。這些是我們自己要補的。

## 四、設計假設：新舊並存（**未驗證**）

「不停機更新」要分兩件事：

| 動作 | 難度 |
| --- | --- |
| 新增或啟停一個插件 | 低。每個 thread 組裝時才讀清單，新 thread 讀新清單即可 |
| **替換同一個插件的新版本** | **高**。Node 的 ESM 模組載入後沒有正式卸載辦法，dsh 自己也做不到 |

**假設**：不照 dsh 做熱替換，改走「新舊並存」。

- 新版放在新的路徑或版本目錄（例如 `plugins/plugin-x/1.2.0/`）。
- ESM 的模組快取以網址為鍵，新路徑會被當成另一個模組。
- 新建的 thread 載入新版，進行中的 thread 繼續用舊版，舊版隨舊 thread 結束後不再被用到。
- 不需要碰 Node 內部，也不會中斷進行中的任務。

**依 AGENTS.md「技術實現標準」的偏離規則**：dsh 的做法是全域熱換；deepagents 建構後不可變，表達不出來，所以退到「新 thread 重新組裝」。要走這條路，決議或 PR 內文要明確標註偏離、理由與退到什麼。

**已知代價與要先想的坑：**

1. **Node 無法卸載舊版模組**，每次更新會多留一份在記憶體，所以仍需要偶爾重啟來清掉。每月更新幾次的企業環境應該可以接受，但要實測。
2. **緊急修補**：安全漏洞的修補不能等舊對話自然結束。要不要支援「在輪與輪之間重建 agent 並接續」？nexus 有會話還原機制，可能辦得到，沒驗證過。
3. **共用狀態**：插件若提供 server 級的服務，或有自己的持久化格式，新舊並存會互相打架。這類插件應該歸到「需重啟」。
4. **相容性**：新版插件要和執行中的 `@nexus/core` 相容。插件只相依 `@nexus/core`（由 pnpm 機械保證），可以借鏡 dsh 的 peer 版本檢查加豁免機制。

## 五、10/12 之前不依賴身分系統，可以先做的事（候選）

這些都不需要等身分規劃，而且做完之後身分系統接上來時不用重工。

1. **實測「新舊並存」**：寫一個最小的探針，確認同一個插件的兩個版本能同時被載入、各被不同的 thread 使用、舊版隨舊 thread 結束後不再被呼叫。回答 §四 的假設。
2. **給插件加「即時／需重啟」宣告欄位，並盤點現有 22 個插件各屬哪一類。** 現有的「必掛／可少掛」區分（#751）與「server 性質」設定（§三 3-1）已經接近你要的那一群，應該可以由它們推出初稿。後台依這個欄位顯示「需重啟」提示。
3. **把插件清單從「啟動時解一次」改成「組 thread 時重讀」**，讓新 thread 讀得到新清單。要注意設定面要分清楚兩個狀態：「已儲存」與「執行中實際生效」；需重啟的項目改了之後顯示「已儲存，待重啟」，並能對照目前執行中的值（現有 `--dump-config` 只印磁碟上疊出來的結果，這裡要多一個執行中的那份）。
4. **稽核事件的格式先留 `actor` 欄位**，等身分系統做好再填；格式本身（誰、何時、改了什麼、前後值）可以先定。

## 六、已拍板的三題（2026-10-07，demian）

| 題 | 決定 | 連帶的結論 |
| --- | --- | --- |
| 1. 更新要生效到哪裡？ | **只給新對話** | 不做「在輪與輪之間重建 agent」的緊急修補推進。§四 第 2 點的原始疑慮因此縮小成殘留風險：發現舊版有洞時，進行中的 thread 仍在用它，要有辦法讓舊 thread 結束（見 §四 的 issue） |
| 2. 插件設定值誰能改？ | **開發者管理員（也就是維運人員）** | 角色矩陣是兩層，不是三層：開發者管理員能插拔、改設定；買方管理員**不能改**，只能看（含稽核）。見下方「待確認」 |
| 3. 要不要買方核准？ | **不做系統內核准**；核准是把**插件名稱與版本登記在甲方的紙本記錄上** | 系統要能產出一份可列印、可對照紙本記錄的變更資訊（見下方「待確認」） |

**後續四題（2026-10-07，demian 回覆）：**

| 題 | 回覆 | 連帶的結論 |
| --- | --- | --- |
| 誰能按重啟？ | 確認是開發者管理員 | 重啟權限與插拔、改設定同屬一個角色 |
| 紙本登記在插拔之前還是之後？ | **異動前的工作** | 它是操作者在動手前要先完成的程序，在系統之外 |
| 稽核要不要有紙本記錄編號欄位？ | **不用** | 稽核紀錄不含紙本編號 |
| 買方管理員的稽核要不要能匯出或列印？ | **不用** | 只需要在後台看得到 |

**由此推出（我的解讀，不是 demian 說的）：** 系統不負責擋「已登記紙本」這道門，也不記錄紙本編號；這是人員程序，不是系統功能。系統這邊只要讓買方管理員看得到「誰、何時、哪個插件、哪個版本、前後的值」，事後有需要時人工與紙本核對。若之後客戶要求系統內留下紙本登記的痕跡，再重開這一條。

這幾題與 10/12 之後的身分規劃相關，但目前都已有答案，不必再放進那時的待辦。

## 七、開發者管理員的安全設計（已同意預留）

開發者管理員能安裝新程式碼，而插件在宿主進程內執行、不受沙箱限制。這個帳號一旦被盜，就等於拿到客戶主機的任意執行權。對國家級單位這會被重點審查。demian 於 2026-10-07 同意在設計時預留：

- **插件包要簽章**，安裝時驗簽，不接受未簽章的包。
- **插件安裝目錄對 agent 進程唯讀**，只有安裝流程能寫。
- **每次插拔都寫稽核**，而且買方管理員要看得到開發者做過什麼。這會是客戶信任的關鍵。

仍未決定的細節（實作時再拍板）：簽章用什麼格式與信任根（誰持有簽章私鑰、公鑰放哪裡）；「安裝流程」本身以什麼身分跑；稽核存哪裡、能不能被開發者管理員自己竄改（應該不能）。

第一版是否只開「啟停與設定已安裝的插件」、不開「安裝新程式碼」：依需求第 1 條，開發者管理員的用途就是更新插件，所以安裝新程式碼大概不能省；上面三項安全設計就是它的前提。

## 八、已同意補上的「需重啟」設計

demian 於 2026-10-07 同意：

- **每個插件要有一個宣告欄位**，標明「可即時套用」或「需重啟」，後台依它顯示提示。需重啟的插件（最小智能體所需的那群）仍要顯示在設定介面。
- **設定畫面要分清楚「已儲存」與「執行中實際生效」兩個狀態。** 需重啟的項目改了之後顯示「已儲存，待重啟」，並能對照目前執行中的值。現有 `--dump-config` 只印磁碟上疊出來的結果，這裡要多一個「執行中」的那一份。
- 誰能按重啟，見 §六 的待確認。
