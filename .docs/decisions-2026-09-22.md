# Jev（System One 模型）導入 nexus-agent：拍板與實測結果（2026-09-22）

**來源**：一次 grilling（Q1–Q24）＋四批 live 實測。

**實測的原始資料與腳本不進版控。** 它們是一次性的量測裝置，跑在 session 的暫存目錄裡：
四批會話日誌（44 個 goal 輪次）、每輪的代理標籤抽取器、Jev 探針（兩種投影 × 四題）、
分析腳本，以及 `completion` 的工作區驗收器。**下面每一個數字都可以從這份文件本身讀懂**，
不需要那些檔；要重現的話，方法寫在第三節裡（題組的形狀、標籤的判準、基線的算法）。

**對照版本**：develop `81902a7`，dsh `ddefc45`（2026-09-17）。

**拍板**：demian 2026-09-22 逐題回覆，列在下面的總表。下半部四題是這次實測反而帶出來的
新問題，**同日照建議拍板**，寫在第四節；總表末四列是它們的摘要。

**產生方式**：先 grilling 把設計樹問完，再跑四批 live 資料（44 個 goal 輪次）對真端點量測。
**每一個數字都配一條「多數類猜到底」的基線**——沒有基線的話 87% 看起來像好成績，其實是
一個常數答案就拿得到的分數。

## 一、背景：Jev 是什麼，射程為什麼是 dev

TypeSafe AI 的 System One 模型，2026-09-15 限量早期存取。不生成自由文字，吃
「非結構化輸入＋結構化程式狀態」，吐**事先宣告好的型別化值＋機率／信心**。
`POST https://api.typesafe.ai/v1/systemone`，一份 `state` 送一次、所有 `questions` 平行判。
64k tokens/請求（state ＋最長那一題 32k）、$0.042/M 輸入、輸出免費、端到端 70–500ms。
題型三種：`noul`（是非，只回純量、**沒有 confidence 欄**）、`choice`、`score`。

**產品路徑關著**：部署完全內網、連不到外網（[`decisions-2026-09-19.md:40`](decisions-2026-09-19.md)），
Jev 只在美西有端點、沒有 on-prem。出貨給甲方的版本不含這顆。

## 三、實測結果（44 個 goal 輪次、88 次 Jev 呼叫、$0.0241）

| 題 | 正解分佈 | 基線 | wide | narrow | 分量 |
|---|---|---|---|---|---|
| **looping**（N=2） | yes=8 / no=36 | 82% | 86% | **95%** | **最紮實** |
| completion | 35/8/1 | 80% | 93% | 93% | **1 個正例** |
| progress | yes=32 / no=12 | 73% | 100% | 100%＊ | 承重證據只有 2 輪 |
| waiting | no=44 | 100% | 100% | 100% | 零資訊 |

＊窄投影的 100% 不算數：窄投影從 `toolOutcomes` 生，而正解就是 `mutatingOk > 0`，
**正解逐字寫在 state 裡**，那只量到 Jev 讀不讀得懂一句話。

### 3.1 `looping` 是唯一撐得起結論的一題

- 舊標籤 `maxRun`（連續同鍵最長串）**漏掉真正的打轉**：A1#1 三十一次呼叫、十三次寫入被拒、
  反覆重試，`maxRun` 只有 2——因為每次重試內容不同、鍵就不同。Jev 在那兩輪都答「是」、信心 0.99。
- 換成「失敗的變更呼叫次數 ≥ N」之後：N=1→窄 93%、**N=2→窄 95%**、N=3→84%、N=4→82%。
- **每一個 N 的漏報都是 0。** Jev 從不漏掉真正的打轉，錯全在誤報那一側——
  對「要不要停迴圈」的用途，**它錯在便宜的那一邊**。

### 3.2 `completion`：一個正例，被信心值乾淨分開

九筆完成宣告裡，**唯一真的假宣告（U1#2）兩種投影都抓到，信心 0.97／0.99；三筆誤報信心
全部 ≤ 0.52**，答對的 credible 最高 0.88。0.9 門檻精確率 1/1、召回 1/1。

跨全部 88 筆驗過（門檻會跑在每一輪上）：`claimed_not_credible` 共 8 次，
**沒有一次落在沒宣告完成的輪次上**；0.9 只觸發 U1#2 那兩筆。

**但 n=1。** 一個樣本驗不出一條門檻。

### 3.3 信心值擋得住一個失敗模式，擋不住另一個

- **判斷本身不確定**（完成可不可信）→ 誤報全低信心，真陽性 0.97。**有效**。
- **狀態編碼得糟** → **高信心答錯**。窄投影第一版送 `{"tools":["write_file:ok"]}`，
  三個正解為 yes 的輪次全答 no、信心 0.66–0.91；同一份資訊改寫成「- write_file（成功）」，
  三輪全對、信心 0.99–1.00。

→ **硬規則：投影函式改動之後必須重新對照正解，不能靠信心值監控。**

### 3.4 寬投影買不到東西

窄投影 222–671 字元、寬投影 80,006 字元（3 筆撞 32k 上限要砍半重試）。
分歧只有 progress 0 輪、completion 2 輪、looping 4 輪（**窄全對、寬全錯**）、waiting 0 輪。
→ 兩個數量級的差距換不到準確率，**在 looping 上更多脈絡反而讓它變差**。

### 3.5 兩件沒達成目的的事，照實記

- **第四批（補 completion）失敗**：設計的「容易漏掉的條件」模型一個都沒漏（6/6 含標記、
  7/7 合格），四筆新宣告全合法，不平衡從 3:1 變成 8:1。
  **44 輪只出現一次假宣告**，而且在「沒有預定結尾」的目標上
  → **假完成宣告的生成器是「目標含糊」，不是「條件刁鑽」**。
- **`waiting` 在這個資料集量不了**：CLI headless 的核准是**自動拒絕**、不會產生懸著的中斷，
  所以正解恆為 no、基線 100%。它原本要當對照組與投影絆索，只有絆索那一半還有用。

## 四、實測帶出來的四題（demian 2026-09-22 照建議拍板）

### A. 射程要不要從 `completion` 換成 `looping`

- **原設計**（Q14）把 `completion`（模型宣告完成可不可信）當主菜，`looping` 是陪襯。
- **量出來相反**：`looping` 有 8 個正例、裁決過的標籤、零漏報；`completion` 只有 1 個正例。
- **拍板：換。** Q15 的「由證據觸發」如果要成立，能倚靠的是 `looping` 的數字。
  `completion` 維持純觀測，等自然累積到足夠的正例再談。
- **後果**：`completion` 的 0.9 門檻（§3.2）**不因此變成判準**——它只有一個正例，
  寫進程式碼的是觀測，不是門檻。

### B. 投影只留窄的，還是兩種都留

- 窄的小兩個數量級、在 looping 上明顯更準、不會撞 32k 上限。
- 寬的唯一站得住的優勢是 §3 那兩輪：敘述與工具衝突時它選了工具——**但窄投影天生看不到敘述，
  所以它在那兩輪也沒錯**。
- **拍板：只留窄的**，並把 §3.3 那條硬規則寫進 plugin 的檔頭。
- **這一條推翻 Q23。** Q23 的「兩種都跑，比差異」是**量測期**的設計，目的就是比出這個結果；
  量完了就沒有第二份投影的理由。寬投影的程式碼不留在 plugin 裡。

### C. Q15 的重開條件算不算已經觸發

- Q15 拍板是「由證據觸發，不由新工具觸發」。
- 現在有的證據：`looping` 窄投影 95%（基線 82%）、四個門檻全部零漏報、8 個正例。
- **拍板：還不算。** 理由是這 44 輪全部由我一個人的題組產生、模型只有一顆
  （`nvidia/nemotron-3-super-120b-a12b`）、而且 `looping` 的正解有 8 筆來自同一種人造機制
  （核准拒絕）。**先讓純觀測在真實使用裡累積**，等正例來自沒被設計過的情境再談承重。
- **下一次要看什麼**：正例來自**沒被設計過**的情境（不是核准拒絕造出來的）、而且跨得過
  一顆以上的模型。在那之前 #263 那條拍板原樣有效。

### D. 偏離登記（**已登記在 [#534](https://github.com/DemianLi/nexus-agent/pull/534) 的內文**）

對照 dsh `ddefc45`，行號逐條親眼核過。**兩筆是對 dsh 的偏離，第三筆不是**，分開寫。

**偏離一：接一顆專職的判斷模型**

- **dsh 怎麼做**：唯一「模型做判斷」的地方是 `packages/experimental/auto-review`
  （LLM-as-authorizer，掛在 `tools/pre-execute` 的 prepend，閉合 enum，每次判斷重建，
  **fail closed**——`src/index.ts:673` 的 `if (decision === undefined) return denied(exec)`）。
  而它**重用當前 agent 自己的 provider/model 路由**（`src/index.ts:620` 的
  `provider: snapshot.provider`；`README.md:14`「the current agent's provider and model
  assess the pending action」）。dsh 的「第二顆模型」形狀是選填的 `provider`+`model`
  成對覆寫、缺省繼承主路由，而且**只用在生成**（會話標題、compaction 摘要、web search），
  **從不用在判斷**。
- **為什麼表達不出來**：Jev 不生成自由文字，當不了 agent 的主模型，所以「重用 agent 路由」
  這一條在它身上沒有對應物。
- **退到什麼**：一顆獨立路由的判斷模型，但**形狀照抄 auto-review 的四個訊號**——閉合輸出
  協定、middleware 掛點、每次判斷重建、fail closed；並且與 auto-review 同級：
  出貨清單外、預設不掛（dsh 的 bundle 與 preset 對 auto-review **零引用**，
  `README.md:14`「ships this layer switched off」）。

**偏離二：純觀測（跑但不承重）**

- **dsh 怎麼做**：兩個範本方向相反，而且**都不是純觀測**。auto-review（判斷）直接承重、
  fail closed；session-title（生成）fail soft，退回先寫好的規則路
  （`packages/session/session-title/src/normalize.ts:70` 的 `fallbackSessionTitle`，
  消費點在 `src/index.ts:788`）。dsh 裡沒有「跑但不承重」這個形狀。
- **為什麼退**：**這一筆不是「表達不出來」，是刻意比標準更保守**，得講清楚。dsh 敢讓
  auto-review 承重，因為那是他們自己已經信任的主模型；我們對 Jev 的判斷品質在開跑時
  一個數字都沒有。**前提不同才是理由**，不是照抄不來。
- **退到什麼**：判斷只寫進會話日誌，`decideGoalRound` 行為零變化（Q14=C、Q16=A）。
  承重要等 §四 C 的重開條件成立。

**第三筆不是偏離**：#263 拍板「會停下來的迴圈偵測不進執行期」是**我們自己**的決定，
Q15 把它的重開條件定成「由證據觸發，不由新工具觸發」。這裡要登記的不是偏離，是
**那條拍板還沒被推翻**——§四 C 已拍板「還不算觸發」。

**這一筆結案**：兩筆偏離已登記在 PR [#534](https://github.com/DemianLi/nexus-agent/pull/534)
的內文，並保留在本節。真的動手寫 plugin 的那張 PR 要再指回這裡，不必重寫一次。

## 六、已知風險

- **信心值不是 P(正確)**，TypeSafe 自己明說門檻要在自己的資料上測。§3.3 是那句話的實例。
- **plugin 目錄權限**：`plugin-config.ts:527`／`:548` 顯示 `assertPrivateFile` **只跑在 patch 檔上，
  不跑在它指到的模組上**。共用主機上，plugin 自己的目錄要同一套 0700/0600 紀律，
  **今天沒有任何東西會檢查**。
  **已開卡 [#542](https://github.com/DemianLi/nexus-agent/issues/542)**（2026-09-23）。上面的行號對的是本檔的對照版本
  `81902a7`，卡裡的對的是 `0b9820d`。這條跟 Jev 直接相關：Q5 定的載體（repo 外的 plugin、patch `insert`）
  走的正是這條沒檢查的路。
  **2026-09-24 已由 #542 擋下**：指到檔案的 `insert` 列，import 之前對模組檔與它的祖先鏈跑同一條檢查，
  不合就拒絕啟動。**所以 Q5 的載體從此要放在私有目錄**（目錄 `0700`、檔案 `0600`、自己擁有）。
  殘留：模組自己再 import 的旁邊檔案不逐一檢查，靠「整個目錄私有」補（`docs/operations.md`）。
- **外送面**：dev 模式下對話會多一個外部接收方（NVIDIA ＋ 美西的 TypeSafe）。
- **供應商風險**：Jev 一週大、閉源、單一供應商、早期存取。`LIVE_MODEL_ID` 的檔頭記著
  `gpt-oss-120b` 是**被下架逼著重選**的——上游斷過一次。

## 七、Q12 重開與結案：用 Jev 加速回覆（2026-09-23～25）

**起因**：2026-09-23 demian 把「速度」重新列為目標——快模型替慢模型做簡單判斷，讓使用者早點收到回覆，
體驗與精度都不能掉。只給 dev 用、可插拔。

**閘門**（開跑前寫死）：扣掉 Jev 自己的延遲之後，**首個可見輸出的中位數至少省 500ms**，而且題組上
**品質零退步**（同一題的通過數比對照組少、且失敗形狀對照組從沒出現過，才算退步）。

**對照版本**：develop `55cc821`（基線）、`5c35274`（grep 修正後的補樣）；模型
`nvidia/nemotron-3-super-120b-a12b`；題組是我們自己寫的 27 題 × 3 次，走 serve 的產品路徑。
原始資料與腳本同第三節，不進版控。

**Jev 自己的延遲**（從開發機量）：中位 310–380ms、p90 約 410ms，其中網路來回約 270ms。

### 7.1 牆鐘時間花在哪

- 模型時間約佔 99%；使用者等的是**推理**：推理片段一開始就在串，文字要等推理結束才出來。
  從推理開始到第一個文字片段，中位數 A 類 0.6 秒、B 類 4.1 秒、C 類 18.4 秒。
- 上游首位元組 170–470ms 就到，**prefill 不是瓶頸**；輸入 token 數對每步延遲的迴歸係數不顯著。
- 長尾來自三種東西，都不是 Jev 能處理的：工具 bug 造成的打轉、正文退化成重複字元寫到輸出上限
  （90 輪裡 2 次，每次 169–236 秒）、供應商過載造成的重試（81 輪裡 33 輪，會話日誌看不到）。

### 7.2 三個位置，全部 no-go

| 位置 | Jev 判斷什麼 | 結果 | 出局的理由 |
|---|---|---|---|
| ③ 工具清單收窄 | 這則訊息會用到哪些工具 | 召回率 108/159＝**67.9%**（門檻 100%） | 漏最多的是 `ls`、`present` 這種我們 harness 自己的習慣，從訊息推不出來；而且 prefill 本來就不是瓶頸 |

### 7.4 量測順帶查到的（與 Jev 無關）

- grep 的 `glob` 帶路徑時靜默回 0 筆：已修（#568，v0.5.15）。
- 讀檔結果被截斷時，結尾沒有「後面還有」的提示；預設強度會自己翻頁，低強度不會。
  我們的 `read_file` 是 deepagents 內建的那支（預設 100 行，只回切片）。dsh 的 `read`
  每次結尾都帶一行：沒讀完就寫下一次該用的 `offset=`，讀完就寫 `End of file` 和總行數，預設一次 2000 行。
  **這是對 dsh 的缺口，不是偏離。** 已開卡 [#594](https://github.com/DemianLi/nexus-agent/issues/594)。
- 正文退化成重複字元時，一路寫到輸出上限才停。dsh 也**沒有**串流中的重複偵測；但它認得
  `finish_reason: length`：整輪標成 `max-tokens`（一旦出現就不被後面的步驟蓋掉）、丟掉被截斷的工具呼叫、
  畫面顯示「已達到輸出 token 上限」，不續寫也不重試。我們完全不讀 `finish_reason`，截斷的回覆被當成正常的最終回答。這一段已有卡 [#433](https://github.com/DemianLi/nexus-agent/issues/433)，新證據補在留言；重複偵測 dsh 沒有，要做就是新偏離，先不做。
- 同一題（「幫 src/math.ts 寫點測試。」）新版多半不先問人就直接寫檔（有效 5 輪裡 1 輪問，基線 3/3）；推理強度與程式碼兩個原因已排除，原因未定。
- 供應商的限流分兩段投遞：串流內 503（被 200 蓋著）與 HTTP 429 交錯出現。
