# 會話日誌的寫入者搬進每條對話的 Rust 組合行程（#2571 設計研究）

**這份只有設計，沒有改任何產品程式碼。** 派工見 #2571 issuecomment-6768805792（#1827 D293），大綱核可見 issuecomment-6769030055。實作照 D246／D252 仍停。

- 基準：nexus `b105ce3e`；dsh `8bd0733`，全部用 `git show 8bd0733:<path>` 讀本機 clone，沒有下載。
- 縮寫：C＝`packages/nexus-core/src`，H＝`apps/harness/src`。dsh 的 J＝`packages/session/session-persistence-jsonl/src`，S＝`packages/core/session/src`。
- 用語：一對＝同一條 thread 的 Rust 組合行程加上 Node 葉子行程（#2583）。「落盤確認」＝那一批事件寫滿並 `fsync` 成功之後的回答。
- 要 demian 決定的九題在 §十三，每題都附推薦。

## 結論

1. **今天的落盤只有一條路，分三層**：記憶體裡的 `SessionLog` 同步發號，持久化協調器開 10 ms 的窗口收批，JSONL 後端逐批寫滿並 `fsync`。唯一不經這條路的是續接時補結。格式版號現值是 56，不是卡上寫的 54（§一）。
2. **dsh 沒有這一題的做法可抄**：它的事件產生端與寫入端在同一個 Node 行程。nexus 今天的三層跟 dsh 同形；要自己定的是兩個行程之間誰發號、落盤確認怎麼過界（§二）。
3. **推薦切在 `StoredSession` 這一層**：葉子留著記憶體裡的 `SessionLog` 照舊發號；組合行程握租約、驗、寫、`fsync`。發號的永遠是 loop 所在的那個行程，#2573 之前是葉子。94 個 `append` 呼叫點都不用改（§三）。
4. **葉子送的是一行一行的位元組，組合行程驗過原樣寫**。落盤的位元組跟今天逐位元組相同，格式維持 56，不升版（§三、§七）。
5. **事件一發出就送，批次窗口搬到組合行程**。葉子死掉時掉的事件，從「10 ms 窗口加上飛在空中的那一批」縮到「還沒寫進 socket 的那幾顆」（§四、§五）。
6. **續接修補與葉子死掉時的當場收尾，都由組合行程做**。代價是補結的規則要在 Rust 再寫一份，跟 TS 那份用同一批夾具逐位元組比（§六）。
7. **舊兩檔與舊版世代的遷移留在 TS**，由葉子在綁定時先做；Rust 只讀現行版本的單檔（§七）。
8. **原 #2531 不必等寫入者搬家**：搜尋對帳之前，前台請活著的對話先排空再冷讀，今天的 TS 寫入者就做得到。搜尋索引與釘選封存維持在前台（§八）。
9. **#2583 的橋有四件事沒定**，本篇寫成對橋的需求，各列選項與推薦，交 #2583 的實作定（§四）。
10. **現在做會白做的有三樣**：把 `append` 呼叫點改成 async、在 K13 定下輪界之前寫 Rust 的補結、在 K12 改預設之前量基準（§十一）。

### 1-6 子代理、租約、行程歸屬

- **子代理**：每個子代理是另一份 `SessionLog`、另一個協調器、另一個檔、另一把 `session.lock`，跟 root 同一個行程寫（C/session-persistence.ts:357-421；H/session-lease.ts 檔頭）。

## 二、dsh 怎麼做、為什麼、代價（`8bd0733`）

**怎麼做：**

- **同一個行程**：`Session.append` 同步發 `seq = log.length`（S/index.ts:829），同步發 `session/event`；JSONL 後端的 listener 把事件複製進把手的緩衝（J/storage.ts:274-281），寫入端只驗 seq 連續（J/storage.ts:323）。產生端與寫入端之間沒有行程邊界。
- **窗口 200 ms**，從第一顆起算，不重置（J/storage.ts:36、:274-281）。每批 `writeFile` 加 `sync()`（J/index.ts:1427-1428）。
- **發事件的人不等落盤**。耐久靠語意檢查點：工具動手之前與每一步之前 `await sessions.flush`（`packages/session/session-checkpoint-policy/src/index.ts:70-82`）。
- **租約**：會話目錄裡的 `session.lock`，kernel `flock`，不設逾期，持有者死了由 kernel 放（J/lease.ts:8-13、:40）。
- **修補分兩層**：存放層只處理撕裂的尾巴；語意補結 `interruptedTurnClosers` 在 agent 層（S/repair.ts:209-211）。續接時補結寫回磁碟（`packages/core/agent-loop/src/index.ts:797-801`）；冷讀只補在記憶體，不寫回（`packages/session-query/session-query/src/cold-read.ts:55`）。

**為什麼**：dsh 是一人一台的桌機程式，整棵樹在同一個 Node 行程。`append` 同步，熱路徑不碰 I/O；耐久用檢查點換，不用每顆事件換。

**代價：**

- 窗口裡的事件與背景寫入失敗後暫停期間的事件只在記憶體，行程死了就丟。
- 寫入者跟插件、工具的宿主同一個行程，行程一死，補結要等下次續接。
- 別的行程讀一條活著的會話，只看得到已落盤的部分。

nexus 今天的三層是照 dsh 做的（C/session-persistence.ts 檔頭、H/session-lease.ts 檔頭都註明出處），所以也付同樣的代價。D249 D 要的「葉子崩潰時寫入者不跟著走」，dsh 沒有對應的做法。

## 三、切在哪一層、誰發號

### 3-1 三案

- **(a) 切在 `StoredSession`**：葉子留著 `SessionLog`，照舊同步發號、同步回呼。`StoredSession` 的實作換成橋的 client：把一批事件送給組合行程。組合行程握租約、驗、寫、`fsync`、回落盤確認。
- **(b) 組合行程發號**：`append` 變成一次過橋的請求，組合行程定 seq 再回。葉子的記憶體日誌變成鏡像，靠組合行程推回來的事件更新。
- **(c) 葉子發暫定號，組合行程定案**：葉子照舊同步發號，組合行程可以插進自己的事件並重排，再把最終的 seq 告訴葉子。

### 3-2 比較

| 標準 | (a) 切在 `StoredSession` | (b) 組合行程發號 | (c) 暫定號 |
| --- | --- | --- | --- |

| 失敗與恢復 | 葉子死：組合行程手上有已收到的事件，當場補結。組合行程死：整對收，同今天 | 同 (a)，而且組合行程收到的就是全部 | 定案訊息還沒到葉子就死，兩邊的 seq 對不上 |

| 基座做不做得到 | 能。要橋保證同一方向的框不重排（§四） | 能 | 能 |

### 3-3 葉子被攻破或寫壞時，能對日誌做什麼

三案在這一條上相同。差別來自兩件跟發號無關的事：組合行程收事件時驗什麼，以及葉子對會話目錄還有沒有寫權限。

| 葉子想做的事 | 組合行程只提供「追加」時 | 還需要什麼 |
| --- | --- | --- |
| 改寫或刪掉已落盤的事件 | 橋上沒有這種請求，做不到 | 葉子不能自己開檔寫。`flock` 是建議鎖，擋不住不拿鎖就寫的行程。葉子今天對會話目錄有寫權限；在監督行程的程式碼裡沒有找到對對話行程上 landlock 的地方（§十五）。要拿掉，見 §七 與 §十三 末段「現在不問」的那一件 |
| 偽造 seq、跳號、重號 | 組合行程驗「這一批的第一顆 seq 等於已收到的顆數」，接不上整批拒 | 無 |
| 讓組合行程與讀方看到不同的內容 | 組合行程驗過之後原樣寫位元組（3-5）。同一行如果有重複的鍵，Rust 的驗證與 TS 的 `JSON.parse` 可能各取一個 | 信封那一層遇到重複的鍵就拒 |
| 灌爆磁碟 | 今天沒有任何上限（§1-7） | 單顆事件的位元組上限（§十三 的 AA）；日誌額度今天只講不擋，這張不改 |
| 寫一顆假的 `approval/decided` | 擋不住：#2572 之前，政策事件本來就由葉子產生 | #2572 把政策搬進組合行程之後，組合行程可以拒收「葉子不該寫的種類」。這張只留位置：驗證有一張「哪個來源能寫哪些種類」的表，初值是葉子全都能寫 |

組合行程收一批事件時驗的：

1. 每一行是合法的 JSON，信封有 `type`（字串）、`seq`（整數）、`time`（數字）、`data`，沒有重複的鍵；
2. seq 從已收到的顆數接著連續；
3. 巢狀深度不超過 600；
4. 單行不超過位元組上限（定了的話）；
5. 種類在「這個來源能寫」的表裡。

`data` 的資料規則（`validateSessionEventData`，C/session-log.ts:2563）不在 Rust 重做。它在葉子的 `append` 已經驗過，重做等於兩份規則要永遠同步。代價：寫壞的葉子可以寫出不合資料規則的事件，讀方讀到時才拒。

### 3-4 續接補結那條直接寫入歸誰

| 做法 | 誰算補結 | 評 |
| --- | --- | --- |
| (i) 組合行程只做存放層的事（拿租約、讀、截尾），把事件交給葉子；葉子用 TS 的 `interruptedTurnClosers` 算，當作第一批送回來 | 葉子 | 補結的規則只有 TS 一份，跟 dsh 的分層一樣。但葉子死掉時沒有人能當場收尾，boundary-shape 文件 §六 四段表的第三段做不出來 |
| (ii) 組合行程拿租約、讀、截尾、算補結、寫回，再把「已落盤加補結」交給葉子當 seed | 組合行程 | 當場收尾與續接修補共用同一份 Rust 實作。代價：補結的規則 TS 一份（`single`、CLI 用）、Rust 一份 |

推薦 (ii)。三案都一樣：補結是葉子不在或還沒起來時寫的，寫的時候沒有別的發號者。兩份實作用同一批夾具逐位元組比（§六）。

### 3-5 推薦

**選 (a)，加兩條規則。**

1. **發號的是 loop 所在的那個行程**。#2573 之前是葉子。組合行程只在葉子不在時寫自己的事件：續接修補在葉子拿到 seed 之前，當場收尾在葉子死掉之後。這跟 D274「loop 所在的行程在 `hello` 宣告」是同一個判準。
2. **葉子送的是一行一行的位元組**（`JSON.stringify(event)` 的結果），組合行程解析只為了驗，寫進檔的是收到的位元組。落盤內容跟今天逐位元組相同是結構保證的，不靠兩種語言的序列化碰巧一致。組合行程自己產生的補結由 Rust 序列化，要跟 TS 逐位元組相同，用夾具釘住。

好在哪：

- 寫入者離開葉子這件事，(a) 就做到了：租約、驗、寫、`fsync`、修補都在組合行程。
- 現在不碰 94 個呼叫點，其中 H/thread-pump.ts 那 22 處 K11–K13 還在改。
- #2573 時不白做：Rust 的讀、驗、寫、租約、修補全部沿用。丟掉的只有葉子那個小的 `StoredSession` 轉接。到那時才改成過橋請求的，是還留在葉子的那些 `append`；那些插件的 hook 在 #2572、#2573 本來就要改成過橋呼叫。

跟 dsh 的關係：dsh 沒有這條邊界。(a) 保住了 dsh 的兩個性質，`append` 同步、產生端發號寫入端驗連續（S/index.ts:829、J/storage.ts:323）；(b) 兩個都丟。

## 四、事件怎麼過橋

### 4-1 #2571 對橋的需求（交 #2583 的實作定）

D265 定的是「只傳資料、雙向、多路、可巢狀的請求→回應，加取消框與串流框」。下面四件沒有定過，本篇不當成已定的前提。

| 需求 | 為什麼 | 選項 | 推薦 |
| --- | --- | --- | --- |
| R1 同一方向的框不重排 | seq 連續靠送出的順序 | 單一 socket 上本來就成立；多條連線就要另外編號 | 寫進橋的契約：一對之間一條連線，同方向先送先到 |
| R2 單框上限 | 宿主那條橋是 256 KiB（`packages/nexus-host-bridge/src/protocol.ts:25`、`native/sandbox-spawner/host/src/host_protocol.rs:24`）。事件沒有位元組上限（§1-7） | (1) 這條橋的上限另外定，不小於單顆事件的上限；(2) 一次請求的 payload 可以分塊送；(3) 超過就拒收事件 | (1)，跟 §十三 的 AA 一起定數字。(3) 是對外看得到的行為改變 |
| R3 巢狀深度 | 宿主那條橋最多 32 層（`native/sandbox-spawner/host/src/json.rs:13`），事件可以到 600 層 | (1) 事件以「行的位元組」放在字串欄位裡過橋，框本身的深度不受影響；(2) 這條橋放寬深度 | (1)。跟 3-5 的第 2 條是同一件事 |
| R4 背壓 | 組合行程寫得慢時，葉子送出去的框會堆在葉子的寫入緩衝 | (1) 不做協定層的背壓：屏障讓每一步都等落盤確認，沒確認的最多一步的量；另設「未確認位元組」的硬上限，超過算落盤失敗；(2) credit 式的視窗 | (1)。橋如果本來就有 (2)，照用，硬上限照留 |

另一件是「葉子送出、不等回答的單向框」。本篇的推薦不需要它（4-2）。

### 4-2 用哪一種框

| 做法 | 需要橋有什麼 | 落盤確認 |
| --- | --- | --- |
| P 每批一次請求，回答就是落盤確認。葉子不逐次等，只在屏障等 | D265 已有的請求→回應，加 R1 | 回答帶「已落盤到第幾顆」 |
| Q 事件走單向框，屏障另發一次 `flush` 請求 | 多一種葉子→組合行程的單向框（D265 沒有） | `flush` 的回答 |

- **若橋只有請求→回應**：用 P。葉子發出請求後不等，接著做事；回答晚一點到。屏障就是等最後一次請求的回答。
- **若橋另有單向框**：P、Q 都能做。Q 少一則回答，但落盤失敗只能等下一次 `flush` 才講得出來（§五）。

推薦 P。它不要求橋多一種框，D265 的字面不用改；每一批都有回答，落盤失敗當批就回得來。

服務名與方法形狀照 ADR 的移動規則不變：就是今天 `StoredSession` 的 `append(events)`、`flush()`、`close()` 三個（C/session-store.ts），加上 `SessionStore` 的 `create(header)`。`resume` 在 per-thread 下改由組合行程在綁定時做（§六），葉子拿到的是 seed。

### 4-3 批次窗口放哪邊

| 做法 | 葉子死掉時掉什麼 | 組合行程看得到多少 |
| --- | --- | --- |
| W1 窗口照舊留在葉子（協調器不動，只換 `StoredSession`） | 最多 10 ms 的窗口加上還沒送出的那一批 | 落後葉子最多一個窗口 |
| W2 事件一發出就送，窗口搬到組合行程 | 還沒寫進 socket 的那幾顆。已經寫進 socket 的，葉子死了組合行程照樣讀得到 | 葉子發出的幾乎全部 |

推薦 W2。D249 D 要的是「葉子崩潰時寫入者不跟著走」；W1 下最新的那一段還在葉子手上，等於沒搬完。W2 的代價：每顆事件一次 socket 寫入（今天是每批一次）。同一個 tick 裡發的幾顆可以併成一次請求，不必一顆一框。這個成本還沒量，§十二 的量測要有它。

組合行程這一側：第一顆沒寫的事件開 10 ms 的窗口、不重置，同今天；收到 `flush` 就立刻排空。

### 4-4 今天每個排空點過界之後

| 排空點（§1-4） | 過界之後 | 等不等落盤確認 |
| --- | --- | --- |
| 模型呼叫之前、工具動手之前、送出請求快照之前 | 葉子發 `flush`，等回答。回答是錯就照今天 fail-closed | 等 |
| goal driver 的檢查點 | 同上 | 等 |
| 評分的落盤確認 | `flush` 等回答；之後照舊由葉子自己唯讀開檔讀回比對（C/session-durability.ts:49）。讀回不經組合行程，所以它驗的是磁碟，不是組合行程的說法 | 等 |
| 分叉的子 thread 登記之前、`observeThread` | `flush` 等回答 | 等 |
| 背景子代理收尾 | 那一份子代理日誌的 `flush`，等回答 | 等 |
| thread 撤掉時 `dispose` | `flush` 等回答，再 `close`。組合行程收到 `close` 才放那一份的租約 | 等 |
| 10 ms 的背景窗口 | 搬到組合行程（4-3） | 不等 |
| `turn/end`、`turn/failed`（今天沒有專用排空點） | **補在組合行程這一側**：收到這兩種事件就立刻排空，不等窗口。葉子不等 | 不等 |

`turn/end` 為什麼補、為什麼不讓葉子等：

- 一輪收尾之後，那對行程最可能閒置、被逐出，或接著被 `drain`。收尾的那幾顆早一點落盤，逐出時就不用再等一次窗口。
- 葉子不等，所以輪次的延遲不變，跟今天一樣「畫面先看到完成、幾毫秒後才落盤」。
- 代價：每輪最多多一次 `fsync`。這改了落盤的時機，不改落盤的位元組；寫成 §十三 的 U。

## 五、死掉時各掉什麼

以下都假設橋選 P、窗口選 W2。選別的，差別寫在表後。

| 誰死 | 掉哪些事件 | 之後 |
| --- | --- | --- |
| 葉子死，組合行程活著 | 葉子還沒寫進 socket 的那幾顆。屏障保證：模型請求與工具的副作用發生時，它們之前的事件都已落盤 | 組合行程把收到的寫完，當場補結（§六），照 D275 回報。今天的對照：掉最多 10 ms 的窗口加飛在空中的那一批，補結要等下次續接 |
| 組合行程死（照 D275 整對收） | 已收到、還沒 `fsync` 的：最多一個窗口加正在寫的那一批。檔尾可能撕裂 | 下次綁定時截尾、補結。跟今天對話行程崩潰一樣 |
| 兩個一起死（主機斷電） | 同上一列 | 同上一列 |
| 宿主死、監督行程還在 | 不掉。事件 log 不經宿主（D249 D） | 無 |

- **若窗口選 W1**：第一列多掉葉子那個 10 ms 的窗口，跟今天一樣。
- **若橋選 Q**：掉的事件一樣；差在落盤失敗的回報（下一節）。

### 5-1 落盤失敗：磁碟滿、`fsync` 失敗

今天的行為（C/session-persistence.ts:254 起、檔頭）：背景寫入被拒，就保留整批、暫停自動路徑、講一行；下一次明確的 `flush` 重試，並向呼叫方拒絕。後端在失敗時把檔截回寫前大小（H/jsonl-session-store.ts:812-816）。

搬過去之後，由組合行程承接：

1. 寫或 `fsync` 失敗：組合行程把檔截回寫前大小再 `fsync`；截回也失敗就把這一份標成壞的，之後一律拒。
2. 那一批與之後收到的事件照順序留在組合行程的記憶體；暫停自動窗口。
3. **葉子怎麼知道**：
   - 橋選 P：那一批的回答是錯。葉子的轉接層記下「暫停中」並講一行，不往發事件的人拋。這一行就是今天「自動路徑暫停了」的那一行。
   - 橋選 Q：沒有逐批的回答，葉子要到下一次 `flush` 才知道。
4. 下一次明確的 `flush`：組合行程重試；還是失敗，回答是錯，葉子照今天向呼叫方拒絕。模型不被叫、工具不跑。
5. 暫停期間葉子照常發事件。能堆多少受兩件事限制：屏障（下一步的模型呼叫或工具過不去），以及 R4 的未確認位元組硬上限。

暫停期間留著的事件，組合行程一死就丟，跟今天一樣。葉子不另留一份：組合行程死了整對收，沒有重送的對象。

## 六、租約與修補各放哪一邊

### 6-1 `session.lock`

- **持有者換成組合行程**。同一個鎖檔、同一種鎖（`flock(2)`）。組合行程是 Rust，直接叫 `flock`，不必再經 `nexus-sandbox-spawner --flock`。
- **新舊寫入者互斥照樣成立**：TS 經 spawner 拿的也是 `flock(2)`，鎖在同一個檔上。升級途中舊的對話行程還握著鎖時，組合行程拿不到，回 `SessionAlreadyOwnedError` 那一類的錯。
- **何時拿**：既有的會話在綁定時拿；新會話在第一次物化之前拿，同今天（H/jsonl-session-store.ts:867）。
- **子代理**：每個子代理各一把（§1-6）。組合行程同時握 root 與活著的子代理的鎖。
- **葉子死掉**：鎖留在組合行程手上，重起的葉子不用重新拿。
- **組合行程卡住**：鎖不逾期，同今天、同 dsh。`--stall-ms` 照 D275 把它殺掉，kernel 放鎖。

### 6-2 修補

| 修補 | 今天在哪 | 搬過去之後 |
| --- | --- | --- |
| 截掉撕裂的尾巴 | 存放層，續接後第一次寫之前（H/jsonl-session-store.ts:953-968） | 組合行程，綁定時讀完就截 |
| 壞行之後還有 `turn/end`／`turn/failed` 就判損壞、不截（`:1254-1258`） | 存放層 | 組合行程，同一條規則 |
| 補 `turn/end{interrupted}`、開著的 `model/start` 補 `model/end`、沒配到結果的呼叫補「結果不明」或「還沒開始」 | agent 層的 `interruptedTurnClosers`，續接時寫回（C/interrupted-turn.ts） | 組合行程（3-4 的 (ii)） |
| 葉子死掉當場收尾 | 沒有。要等下次續接 | 組合行程，葉子一死就做 |

**當場收尾與重開時修補是同一份程式，進來的地方不同：**

- 重開時：組合行程讀整份檔，掃出開著的那一輪，補結。
- 當場：組合行程邊收事件邊維持同一份掃描狀態（開著的輪、沒配到結果的呼叫、開著的 `model/start`）。葉子一死，用這份狀態直接補結。

掃描狀態只跟開著的那一輪有關，組合行程不必把整份日誌留在記憶體。重起的葉子要 seed 時，由組合行程讀檔交出去。這關係到 D273 要量的組合行程記憶體常數。

**兩份實作怎麼不走樣**：TS 的 `interruptedTurnClosers` 留給 `single` 與 CLI。準備一批「開著的輪」的夾具，餵給兩邊，比輸出的位元組；補結的 `time` 由夾具給。兩邊有一邊改了規則，這個測試就紅。

**一件要先定的事**：補結依賴輪界的定義。K13 可能照 D253 把核准改成 dsh 的「一輪不收」，那會改到「開著的輪」怎麼認（§十一）。

## 七、格式：舊格式讀取與升版

### 7-1 要不要再升一次版

**不用，維持 56。** 理由：

- 事件的位元組由葉子產生、組合行程原樣寫（3-5），跟今天的寫入器逐位元組相同。
- header 行照舊由 TS 組（`encodeHeaderLine`，H/jsonl-session-store.ts:580），當作第一批的一部分以位元組送過去。
- 佈局不變：`<會話目錄>/session.v<N>.jsonl` 與 `session.lock`。

所以 56 的讀方讀 Rust 寫的檔，跟讀 TS 寫的沒有差別，也不需要升級指南。#2336 那一串之後會不會再升，見 §十一。

### 7-2 舊格式誰讀

今天的規則（C/session-format.ts 檔頭）：版本邊全是 `additive`；續接時把舊檔的事件原樣搬進這一版的世代檔，只把 header 換成最新；v0.5.19 以前的舊兩檔另外遷移並留墓碑，要多拿一把 `<base>.lock`（H/jsonl-session-store.ts:2592、:2429）。這些加起來是 H/jsonl-session-store.ts 的大半（全檔 2,999 行）。

| 做法 | Rust 要寫的 | 代價 |
| --- | --- | --- |
| F1 Rust 全部重寫：舊兩檔、墓碑、世代遷移 | 整份 jsonl-session-store 的對應 | 兩份遷移實作；舊佈局的夾具要兩邊都過。舊兩檔是要淘汰的東西 |
| F2 遷移留在 TS，由葉子在綁定時先做；Rust 只讀現行版本的單檔 | header 的最小檢查（id、版本等於現行）、切行、驗 seq、截尾、補結、追加、物化 | 綁定時多一步；葉子在這一步要有會話目錄的寫權限 |

F2 的流程：

1. 組合行程收到 `bind`，先看會話目錄：已經是現行版本的單檔，就直接拿租約、讀。
2. 不是的話，請葉子做 `prepare`：就是今天的 `store.resume(id)` 接著 `close()`，拿鎖、遷移、截尾、放鎖。
3. 葉子做完，組合行程再拿租約、讀。兩步之間鎖空了一瞬間；別的行程搶到的話，組合行程拿不到鎖，照 `SessionAlreadyOwnedError` 回報。

推薦 F2。升過一次的會話之後都走第 1 步，`prepare` 只在升版後第一次續接時跑。代價是葉子還留著會話目錄的寫權限，§3-3 的第一列因此收不乾淨；要等舊兩檔的支援撤掉，才能把這條權限拿掉（§十三 末段「現在不問」的那一件）。

### 7-3 搬前搬後互讀怎麼驗

- **同一串事件、兩個寫入器**：同一批事件分別經 TS 的 `JsonlStoredSession` 與 Rust 的寫入端落盤，比整個檔的位元組。
- **凍結夾具**：`apps/harness/src/fixtures/session-format/` 裡現行版本的夾具，Rust 的讀方每一份都要讀得出一樣的事件數與尾巴判定。
- **來回**：Rust 寫的檔用 TS 續接再寫；TS 寫的檔用 Rust 續接再寫。之後兩邊的讀方都讀得出同一串。
- **撕裂與損壞**：同一份截斷的檔，兩邊截在同一個位元組；同一份損壞的檔，兩邊都拒。

## 八、原 #2531：內容搜尋讀不到還沒落盤的那一句

**現況**：搜尋索引是記憶體裡的 sqlite（H/thread-search.ts:529），只在前台與 `single` 建（H/serve-run.ts:1470-1477）。`single` 下活著的 thread 讀記憶體（#1599）。`per-thread` 下前台手上沒有 thread，冷讀磁碟，送出後 80–90 ms 才搜得到（docs/operations.md:1650）。測試在 H/serve-thread-search.test.ts:333-334 對 `per-thread` 跳過。

| 做法 | 怎麼做 | 評 |
| --- | --- | --- |
| S1 前台向每條活著的對話要整份記憶體裡的日誌 | 寫入者要把整份日誌留在記憶體，每次搜尋整份過橋 | 組合行程的記憶體常數變大，直接吃 D273 的容量；每次搜尋的傳輸量跟日誌長度成正比 |
| S2 前台讀磁碟，再向寫入者要「還沒落盤的尾巴」拼起來 | 兩個來源要對在同一個位置 | 今天的穩定觀察已經會「連兩次都對不上」（docs/operations.md:1651），再加一個來源更難對 |
| S3 搜尋對帳之前，前台請每條活著的對話先排空，再照舊冷讀 | 一次 `flush` 請求；沒有待寫事件的當場回 | 讀的來源只有磁碟一個。每次搜尋對每條活著的對話多一次來回 |

推薦 S3。

- 它**不依賴寫入者搬家**：今天的對話行程收到這個請求，叫協調器的 `flush()` 就行。所以原 #2531 可以從 #2571 拆出去先做。
- 窗口搬到組合行程之後（4-3），同一個請求改由組合行程回答，前台不用改。
- dsh 的做法是 S1 的同行程版本：live 的讀記憶體（`packages/session-query/session-query/src/corpus.ts:62-87`）。它沒有「別的行程要看最新那一句」的情況。

**順帶重答 D266**：搜尋索引、釘選封存維持在前台。寫入者是每條對話一個，看得到所有 thread 的行程只有前台；宿主不寫日誌、也不在資料路徑上（D249 D、E），搬進宿主沒有換到東西。

驗收照卡上的：拿掉 H/serve-thread-search.test.ts:333-334 的 skip 與 `TODO`，改 docs/operations.md:1650 那一句。

## 九、投影怎麼搬

投影單元是插件交進來的 TS 程式碼：`init`、`apply`、`view`，純、同步（C/projections.ts:42 起）。今天沒有投影快取，fold 在持有 thread 的行程裡跑，值整份送給 web。單元由插件與 harness 登記，例如 trajectory（`packages/nexus-plugin-trajectory/src/index.ts:109-110`）、token-meter、permission-presets，以及 harness 的模型選擇（H/model-selection-host.ts:289）。

| 路 | 怎麼做 | 評 |
| --- | --- | --- |
| 每筆事件叫一次 TS | 組合行程 fold，每顆事件對每個單元過橋一次 | 來回最多；fold 的狀態放哪一邊都彆扭 |
| 葉子訂閱事件串流，自己 fold | 單元照舊在葉子跑 | #2573 之前葉子本來就有記憶體裡的日誌與同步訂閱，**一行都不用改**。#2573 之後葉子靠組合行程推回來的事件串流維持鏡像 |
| 投影用 Rust 重寫 | 單元搬進組合行程 | trajectory 與 token-meter 的單元宣告分別在各自檔案的第 1,318 行與第 821 行，前面都是 fold 的程式（`packages/nexus-plugin-trajectory/src/trajectory.ts:1318`、`packages/nexus-plugin-token-meter/src/fold.ts:821`）；插件作者要寫 Rust |

推薦第二條。fold 是純函式：葉子死了重起，從 seed 重折一次就回到同一個值。代價：葉子不在的那段時間，投影不更新。

dsh 的投影也跟寫入者同一個行程，訂閱 `session/event` 即時 fold（`packages/session/session-projection/src/index.ts:297-309`）。

這張對投影不用做任何事。#2573 要做的是把事件串流推回葉子。

## 十、子代理、CLI、`single`

- **子代理**：每個子代理的日誌是另一份檔。葉子的 `SessionRegistry` 每觀察到一份新日誌，就向組合行程 `create` 一份；組合行程握那一份的鎖、各自驗 seq。背景子代理冷復活（H/background-cold.ts:147）跟 root 的續接走同一條路：組合行程做修補，交 seed。
- **CLI 與 `single`**：沒有監督行程，也就沒有組合行程。寫入者照舊是 Node 的 `JsonlStoredSession`。

所以**兩個寫入者長期並存**：`per-thread` 用 Rust，`single` 與 CLI 用 TS。這跟 D279 對 MCP 連線池的判斷同形。兩邊靠 §7-3 的對照測試綁在一起。這件要 demian 確認（§十三 的 X）。

`per-thread` 只在 Linux 起得來（H/settings/process-model.ts:7），所以組合行程一定拿得到 `flock`。「這個平台沒有鎖」那條退路只留在 TS 那一側。
