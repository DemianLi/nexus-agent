# 單一職責盤點（2026-09-19，develop `8fb2e51` 對 dsh `ddefc45`）

> **後續**：SRP-1（設定機制）＝ #46，第 12 題拍板啟動；SRP-3（拆摘要器）已開卡 #446；SRP-2 與 SRP-4 尚未開卡。見 [`decisions-2026-09-19.md`](decisions-2026-09-19.md) 第 12 題。

## 判準

- **一個職責＝一個會讓這段程式碼改變的理由。** 判定看 git 歷史：幾個職責有沒有各自獨立變化過。檔案大、職責多，但總是一起變，仍然算 single。
- **不看行數，也不看套件數。** dsh 有 291 個 package、我們有 19 個，這個對比說明不了什麼。
- **拿 dsh 房規當尺**（`references/deepseek-harness/AGENTS.md` Conventions 一節、`packages/AGENTS.md`）：
  - Plugins, not loop changes：新行為加在擴充點上，不改迴圈。
  - capability seam 由定義、提供者、消費者三個角色組成，只有在這些角色各自變化時才拆開。
  - No hardcoded tunables in plugins：會隨部署改變的值，要做成可從 `cordis.yml` 改的 Config 欄位；`DEFAULT_*` 常數或測試鉤子不算可設定。協定常數、外部規格、安全不變量不在此限。
  - 模型看得到的文字要逐字釘住。所以提示詞、工具描述不算「可調的值」。

- 一開始判成非 single 的有 22 個檔，**每個都經過一位懷疑者查核**：3 個確認、13 個部分成立（改成調整後的判定）、6 個被推翻。
- 有 12 個檔原本判成「多職責」，後來改成 single。多半是因為 git 歷史顯示那幾個職責每次都一起改（見文末）。
- **用「改變的理由」這把尺量，我們的程式碼大致是單一職責的。** 真正的落差不在檔案怎麼切，而在兩件跟 dsh「萬物皆插件」直接相關的事：
  - 可調的值寫死在程式碼裡。部署方想改的約有 28 個，dsh 會把它們做成 Config 欄位。
  - core 內建的能力，有兩顆關不掉，也換不掉。

## 方法與限制

- **範圍**：`apps/harness/src`、`packages/*/src` 的非測試原始碼，共 131 個檔；web 另外 37 個檔，只給 dev-ui 參考。排除了測試、fixture、`apps/web/src/components/ui`（shadcn 產生的元件）。
- **怎麼查的**：
  - 分 14 組，逐檔列出職責，並附行號與 git 歷史；
  - 每個非 single 的判定，交給一位懷疑者嘗試推翻；
  - core 12 顆逐一對照 dsh 的出廠條目，每組再交給一位懷疑者更正。
- **合成那一步不可靠**：自動合成的報告數字前後矛盾，完整性檢查標出了 15 條沒有出處的主張。所以本報告的數字全部由程式從原始判定算出來。工項、core 表格、可調值清單，則由主線依懷疑者的查核結果整理。
- **可調值清單經過人工篩選**：agent 判定「部署會想改」的有 50 個，照上面的排除規則篩成約 28 個。
- **沒做的**：沒有量耦合度的數字指標，也沒有跑任何重構實驗。
