# 政策 hook 與攔截插件搬進每條對話的 Rust 組合行程（#2572 設計研究）

**這份只有設計，沒有改任何產品程式碼。** 派工見 #2572 issuecomment-6770641434（#1827 D296），大綱核可見 issuecomment-6771063953。實作照 D246／D252 仍停。

- 基準：nexus `78daf052`；dsh `8bd0733`，全部用 `git show 8bd0733:<path>` 讀本機 clone，沒有下載。
- 縮寫：C＝`packages/nexus-core/src`，H＝`apps/harness/src`，T＝`packages/nexus-tools/src`，P/x＝`packages/nexus-plugin-x/src`。dsh 的路徑都在 `packages/` 底下，省略這一層。
- 用語：一對＝同一條 thread 的 Rust 組合行程加上 Node 葉子行程（#2583）。「前段」＝#2573 之前，loop 還在葉子；「終點」＝#2573 之後，loop 在組合行程。
- 範圍：只對 `--agent-loop=native` 設計；`langgraph` 那條路不動，等 K13（#2363）拿掉。
- 攻破的假設：葉子裡能跑任意程式碼（含第三方 TS 插件）；組合行程、監督行程、宿主、前台可信。
- 要 demian 決定的九題在 §十一，每題都附推薦。

## 結論

1. **卡上的「9 個插件、四種掛法」已經過時**。今天插件能掛的掛點有十一種，照做的事分五類：決定放不放行的閘門 3 位、政策狀態的寫入者 4 種事件、追加訊息或提示詞段 8 位、包住執行 4 位、觀察但會寫事件 1 位（§一）。
2. **dsh 沒有這一題的做法可抄**：它所有決定都在同一個 Node 行程做，跨出行程的只有「人的答覆」。出廠五個 profile 都沒有預設開啟、會否決工具呼叫的閘門（§二）。
3. **推薦只搬「決定」，不搬「插件」**：核准閘門的判斷（規則、管道、政策）、人的答覆以誰為準、政策狀態的驗證搬進 Rust；追加訊息、提示詞段、包住執行的插件都留在葉子。插件的閘門改成宣告式的規則，交給組合行程判（§三、§四）。
4. **`tools/execute` 的包裝不必過橋**：工具本體在葉子跑，包住它的監聽者整段留在葉子內。#2568 邊界形狀文件預期的「waterfall 拆兩則訊息」，在這一類用不到（§3-4）。
5. **前段裡，核准事件仍由葉子發號寫入，組合行程改成「驗它對不對得上自己手上的事實」**。這樣不違反 #2571 的 S（發號的是 loop 所在的行程），又讓葉子偽造不出一筆人的核准。終點才把這些種類從葉子能寫的清單拿掉（§五、§六）。
6. **人的答覆以組合行程收到的為準**：前台連的是組合行程（D249 E），答覆先到它，它記下結局再轉給葉子（§六）。
7. **核准不加逾時**，跟今天、跟 dsh 一樣，只受「停止」與一輪的時鐘約束（§6-4）。
8. **`single` 與 CLI 照舊用 TS 的判斷函式**，兩份實作用同一批向量綁住（§八）。
9. **現在做會白做的有三樣**：在 K13 定下輪界之前寫 Rust 的「開著的核准怎麼收」、為 `langgraph` 的中斷重跑另設計一份、在 #2573 之前把追加訊息的插件改成過橋呼叫（§6-6）。

### 這張做完之後仍然擋不住的

對「寫壞的葉子」（有 bug、不是惡意），fail-closed 都成立。對「被攻破的葉子」，下面四件擋不住，全部列在這裡，細節在 §五：

| 擋不住的事 | 哪一段 | 為什麼 | 要擋得另外做什麼 |
| --- | --- | --- | --- |
| 葉子不問就自己執行工具本體 | 前段、終點都是 | 工具本體在葉子跑，問不問是葉子的程式碼在走 | 沒有通用解。組合行程只能事後發現（§5-2 的對帳） |
| 葉子繞過檔案政策直接讀寫檔 | 前段、終點都是 | 檔案工具的圍堵是行程內的檢查，不是核心邊界（H/contained-backend.ts:66）；spawner 只管 ripgrep 與 git 這兩種子行程 | 葉子行程自己上核心級限制。另開卡，不在這張 |
| 葉子不經核准直接呼叫 MCP 工具 | 前段、終點都是 | MCP 呼叫由葉子向宿主發，宿主不知道核准 | 組合行程對宿主發一次性的許可。另開卡，不在這張 |
| 葉子自己發起政策切換（例如把沙箱切到全權） | 前段 | `/permission` 的命令處理在葉子；組合行程只能驗內容合不合法，分不出是不是人下的 | 終點時入口搬到組合行程（§5-4） |

這張做完之後**保證得了的**是兩件：日誌裡的核准軌跡與政策切換軌跡偽造不出來；終點時，模型發的工具呼叫在決定出來之前不會交給葉子。

### 1-3 核准怎麼走

要不要問，在 core 的一步裡判（`approvalGateToolStep`，C/approval.ts:422）。順序：

1. 跑所有閘門（`runApprovalGate`，`:274`）。`allow` 往內交；`deny` 回拒絕；`ask` 往下。
2. 管道：這次組裝關掉了核准，或是背景子代理，回 `APPROVAL_POLICY_NEVER`（`:452`）；沒有管道回 `APPROVAL_NO_CHANNEL`（`:467-480`）。
3. 政策：現讀，是 `never` 就拒絕（`:484`）。
4. 問人：native 下 await 等人服務（`:507-509`）。
5. 人答 `approve` 之後，把 1–3 照同一個順序再判一次（`:528-530`），因為等的期間政策可能切了。

稽核事件：

| 情況 | `approval/asked` | `approval/decided` |
| --- | --- | --- |
| 不必問人就確定（2、3） | C/approval.ts:335 | C/approval.ts:344 |
| 問了人 | pump，記 `interrupt/raised` 的同一刻（H/thread-pump.ts:3683、`:3804-3805`） | pump，收到答覆（`:3250`）或被收回（`:2417`）時（`:3714`） |

結局有四種：`allowed-once`、`rejected`、`cancelled`、`unavailable`（H/thread-pump.ts:3703-3714）。

輪界照 D253：停下來問時寫 `interrupt/raised`、`approval/asked`、`turn/end`；答覆時寫 `turn/start{resume}`、`approval/decided`，接著跑同一個呼叫。K8（#2358）已關，native 的行程內等待是 PR #2593。

在工具本體裡問人的（不經閘門）：`exit_plan_mode`（P/plan-mode/index.ts:565）、`request_sandbox_escalation`（P/sandbox-policy/sandbox-escalation.ts:394）、宿主頁工具（H/host-tools.ts:161）。升級工具發的中斷跟核准同一個形狀，所以 pump 也替它記核准的一對（H/thread-pump.ts:3664-3672）。

**核准本身沒有逾時。** 我自己核的：對 C/approval.ts、C/approval-policy.ts、C/human-input.ts、C/native-loop/suspension.ts grep `timeout|deadline|逾時|setTimeout`（不分大小寫），只命中 C/human-input.ts:88 一行註解，講的是工具時限在等人期間停表。pump 裡的 `setTimeout` 只有宿主頁工具那一支（H/thread-pump.ts:3173）。開著的核准會被兩件事收掉：使用者按停止，以及一輪的時鐘到點（`:3700` 的註解），兩者都記 `cancelled`。

**續接補結不處理核准。** 對 C/interrupted-turn.ts grep `approval|interrupt/`，沒有命中。

## 二、dsh 怎麼做、為什麼、代價（`8bd0733`）

### 2-1 機制

工具管線四段事件（`core/tools/src/events.ts:9-49`）：`tools/pre-execute`、`tools/execute`、`tools/post-execute` 是 waterfall，`tools/result` 是 emit。

- `tools/pre-execute` 的鏈底是 `allow`（`core/tools/src/pipeline.ts:199-202`）。決定只有 `allow`、`deny`、`cancel`、`ask` 四種，不能改寫參數，理由是參數已經記進日誌、也給人看過了（`core/tools/src/contracts.ts:348-361`）。
- 回 `ask` 就交給核准服務（`pipeline.ts:203-205`）。拿不到核准服務就拒絕（`:436-441`）。

核准服務（`interaction/user-approval/src/index.ts`）：

- 不在開著的一輪裡就拋錯（`:244-249`）。先寫 `approval/asked`，判完再寫 `approval/decided`（`:252-259`）。
- 政策是 `never` 就在服務裡直接回 `rejected`，不經任何監聽者（`:296-301`）。註解寫了理由：監聽者形狀的閘門保證不了「不論登記順序都拒絕」。
- 否則跑 `approval/request` 的 waterfall，鏈底是 `unavailable`（`:306-310`）。沒有人接、接的人拋錯、回了不認得的值，都是 `unavailable`，也就是拒絕。

### 2-2 跨出行程的只有「人的答覆」

- 能轉到遠端的 waterfall 只有白名單上的兩個：`approval/request` 與 `user-questions/request`（`api/remotes/src/remote-events.ts:27-59`）。
- `user-approval/src/index.ts:125`、`:225` 兩處註解寫明請求是 same-process 的：服務直接借用請求、agent、會話與活的 signal。
- 送到遠端的是 `{toolName, callId, reason}` 這類資料；參數不重送，靠 `callId` 對回已經給人看過的那一次呼叫。
- 瀏覽器斷線時，開著的請求不結案，重連後重送（`api/gateway/src/index.ts:734-738`）。
- 子代理的核准政策一律釘 `never`（`subagent/subagent/src/child-agent.ts:249-256`）。

`tools/*` 的 waterfall 沒有轉到遠端的路：payload 帶活的 agent 與 signal，白名單也不收它們。

有一個跑在別的行程的攔截：`experimental/hook-protocol` 用子行程跑使用者寫的 hook 指令。它是 fail-open：指令跑不起來不擋，那一輪照走（`experimental/hook-protocol/src/runner.ts:96-105`）。它沒有掛在任何出廠 profile 上（§2-3）。

### 2-3 出廠的五個 profile

`util/official-bundles/src/bundles.ts:10-26` 列出全部五個：acp、web、headless、sdk、sdk-minimal。

| profile | 核准服務 | 誰回答 |
| --- | --- | --- |
| acp、web、sdk | 有（`bundle/base/cordis.patch.yml:259-262`：全權模式是 `never`，其餘 `ask`） | ACP client、瀏覽器、SDK client |
| headless | 有 | 沒有人接，`ask` 變 `unavailable`，拒絕 |
| sdk-minimal | 沒有 | — |

**五個 profile 都沒有預設開啟、會否決工具呼叫的 `tools/pre-execute` 閘門。** 會否決的四個（auto-review、hooks-claude-code、hooks-codex、liveshare）都在 `experimental/` 底下；auto-review 與 liveshare 在預設關閉的選用清單上，兩個 hooks 沒有任何 bundle 掛。出廠路徑上會問人的，是工具本體裡的沙箱升級（`sandbox/sandbox/src/escalation.ts:172`）。

這一句的依據是子代理數的五份 patch，我自己核了 `bundles.ts` 與 base 的那四行；web-app 的 patch 有 601 行，是用 id grep 檢查的，沒有逐行讀（§十三）。

### 2-4 行程死在等核准的時候

- `tool/call` 在跑閘門之前就寫了（`core/tools/src/batch.ts:157-159`）。
- 重載時的修補不處理核准：對 `core/session/src/repair.ts` grep `approval`，沒有命中（我自己核的）。日誌會留下沒配對的 `approval/asked`，那顆呼叫補成「結果不明」，雖然本體其實沒跑。

### 2-5 為什麼、代價

- 為什麼：閘門就是訂閱事件的普通插件，組合靠 waterfall；核准的回答者用 waterfall 是為了「沒人接就拒絕」不用另外寫。dsh 沒有另一個行程要保護，所以沒有理由把決定搬出去。
- 代價：
  - 決定跟活物件綁在一起，搬不出行程；
  - 攔截者有沒有守規矩，全靠同一個行程裡的程式碼自律；
  - 等核准時死掉，日誌留下孤兒。

nexus 今天的形狀跟它相同：`gate` 是 waterfall、鏈底 `allow`、三格決定、同一行程。要自己定的是兩個行程之間誰做決定、誰的話算數。

## 三、切在哪一層

### 3-1 三案

- **(a) hook 全留葉子，組合行程按名字呼叫**。閘門、政策狀態、核准的判斷都還是 TS。終點時組合行程每次工具呼叫前向葉子問一次決定。
- **(b) 只搬決定**。Rust 做：閘門規則的判斷、管道與政策的判斷、人的答覆以誰為準、政策事件的驗證。插件的閘門改成宣告式的規則交給組合行程。追加訊息、提示詞段、包住執行、會寫事件的觀察者都留葉子。
- **(c) 全部用 Rust 重寫**。§1-2 的五類全部搬。

### 3-2 #2573 之前各能交付什麼

| 案 | 前段能交付的 |
| --- | --- |
| (a) | 沒有。loop 與 hook 都在葉子，沒有東西過界。這張卡等於併進 #2573 |
| (b) | 葉子的核准那一步改成問組合行程；人的答覆由組合行程記結局；核准與政策事件由組合行程對帳（§五）。追加訊息與包住執行的插件不動 |
| (c) | 跟 (b) 一樣多。其餘的重寫在前段沒有接線的地方：loop 在葉子，Rust 版的追加訊息沒有人叫 |

### 3-3 比較

| 標準 | (a) | (b) | (c) |
| --- | --- | --- | --- |
| 正確性 | 決定的規則只有 TS 一份 | 決定的規則兩份（Rust 給 `per-thread`，TS 給 `single` 與 CLI），靠同一批向量綁住（§八） | 插件的邏輯全部兩份，或 `single` 也改掉 |
| 失敗與恢復 | 葉子不在就沒人能決定，只能一律拒絕 | 葉子不在時組合行程仍能判規則；要問人的照樣能問，因為答覆不經葉子 | 同 (b) |
| 葉子被攻破 | 葉子回什麼算什麼。偽造一筆核准，日誌上看不出來 | 核准與政策的軌跡偽造不出來；終點時呼叫在決定之前不交給葉子。副作用仍擋不住（結論的表） | 多擋不到什麼：檔案與 MCP 的副作用還是在葉子做 |
| 效能 | 終點每次工具呼叫多一次來回 | 前段每次工具呼叫多一次來回；終點不多，決定就在 loop 旁邊 | 同 (b)；追加訊息少一次來回 |
| 維護成本 | 最低 | 規則的判斷函式、三位閘門改寫成規則、向量 | 8 位追加訊息與 4 位包裝各重寫一份，檔案系統、git、MCP 連線都要在 Rust 再接一次 |
| nexus 的需求（稽核、多人共用主機） | 稽核軌跡的可信度跟今天一樣 | 稽核軌跡不靠葉子自律 | 同 (b) |
| 基座做不做得到 | 能 | 能。要橋支援葉子向組合行程發請求、長時間掛著（§七） | 能，但插件留在 TS 是 D245 的前提 |

### 3-4 推薦 (b)

好在哪：

- **搬的正好是 ADR 說該放 Rust 的那種東西**：每次工具呼叫都會跑、出錯代價高。三位閘門今天都只看工具名與宣告（§1-2 甲），改成資料不損失表達力。
- **前段就有東西可以交付，而且終點不白做**。規則的判斷、答覆的權威、事件的對帳，#2573 之後原樣沿用；丟掉的只有葉子裡「問組合行程」的那一小段轉接。
- **不碰 K11–K13 還在改的檔**。pump 裡記核准的那幾行照舊，改的是組合行程收事件時多驗一件事。

兩個要講清楚的地方：

1. **`tools/execute` 的包裝不過橋。** 工具本體在葉子跑。終點時組合行程送「執行這個工具」給葉子，葉子在本地跑完包裝與本體再回結果。sandbox-policy 與 workspace-changes 的監聽者不用拆成前後兩則訊息。要改的只有一處：sandbox-policy 靠 AsyncLocalStorage 把委派那一刻的模式帶進子代理，終點時子代理的 loop 在組合行程，這一格要改成跟著子代理的 run 帶過去的資料（#2568 邊界形狀文件 §二 第 3 點）。
2. **追加訊息與提示詞段在終點是按名字的呼叫，不是政策。** 它們擋不下任何事。組合行程每一步向葉子要「這一步要追加的訊息與各段的文字」，一次來回拿齊。葉子不在時怎麼辦見 §九。

跟 dsh 的關係：dsh 沒有這條邊界。(b) 保住 dsh 的三個性質：鏈底是放行、政策是 `never` 時不經任何監聽者就拒絕、沒有人接就拒絕。跟 dsh 不同的一處：閘門從函式改成資料。dsh 的閘門能看參數、能做任意判斷；nexus 今天沒有一位用到，代價是將來要看參數的閘門得走 §4-2 的退路。

### 4-2 規則長什麼樣

三位閘門今天用到的判斷只有這些，規則就做到這麼多：

- 比對：工具名在一個名單裡、工具名有某個前綴、或「其餘全部」；可以帶一個豁免名單。
- 結果：`ask`（帶理由的文字）、`deny`（帶理由）、或交給下一條。
- 順序：照登記順序，第一條有結果的算數；都沒有就是放行。

**不做的**：看參數、看日誌、任意函式。需要這些的閘門走退路：`gate(listener)` 留著，`per-thread` 下組合行程按名字向葉子問。退路的答案在葉子被攻破時不算數，契約裡要寫明。

規則在一對交換 `hello` 時由葉子交出；MCP 重連之後工具清單會變，要能在 `hello` 之後更新（§七 的 B3）。

## 五、葉子被攻破或寫壞時

### 5-1 四個咽喉點

「擋得住」只成立在不在葉子手上的地方。逐一看：

| 咽喉點 | 今天在誰手上 | 這張之後 |
| --- | --- | --- |
| 日誌寫入 | #2571 之後是組合行程 | 接上「哪個來源能寫哪些種類」的表（5-3） |
| 人的答覆進來的路 | 前台連組合行程（D249 E），#2573 之前由它轉給葉子 | 組合行程記下結局再轉（§六） |
| 子行程的沙箱 | 葉子起 spawner、帶模式 | 不動。只搬這個沒有用：檔案工具根本不經 spawner（§1-4） |
| MCP 呼叫 | 葉子向宿主發 | 不動。要擋得宿主認得「這次呼叫有沒有核准」，是另一張卡 |

### 5-2 葉子不問就執行：只能事後發現

工具本體在葉子跑。被攻破的葉子可以不問、直接做事，然後寫一對正常的 `tool/call`、`tool/result`，或者乾脆不寫。

組合行程做得到的是對帳：它手上有規則，收到 `tool/result` 時看那顆呼叫的名字照規則該不該問；該問而它沒有發過 `allowed-once`，就記一筆違規。**記，不拒收**：拒收會把證據丟掉。記在哪照 D255 的判準：正常情形也會走到的進運作 log，否則進稽核。本篇推薦進稽核，因為守規矩的葉子走不到這條路；Q3 動工時要先確認葉子重起、事件晚到這類正常情形不會誤判。

終點時多一層：模型發的呼叫由組合行程分派，決定出來之前不交給葉子。但葉子自己起的副作用還是擋不住。

### 5-3 種類來源表怎麼接

#2571 研究 §3-3 留的表，初值是葉子全都能寫。這張分兩段改：

| 種類 | 前段 | 終點 |
| --- | --- | --- |
| `approval/asked` | 葉子能寫，但 `id`、`toolName`、`callId` 要對得上組合行程手上一筆開著的詢問 | 從葉子的清單拿掉 |
| `approval/decided` | 葉子能寫，但 `id` 要是開著的那一筆，`outcome` 要等於組合行程記下的結局 | 拿掉 |
| `approval/policy`、`sandbox/mode`、`permission/preset` | 葉子能寫；組合行程驗值域，並把自己手上的現值更新成這一顆 | 拿掉 |
| `interrupt/raised`、`turn/start`、`turn/end` 等輪界事件 | 不動 | 跟 loop 一起搬，歸 #2573 |
| `plan/mode`、`workspace/changes`、`deliverables/presented`、`user/message` | 不動 | 不動，葉子照寫 |

前段為什麼不直接拿掉：照 #2571 的 S，發號的是 loop 所在的行程。組合行程在葉子發號的串流中間插自己的事件，就要另一套搶號的協定。改成「驗它對不對得上」不用動發號，偽造同樣做不到。

不必問人就確定的那一對（C/approval.ts:335、`:344`）前段也照這張表：組合行程判出「拒絕」或「沒有管道」時記一筆已結的詢問，葉子寫的那一對要對得上。

### 5-4 政策切換：前段擋不住

`/permission` 的命令處理在葉子（P/permission-presets/index.ts:305）。前段組合行程只能驗一顆 `sandbox/mode` 的值合不合法，分不出這次切換是人下的，還是葉子自己編的。

兩種做法：

| 做法 | 前段 | 代價 |
| --- | --- | --- |
| (i) 前段只驗內容；終點把切換的入口搬到組合行程（它從上行認出命令，自己寫事件，再通知葉子） | 擋不住，但軌跡是真的：日誌上看得到切換 | 終點時 `commands` 這個插件要讓出這幾個命令 |
| (ii) 前段就搬入口 | 擋得住偽造的切換 | 現在就要動 `commands` 與前台的上行；而切過去之後，檔案政策還是葉子自己在執行（§1-4），擋住切換換不到實質的保護 |

推薦 (i)。理由就是 (ii) 代價欄的後半：沙箱模式的執行點在葉子，葉子被攻破時模式是什麼都不重要。

## 六、核准過界之後

### 6-1 問

前段：葉子的核准那一步（C/approval.ts:422）改成向組合行程發一個請求，帶工具名、參數、`callId`。組合行程照 §1-3 的 1–3 判：

- 放行、拒絕：當場回。
- 要問：記一筆開著的詢問（`id`、工具名、`callId`、理由），回「要問」與那個 `id`。葉子照今天的路發中斷、寫事件、把問題送上行。

`id` 由組合行程發。今天它是等人服務發的 32 位十六進位（C/native-loop/suspension.ts 的 `PendingAsk.id`）；改成由組合行程給，葉子原樣用。

終點：這一步就在組合行程裡，沒有請求。

### 6-2 等

前段的等在葉子（native 的行程內 await，D253）。組合行程不佔任何執行緒，只留那筆開著的詢問。

### 6-3 答

人的答覆經前台到組合行程。組合行程：

1. 找到開著的那一筆；找不到就回前台今天的 `no_such_interrupt`。
2. 記下結局：`approve` 是 `allowed-once`，`reject` 是 `rejected`，看不懂是 `unavailable`（照 H/thread-pump.ts:3703-3714）。
3. 轉給葉子。葉子照今天的路寫 `turn/start{resume}`、`approval/decided`；那顆 `decided` 要對得上第 2 步（§5-3）。

人答 `approve` 之後的補判（§1-3 第 5 步）也在組合行程：葉子再問一次，組合行程照現值判。

升級工具（`request_sandbox_escalation`）發的中斷同形，照同一條路。`exit_plan_mode` 與宿主頁工具是提問不是核准，不在這張表上，照舊。

### 6-4 逾時

不加。今天沒有，dsh 也沒有（對 `interaction/user-approval/src` 與 `api/remotes/src` grep `timeout|deadline`，沒有命中，我自己核的）。dsh 留著不結案的理由是瀏覽器重新整理的那一小段不該讓詢問失敗。

開著的詢問照今天由兩件事收：停止，以及一輪的時鐘。兩者前段都在葉子（pump），收的時候葉子寫 `approval/decided{cancelled}`，組合行程要先知道才驗得過。所以葉子收回詢問時先告訴組合行程，再寫事件。

### 6-5 葉子死掉時開著的核准

照 D253 的輪界，停下來問的那一刻已經寫了 `turn/end`。所以葉子死在等的時候，日誌上沒有開著的一輪，只有一筆沒配對的 `approval/asked`。

今天的續接補結不碰核准（§1-3）。dsh 也不碰（§2-4）。

組合行程照活，手上有那筆開著的詢問。兩種收法：

| 收法 | 做什麼 | 評 |
| --- | --- | --- |
| (i) 當場結案 | 組合行程寫 `approval/decided{cancelled}`，撤掉前台的那張卡 | 日誌乾淨；但葉子重起之後那個呼叫沒有人接，等於那一輪斷了 |
| (ii) 留著 | 詢問不結案，等葉子回來接 | 要先確認 native 下葉子重起之後接不接得回一顆停在核准點的呼叫 |

**這一題現在不選**。它取決於兩件還沒定的事：

- K13 要不要把核准改成「一輪不收」（D253 留到 #2363）。改了的話，葉子死在等的時候日誌上是開著的一輪，補結的規則整個不同。
- native 下「停在核准點重啟」實際怎麼接回。D254 的 web e2e 有這個情境，但我沒有讀它在行程死掉（不是正常停機）時走哪條路（§十三）。

在那之前，葉子死掉時照 #2571 的 V 做當場收尾，核准這一筆照今天留著不配對。

### 6-6 哪些現在做會白做

- **Rust 的「開著的核准怎麼收」**：等 K13 定輪界（§6-5）。
- **對輪界事件與核准事件相對順序的驗證**（例如「`decided` 一定在 `turn/start{resume}` 後面」）：同上。§5-3 只驗內容，不驗相對位置，就是為了不綁輪界。
- **為 `langgraph` 的中斷重跑設計過界**：那條路在圖內整段重跑、閘門會判兩次（C/approval.ts 的 `auditDecision` 註解），K13 就拿掉。
- **前段把追加訊息的插件改成過橋呼叫**：loop 還在葉子，沒有人在另一邊叫。

不會白做的：規則的格式與判斷、三位閘門改成規則、答覆的權威、事件內容的對帳。這些不看輪界。

## 七、對 #2583 那條橋的需求

D265 定的是只傳資料、雙向、多路、可巢狀。下面幾件沒有定過，寫成需求交 #2583 的實作定。編號接在 #2571 的 R1–R4 後面，用 B。

| 需求 | 為什麼 | 選項 | 推薦 |
| --- | --- | --- | --- |
| B1 葉子能主動向組合行程發請求，不只是在回答別人的請求途中 | 前段的核准請求是葉子起頭的 | (1) 兩個方向對等；(2) 只准巢狀 | (1)。#2571 的事件追加已經需要 |
| B2 請求沒有預設的時限 | 前段「問組合行程」的請求不掛人；但終點時組合行程叫葉子執行的工具可能在本體裡問人，一掛幾小時 | (1) 橋不設時限，由發請求的一方用取消框收；(2) 橋設時限、長的另外標 | (1) |

## 八、`single` 與 CLI

沒有監督行程，也就沒有組合行程。判斷照舊用 TS 的 `approvalGateToolStep`。

- 規則兩邊共用：插件登記的是同一份宣告式的規則，`per-thread` 交給組合行程，`single` 與 CLI 交給 TS 的判斷函式。
- 兩份實作靠一批共用的向量綁住：每筆是「規則、管道、政策、一次呼叫 → 決定與拒絕碼」。做法跟監督行程協定的向量檔一樣，兩種語言各讀同一份檔。
- CLI 的核准是關的（§1-5），只會走「管道是 `policy-never`」那一格，向量要有這一格。
- §五 的保證在 `single` 與 CLI 都不成立：只有一個行程，沒有誰可以對帳。這跟 #2571 的 X 同形。

## 九、插件契約要加的規則

卡上 PM 留言的兩條（issuecomment-6738200495），加上這份研究多出來的：

1. **撐得過葉子重起的狀態要在日誌裡。** 記憶體裡的會遺失。今天已經這樣做的：plan-mode、sandbox-policy、permission-presets、time-context 都從日誌事件折回狀態。要查的：present 那張「工具本體寫入、`onResult` 取出」的暫存表（P/present/index.ts:339）只活在一次呼叫裡，葉子死了那次呼叫本來就結果不明，不用改。
2. **葉子不在時 fail-closed。** 終點時下一個工具呼叫等葉子回來，有上限，超過回工具錯。追加訊息與提示詞段也一樣：葉子不在就不叫模型，不能當成「沒有要追加的」往下走。理由：sandbox-policy 的那一段在告訴模型檔案政策，少了它模型會照錯的假設做事。
3. **閘門用規則登記。** `gate(listener)` 留著當退路，文件寫明 `per-thread` 下它的答案在葉子被攻破時不算數。
4. **追加訊息與提示詞段的函式要能在一次呼叫裡回完**，不能依賴「同一步裡別的監聽者先跑過」的副作用。今天有一處這種依賴：plan-mode 的段要在它自己的 `pre-step` 交完待關之後才判（P/plan-mode/index.ts:603-604）。終點時按名字呼叫要保住這個先後，或把兩者併成一次呼叫。

契約的版號：加規則登記是新增，`2.12.0`；不拿掉 `gate(listener)` 就不是不相容變更，不需要升級指南。
