ADR 清單上有五項，nexus 沒有拍過要用 Rust。D235 R1 把其中三項（loop、日誌、政策）定成「在主機」，可是主機上有兩個行程：
- Rust 監督行程；
- Node 前台：C3 #2341 之後由它收 HTTP、轉送到對話行程。

葉子行程評估 §一的表格裡，「agent loop」那一列寫的就是「主機」兩個字。所以 R1 定了組合層放哪台機器，沒定用哪一種語言。

## 二、四方怎麼做

**dsh（`05b1cae8`）**
- 產品每一部分都是插件，包括模型適配器、工具註冊表、會話日誌與 agent loop（`docs/architecture.zh.md:9`）。
- 沒有特權內核，擴充靠把插件掛在旁邊（`docs/architecture.zh.md:11`）。
- 它在解決的問題：每一塊都能從設定替換。代價：所有東西在同一個 TS 行程，沒有整體的資源保險絲。
- 0.2.2-alpha.3（根 `package.json`），不收外部 PR（`CONTRIBUTING.md:9`）。ADR 拿這兩點當作不採用「全 TS」的理由之一，本篇核過屬實。

**rutis（本機 `921892d9`，`Cargo.toml` 版本 0.6.0）**
- 雙核永久：Rust 是脊柱，TS 跑完整的 dsh 棧，包括 agent loop（`docs/design-dual-core-2026-08-20.md:11-14`）。
- 2026-08-21 的修訂：loop 尚未收斂，按判據留 TS，不急著鏽化（同檔 `:6-7`、`:40-43`）。
- 鏽化判據：語意已收斂、是機制而非措辭、對效能或分發敏感、不綁 npm、或在信任邊界上（同檔 `:28-30`）。
- 「不做」清單有一條：loop 還沒收斂時不在 Rust 裡複刻它，因為雙份實作等於把追趕成本搬到自己身上（同檔 `:22-24`）。
- ADR 寫的是「0.21.0」，跟本機 clone 對不上。本篇沒讀上游，不判斷哪一個是新版。

**ADR**
- 宿主是 Rust，內含 loop、事件 log、政策 hook、LLM adapter（ADR〈名詞〉「宿主」、〈元件切分〉表）。
- 移動規則：TS plugin 成為熱路徑時移到 Rust；移動時不可改變服務名與方法形狀；用 trace 統計判斷，不憑經驗（ADR〈移動規則〉）。
- 跨邊界只用 emit 與 parallel，waterfall 只在 Rust 裡跑（ADR〈跨邊界契約〉「事件」列）。

**比較文件**
- 五款 harness 裡只有 Codex 是「Rust CLI + App Server」（〈並列比較表／架構與執行〉）。Codex 的 loop 在不在 Rust 裡，比較文件沒寫，本篇也沒查。
- 跟本題有關的建議：用 append-only 的 typed event log 當唯一的權威來源，context、UI、稽核都從 log 產生（〈決策表〉「狀態的權威來源」列）。
- 規則必須寫在程式裡，不能只寫在指令裡（〈三條跨維度原則〉）。

ADR 和 rutis 在「loop 放哪裡」上相反。差別在前提：
- rutis 的 loop 是 dsh 的 loop，不是它自己的，它不想追別人的變動。
- ADR 的使用情境是自建 harness，loop 是自己的。

nexus 的情況比較接近 ADR：#2336 做完以後，loop 是 nexus 自己寫的，沒有上游可追。

## 三、nexus 自己的條件

**1. 多人共用主機，組合層是共用的。** 葉子行程把 loop 從每條對話的行程搬到主機，主機上那一份要同時服務所有對話。容量照 Q6b，64 GiB 的主機約 155 條。

**2. Node 的單一事件迴圈有量過的上限。** C0（#1947 issuecomment-6601117039）量的是前台只做轉送的情況：
- 每輪 CPU 是 serve 的 13.2%；
- 推算 60–110 條同時串流吃滿一顆核。這是推論，不是實測滿載。

組合層要做的事比轉送多：推導訊息、組 prompt、壓縮、跑政策。如果把它放進一個共用的 Node 行程，會比轉送更早撞到這條線。要繞開，就得開多個 Node worker，再在 worker 之間分配對話。這樣等於又回到「每條對話一個行程」，只是名字換了。

**3. 一份組合層出錯，影響所有對話。** 共用的組合層崩潰時，所有對話一起停。ADR 把它放 Rust 的理由（「每次呼叫都會執行、而且出錯代價高的元件，放在 Rust」，ADR〈元件切分〉切分原則），在多人共用主機上比在單人桌機上更成立。

**4. 稽核與重建。** 公務機關客戶要能從紀錄重建每次模型請求。ADR 的「可驗證性」限制，跟比較文件「事件 log 是唯一權威來源」的建議，說的是同一件事。事件 log 放在 Rust 宿主，等於放在監督行程旁邊：對話行程崩潰時，紀錄仍由一個不會跟著崩潰的行程寫入。

**5. 要搬的量**（`7392e602`，不含測試，算法見附錄）：

| 範圍 | 檔數 | 行數 |
| --- | --- | --- |
| `packages/nexus-core/src`（含 `native-loop/`） | 143 | 43,794 |
| 其中 `native-loop/` | 8 | 2,168 |
| `packages/nexus-plugin-*` | 99 | 20,566 |
| 現有的 Rust（`native/**/*.rs`） | — | 7,730 |

`nexus-core` 裡最大的幾個檔是 `session-log.ts`（166.7K）、`summarization.ts`（127.3K）、`fold.ts`（121.8K）、`registry.ts`（110.8K）、`session-store.ts`（87.3K）。一次重寫，光核心就是現有 Rust 碼量的 5.7 倍，連插件是 8.3 倍；而且重寫期間 TS 那一份還在改。rutis 說的「雙份實作的追趕成本」就是這個。

**6. 攔截鏈。** 葉子行程評估 §四數過：至少 8 個插件套件掛在 `agentLoop.preStep` 或工具 middleware 上。ADR 規定 waterfall 只在 Rust 裡跑，所以 loop 搬到 Rust 時，這 8 個要麼搬進 Rust，要麼改寫成按名字呼叫的 RPC。這一點不管組合層選哪一種語言都一樣，只要組合層不在對話行程裡就躲不掉。

## 四、選項與比較

- **P1 一次重寫**：組合層（事件 log、loop、政策、LLM adapter、閘道）一次搬進 Rust 宿主。照 ADR 的終態，不照它的移動規則。
- **P2 組合層留 TS**：組合層放在主機上的 Node 行程（前台，或另一個共用行程），Rust 只做底座。照 rutis。
- **P3 終點 Rust、逐塊搬**：終點同 P1；搬法照 ADR〈移動規則〉加上 rutis 的鏽化判據，一次一塊，服務名與方法形狀不變。#2336 先做完，產出 TS 版的服務形狀。

| 標準 | P1 一次重寫 | P2 組合層留 TS | P3 終點 Rust、逐塊搬 |
| --- | --- | --- | --- |
| 正確性 | 組合語意只有一份，在 Rust；但重寫期間 TS 那份還在動，兩份要對齊 | 一份，在 TS；靠測試與規範維持 | 每搬一塊，那一塊的語意只剩 Rust 一份；沒搬的照舊 |
| 失敗與恢復 | 宿主是 Rust，共用的組合層崩潰機率最低 | 共用的 Node 行程崩潰，所有對話一起停 | 事件 log 先搬，紀錄先拿到最穩定的寫入者；loop 最後搬 |
| 效能 | 沒有單一事件迴圈的上限 | **撞 C0 的那條線**：60–110 條推算吃滿一核，小於容量 155 | 熱路徑照 trace 決定搬的順序；loop 搬之前，loop 仍在對話行程，不撞那條線 |
| 維護成本 | 最高：約 4.4 萬行核心加 8 個攔截插件同時重寫，兩份並存到切換為止 | 最低：一種語言 | 中：每次只有一塊有兩份，搬完就刪 |
| 產品需求（多人共用、稽核、內網、公務機關） | 最合 | 稽核可做；共用行程的爆炸半徑大 | 合；稽核那一塊（事件 log）最先到位 |
| 現有基座做不做得到 | 做不到：loop 還沒脫離 LangChain（#2336 OPEN） | 做得到 | 第一塊做得到：事件 log 的格式在 #2336 的 F2–F4（D168 Q4）之後定型 |

**選 P3。**
- 比 P1 好在兩點：不用同時維護兩份完整的組合層；而且每一步都能退回，這是 rutis〈決策〉第 1 條的做法。
- 比 P2 好在三點：效能有量過的上限；共用行程的爆炸半徑；稽核。
- P3 輸 P2 的地方是語言邊界：多一份跨邊界契約，除錯更難，ADR〈後果〉也列了。在多人共用主機上，這個代價換得到的東西比較多。

## 五、#2336 會不會白做

不會，理由有三：
1. ADR 的移動規則要求搬的時候「不可改變服務名與方法形狀」。#2336 正在定的就是這些形狀：nexus 自己的訊息型別（K2）、`@nexus/tools` 2.0（K3a）、middleware 遷成事件與服務（K7 #2357）。沒有這一步，Rust 那邊沒有東西可以對齊。
2. rutis 不在 Rust 裡複刻還沒收斂的 loop。#2336 做完之前，nexus 的 loop 也還沒收斂：K12 #2362 才會把 native loop 改成預設。
3. #2336 設計 §八的清單（六類 JS 函式、四種不可序列化的物件），就是 P3 每一塊要處理的邊界清單。

會受影響的只有一件事：#2336 之後的 TS 事件 log 要寫成「換一個寫入者也能讀」。D168 Q4 的格式升版已經是落盤格式，本篇沒有找到要改它的理由。
