# Rust 宿主死掉時對話不能一起斷（#2568 第二輪：重做第 2 題）

這是 #2568 的第二輪。#1827 D248 的 A 答「否」：

所以第一輪的 `.docs/rust-host-design-2568-2026-11-08.md`（PR #2578）裡，§四 與 §九 A 那個「接受一起斷」的推薦作廢。本篇重做第 2 題，再寫第 1、4、5、7、8 題要怎麼跟著改。第一輪那份文件不改寫。第 3、6 題照 D247，等 #2336 做完。

範圍照 D247：只讀程式碼，沒有量測，沒有下載，沒有改產品碼。版本是 nexus `origin/develop` `58ff9465`、dsh `8bd0733`（一律 `git show 8bd0733:`）。

## 結論

**推薦**：主機級的 Rust 宿主只放全機共用的服務：MCP 連線池、模型請求並行閘、插件版本登記、搜尋索引、釘選封存。組合層（loop、事件 log、政策）不進宿主，終點是**每條 thread 一個 Rust 組合行程**，跟那條 thread 的 Node 葉子行程分開。

照這個做法，宿主死的時候：
- 正在跑的 turn 不斷；
- 正在串流的回覆繼續出字；
- 等宿主服務的那一步會暫停，宿主回來之後接著跑；
- 只有正在跑的那一次 MCP 工具呼叫會回「結果不明」，交給模型判斷。

這會改到 D245 Q1b，以及 D235 R1 的措辭，寫成 §七 的是非題 D、E。D245 Q1a（終點用 Rust）不變，但支撐它的理由少了一條：「單一事件迴圈的上限」在每條 thread 一份的形狀下不再成立（§五）。

## 一、基準：今天前台死了，對話不斷

這個要求今天的前台已經做到。#1947 設計的判準是「前台死了，監督行程重起它；對話行程照跑，web 重連即可」（`.docs/supervisor-1947-design-2026-11-03.md:77`），C3 的驗收是「前台被殺，監督行程重起它，活著的對話行程不中斷，web 重連後繼續」（同檔 `:338`）。

前台做得到這件事，靠兩個條件：
1. 正在跑的 turn 不在前台裡；
2. 前台裡沒有那一輪每一步都要等它回答的東西。

第一輪推薦把 loop、事件 log、政策都搬進宿主，兩個條件都不成立：每一步都要經過宿主，宿主一死，所有 turn 一起停。所以 A 答否之後，問題變成：**宿主要怎麼做，才能跟今天的前台一樣，死了對話不斷。**

dsh 沒有對應的做法。dsh 的 host 一死，所有對話一起停，靠 flock 租約加上 log 修補收尾（`packages/session/session-persistence-jsonl/src/lease.ts:1-13`、`packages/core/session/src/repair.ts:14-35@8bd0733`）。這是單人桌機的取捨，不適用 nexus 的多人共用伺服器。

dsh 有一處局部的先例：MCP 斷線時，loop 不停，只有呼叫那一支工具時回錯，重連之後同一條 session 又叫得動（`packages/mcp/mcp-client/src/connection.ts:228-234`、`:354@8bd0733`）。nexus 的 MCP 連線池照搬了這條（`packages/nexus-plugin-mcp/src/pool.ts:22-24`）。下面 (b2)、(c) 都把這個先例推廣到宿主的每一項服務。

## 二、五條路

- **(a) 宿主分片**：每 N 條 thread 一個宿主，組合層照第一輪放在宿主裡。
- **(b) loop 留在 Node 對話行程，宿主等服務恢復**：PM 指定要看的那一條，分兩個子案：
  - **(b1)** 事件 log、政策、MCP、並行閘都照第一輪放在宿主。宿主不在時，對話行程先把事件暫存在記憶體，政策判斷等宿主回來；
  - **(b2)** 只把全機共用的服務放進宿主：MCP、並行閘、版本登記、搜尋、釘選封存。事件 log 與政策照今天，留在對話行程。
- **(c) 每條 thread 一個 Rust 組合行程**：組合層（loop、事件 log、政策）用 Rust 寫，一條 thread 一個行程，跟那條 thread 的 Node 葉子行程（TS 插件與工具）分開。主機級宿主同 (b2)。
- **(c′) 每條 thread 一個 Node 組合行程**：同 (c)，只是組合層用 TS 寫。拿來對照：(c) 跟 (c′) 的差別只在語言。
- **(d) loop 在宿主，宿主重起後自動續跑**：照第一輪，但每一步先落盤。宿主重起後，從 log 找出開著的 turn，從最後一個落盤的步驟續跑。

## 三、宿主死的時候，正在跑的 turn 會怎樣、網頁上看到什麼

| | 正在跑的 turn | 網頁上看到 |
| --- | --- | --- |
| (a) 分片 | 那一片的 N 條：中斷，照 dsh 修補收尾；其他片照跑 | 那一片的使用者看到回覆停住、標「中斷」，要自己重送；其他人沒感覺 |
| (b1) | 暫停：每一步工具呼叫都要過政策，政策在宿主，所以所有 thread 的下一個工具呼叫一起卡住，等宿主回來才接著跑。純文字的串流可以繼續出字，事件先暫存 | 所有人的工具呼叫一起停住，宿主回來後一起接著跑 |
| (b2)、(c)、(c′) | 不斷。已經拿到名額的模型串流照跑；要新名額的那一步暫停，等宿主回來；MCP 呼叫回錯或「結果不明」 | 字照樣出，或停幾秒再接著出；MCP 工具那一格顯示錯誤，模型自己決定重試 |
| (d) 宿主重起後續跑 | 所有 turn 一起停，宿主回來後從最後落盤的步驟重送模型請求 | 所有人的回覆一起停；已經出現的半句被收掉、從頭再出；那一刻正在跑的工具標「結果不明」 |

**(b1) 的兩個問題**：
1. **政策要 fail-closed。** 宿主不在時，不能放工具過去，所以所有 thread 的工具呼叫一起卡住。turn 沒斷，但所有人一起停，跟 D248 要避免的情況只差在「停」與「斷」。
2. **暫存的事件會丟。** 宿主不在的那段時間，事件只在對話行程的記憶體裡。這段期間對話行程如果也死了，這些事件就丟了，稽核出現缺口。#2562 理由 5 要的是「寫入者不跟著崩潰」，(b1) 在這段空窗裡反而沒有寫入者。

所以 (b) 推薦 (b2)：事件 log 與政策不能放進一個會死、所有 thread 又都要等它的行程裡。

(b2)、(c)、(c′) 在宿主不在時，各項服務的處置：

| 服務 | 宿主不在時 | 依據 |
| --- | --- | --- |
| 模型請求並行閘 | 已經拿到名額的請求照跑，模型串流在 thread 自己的行程裡。要新名額的那一步排隊等宿主回來，等待時間算在既有的 `maxWaitMs` 裡，超過就照今天的 `LOCAL_CAPACITY` 處理。宿主重起後，各 thread 回報自己握著幾個名額，宿主據此重建計數 | `apps/harness/src/request-gate.ts:22-31`：閘只活在記憶體，排隊者聽中止訊號，逾時拋 `LOCAL_CAPACITY`、不送請求 |
| MCP 工具 | stdio 伺服器是宿主那支 spawner 的子行程，宿主死了它跟著走。正在跑的那一次呼叫回「結果不明」，空窗期的新呼叫回「伺服器斷線」，宿主回來重連之後叫得動。Streamable HTTP 的伺服器本身不受影響，只有連線要重建 | `pool.ts:22-24` 的斷線空窗規則；「結果不明」的措辭照 dsh `repair.ts:34@8bd0733` |
| 事件 log | 不經宿主，thread 自己寫，照舊 | §五 |
| 政策 | 不經宿主，thread 自己判 | §五 |
| 搜尋、`@` 候選、釘選封存、列 thread | 前台對這幾個請求回 503，web 顯示「暫時無法取得」；對話本身不受影響 | 第一輪 §八 把它們搬進宿主 |
| 插件版本登記 | 正在跑的 thread 照用已經綁好的版本；空窗期要新開的 thread 等宿主回來 | #2569 |

**這幾條路也有會失敗的情況**：
- 宿主停太久（超過 `maxWaitMs`），要新名額的那一步會失敗，跟今天閘滿了等不到一樣。所以宿主的重起退避要比 `maxWaitMs` 短。兩個數字都沒定，跟 #2523 一起定。
- 正在跑的那一次 MCP 呼叫會失去結果。要讓 MCP stdio 伺服器撐過宿主重起，得把它們的 stdio 管道交給宿主以外的行程保管，例如由監督行程起 spawner，再用 `SCM_RIGHTS` 把 fd 交回給重起後的宿主。這太複雜，本篇不推薦，記在 §八。

| --- | --- | --- | --- | --- | --- |
| 合不合 D248 | 部分：每一片的 N 條還是一起斷 | 合 | 合 | 合 | 不合：所有人的回覆一起停、一起重出 |
| 正確性 | 跟第一輪相同 | 每項服務都要定義「宿主不在時」怎麼辦（§三） | 同 (b2) | 同 (b2) | 每一步都要先落盤；重送模型請求，結果跟原本那次不同，還多付一次錢 |

| #2562 的三個理由（§五） | 理由 2 減輕；3、5 同第一輪 | 2 消失；3 縮成一條 thread；5 不成立：事件 log 跟 TS 插件同行程 | 三個都保住 | 三個都保住 | 同第一輪 |
| 行程數 | 加 ⌈thread 數／N⌉ 個 | 同第一輪 | 每條 thread 多一個 Rust 行程，**沒量** | 每條 thread 多一個 Node 行程，**沒量** | 同第一輪 |
| 維護 | 要寫分片路由 | 最少：今天的 loop 就在對話行程（#2336 的 native loop） | 要寫 Rust 組合層，加上它跟葉子行程之間的橋（第 6 題） | 要把今天的組合層跟 TS 插件拆成兩個行程，加上橋（第 6 題）；一種語言 | 要寫續跑，加上「每一步先落盤」的保證 |
| 現有基座 | 第一輪規劃的延伸 | 今天的形狀，加一個宿主 | 要等 #2336 收斂、第 6 題定下來 | 同 (c)，但不用重寫 | 今天沒有 |

**推薦：終點選 (c)，過渡期走 (b2)。**

- 合 D248、又保住 #2562 三個理由的，是 (c) 和 (c′)。也就是說，**在每條 thread 一份的形狀下，#2562 的三個理由分不出語言**，選 Rust 要另外有理由。理由見下。
- (b2) 是 (c) 之前必經的一段：把全機共用的服務先搬進宿主，組合層暫時留在今天的對話行程。(b2) 跟 (c) 對宿主的要求完全一樣，過渡期做的宿主到終點不用重做。

**(c) 比 (c′) 好在哪**：
1. **ADR〈元件切分〉的切分原則**：「每次呼叫都會執行、而且出錯代價高的元件，放在 Rust」（`.docs/core-base-rust-reeval-2026-11-08.md:104` 引）。組合層正是這種元件。這條原則不依賴形狀，per-thread 下照樣成立。
2. **這條線的目標**：demian 2026-11-08 定的範圍是「harness 的核心底座轉 rust (like cordis)」（D246），D245 Q1a 定了組合層的終點用 Rust。(c′) 等於撤回 Q1a。
3. **每條 thread 多一個行程的成本**：(c′) 多的是一個 V8，(c) 多的是一個 Rust 行程。推論 (c) 比較小，**沒量**，D166 的容量要重估時兩個都要量。

(c) 輸 (c′) 的地方：要用 Rust 重寫組合層（#2562 附錄算的上限約 4.4 萬行），而且語言邊界上多一份跨界契約。這是 D245 拍板時就接受的代價（#2562 §四「P3 輸 P2 的地方是語言邊界」）。

## 五、跟 #2562 的理由對帳

D245 Q1a、Q1b 依據的是 #2562 §三 的三個理由（`.docs/core-base-rust-reeval-2026-11-08.md:98-119`）。逐條看 (c)：

1. **理由 2，單一事件迴圈的上限**：共用的 Node 組合層會撞到單一事件迴圈的上限。(c) 的組合層一條 thread 一份、不共用，這條**不再成立**。它原本是 Q1a「用 Rust」的理由之一；per-thread 之後，Q1a 只剩理由 3、5 和 ADR 的切分原則支撐。
2. **理由 3，共用組合層出錯，影響所有對話**：(c) 的組合層出錯只影響那一條 thread。這也是 D248 要的。
3. **理由 5，稽核要一個不跟著對話行程崩潰的寫入者**：(c) 的事件 log 由 Rust 組合行程寫，跟 TS 插件與工具所在的葉子行程分開。葉子行程崩潰，寫入者還在，可以照 dsh `repair.ts` 收尾，把那一步標成「結果不明」。這正是 D235 R1「對話行程的終點是只裝工具的葉子行程」要的分離，差別只在寫入者是每條 thread 一個，不是全機一個。

**付出的代價**：
- 每條 thread 多一個行程。記憶體沒量，D166 的容量（64 GiB 約 155 條）要重估。
- 第一輪 §八 有一項好處要重做：「宿主是 log 的寫入者，讀得到還沒落盤的那一句」。(c) 下宿主不寫 log，搜尋要讀到最新的那一句，得改成由各 thread 把事件推給宿主。前台今天已經收對話行程推來的事件（`front-turn-failures.ts`），走同一種方式。
- 寫入租約照舊是今天的 `session.lock`（`apps/harness/src/session-lease.ts`），持有者從 Node 對話行程換成 Rust 組合行程。
