# Rust 宿主死掉時對話不能一起斷（#2568 第二輪：重做第 2 題）

這是 #2568 的第二輪。#1827 D248 的 A 答「否」：

> 不能所有正在跑的對話都斷，因為此項目不像 dsh 裝在每個人的電腦裡，我的項目是裝在 server 每個人透過網頁訪問

所以第一輪的 `.docs/rust-host-design-2568-2026-11-08.md`（PR #2578）裡，§四 與 §九 A 那個「接受一起斷」的推薦作廢。本篇重做第 2 題，再寫第 1、4、5、7、8 題要怎麼跟著改。第一輪那份文件不改寫。第 3、6 題照 D247，等 #2336 做完。

範圍照 D247：只讀程式碼，沒有量測，沒有下載，沒有改產品碼。版本是 nexus `origin/develop` `58ff9465`、dsh `8bd0733`（一律 `git show 8bd0733:`）。

## 結論

**推薦**：主機級的 Rust 宿主只放全機共用、而且沒有它 turn 也能往下走的服務：MCP 連線池、插件版本登記、搜尋索引、釘選封存。模型請求並行閘每一步都要用，不放宿主，改放監督行程（§三之二）。組合層（loop、事件 log、政策）不進宿主，終點是**每條 thread 一個 Rust 組合行程**，跟那條 thread 的 Node 葉子行程分開。

照這個做法，宿主死的時候：
- 正在跑的 turn 不斷；
- 正在串流的回覆繼續出字；
- 模型請求不經宿主（閘在監督行程），不受影響；
- 新的 MCP 呼叫停下來等宿主回來（有上限），回來後接著跑；
- 只有正在跑的那一次 MCP 工具呼叫會回「結果不明」，交給模型判斷；這不會讓 turn 失敗。

這會改到 D245 Q1b、D235 R1 的措辭，以及 #1948 Q21 的「並行上限在主機級的樹」，寫成 §七 的是非題 D、E、F。D245 Q1a（終點用 Rust）不變，但支撐它的理由少了一條：「單一事件迴圈的上限」在每條 thread 一份的形狀下不再成立（§五）。

## 一、基準：今天前台死了，對話不斷

這個要求今天的前台已經做到。#1947 設計的判準是「前台死了，監督行程重起它；對話行程照跑，web 重連即可」（`.docs/supervisor-1947-design-2026-11-03.md:77`），C3 的驗收是「前台被殺，監督行程重起它，活著的對話行程不中斷，web 重連後繼續」（同檔 `:338`）。

前台做得到這件事，靠兩個條件：
1. 正在跑的 turn 不在前台裡；
2. 前台裡沒有那一輪每一步都要等它回答的東西。

第一輪推薦把 loop、事件 log、政策都搬進宿主，兩個條件都不成立：每一步都要經過宿主，宿主一死，所有 turn 一起停。所以 A 答否之後，問題變成：**宿主要怎麼做，才能跟今天的前台一樣，死了對話不斷。**

dsh 沒有對應的做法。dsh 的 host 一死，所有對話一起停，靠 flock 租約加上 log 修補收尾（`packages/session/session-persistence-jsonl/src/lease.ts:1-13`、`packages/core/session/src/repair.ts:14-35@8bd0733`）。這是單人桌機的取捨，不適用 nexus 的多人共用伺服器。

dsh 有一處局部的先例：MCP 斷線時，loop 不停，只有呼叫那一支工具時回錯，重連之後同一條 session 又叫得動（`packages/mcp/mcp-client/src/connection.ts:228-234`、`:354@8bd0733`）。nexus 的 MCP 連線池照搬了這條（`packages/nexus-plugin-mcp/src/pool.ts:22-24`）。下面 (b2)、(c) 都把這個先例推廣到宿主的每一項服務。

## 二、五條路

- **(a) 宿主分片**：每 N 條 thread 一個宿主，組合層照第一輪放在宿主裡。
- **(b) loop 留在 Node 對話行程，宿主等服務恢復**：PM 指定要看的那一條，分兩個子案：
  - **(b1)** 事件 log、政策、MCP、並行閘都照第一輪放在宿主。宿主不在時，對話行程先把事件暫存在記憶體，政策判斷等宿主回來；
  - **(b2)** 只把全機共用的服務放進宿主：MCP、版本登記、搜尋、釘選封存；並行閘的位置見 §三之二。事件 log 與政策照今天，留在對話行程。
- **(c) 每條 thread 一個 Rust 組合行程**：組合層（loop、事件 log、政策）用 Rust 寫，一條 thread 一個行程，跟那條 thread 的 Node 葉子行程（TS 插件與工具）分開。主機級宿主同 (b2)。
- **(c′) 每條 thread 一個 Node 組合行程**：同 (c)，只是組合層用 TS 寫。拿來對照：(c) 跟 (c′) 的差別只在語言。
- **(d) loop 在宿主，宿主重起後自動續跑**：照第一輪，但每一步先落盤。宿主重起後，從 log 找出開著的 turn，從最後一個落盤的步驟續跑。

## 三、宿主死的時候，正在跑的 turn 會怎樣、網頁上看到什麼

**用同一把尺**：下面把宿主空窗期的結果分成三種。
- **斷**：turn 失敗。
- **停**：有上限的等待，等完接著跑。
- **降級**：模型收到一個工具錯，turn 繼續。

分得出這三種，靠的是兩個事實：
- **模型請求失敗會讓這一輪失敗**。失敗分類器把它寫成 `turn/failed.error`，`LOCAL_CAPACITY` 也在表上，而且不在可重試碼裡（`apps/harness/src/live-model.ts:2006-2007`、`:2029`）。
- **工具失敗不會讓這一輪失敗**。圍堵把工具拋的錯翻成給模型的回饋（`packages/nexus-core/src/containment.ts:1-3`）。

D248 不能接受的是「所有人一起斷」。「停」與「降級」波及所有人時也要寫明，拿範圍與上限來比。

| | 正在跑的 turn | 網頁上看到 |
| --- | --- | --- |
| (a) 分片 | 那一片的 N 條：中斷，照 dsh 修補收尾；其他片照跑 | 那一片的使用者看到回覆停住、標「中斷」，要自己重送；其他人沒感覺 |
| (b1) | 暫停：每一步工具呼叫都要過政策，政策在宿主，所以所有 thread 的下一個工具呼叫一起卡住，等宿主回來才接著跑。純文字的串流可以繼續出字，事件先暫存 | 所有人的工具呼叫一起停住，宿主回來後一起接著跑 |
| (b2)、(c)、(c′)，閘照 §三之二 (G3) 放監督行程 | 不斷。模型請求不經宿主；新的 MCP 呼叫等宿主回來（有上限）；正在跑的那一次 MCP 呼叫回「結果不明」 | 字照樣出；用到 MCP 的那一步停幾秒再接著跑；正在跑的那一格 MCP 顯示「結果不明」，模型自己決定 |
| 同上，但閘放在宿主 | 所有 thread 在下一次模型請求一起停；空窗超過 `maxWaitMs` 就一起以 `LOCAL_CAPACITY` 失敗（§三之二） | 所有人一起停；最壞一起失敗 |
| (d) 宿主重起後續跑 | 所有 turn 一起停，宿主回來後從最後落盤的步驟重送模型請求 | 所有人的回覆一起停；已經出現的半句被收掉、從頭再出；那一刻正在跑的工具標「結果不明」 |

**(b1) 的兩個問題**：
1. **擋住的範圍是每一支工具。** 政策要 fail-closed：宿主不在時，不能放工具過去。所以所有 thread 的每一支工具（不只 MCP）都會在宿主空窗時停住。等待加了上限，就是「停→降級」，不是斷；不加上限，就沒有盡頭。(b2) 下會停的只有 MCP 呼叫，範圍小得多。
2. **暫存的事件會丟。** 宿主不在的那段時間，事件只在對話行程的記憶體裡。這段期間對話行程如果也死了，這些事件就丟了，稽核出現缺口。#2562 理由 5 要的是「寫入者不跟著崩潰」，(b1) 在這段空窗裡反而沒有寫入者。

所以 (b) 推薦 (b2)：事件 log 與政策不能放進一個會死、所有 thread 又都要等它的行程裡。

(b2)、(c)、(c′) 在宿主不在時，各項服務的處置：

| 服務 | 宿主不在時 | 依據 |
| --- | --- | --- |
| 模型請求並行閘 | 照 §三之二 (G3) 放在監督行程，不經宿主，宿主死了不受影響。若照第一輪放在宿主：所有 thread 的下一次模型請求一起等宿主，空窗超過 `maxWaitMs` 一起失敗 | §三之二 |
| MCP 工具 | stdio 伺服器是宿主那支 spawner 的子行程，宿主死了它跟著走。正在跑的那一次呼叫回「結果不明」；空窗期的新呼叫先等宿主重連（有上限），超過才回「伺服器斷線」。工具錯由圍堵翻成給模型的回饋，turn 不失敗。Streamable HTTP 的伺服器本身不受影響，只有連線要重建 | `pool.ts:22-24`；`containment.ts:1-3`；「結果不明」的措辭照 dsh `repair.ts:34@8bd0733`；§三之二 |
| 事件 log | 不經宿主，thread 自己寫，照舊 | §五 |
| 政策 | 不經宿主，thread 自己判 | §五 |
| 搜尋、`@` 候選、釘選封存、列 thread | 前台對這幾個請求回 503，web 顯示「暫時無法取得」；對話本身不受影響 | 第一輪 §八 把它們搬進宿主 |
| 插件版本登記 | 不經宿主，不受影響 | D264；`.docs/rust-host-boundary-shape-2568-2026-11-09.md` §四 |

**這幾條路也有會失敗的情況**：
- 宿主停太久，超過 MCP 等待的上限，新的 MCP 呼叫會回錯給模型（turn 不失敗）。宿主的重起退避要比這個上限短，兩個數字都沒定，跟 #2523 一起定。
- 正在跑的那一次 MCP 呼叫會失去結果。要讓 MCP stdio 伺服器撐過宿主重起，得把它們的 stdio 管道交給宿主以外的行程保管，例如由監督行程起 spawner，再用 `SCM_RIGHTS` 把 fd 交回給重起後的宿主。這太複雜，本篇不推薦，記在 §八。

## 三之二、並行閘與 MCP：用同一把尺重看

PM 審 #2579 時指出：批評 (b1) 用的尺是「所有人一起停」，§三 卻沒有拿同一把尺量 (b2)、(c)。本節補上。

### 並行閘放在宿主會怎樣

先看閘今天怎麼運作（`origin/develop` `58ff9465`）：

- **閘是選配的**。沒設 `maxConcurrentRequests` 就不建（`apps/harness/src/request-gate.ts:186-196`），出廠的 serve 沒有閘。沒有閘時，宿主死不死都不影響模型請求。下面講的是**設了閘**的部署。
- **每一次模型請求都要先拿一個名額**。名額掛在模型類別的三個呼叫方法上，每一次嘗試各拿各的（`apps/harness/src/gated-chat-openai.ts:1-27`）。
- **串流期間一直握著**，到 `yield*` 結束才還；按停止的那一刻也還（同檔 `:26-28`、`#enter`）。
- **排隊照 FIFO**。等超過 `maxWaitMs` 就拋 `LOCAL_CAPACITY`，請求不送出（`request-gate.ts:24-31`）。`maxWaitMs` 預設 60 秒（`apps/harness/src/settings/live-model.ts:184`）。
- **per-thread 下，今天每個行程各有一份閘**。#2576 已經把這件事宣告成退步：「並行上限只數自己那條」。要恢復成全機一份，一定要有一個跨行程的仲裁者。

照 (b2)、(c) 把閘放進宿主，宿主不在的時候：
- 已經握著名額的串流照跑，因為串流在 thread 自己的行程裡；
- **但每一條 thread 的下一次模型請求都要等宿主**。一輪裡每一步都要一次模型請求，所以所有 thread 會在各自的下一步一起停住；
- 空窗超過 `maxWaitMs`（崩潰迴圈、退避拉長），這些 turn 會**一起以 `LOCAL_CAPACITY` 失敗**（模型請求失敗會讓整輪失敗，見 §三 開頭），等於所有正在跑的對話一起斷，正好違反 D248。

所以 §三 那句「字照樣出，或停幾秒」寫得不完整。閘放在宿主，跟 (b1) 是同一類問題，只是卡在模型請求，不是卡在工具呼叫。下面比三種做法。

### 選項

- **(G1) 閘留在宿主，宿主不在時降級成本地上限**：空窗期每條 thread 改用本地上限，fail-open，但有上限。
- **(G2) 閘不靠任何行程，用 flock 名額檔**：N 個名額檔，各自用 flock 鎖。持有者一死，核心就釋放，不需要活著的協調者，跟 dsh 的 lease 同一個道理。
- **(G3) 閘放在監督行程**：計數與排隊放進監督行程，thread 經既有的控制管道取名額、還名額。

**(G1) 上限怎麼分、宿主回來怎麼收斂**

上限有兩種分法：
- **每條 thread 本地上限 1**。一條 thread 的主迴圈是一步接一步跑的，1 夠它往前走，但同一步的子代理會排隊。全機總數最多等於活著的 thread 數，D166 的容量是 64 GiB 約 155 條。這遠超過管理者設的上限，而設上限本來就是要保護全機共用的那份供應商配額。超出去會撞 429，交給重試層退避。
- **照宿主最後一次分配的份額**：宿主活著時，持續告訴每條 thread「你最多可以自己用幾個」。份額要加起來不超過上限，所以 thread 一多，每條分到 0，等於沒降級。

宿主回來時怎麼收斂：各 thread 回報自己握著幾個名額，宿主據此重建計數。計數可能已經超過上限，這時宿主不搶回名額，只是先不發新的，直到在跑的數量降回上限以下。

**(G2) 讀程式碼確認的事**

- **串流期間一直握著**：握著 fd 就是握著鎖，做得到。
- **中止時釋放**：關掉 fd 就放鎖，做得到。
- **持有者死了自動釋放**：核心會放，這正是 G2 要的性質。
- **FIFO 保不住**：nexus 今天只會拿非阻塞的 flock（`apps/harness/src/kernel-file-lock.ts:1-8`）。拿不到就只能輪詢 N 個檔，沒有跨檔的公平佇列，輪詢得勤的那條 thread 先拿到。阻塞式 flock 只能在單一檔上等，而且核心不保證喚醒順序。#1505 選 FIFO 的理由是「一條失控 thread 後來的請求排在別人已經在排的後面」（`request-gate.ts:26`），G2 做不到這一點。
- **Node 自己拿不了 flock**：今天每拿一次鎖，就起一次 `nexus-sandbox-spawner --flock`（`kernel-file-lock.ts:17-20`）。用在模型請求上，等於每一次嘗試都多起一個行程。到了 (c)，Rust 組合行程可以直接呼叫 `flock(2)`，這一點才消失。
- **平台不是差別**：靠 spawner 拿 flock 只在 Linux 做得到，但 per-thread 本身就只在 Linux 起得來（`apps/harness/src/process-launcher.ts:375-377`，監督行程要 signalfd、`/proc` 與 `PR_SET_PDEATHSIG`）。三案都只在 per-thread 下有意義。
- **改上限**：N 是檔案數，所有行程要看到同一個 N，改設定要整台重起。

**(G3) 為什麼監督行程放得下**

- **它本來就做容量准入**。同時活著的對話行程數已經由監督行程管，名額滿了就排隊，回 `capacity`（`native/sandbox-spawner/src/supervisor/mod.rs:15-27`，設計 §七）。模型請求的並行上限是同一類工作，所以「監督行程只管控制面」那條規則不用改。
- **不多出新的「一起斷」**。監督行程死了，所有行程本來就會靠 PDEATHSIG 一起走（`process.rs:31-56`），閘放進去不會多一個讓所有人一起斷的點。
- **持有者死了自動釋放，也保住 FIFO**。監督行程靠 SIGCHLD 收子行程，收到時把那個行程握著的名額全部還回去，效果跟 flock 的自動釋放一樣。排隊在監督行程的記憶體裡，FIFO 照今天的做法。
- **中止**：thread 送一個取消框，監督行程把它從佇列拿掉，或把名額收回。
- **串流期間握著**：不送還名額的框，名額就一直握著。
- **代價**：每一次模型請求，在既有的控制管道上多一個來回，延遲**沒量**。監督行程多兩種訊息，加上一個計數器和一個佇列，每則訊息都是 O(1)，單執行緒也撐得住，但這是推論，**沒量**。另外，輸入是我們自己行程送的框，不是外部的 HTTP，攻擊面不變。

| 標準 | (G1) 宿主＋本地降級 | (G2) flock 名額檔 | (G3) 監督行程 |
| --- | --- | --- | --- |
| 宿主死時 | 不一起停；空窗期上限失守，最多到 thread 數 | 不受影響 | 不受影響 |
| 持有者死時 | 宿主要從連線斷掉推出名額釋放 | 核心自動釋放 | SIGCHLD 時釋放 |
| FIFO | 宿主在時保住，空窗期沒有 | 保不住 | 保住 |
| 每次請求的成本 | 一個 socket 來回 | 過渡期多起一個 spawner；(c) 下是一次系統呼叫 | 一個管道來回 |
| 要不要等宿主落地 | 要 | 不用 | 不用：今天的 per-thread 就能做，也順便收掉 #2576 宣告的「並行上限只數自己那條」 |
| 維護 | 兩套語意：正常與降級 | 名額檔目錄、N 的一致性 | 監督行程多兩種訊息 |
| 改到的拍板 | 無 | 無 | #1948 Q21「並行上限在主機級的樹」（已帶進 #2569） |

`single` 模式沒有監督行程、也沒有宿主，三案都不適用，照舊用行程內的 `RequestGate`。

**推薦 (G3)。** 只有它同時做到三件事：宿主死了不影響、持有者死了自動釋放、FIFO 保住。G1 在空窗期把上限本身放掉了；G2 把 #1505 選 FIFO 的理由放掉了。G3 要改的是 #1948 Q21 的一部分，寫成 §七 的是非題 F。dsh 沒有跨 session 的並行閘（`request-gate.ts:7-9` 的偏離登記），所以這一題沒有 dsh 的對照。

### MCP 用同一把尺

宿主不在時，**所有 thread 的 MCP 呼叫會一起失敗**：
- 正在跑的那一次回「結果不明」；
- 空窗期的新呼叫回 `server is disconnected`（`packages/nexus-plugin-mcp/src/index.ts:616-638`）。

**turn 本身不會因此失敗。** 工具拋的錯由圍堵翻成給模型的回饋，不讓整輪死掉（`packages/nexus-core/src/containment.ts:1-3`）；dsh 也一樣，「调用失败但不终止当前轮次」（同檔引 dsh `docs/subsystems/tools.zh.md:404`）。

照 §三 開頭的尺，今天的寫法是**所有用到 MCP 的 thread 同一時間降級**：沒有斷，但所有人的回答品質一起掉一下，模型可能重試、放棄，或者不用工具直接回答。

推薦改成「停→降級」：空窗期的新 MCP 呼叫不當場回錯，先等宿主重連，等待有上限，超過才回錯。宿主短暫重起時只是停一下，接著跑；宿主停太久，退回今天的降級。正在跑的那一次仍是「結果不明」，屬於降級。這一項波及所有用到 MCP 的 thread，範圍是 MCP 呼叫，結果最壞是降級、不是斷。這跟閘放在宿主不同，閘放在宿主最壞是斷。上限要比 MCP 工具呼叫自己的逾時短，數字沒定。寫進 #2570 的改法。

**推薦：終點選 (c)，過渡期走 (b2)。**

- 合 D248、又保住 #2562 三個理由的，是 (c) 和 (c′)。也就是說，**在每條 thread 一份的形狀下，#2562 的三個理由分不出語言**，選 Rust 要另外有理由。理由見下。
- (b2) 是 (c) 之前必經的一段：把全機共用的服務先搬進宿主，組合層暫時留在今天的對話行程。(b2) 跟 (c) 對宿主的要求完全一樣，過渡期做的宿主到終點不用重做。

**(c) 比 (c′) 好在哪**：
1. **ADR〈元件切分〉的切分原則**：「每次呼叫都會執行、而且出錯代價高的元件，放在 Rust」（`.docs/core-base-rust-reeval-2026-11-08.md:104` 引）。組合層正是這種元件。這條原則不依賴形狀，per-thread 下照樣成立。
2. **這條線的目標**：demian 2026-11-08 定的範圍是「harness 的核心底座轉 rust (like cordis)」（D246），D245 Q1a 定了組合層的終點用 Rust。(c′) 等於撤回 Q1a。
3. **每條 thread 多一個行程的成本**：(c′) 多的是一個 V8，(c) 多的是一個 Rust 行程。推論 (c) 比較小，**沒量**，D166 的容量要重估時兩個都要量。

(c) 輸 (c′) 的地方：要用 Rust 重寫組合層（#2562 附錄算的上限約 4.4 萬行），而且語言邊界上多一份跨界契約。這是 D245 拍板時就接受的代價（#2562 §四「P3 輸 P2 的地方是語言邊界」）。

## 五、跟 #2562 的理由對帳

D245 Q1a、Q1b 依據的是 #2562 §三 的三個理由（`.docs/core-base-rust-reeval-2026-11-08.md:98-119`）。逐條看 (c)：

1. **理由 2，單一事件迴圈的上限**：共用的 Node 組合層會撞到單一事件迴圈的上限。(c) 的組合層一條 thread 一份、不共用，這條**不再成立**。它原本是 Q1a「用 Rust」的理由之一；per-thread 之後，Q1a 只剩理由 3、5 和 ADR 的切分原則支撐。
2. **理由 3，共用組合層出錯，影響所有對話**：(c) 的組合層出錯只影響那一條 thread。這也是 D248 要的。
3. **理由 5，稽核要一個不跟著對話行程崩潰的寫入者**：(c) 的事件 log 由 Rust 組合行程寫，跟 TS 插件與工具所在的葉子行程分開。葉子行程崩潰，寫入者還在，可以照 dsh `repair.ts` 收尾，把那一步標成「結果不明」。這正是 D235 R1「對話行程的終點是只裝工具的葉子行程」要的分離，差別只在寫入者是每條 thread 一個，不是全機一個。

**付出的代價**：
- 每條 thread 多一個行程。記憶體沒量，D166 的容量（64 GiB 約 155 條）要重估。
- 第一輪 §八 有一項好處要重做：「宿主是 log 的寫入者，讀得到還沒落盤的那一句」。(c) 下宿主不寫 log，搜尋要讀到最新的那一句，得改成由各 thread 把事件推給宿主。前台今天已經收對話行程推來的事件（`front-turn-failures.ts`），走同一種方式。
- 寫入租約照舊是今天的 `session.lock`（`apps/harness/src/session-lease.ts`），持有者從 Node 對話行程換成 Rust 組合行程。
